## 3. 每个项目的唯一内容职责

为了避免同一内容再次散落到多个文件，新增或修改内容时遵循下表：

| 内容类型 | 应写在哪里 | 其他文件如何处理 |
| --- | --- | --- |
| 当前架构与源码执行链 | `01-机制原理` | 题库只给压缩答案和链接 |
| 一次真实请求、故障或变更的完整过程 | `02-场景案例` | 机制篇只引用该案例，不再复述全文 |
| 高频问题的 30 秒 / 2 分钟回答 | `03-项目题库` | 不复制大段源码分析 |
| 已知短板、失败模式、优先级 | `04-复盘与表达` 或 TCUM-AI 的 `05-演进与对比` | 题库只保留最关键三点 |
| 与其他框架的源码级横向对照 | `02-框架和中间件/02-AI-Agent与Harness` 或 TCUM-AI 通用深度专题 | 项目机制篇只保留与本项目决策直接相关的差异 |
| 面试反问 | `04-面试表达` | 被反问后的技术答案链接到题库/机制篇 |
| 原始核验记录 | `04-源码和参考文档` | 正式文档吸收结论后不复制搜索过程 |

判断是否应该新建文件的标准：只有当它有独立读者、独立使用时机和清晰的内容所有权时才新建；否则并入现有权威文档。

## 4. 面试回答统一结构

所有项目题优先按五步回答：

1. **为什么会有这个问题**：用业务场景、失败现象或规模约束开场。
2. **当时有哪些选择**：至少说明为什么没有选另外一种显而易见的方案。
3. **现在怎么实现**：讲组件、数据流、关键状态和失败路径，不逐行背代码。
4. **代价与边界**：主动区分已经实现、部分实现和设计目标。
5. **如果继续演进**：给出优先级、收益、成本和验收指标。

一段可信的回答应同时包含三个层次：

```text
宏观：解决什么业务问题，系统边界是什么
  ↓
实现：请求如何流动，状态存在哪里，失败如何处理
  ↓
判断：为什么这么选，哪里会失效，下一步如何验证
```

### 事实表述词典

| 证据状态 | 可以怎么说 | 不应该怎么说 |
| --- | --- | --- |
| 源码已验证 | “代码中由 X 调用 Y”“当前常量是 N” | 用源码推断生产效果和历史动机 |
| 配置 / 数据已验证 | “导出配置中有 N 条”“当前绑定了这些工具” | 将配置存在等同于每次必然执行 |
| 只有设计推断 | “从实现结果看，我理解当时是在权衡……” | “我们当时就是因为……” |
| 只有改进方案 | “如果我重做，会先……” | “系统已经支持……” |
| 无法取得证据 | “当前仓库无法证明，需要以运行配置/平台数据为准” | 用常识补成项目事实 |

## 5. 三条最重要的项目口径红线

| 容易夸大的说法 | 当前更准确的表述 |
| --- | --- |
| “TCUM-AI 使用 Supervisor 框架编排多 Agent” | 当前主力是 Eino Deep 模式：子 Agent 通过 `Agent-as-Tool` 暴露给入口 Agent；名为 supervisor 的业务 Agent 不等于使用了 `supervisor.New`。 |
| “已经形成统一三层记忆体系” | 当前是会话历史/摘要、Skill 缓存和记忆条目等多个机制组合；统一记忆抽象、默认读写和治理闭环仍是演进目标。 |
| “混合检索已经很好地融合 BM25 和向量分数” | 监控元数据 RAG 确实同时检索，但 ES 内部关闭 RRF 后存在分数量纲问题；应用层另有双 query 位次交织，二者必须分开描述。 |

同样的纪律适用于所有项目：配置存在不等于生产必经，接口存在不等于能力闭环，TODO 不等于已经实现，设计建议不等于历史事实。

## 6. 面试前的最小验收清单

针对准备主讲的每个项目，至少确认：

- 能在 90 秒内说清业务背景、用户、系统边界和个人职责。
- 能画出入口、核心服务、存储、外部依赖和关键数据流。
- 能深入解释三个实现机制，包括失败路径和关键状态。
- 能讲两个真实问题：现象、根因、修复、代价和结果。
- 能主动说三个尚未解决的问题，并给出分优先级的方案。
- 能区分源码事实、生产数据、工程推断和未来设计。
- 能回答“为什么不用另一种方案”“如何验证改动有效”。
- 准备三个与岗位相关、能引出技术讨论的反问。

如果某个项目还做不到以上八点，就优先补项目主线和证据，不要继续增加孤立题目数量。

## 7. 维护规则

1. 正式文档中的代码行号可能随仓库演进漂移，优先同时记录文件、函数和关键符号；行号只作辅助定位。
2. 源码核验后，将结论写回唯一权威正文；搜索命令、临时笔记留在核验目录或删除。
3. 发现语义重复时，保留解释最完整、来源最可靠的一份，其他位置改为短答案和链接。
4. `90-总册与草稿`、`99-归档` 不参与正式内容的重复度验收。
5. 新增“已经上线、性能提升、规模、准确率”等陈述时，必须附可追溯证据；无法验证则明确降级为待核实口径。
