# 项目驱动追问题库：从真实实现倒推面试

> 这不是“技术方向 × 固定模板”的题库。每题从仓库中一个具体设计、代码分支或测试行为出发，考察你是否真正理解当时的取舍。回答中的“我”应替换为你真实参与的范围；若非亲自实现，应明确说“我走读 / 协作的部分是……”。

## 一、架构决策与边界

### 1. 为什么没有直接使用原生 Collector，而要注册自定义 Kafka receiver 和 remote-write exporter？

**答题主线：** 先确认并非“完全重写 Collector”。项目复用 Collector 的组件框架，只为实际接入语义做扩展：`components.go` 将 OTLP receiver、Kafka receiver、delta-to-cumulative processor、自定义 remote-write exporter 与 proxy 放进同一个 factories 集合。这样复用配置、生命周期和 telemetry 能力，同时把非标准输入编码、OTLP→Prometheus 转换与写出控制留在可维护的自定义组件中。代价是要跟随上游 API 演进、补齐集成测试；因此我会把自定义边界压在协议适配和目标端语义上，不复制 Collector 通用能力。

**源码落点：** [components.go](/Users/yaao/Documents/code/unified-gateway/cmd/components.go:19)。

### 2. 你如何发现“代码支持”和“当前链路启用”不是一回事？

**答题主线：** 不靠目录判断，要沿“注册 → 配置 → pipeline”三步核验。组件注册表里有 Kafka receiver，配置也有 `kafka/barad` 段；但 metrics pipeline 只写了 `otlp` receiver。因此正确结论是 Kafka / Barad 是已实现且可配置的能力，却不是该示例 metrics pipeline 的已启用入口。这个检查避免在面试里把能力清单夸成线上拓扑。

**源码落点：** [注册](/Users/yaao/Documents/code/unified-gateway/cmd/components.go:23)，[Kafka 配置](/Users/yaao/Documents/code/unified-gateway/config/config.yaml:10)，[pipeline](/Users/yaao/Documents/code/unified-gateway/config/config.yaml:50)。

### 3. CMDB 为什么采用统一事件协议，而不是每个资源模型一套 Topic 和 consumer？

**答题主线：** `SyncMessage` 将公共控制面字段（`trace_id`、`model_type`、`event_time`、`source`）与各类 payload 分离。consumer 可以基于 `model_type` 做模型路由，属性转换器基于字段定义处理动态属性；新增模型不必复制一套消费框架。代价是协议演进、字段兼容、错误隔离更重要：未知字段当前测试选择忽略而不是失败，避免生产者先升级时阻断全局同步，但必须有 schema 审计和告警，否则可能静默丢业务字段。

**源码落点：** [协议](/Users/yaao/Documents/code/tcum-cmdb-global/service/kafka/kafkapb/common_incr_sync_message.proto:11)，[未知字段测试](/Users/yaao/Documents/code/tcum-cmdb-global/service/bizservice/incr_sync_service/incr_sync_service_test.go:94)。

### 4. 为什么 Flink CDC 不被视为一种数据源类型？

**答题主线：** 代码把数据源位置（DIRECT_DB / REGION_DB）和同步方式（DIRECT / FLINK_CDC）建模为正交关系。这样同一类数据源可选择直接同步或 CDC，不需要为四种组合复制模型与发布流程。脚本又单独保存数据源、sink、SQL、版本、灰度地域和 Lint，使“接入什么”和“如何同步”可以独立演进。

**源码落点：** [Flink CDC 实体说明](/Users/yaao/Documents/code/tcum-cmdb-global/service/dao/entity/custom_model_entity/flink_cdc_entity.go:3)。

## 二、一致性、失败和恢复

### 5. remote-write 遇到 400、429、500 时，你希望系统分别做什么？

**答题主线：** 代码将 2xx 视为成功，5xx 视为可恢复错误；429 仅在 feature gate 开启时可重试；其他 4xx 被包装为 permanent error。这是合理的，因为错误请求反复发送只会扩大压力，而下游瞬态故障可能恢复。我要补充的工程动作是：4xx 抽样记录请求特征与转换失败原因，5xx / 429 看重试次数、写入延迟、队列/WAL 积压，并在预算耗尽前限流或降级。

**源码落点：** [HTTP 状态分类与退避](/Users/yaao/Documents/code/unified-gateway/exporter/prometheusremotewriteexporter/exporter.go:372)。

### 6. WAL 打开后，什么时候才能删掉日志？会不会重复写？

**答题主线：** WAL 不是“写入即成功”。发送路径先从 WAL 读批次，只有 `exportSink` 成功后才 sync 并截断前部；失败时保留记录以便重放。进程在“远端已收到、截断前宕机”的窗口仍可能重发，所以远端或时序写入语义要容忍重复。监控上要看 read/write index 距离和磁盘占用，而不只看请求成功率。

**源码落点：** [读取、发送、成功后截断](/Users/yaao/Documents/code/unified-gateway/exporter/prometheusremotewriteexporter/wal.go:184)，[持久化批次](/Users/yaao/Documents/code/unified-gateway/exporter/prometheusremotewriteexporter/wal.go:300)。

### 7. Kafka consumer 为什么要在 rebalance 后循环调用 `Consume`？

**答题主线：** consumer group 的 claim 在服务端 rebalance 后需要重建；单次 `Consume` 返回并不等于消费者永久停止。代码的无限循环在 context 未取消时重新进入 `Consume`，并在 shutdown 时 cancel、等待 goroutine、关闭 group。这里的风险不是“循环会不会无限”，而是重平衡频繁时的处理延迟、重复处理和 commit 边界，所以要结合 lag、rebalance 次数和下游幂等性排查。

**源码落点：** [消费循环与优雅退出](/Users/yaao/Documents/code/unified-gateway/receiver/kafkareceiver/kafka_receiver.go:160)。

### 8. 仅靠 `event_time` 版本比较，哪些异常仍然解决不了？

**答题主线：** 它能收敛乱序与全量/增量竞争：只接受新版本。但它依赖事件时间可信且可比较，不能自动解决时钟漂移、同一时间戳冲突、错误生产者发未来时间、删除 tombstone 语义、跨资源事务与消息重复。设计文档因此定位为最终一致性，而不是分布式锁或强一致。面试里要先说它解决了什么，再主动列出不解决的边界。

**源码落点：** [版本控制与最终一致性](/Users/yaao/Documents/code/tcum-cmdb-global/INCR_SYNC_DESIGN.md:83)，[冲突场景](/Users/yaao/Documents/code/tcum-cmdb-global/INCR_SYNC_DESIGN.md:190)。

### 9. 自定义模型如何避免“唯一键选错，导致两台资源合并”？

**答题主线：** 唯一性不是在 consumer 中写死单一 ID，而是依据模型字段定义提取单列或组合唯一键。测试明确覆盖 `server_ip` 单键和 `server_ip + port` 组合键。实际接入时先让业务确认资源自然键，再做历史数据冲突扫描、灰度写入、重复率监控；仅凭可变名称当 key 会造成错误合并。

**源码落点：** [单键测试](/Users/yaao/Documents/code/tcum-cmdb-global/service/bizservice/incr_sync_service/incr_sync_service_test.go:348)，[组合键测试](/Users/yaao/Documents/code/tcum-cmdb-global/service/bizservice/incr_sync_service/incr_sync_service_test.go:371)。

## 三、Agent 工程化，而不是 Demo

### 10. 为什么所有 Agent—even 没有子 Agent—都通过 `BuildDeepAgent` 构建？

**答题主线：** 这不是为了“看起来多 Agent”，而是让不同形态的 Agent 拥有同一条中间件装配路径。注释说明这样可确保 COS Skill backend 等中间件正确构建；初始化时还先注入全局 tool middleware，避免 deep 模式重新创建 ToolsNode 时丢失结果截断。这个细节能说明你关注的是行为一致性，而非只把 Agent 包装成不同类。

**源码落点：** [统一 Deep 构建](/Users/yaao/Documents/code/tcum-ai/cmd/server/common/agentserver/agent_builder.go:19)，[先注入工具中间件](/Users/yaao/Documents/code/tcum-ai/cmd/server/common/agentserver/agent_builder.go:76)。

### 11. 工具报错为什么不直接让整轮会话失败？

**答题主线：** Deep Agent 将 ToolErrorHandler 放在 handlers 链前部，把工具（也含动态 MCP）的执行错误转为模型可理解的正常结果；模型可改参数、切换工具或给出降级解释。这里必须把“可恢复的工具失败”与“不可恢复的安全失败”区分：参数、暂时性依赖错误可引导重试；越权和危险操作仍应明确拒绝，不能让模型无限试。

**源码落点：** [工具错误中间件装配与意图](/Users/yaao/Documents/code/tcum-ai/cmd/server/common/agentserver/agent_builder.go:198)。

### 12. 上下文超限后，为什么不是一刀切截掉最旧消息？

**答题主线：** 实现先原样调用；只在识别到 overflow 后启用真实 token counter 和渐进压缩，按候选优先级节省目标 token。第一轮不压缩未读内容；工具结果依次保留结构化样本、警告/COS 链接、引用占位，后续才压缩 assistant 长文本。这比简单删历史更能保留仍可能影响本轮决策的事实。边界也要承认：目前 stream 路径不做该自适应重试。

**源码落点：** [超限捕获与重试](/Users/yaao/Documents/code/tcum-ai/pkg/agent/adaptive_context_retry.go:188)，[压缩优先级](/Users/yaao/Documents/code/tcum-ai/pkg/agent/adaptive_context_retry.go:476)，[流式边界](/Users/yaao/Documents/code/tcum-ai/pkg/agent/adaptive_context_retry.go:272)。

### 13. Agent 热更新如何保证失败时不影响正在服务的版本？

**答题主线：** 每个 AG-UI 请求触发检查配置 hash；hash 不变直接跳过，变更时先 rebuild。重建失败就保留旧配置；新 handler 成功后才替换 Agent 和 hash。AG-UI 使用可变 handler，路由本身只注册一次；并且刻意使用精确 path 而不是 path prefix，避免相似路径被先注册的 handler 吞掉。这是典型的“先构建、后切换”的安全更新策略。

**源码落点：** [hash 驱动热更新](/Users/yaao/Documents/code/tcum-ai/pkg/agent/manager.go:147)，[可变 handler 与精确路由](/Users/yaao/Documents/code/tcum-ai/pkg/agent/manager.go:304)。

### 14. Skill 发布怎样避免把内部凭证和地址带到公开产物？

**答题主线：** 构建不是简单 copy：脚本生成 private / public 两种产物，public 侧改用 Bearer token，private 侧也删除指定 SecretId / SecretKey headers。要说清楚这减少了 Skill 配置层的凭证泄露风险，但不替代运行时鉴权、访问审计和密钥轮换；产物检查应作为 CI gate。

**源码落点：** [产物定义](/Users/yaao/Documents/code/tcum-ai-skills/scripts/build_skills.py:4)，[敏感头处理](/Users/yaao/Documents/code/tcum-ai-skills/scripts/build_skills.py:36)，[配置重写](/Users/yaao/Documents/code/tcum-ai-skills/scripts/build_skills.py:61)。

## 四、项目交付与 Ownership

### 15. 你怎样证明一个“设计完成”已经可以上线，而不是只有文档和代码？

**答题主线：** 我会把证据分四层：接口 / 数据契约有测试；错误和边界有故障注入；部署配置确认启用；运行指标和灰度结果证明行为符合预期。例如 CMDB 有属性转换与唯一键测试，网关有 WAL / retry 代码，但若没有 production values 与指标，就只能说“具备能力或已完成实现”，不能说“线上无损”。这个回答比泛泛的“充分测试”更诚实也更专业。

### 16. 面试官问“这是谁的代码，你具体贡献了什么”时怎样答？

**答题主线：** 使用四层表达：背景是哪个系统问题；我负责哪一个边界（协议、consumer、状态机、测试、发布或监控）；我做了哪项可核验改动；结果用什么指标或验收证明。不要把代码库全貌归为个人成果。例如可说“我负责统一增量消息契约和消费者链路的走读 / 实现 / 测试中的某部分”，随后展示 `SyncMessage → MessageHandle → ProcessSyncMessage` 的调用链；没有个人提交记录或任务记录时，不把整个 Global CMDB 归为个人项目。

### 17. 一个新资源模型接入失败，你的排障路径是什么？

**答题主线：** 从输入到事实逐段缩小：先看 producer 是否按 schema 填了 `model_type`、event_time、resource ID；再看 Kafka topic / partition / offset 与 protobuf 反序列化；然后看模型路由、字段映射和未知字段处理；再核验唯一键、版本条件和数据库写入；最后检查搜索 / 缓存是否刷新。消费者日志本身已记录 model_type、操作、resource_id、trace_id、topic、partition、offset 与耗时，先以 trace_id 串联，而不是直接改重试。

**源码落点：** [消费日志字段与服务调用](/Users/yaao/Documents/code/tcum-cmdb-global/service/kafka/consumer/unified_incr_sync_consumer.go:247)。

### 18. 如何把一个“技术方案”讲成对业务有价值的项目？

**答题主线：** 用“原始痛点 → 决策 → 可验证结果 → 剩余风险”讲：例如全量同步有延迟高、资源消耗大、不能及时响应变更的问题；所以引入统一 Kafka 增量协议和版本收敛；验证不是只看消息消费成功，还要看资源新鲜度、冲突跳过、失败重放、搜索可见时间；剩余风险包括事件时间可信度、schema 演进和最终一致窗口。这样的表达同时体现产品意识、工程取舍和风险意识。

**源码落点：** [全量同步痛点与目标](/Users/yaao/Documents/code/tcum-cmdb-global/INCR_SYNC_DESIGN.md:30)。

## 使用建议

每次模拟面试任选 3 题：一题“决策”、一题“异常 / 一致性”、一题“ownership”。答题时先讲 60 秒结论，再接受源码走读追问。能清楚指出证据边界，比把所有能力都说成个人上线成果更有说服力。
