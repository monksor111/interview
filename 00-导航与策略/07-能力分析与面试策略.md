# 能力分析、简历口径与面试策略

## 一、总体判断

你的优势不是单一中间件深度，而是把“稳定性数据面、元数据面、智能决策面、运营控制面”连接成一个统一运维体系：监控负责感知，CMDB 负责关系与语义，TCUM-AI 负责分析编排，TCUM 底座负责权限、审批、发布和规模化接入。这个组合比单讲 Prometheus、CMDB 或 Agent 更有架构师辨识度。

## 二、四条主叙事

### 1. 可观测：从采集系统升级为客户可用性数据产品

- 已证实能力：统一指标网关、流式/二次计算、CMDB 关系补全、时序存储、拨测、Trace、日志、告警和 SLO。
- 简历结果：100+ 云产品、43 地域、70+ TCS 集群；覆盖率 81%；故障可观测率 55%→85%；分钟级 MTTD；年度主动发现 25 个问题；告警准确率 70%。
- 面试亮点：不是只做“采集+大盘”，而是把域名、服务、实例三层 SLI 和错误预算变成稳定性运营抓手，并用 CMDB 支持指标下钻和影响面。
- 主要追问风险：SLO 分子分母定义、低流量处理、故障标注来源、准确率样本集、网关容量和存储成本。回答时必须给计算口径，不能只报百分比。

### 2. CMDB：从资源台账升级为模型驱动的元数据底座

- 已证实能力：三套异构 CMDB 统一、模型组/模型/字段/关系元模型、自定义模型、SPI/直连库/多 Region/Flink CDC、Kafka 增量协议、版本控制、统一搜索与拓扑。
- 简历结果：接入周期周级→小时级；一致性延迟小时/天级→分钟级；查询性能 +50%；最大 QPS +100%；纳管 100+ 云产品。
- 面试亮点：能讲清 Schema 治理、数据接入、最终一致性、查询与关系消费的完整闭环，而不是只讲表结构。
- 主要追问风险：事件时间作为版本号的时钟问题、全量与增量覆盖、Schema 变更、唯一键、毒消息、数据质量 SLO、迁移双轨一致性。

### 3. TCUM-AI：Agent 工程化与运维域结合

- 已证实能力：Deep 多 Agent、MCP Provider/Consumer、A2A、AG-UI、声明式 Skill、多层上下文压缩、工具错误兜底、记忆 Rerank、Langfuse 和配置热更新。
- 简历结果：13 Agent、11 MCP Server、48 Skill；30 个云产品接入；月活 UV 100+；诊断覆盖率 85%、分析准确率 55%。
- 面试亮点：重点不在“调用大模型”，而在工具治理、上下文预算、协议开放、长任务可靠性和可观测性。
- 主要追问风险：路由评测、端到端任务成功率、权限和沙箱、提示词注入、记忆污染、评测集、模型成本、55% 准确率的定义。原题库已明确部分能力仍是短板，面试时应主动承认。

### 4. TCUM 底座：规模化产品接入和稳定运营控制面

- 已证实能力：产品入驻、CAM/策略、多租户权限、审批流、前端/配置发布、API 入口、多地域多集群、任务调度、资源配额和两地三中心容灾。
- 简历结果：公私一致入驻标准、核心云产品规模化上云；蚂蚁阶段 30+ 产品上云，周期三个月→一周，10 个应用统一稳定性覆盖。
- 面试亮点：体现平台架构、组织推动与治理能力，适合架构师/一号位岗位。
- 主要追问风险：控制面与数据面边界、审批状态机、策略爆炸、跨地域数据归属、RTO/RPO 演练、发布回滚和租户隔离。

## 三、最值得准备的跨域因果链

1. 指标进入统一网关后完成协议标准化，经流式计算产出 SLI，再由 CMDB 补全产品/实例/客户关系，最终进入 SLO 视图和告警；这条链同时考察网关、Kafka/Flink、时序存储、CMDB 和 SRE。
2. CMDB 增量消息可能乱序，因此用事件版本做条件更新；消费侧仍需幂等、毒消息隔离、全量对账和数据新鲜度监控，才能支撑监控关系补全与影响面分析。
3. Agent 根据意图选择子 Agent 和工具；工具结果过大时压缩或卸载，工具失败转为模型可见结果，上下文超限时原地压缩重试，最后通过 AG-UI/Langfuse 观测。这条链最能证明 AI 工程化深度。
4. 云产品入驻时同时创建导航、API、CAM 策略、审批和发布配置；变更通过灰度、审计和回滚治理，多地域部署再由容灾监控保证。这条链最能证明平台治理能力。

## 四、简历数字的核验清单

| 数字 | 面试前必须准备的定义 |
|---|---|
| 100+ 产品、81% 覆盖 | 分母是什么，按产品、实例还是核心链路统计，何时截数 |
| 可观测率 55%→85% | “故障可观测”的判定标准、故障样本来源、统计周期 |
| 告警准确率 70% | TP/FP 定义、人工标注流程、低样本产品如何处理 |
| CMDB 查询 +50%、QPS +100% | 基线版本、数据量、查询集合、P50/P99、硬件是否一致 |
| Agent 准确率 55%、覆盖率 85% | 任务级还是步骤级、测试集规模、是否含工具故障 |
| 根因定位 90%、挽回 2700w 笔 | 归因方法、对照组、审计或业务确认方式 |

## 五、证据缺口与补强建议

- 29 个普通 iWiki 节点持续空响应或限流；不能按标题推断正文。
- 30 个企微特殊文档因授权轮询 TLS 断连未读取，主要涉及审批、自动化运维、Trace 对焦和事故复盘。
- XStor 是内部系统，公开通用原理不能代替内部实现；面试前应重点复习 `XStor 读写优化总体设想` 和实际代码/运行指标。
- MySQL、Redis、Kafka、ClickHouse、Flink 等题库中的高级机制标记为“通用原理延伸”；只有本地代码和配置能证明实际启用状态。
- 建议为每个主项目再准备一张真实架构图、一条典型请求/数据链路、一次事故复盘和一次性能压测记录。

## 六、推荐面试节奏

- 1 分钟：用四层统一运维体系建立坐标系。
- 5 分钟：选一个最匹配岗位的项目，按背景—约束—设计—结果—不足讲。
- 15 分钟：准备一条跨域因果链接受深挖。
- 被问到未证实细节：明确说“代码/文稿能确认到这里，具体线上参数我会查配置和监控，不凭记忆报数”。
