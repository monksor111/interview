# §1 · 一致性巡检 · cmdb-check

## §1.1 存在原因

**核心矛盾**：增量同步靠乐观锁保证最终一致性，但仍然有**三类无法从消息本身识别的漏洞**：

1. **消息永久丢失**：Kafka 保留期过后被清理
2. **数据源本身错误**：数据源 DB bug 导致的错误也会被同步
3. **规则升级导致回滚**：字段口径变更后历史数据未重刷

这三类都需要**独立对账机制**——把"我以为的"（本地 CMDB）和"权威源"（数据源）做对比。

**`cmdb-check/README.md`**：**"处理 cmdb 信息校验的模块"** —— 一句话定义。

## §1.2 三模式对账

**模式 1 · 全量对账**
- 触发：凌晨低峰 cron
- 流程：拉源全量 → 拉本地全量 → 逐条对比 → 产出差异报告
- 差异分类：insert/update/delete
- 响应：自动修复（限流） / 告警人工 / 拒绝

**模式 2 · 抽样对账**
- 触发：每小时 cron
- 流程：随机抽样 N 条 → 对比
- 用途：高频运行，快速发现问题

**模式 3 · 触发式对账**
- 触发：某类实体大量同步失败
- 流程：针对该类做定向对账
- 用途：故障应急

## §1.3 三响应策略

**策略 1 · 自动修复**
- 差异条数 **< 阈值** → 直接补写
- 有限流保护（每分钟最多 100 条）

**策略 2 · 告警人工**
- 差异条数 **> 阈值** → 告警值班
- 值班判断是否修复

**策略 3 · 拒绝修复**
- 异常模式（比如整表消失）→ **拒绝**
- 防止数据源侧半挂返回空数据导致误删

## §1.4 巡检的四大坑

**坑 1 · 时间点漂移**
- 对账用 A 时刻拉源，B 时刻拉本地
- **A ≠ B** → 中间有增量同步 → **假差异**
- **修法**：快照对账（都取 T-5 分钟）或差异二次校验

**坑 2 · 对账开销**
- 全量对账 = 拉源 + 拉本地 + 比较 → 百万级实体几十分钟
- **修法**：分片对账 + 断点续 + 增量对账（只对比近 24h）

**坑 3 · 自动修复级联风暴**
- 发现 1000 条差异 → 自动修复 → 每条触发下游通知 → 冲击
- **修法**：修复限流 + 异常量差异只告警

**坑 4 · 对账逻辑本身可能有 bug**
- 对账代码写错 → 把正确数据当差异修复 → 反而搞坏
- **修法**：默认 dry-run（只报告不修复），人工确认后再启用自动修复

## §1.5 与业界对比

| 系统 | 巡检机制 |
|---|---|
| Netflix Edda | Poll 时被动发现 |
| DataHub | 无独立巡检（靠 Kafka 补偿） |
| ServiceNow | Reconciliation Engine（重量级） |
| TCUM cmdb-check | **三模式 + 三响应**（较均衡） |

# §2 · 元模型 · 从"死模型"到"自定义模型"

## §2.1 死模型时代（阶段 2）

**静态定义**：每类实体一张表 + DO 类型 + service handler

**痛点**：新增字段需要 `ALTER TABLE` + 改代码 + 重新发布

## §2.2 自定义模型时代（阶段 4~6）

**iwiki 4024143170 明示的元表结构**：

```sql
-- 模型定义表
t_cmdb_custom_model_definition
├── model_uid VARCHAR(128) PRIMARY KEY
├── model_name
├── data_source_type ('DIRECT_DB', 'REGION_DB')
├── sync_mode ('DIRECT', 'FLINK_CDC')          -- ★ 阶段 6 扩展
├── active_script_id                            -- 阶段 6 关联脚本
└── flink_sink_table

-- 列映射表
t_cmdb_custom_column_mapping
├── model_uid FK
├── source_column
├── cmdb_column
├── data_type
├── is_pk
├── is_searchable
└── ignore_in_flink_cdc                         -- 阶段 6 扩展

-- FlinkCDC 脚本表（阶段 6）
t_cmdb_custom_flink_cdc_script
├── model_uid FK
├── script_version
├── covered_regions
├── flink_sql MEDIUMTEXT
├── cmdb_ddl MEDIUMTEXT
├── lint_status
├── script_status                                -- 状态机
└── ai_dialog_id                                 -- ★ 与 TCUM-AI 关联
```

## §2.3 自定义模型的四大能力

**能力 1 · 用户自定义实体类型**
- 用户填写：模型 UID、名称、数据源、字段映射
- 系统自动：建表、注册 ModelRegistry、生成 DO

**能力 2 · 字段映射的灵活性**
- 源字段 → CMDB 字段（可改名）
- 类型转换（VARCHAR → INT）
- 是否搜索、是否主键、是否忽略

**能力 3 · 多数据源支持**
- DIRECT_DB（直连他人 MySQL，阶段 3）
- REGION_DB（多 region 库，阶段 5）
- FLINK_CDC（阶段 6）

**能力 4 · AI 辅助**
- 用户上传 xlsx / csv / 文本描述数据源
- **`tcum_cmdb_expert` Agent 通过 `cmdb-datasource-parse` skill 自动解析**
- 生成完整配置 + 供用户确认

## §2.4 数据存储：字段级 vs 表级

**两种可选**：
- **表级**：每个模型一张表（TCUM 走这条）—— 好处：类型强、查询快；代价：schema 演进需要 ALTER
- **字段级**：一张宽表 + attributes JSON —— 好处：schema 演进灵活；代价：查询慢、无类型

**TCUM 选表级**——因为查询性能优先于 schema 灵活性。

## §2.5 自定义模型的治理

**当前问题**：用户可以任意创建自定义模型 → 命名混乱、字段口径不一

**修法**：
- **注册审批流程**：新模型需要 owner 审批
- **命名规范**：model_uid 强制前缀（`prod_xxx_v1`）
- **owner 强制字段**：每个模型必须指定 owner

# §3 · 自定义模型控制器 · `custom_model_controller`

## §3.1 代码位置

`code/tcum-cmdb-global/controller/custom_model_controller/`

**推演能力**（基于 iwiki 4024143170 DDL 反推）：
- **CRUD 模型定义**：`t_cmdb_custom_model_definition`
- **CRUD 列映射**：`t_cmdb_custom_column_mapping`
- **CRUD FlinkCDC 脚本**：`t_cmdb_custom_flink_cdc_script`
- **CRUD AI 解析记录**：`t_cmdb_custom_ds_parse_record`

## §3.2 关键 API

**API 1 · 创建模型**
```
POST /custom/model
Body: {
  "model_uid": "xxx",
  "model_name": "...",
  "data_source_type": "DIRECT_DB" | "REGION_DB",
  "sync_mode": "DIRECT" | "FLINK_CDC",
  "columns": [
    {"source_column": "id", "cmdb_column": "id", "data_type": "BIGINT", "is_pk": true},
    ...
  ]
}
```

**API 2 · AI 解析数据源**
```
POST /custom/parse-datasource
Body: {input_type: "XLSX", input_file: <base64>}
Response: 完整 model + column mapping 建议
```

**API 3 · 保存 FlinkCDC 脚本**
```
POST /custom/flink-cdc-script
Body: {
  "model_uid": "xxx",
  "covered_regions": ["ap-guangzhou", "ap-beijing"],
  "flink_sql": "...",
  "cmdb_ddl": "..."
}
Response: {script_id, script_version, lint_status}
```

**API 4 · 激活脚本**
```
POST /custom/flink-cdc-script/{id}/activate
```
状态机：DRAFT → VALIDATED → **ACTIVE**（同时把旧 ACTIVE 置 SUPERSEDED，事务内）

## §3.3 与 TCUM-AI 的对接

**对接点**（iwiki 4024143170 明示）：
- `ai_dialog_id` → 关联 tcum-ai 会话
- `agent_name = "tcum_cmdb_expert"`
- `skill_name = "cmdb-datasource-parse"`
- `llm_model / llm_token_in / llm_token_out / llm_cost_ms` 全审计

**AI 辅助的完整流程**：
1. 用户上传数据源文件（xlsx / csv / 文本）
2. Agent 通过 skill 解析
3. 用 hunyuan 或 openai LLM
4. 输出 model + column mapping + Flink SQL
5. 记录到 `t_cmdb_custom_ds_parse_record`
6. 用户 review 后保存到 `t_cmdb_custom_flink_cdc_script`

**面试价值**：**"我们 CMDB 的接入不只是给用户 UI 让他填字段，还有 AI 帮他从原始数据自动推断字段类型和 Flink SQL —— LLM token 消耗都被审计"**

# §4 · 全量同步 · SPI Pull 引擎（`cmdb-sync`）

## §4.1 定位

**老版全量同步引擎**——用于**云梯这种"每天一次全量"**的场景。

**为什么保留**：
- 云梯是外部系统，接入 SPI 成本高
- 云梯 SPI 已经存在，无需重写
- **每天一次的低频场景，全量同步够用**

## §4.2 SPI 接口（推演）

```
GET /cmdb/spi/entities?type={entity_type}&updated_since={timestamp}&page={n}&page_size={size}

Response: {total, page, entities: [{id, type, attributes, relations, updated_at}]}
```

## §4.3 增量 vs 全量的分工

| 场景 | 增量 (阶段 4 Kafka) | 全量 (SPI Pull) |
|---|---|---|
| 频率 | 秒级 | 分钟到天级 |
| 数据源侧成本 | 每次变更都要生产 Kafka | 只需要暴露一个 HTTP 接口 |
| 数据源侧配合度 | 需要主动 push | 只需要被 pull |
| 覆盖历史 | 无（只处理增量） | 完整 |
| 幂等保证 | 乐观锁 | 靠 diff 比对 |
| 数据一致性 | 秒级最终一致 | 分钟到天级最终一致 |

**结论**：**增量 + 全量组合**——增量做实时性、全量做完整性。

# §5 · 短板与改进

## §5.1 巡检层

- **修法优先级**：见第一卷监控卷 §2.3 已详细列出

## §5.2 元模型层

**M1 · 自定义模型治理缺失**
- 现象：命名混乱、字段口径不一
- **修法**：注册审批流程 + 命名规范 + owner 强制

**M2 · 数据存储表级 vs 字段级僵化**
- 现象：字段变更需要 ALTER TABLE
- **修法**：主字段 + 扩展 JSON 混合（后续演进）

**M3 · AI 生成的 SQL 质量**
- 现象：AI 可能生成不最优的 SQL
- **修法**：Lint 强化 + 人工 review + 版本回滚

## §5.3 全量同步层

**F1 · 全量与增量的 sync_version 语义不完全对齐**
- 全量 = `time.Now()`，增量 = `event_time` —— 极端场景可能误伤
- **修法**：全量传递数据源 event_time 而非 `time.Now()`

**F2 · SPI 无版本管理**
- 现象：SPI 升级卡壳
- **修法**：`/v1/entities` 版本号 + 多版本并存
