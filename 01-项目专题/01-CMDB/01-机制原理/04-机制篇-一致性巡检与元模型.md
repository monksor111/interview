# 第二卷 · 机制篇 D · 一致性校验、元模型与全量同步

> **一句话定位**：`cmdb-check` 提供的是一套仍有限制的校验与冲突处理能力；`tcum-cmdb-global` 承担自定义模型、动态注册、SPI 全量同步和 FlinkCDC。它们可以共同提升数据可信度，但源码不能证明存在一个覆盖所有模型、自动修复所有差异的“最终一致性总控平台”。

## 0. 先划清源码边界

| 能力 | 当前源码仓库 | 能确认的事实 | 不能宣称 |
| --- | --- | --- | --- |
| 周期校验任务 | `cmdb-check` | DB 任务配置、进程内 worker、周期/手动触发、结果落库 | 已支持全量/抽样/故障触发三模式 |
| 上报与冲突处理 | `cmdb-check` | host/process/hardware 上报、冲突告警、自动更新/忽略/人工处理 | 有按差异量阈值和固定限速的通用修复器 |
| 自定义模型 | `tcum-cmdb-global` | 模型、字段、索引、DDL、数据源、生命周期 | 仅靠 UI 配置就自动生成所有运行代码 |
| 增量模型路由 | `tcum-cmdb-global` | 静态 DO + 动态 `ModelRegistry`，动态模型 60 秒刷新 | 所有数据源类型都能走 Kafka 增量写本地表 |
| SPI 全量同步 | `tcum-cmdb-global` | 分布式锁、分页拉取、两类 Diff、增量暂停/暂存/回放 | 旧 `cmdb-sync` 是当前唯一实现 |
| FlinkCDC | `tcum-cmdb-global` | 预检、渲染、Lint、版本保存、灰度、Oceanus 作业编排 | Lint 通过等于真实运行一定正确 |

面试中应把“代码事实”“架构作用”和“建议改进”分开说。尤其不要把建议中的 dry-run、阈值、分片、限速说成已经落地。

# 1. `cmdb-check`：真实是两条链路

## 1.1 链路 A：可配置周期校验任务

真实调用链：

```text
check_task 数据库配置
  → SyncCheckWorker 每 10 分钟刷新任务列表
    → 每个任务一个 CheckJob goroutine
      → 按 CheckCycle 分钟定时触发，或 StartCheckTask 手动触发
        → StartCheck 读取任务并写 running
          → 按 DataType 路由 Handler
            → 对比外部真实值与 CMDB 值
              → 写 success / conflict / failed、details 和错误信息
```

`CheckTask` 的关键字段包括 `DataType`、`ModelUuid`、`Plugin`、`Input`、`CheckCycle`、开始/结束时间、状态、详情和错误码。它证明系统具备“任务化校验”的骨架，但当前实现覆盖面很窄：

- `checkhandler.StartCheck` 只显式处理 `module_host_config`；其他 `DataType` 落入空分支。
- `module_host_config` 声明了 `db/http/shell` 三种插件，但只有 `db` 分支有实际逻辑。
- DB 插件通过 Pajero 获取端点，执行任务配置中的 SQL，提取 IP 列表，再与 CMDB 中指定 `node_uuid` 的主机 IP 集合比较。
- 集合相同输出 `success`，不同输出 `conflict` 并保存两侧数据；连接、配置或查询问题输出 `failed`。

因此准确表述是：**它有可扩展的任务和插件抽象，但当前新框架的生产实现主要落在“模块—主机配置的 DB 对账”上。**

## 1.2 链路 B：上报、冲突告警与处理

另一条较早的链路分布在 `api/v3/report.go`、`check_alarm.go` 和模型层，面向主机、进程、硬件和模块关系等上报数据：

```text
外部上报事实
  → 与 CMDB 当前值比较
    → 相同：正常收敛
    → 不同：写冲突告警历史
      → 根据全局规则自动更新 / 自动忽略 / 保留人工处理
        → 人工可执行 cover 或 ignore
```

全局规则真实只有三种枚举：

| 值 | 常量 | 含义 |
| --- | --- | --- |
| 1 | `GeneralCheckRuleAutoUpdate` | 自动用上报值更新对应 CMDB 数据 |
| 2 | `GeneralCheckRuleAutoIgnore` | 自动忽略冲突 |
| 3 | `GeneralCheckRuleManualUpdate` | 保留告警，由人处理 |

人工处理接口 `HandleCheckAlarm` 只接受：

- `cover`：将上报值覆盖到 CMDB/关联表，并更新告警状态；
- `ignore`：不改业务数据，只更新告警状态。

这不是“差异少自动修、差异多告警、整表消失拒绝”的通用三响应策略。源码没有发现“每分钟最多 100 条”或通用差异量阈值，不能这样回答。

## 1.3 两条链路的关系

- 周期任务链是“配置一个校验任务，定时主动拉两侧事实做比较”。
- 上报告警链是“外部主动上报事实，系统比较后形成冲突及处置”。
- 两者共享“比较—记录—处置”的思想，但不是同一个统一执行引擎。
- 它们也没有与 `tcum-cmdb-global` 的所有自定义模型形成源码可证的全覆盖闭环。

## 1.4 当前问题与改法

| 当前问题 | 源码表现 | 风险 | 推荐解法 |
| --- | --- | --- | --- |
| 多副本调度所有权不清 | `JobList` 是进程内全局 map，每实例都从 DB 加载任务 | 多副本可能重复执行同一任务 | DB lease/任务分片，增加 owner、lease_until、fencing token |
| 状态抢占不是 CAS | 先读状态，再单独更新 running | 两个执行者都可能通过检查 | `UPDATE ... WHERE status != running` 并检查 affected rows |
| 定时器刷新可能泄漏 | `time.Tick` 后直接替换 channel | 旧 ticker 无法 `Stop` | 使用 `time.NewTicker`，刷新和退出时显式 `Stop` |
| 超时只改状态，不取消执行 | 每 10 分钟把运行超过 2 小时的任务标失败 | 旧 handler 仍可能继续写结果 | `context.WithTimeout` + attempt_id，只有当前 attempt 可落终态 |
| 新框架覆盖有限 | 仅一个 DataType，且仅 DB 插件实现 | “通用巡检平台”名不副实 | 定义统一 Plugin 接口、契约测试和插件注册表 |
| 处置策略过粗 | Redis 中保存一个全局规则 | 高风险字段与普通字段同策略 | 模型/字段/来源/差异类型分级策略，默认 dry-run |
| 自动覆盖保护不足 | 未见通用差异量门槛、速率门禁、熔断 | 错误源可能批量污染 CMDB | 二次确认、最大影响面、限速、审批、回滚快照 |

# 2. 自定义模型：元数据驱动，不等于“无代码万能模型”

## 2.1 核心实体

`CustomModelDefinition` 当前至少承载：

- 标识与物理映射：`ModelUid`、`ModelType`、`ModelName`、`TableName`；
- 治理：展示名、描述、分类、Owners、产品归属、来源；
- 生命周期：草稿、已发布、已停用，另有 DDL 状态和模型版本；
- 数据源：`LOCAL`、`DIRECT_DB`、`REGION_DB`；
- 同步模式：`DIRECT` 或 `FLINK_CDC`；
- FlinkCDC：`ActiveScriptId`、`FlinkSinkTable`；
- 大表查询：分页或游标模式；
- Schema 健康：`HEALTHY/DRIFTED/TABLE_MISSING/DB_UNREACHABLE/UNKNOWN`。

字段和索引不是一个 JSON 随意塞入模型表，而是独立定义：字段包含物理名、结构体名、类型、长度、可空、唯一键、是否可检索和排序；索引另表管理。这使 DDL 生成和查询校验可以程序化，但 Schema 演进也变成必须治理的生产变更。

## 2.2 生命周期的真实步骤

```text
CreateCustomModel
  → 只保存模型/字段/索引元数据，状态为 DRAFT
  → PreviewDDL
  → ApplyCustomModelDDL
       当前代码直接 ExecuteDDL
       审批平台仍是 TODO
  → DDL 成功后尝试 PublishModel
  → 已发布模型进入缓存/查询/同步体系
```

创建接口会生成 `model_uid`；本地模型生成 `t_custom_*` 表名，直连 DB 模型不创建本地业务表。写接口有 Owner/管理员权限检查，但创建模型允许已登录用户发起，创建者成为 Owner。

需要主动暴露一个短板：代码注释说“提交 DDL 审批”，但当前 `ApplyCustomModelDDL` 仍直接执行 DDL，审批对接是 TODO。这意味着面试中应说“已经预留审批状态和接口，生产治理仍需补齐”，不能说审批闭环已完成。

## 2.3 `ModelRegistry` 如何让增量链认识动态模型

`ModelRegistry` 同时支持两类模型：

- 静态模型：从 `ModelTypeMap` 注册实现 `BaseDO` 的 Go 类型，通过反射创建实例；
- 动态模型：保存 `model_type → table_name + field_defs`，写入时使用 `map[string]interface{}`，不依赖编译期 DO。

动态刷新链路：

```text
已发布模型进入 SuperCache
  → IncrSyncService 启动时刷新一次
  → 之后每 60 秒比较缓存与 Registry
    → 新增：RegisterDynamic
    → 字段变化：覆盖注册
    → 停用/删除：UnregisterDynamic
```

直连 `DIRECT_DB` 模型会被排除，因为它没有本地表，误注册后增量消息会写入不存在的表。这里体现了一个重要设计原则：**元数据动态化之后，运行时路由也必须有显式适用边界。**

## 2.4 元模型仍需解决的问题

1. **缓存生效窗口**：发布后不是瞬时进入增量 Registry；需要版本化配置和“已发布但未加载”监控。
2. **Schema 变更安全**：DDL 预览不等于在线变更安全；应增加影响评估、审批、灰度和回滚。
3. **命名与语义治理**：字段类型合法不代表含义统一；需要 owner、数据字典、同义字段检测和废弃策略。
4. **动态 map 的类型风险**：编译期检查减少；应在入口做字段白名单、类型转换错误隔离和契约测试。
5. **查询性能**：`IsSearchable` 只控制是否可过滤，不保证命中索引；需结合慢查询、EXPLAIN 和索引健康治理。

# 3. SPI 全量同步：当前实现位于 `tcum-cmdb-global`

## 3.1 完整流程

```text
加载 SPI 配置
  → 按 model_type 获取 30 分钟分布式锁
  → 设置 35 分钟增量暂停标记
  → 加载模型、字段定义和字段映射
  → 根据本地行数选择 Diff 策略
  → 分页拉源、映射、Diff、批量写入/软删除
  → 写同步日志和指标
  → 清暂停标记
  → PopAll 暂存增量并逐条回放
  → 释放锁
```

它不是旧文档中推演出的通用 `GET /cmdb/spi/entities` API；真实请求形状来自每条 `CustomSpiConfig`，支持原生 SPI 和自定义映射、OFFSET/CURSOR 分页等配置。

## 3.2 两类 Diff

| 条件 | 策略 | 特点与边界 |
| --- | --- | --- |
| 本地行数 `≤ 200000` | 内存 `diffAndWrite` | 拉取并映射全部远端数据，适合中小模型 |
| 本地行数 `> 200000` | `StreamHashDiffEngine` | 本地只读 id、单唯一键、row_hash 和可选版本；远端逐页比较，500 条批写 |

流式策略只支持单唯一键；业务字段按固定顺序计算 xxHash64。远端不存在而本地仍存在的记录走 tombstone 软删除，后续再由清理任务处理。远端唯一键为空会拒绝入库并记录脏数据告警。

## 3.3 全量与增量如何协调

全量期间，增量消费者看到 pause flag 后把消息 `RPUSH` 到每模型 Redis List，队列 TTL 为 1 小时。全量成功后先清 pause flag，再 `LRange` 取全量消息并删除 List，随后通过回调逐条回放。

这比“全量和增量自由竞争，最终只靠版本号”更完整，但仍不是可靠队列：

- pause flag 设置失败被当作非致命错误，全量仍继续；
- 锁 30 分钟、pause 35 分钟、队列 1 小时，长任务可能越过 TTL；
- `PopAll` 是先读取再删除，回放失败没有 ACK、重试队列或 DLQ；
- 回调未注册时，代码明确记录“已丢弃”；
- 回放对“版本过旧/版本检查失败”通过错误字符串分类，协议较脆弱。

推荐改成带状态的 durable outbox/stream：消息有 ID，回放成功后 ACK；失败重试并进入 DLQ；pause/lock 使用可续租 lease 和 fencing token；全量完成水位与增量 offset 形成明确切换点。

# 4. FlinkCDC：脚本是一等制品，但 Lint 不是运行真值

控制器真实注册了预检、预览、保存、发布、恢复、灰度发布、暂停/恢复、解析数据源、SQL patch、诊断和 Oceanus 作业管理等接口。

`SaveScript` 的关键事务步骤是：

1. `LintStatus=FAIL` 直接拒绝保存；
2. 计算当前最大版本 `+1`；
3. 旧 ACTIVE 更新为 SUPERSEDED；
4. 插入新 ACTIVE 脚本及灰度地域状态；
5. 事务内分配 server-id；
6. 更新模型的 `active_script_id`；
7. 执行生成的 sink DDL；
8. 记录新增灰度地域审计。

需要注意：注释写了 `SELECT FOR UPDATE`，但当前查询最大版本的代码没有显式加锁；并发保存主要依赖唯一索引冲突后重试。这个差异应作为代码审查发现来讲，而不是照注释背诵。

Lint 只能证明规则集覆盖的静态问题，例如基础语法、关键字、字段对齐和必需 options；它不能证明：

- 源库账号、网络和 catalog 在真实环境可用；
- binlog 权限、server-id 和 checkpoint 长期稳定；
- SQL 在 Oceanus 对应 Flink 版本能正确运行；
- 数据量、乱序、Schema 漂移和下游写入满足 SLA。

所以发布链应形成 `静态 Lint → 预检 → 测试作业 → 小地域灰度 → 指标门禁 → 扩大范围 → 可恢复版本`，并保留脚本、运行配置、作业 ID、数据水位和回滚记录。

# 5. 面试回答模板

## 5.1 90 秒回答

> “CMDB 的数据可信不能只靠消费 Kafka。我们有 `cmdb-check` 做独立校验，但源码上要分两条链：一条是 DB 配置驱动的周期任务，支持定时和手动触发；当前新 Handler 主要实现模块—主机关系的 DB 对账。另一条是主机等事实上报后的冲突告警链，按全局规则自动更新、自动忽略或留给人工 cover/ignore。它不是文档里原来写的通用三模式三响应平台。
>
> 自定义模型和同步能力在 `tcum-cmdb-global`。模型、字段、索引和数据源都元数据化；发布后的本地动态模型每 60 秒进入 `ModelRegistry`，增量链用 map 写动态表。全量同步按模型加分布式锁，把期间增量暂存在 Redis，然后按 20 万行阈值选择内存 Diff 或流式 Hash Diff，完成后再回放增量。这里我也会主动说短板：Redis 回放是先删后逐条处理，没有 ACK/DLQ；pause flag 失败仍继续；`cmdb-check` 多副本没有可靠任务所有权。我的改进会优先做 lease/fencing、CAS 抢占、durable replay 和默认 dry-run 的风险分级修复。”

## 5.2 高频追问

**为什么 Kafka 增量还要校验？**

消息送达不等于业务事实正确。生产端可能漏发、字段映射可能错、历史数据可能没重刷；校验需要独立获取事实并对比。

**为什么不能发现差异就自动覆盖？**

校验源、规则和时间点也可能错。自动覆盖必须限定权威源、字段风险、影响面和速率，并支持 dry-run、二次确认和回滚。

**元模型的核心价值是什么？**

不是“少写几个结构体”，而是把模型、字段、索引、数据源、同步方式和生命周期变成可治理配置，并让查询、DDL、全量和增量都消费同一份元数据。

**全量期间为什么暂停增量？**

避免全量 Diff 与增量写并发造成快照边界不清。暂停只是手段，真正可靠的方案还要定义水位、持久消息、ACK 和失败恢复。

**Lint 通过为什么还会失败？**

静态规则看不到真实网络、权限、catalog、Flink 版本和数据分布；必须用预检、测试作业和灰度运行补足动态证据。

# 6. 源码锚点

- `cmdb-check/service/timingtask/timing_task.go`：任务列表同步与超时状态清理。
- `cmdb-check/service/checkworker/check_worker.go`：每任务 goroutine、周期/手动控制。
- `cmdb-check/service/checkhandler/*.go`：DataType 和插件真实覆盖范围。
- `cmdb-check/api/v3/report.go`、`check_alarm.go`、`check_rule.go`：上报、三类全局规则与 cover/ignore。
- `tcum-cmdb-global/service/dao/entity/custom_model_entity/model_definition.go`：模型、数据源、同步模式和状态。
- `tcum-cmdb-global/service/bizservice/custom_model_service/`：模型、DDL 和生命周期。
- `tcum-cmdb-global/service/bizservice/incr_sync_service/model_registry.go`：静态/动态模型注册。
- `tcum-cmdb-global/service/bizservice/incr_sync_service/incr_sync_service.go`：动态模型 60 秒刷新。
- `tcum-cmdb-global/service/bizservice/spi_sync_service/`：全量锁、Diff、增量暂存回放。
- `tcum-cmdb-global/service/bizservice/flink_cdc_service/`：脚本、Lint、灰度和 Oceanus 编排。
