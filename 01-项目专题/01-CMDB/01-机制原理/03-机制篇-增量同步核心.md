# §1 · 统一消息协议 SyncMessage

## §1.1 Protobuf 定义（`INCR_SYNC_DESIGN §2.1`）

```protobuf
message SyncMessage {
  string trace_id = 1;                          // 全链路追踪
  OperationType operation = 2;                  // 操作类型
  string model_type = 3;                        // 对应数据库表
  google.protobuf.Timestamp event_time = 4;     // 数据源侧事件时间
  string source = 5;                            // 数据源标识
  
  oneof payload {
    CreatePayload create = 10;
    UpdatePayload update = 11;
    DeletePayload delete = 12;
    BatchPayload batch = 13;
  }
}

enum OperationType {
  CREATE = 0;
  UPDATE = 1;
  DELETE = 2;
  BATCH_UPSERT = 3;
}
```

## §1.2 字段设计深度

**每个字段的存在理由**：

| 字段 | 存在理由 |
|---|---|
| `trace_id` | 跨系统追踪（云产品 → Kafka → CMDB → 消费方） |
| `operation` | 决定走哪个 handler（Create/Update/Delete/Batch）|
| `model_type` | **表驱动核心** —— 决定路由到哪个表 handler |
| `event_time` | **乐观锁版本号** —— 数据源侧事件发生时刻 |
| `source` | 数据源标识（区分同一 model_type 的多个来源）|
| `payload oneof` | 不同操作类型不同载体 |

**为什么用 Protobuf 而不是 JSON**：
- **二进制紧凑** —— Kafka 消息体积小
- **强 schema** —— 字段变更需要显式定义
- **版本兼容** —— proto 保留字段号
- **性能** —— 反序列化比 JSON 快 10 倍

## §1.3 消息示例（`INCR_SYNC_DESIGN §6.3` 原文）

**创建消息**：
```json
{
  "trace_id": "tid-abc-123",
  "operation": "CREATE",
  "model_type": "tcs_redis_entity_instance",
  "event_time": "2025-11-26T10:00:00Z",
  "source": "redis-cvm-sync",
  "create": {
    "data": {
      "id": 12345,
      "tenant_id": "cvm",
      "instance_name": "redis-prod-001",
      "port": 6379,
      "status": "RUNNING"
    }
  }
}
```

**更新消息**：类似但用 `update.id + update.updateFields`

**关键设计 2 · Kafka 配置**（`:56-70`）：

```go
    "bootstrap.servers":  config.Cfg.Kafka.IncrSyncConsumerServers,
    "group.id":           config.Cfg.Kafka.IncrSyncConsumerGroupId,
    "auto.offset.reset":  "latest",                  // ★ 从最新开始
    "security.protocol":  "plaintext",
    "session.timeout.ms": 10000,                     // 10s
    "request.timeout.ms": 30000,                     // 30s
    "socket.timeout.ms":  30000,                     // 30s
    "enable.auto.commit": false,                     // ★★★ manual commit
}
```

**六个配置的深度分析**：

**配置 A · `auto.offset.reset: latest`**
- 新 consumer 加入 group 时**从最新开始消费**（不回溯历史）
- **含义**：新 consumer 启动时会丢失历史消息 —— **对增量同步是正确策略**（历史通过全量同步兜底）
- 反例：如果是 `earliest`，consumer 重启会重新消费所有历史消息 → 冲击 DB

**配置 B · `enable.auto.commit: false`** ⭐ 最重要
- 基础消费者在 `MessageHandle` 成功后调用 `CommitMessage`，失败时不提交当前消息；过滤消息也会提交。
- 但消息先进入大小为 50 的协程池，同一 partition 的多个 offset 可能并发、乱序完成。
- 如果 offset 101 先成功并提交，offset 100 随后失败，group 的已提交位置可能已经越过 100；重平衡或重启后 100 不一定重放。
- `CommitMessage` 的返回值也没有检查，提交失败没有重试、告警或停消费。
- 因此代码只能证明“关闭自动提交并尝试成功后提交”，**不能据此证明严格 at-least-once 或 exactly-once**。乐观锁只能降低重复/乱序更新对最终状态的影响，不能修复消息被跳过。

**配置 C · `session.timeout.ms: 10000`**
- Consumer 与 broker 心跳超时 10s
- 超过 10s 无心跳，broker 认为该 consumer 挂，触发 rebalance
- **权衡**：调低 → 快速故障发现但网络抖动误判；调高 → 反之

**配置 D+E · `request.timeout.ms / socket.timeout.ms: 30000`**
- 单次 Kafka 请求超时 30s
- 略大于 session.timeout 保证网络请求不会拖累心跳

## §2.4 主消费循环（当前源码）

真实循环位于 `base_kafka_consumer.go`，不是旧稿中的 `Run + ReadMessage(1s)`：

```text
SubscribeTopics
  → NewGoroutinePool(size=50)
  → ReadMessage(-1) 阻塞读取
  → 复制 kafka.Message
  → 投递 MsgHandlerTask 到协程池
  → MessageFilter
  → MessageHandle
  → 成功或被过滤时 CommitMessage
```

这里有四个必须说准确的事实：

1. `ReadMessage(-1)` 是无限阻塞，不是 1 秒超时；外层虽然检查 `ctx.Done()`，但没有消息时无法及时回到 select。
2. 同一 consumer 拉到的消息统一进入 50 协程池，没有按 partition 建有序 worker。
3. `MessageHandle` 失败时不会提交当前消息，但更大 offset 可能已由其他协程提交，失败消息不保证重放。
4. `CommitMessage` 的返回值在当前基础消费者中被忽略；提交失败没有重试或告警。

## §2.5 过滤、反序列化与业务处理的真实分层

- `MessageFilter` 使用 Kafka `msg.Timestamp` 与 `MsgExpireTime` 判断过期，并检查增量总开关与 `SuperCache.StopCommonInc`；被过滤消息仍会提交 offset。
- `MessageHandle` 才反序列化 Protobuf、恢复 `trace_id` 并调用 `IncrSyncService.ProcessSyncMessage`。
- `ProcessSyncMessage` 先检查 SPI 全量暂停标记；命中时把消息序列化进 Redis 待回放队列。
- 未暂停时通过 `ModelRegistry.Get(model_type)` 取模型元数据，再按静态/动态模型分支执行转换和写入。

旧稿把过期判断写成 `syncMsg.EventTime`、把模型查找写成 `SuperCache.GetModel`，都不是当前调用链，应以上述源码分层为准。

# §3 · VersionControlMiddleware 的真实能力边界

## §3.1 三个钩子并不对称

| 钩子 | 当前行为 | 边界 |
| --- | --- | --- |
| `BeforeCreate` | 版本控制开启时仍直接返回 | 创建没有版本比较 |
| `BeforeUpdate` | 先查询当前版本；新版本不大于当前值则跳过，否则给 `updateFields` 加版本信息 | 查询和最终 `BaseBatchUpdate` 分离，不是原子 CAS；读版本失败时 fail open，继续更新 |
| `BeforeDelete` | 当前直接返回 `true` | 注释明确“如果需要，可以添加”，所以删除尚无版本保护 |

`CheckDOHasVersionFields` 会检查 `sync_version / last_update_time / updated_at / update_time` 等字段；没有这些字段的 DO 直接绕过版本控制。`AddVersionFields` 中写 `sync_version/sync_source` 的两行当前被注释，只会给检测到的时间字段写 `time.Now()`，因此“创建时已保存 event_time 版本”不能一概而论。

## §3.2 设计文档里的原子 SQL 尚未接入生产路径

仓库中确实定义了：

```sql
AND (sync_version < new_version OR sync_version IS NULL)
```

但 `BuildVersionedUpdateSQL` / `BuildVersionedDeleteSQL` 目前只有函数定义和单元测试，没有非测试调用。真实更新路径是：

```text
SELECT current version
  → Go 中比较
    → BaseBatchUpdate
```

两个并发消息可能都读到旧版本、都通过比较，最后完成的写入反而可能是较旧事件。这是典型 TOCTOU，不能用设计文档中的条件更新为当前代码做正确性证明。

## §3.3 正确修法

将版本判断和写入合并成单条原子 SQL，并检查 `RowsAffected`：

```sql
UPDATE target
SET ..., sync_version = :new_version
WHERE id = :id
  AND (sync_version IS NULL OR sync_version < :new_version);
```

- `RowsAffected=1`：本事件成功成为新状态；
- `RowsAffected=0`：事件过旧或对象不存在，再按需要区分；
- 删除使用墓碑版本或软删字段，避免旧 create/update 在 delete 后把对象复活；
- 无版本字段的模型不能默默享受“版本一致性”宣传，应在 ModelRegistry 明确能力标签并监控覆盖率。

# §4 · 全量、增量和乱序冲突的当前处理

## §4.1 全量期间到达增量

当前主机制是“按模型分布式锁 + Redis 暂停标记 + 增量暂存 + 全量后回放”，不是完全并发写后只靠 `sync_version` 决胜。版本控制主要用于回放时过滤旧事件。完整链路见场景篇 B。

## §4.2 普通乱序更新

`BeforeUpdate` 的版本预检查可以过滤已经观察到的旧事件，但由于检查和更新不原子，并发乱序仍可能穿透。只有改为数据库条件更新后，才能在并发下可靠保证较小版本不覆盖较大版本。

## §4.3 删除与无版本字段模型

- `BeforeDelete` 当前不比较版本，旧删除事件可能删除更新对象；
- 没有受支持版本字段的 DO 会直接修改；
- 创建路径未统一写入 event-time 版本；
- 版本读取异常时更新 fail open。

因此当前更准确的说法是“已有版本控制骨架和部分乱序防护”，不是“所有模型都由乐观锁保证最终一致”。

# §6 · manual commit、幂等与当前交付语义边界

## §6.1 三个概念必须拆开

| 能力 | 当前证据 | 正确结论 |
| --- | --- | --- |
| 自动提交关闭 | `enable.auto.commit=false` | 不会由客户端定时自动提交，但不自动等于可靠手动提交 |
| 业务成功后提交 | `asynMessageHandle` 在 `err == nil` 时调用 `CommitMessage` | 单条处理意图是“成功再提交”；提交结果当前未检查 |
| 状态幂等 | `event_time` 派生版本，旧版本更新被跳过 | 对支持版本字段的实体，重复/乱序更新通常不会覆盖更新状态；它不是消息交付 exactly-once |

Kafka 的 offset 是 partition 级连续位置，不是每条消息的独立 ACK。当前 `ReadMessage` 后把消息投递到 50 协程池，没有为同一 partition 建立有序队列或连续完成水位：

```text
partition P0: offset 100 ──慢/失败──────────────X
              offset 101 ──快/成功──Commit(102)

重启或 rebalance 后从 102 开始，offset 100 可能不再重放。
```

因此下面三个说法都不成立：

- “失败的消息一定会重新消费”；
- “关闭 auto commit 就保证 at-least-once”；
- “at-least-once + 幂等就等于 Kafka exactly-once”。

即使修复 offset 水位，最多也应称为“**至少一次交付 + 数据库最终状态幂等**”。Kafka EOS 通常讨论事务生产/消费链；数据库写入若不与 offset 提交处于同一事务域，不能宣称端到端 exactly-once。

## §6.2 当前仍然有价值的部分

- `event_time` 版本比较能抵抗大部分重复消息和乱序更新；
- 处理失败时不会主动提交该条消息，设计意图正确；
- 全量/增量共享版本规则，有机会收敛到确定的最终状态。

但这些结论有作用域：仅适用于真正接入版本控制的实体和写路径；外部副作用、无版本字段模型、删除/创建边界以及提交失败都要单独验证。

## §6.3 正确修法

1. **partition 内串行，partition 间并行**：每个 partition 一个有序 worker；处理成功后提交连续 offset。这是最简单、最可靠的方案。
2. 若必须保持 partition 内并发，维护完成位图和 `nextCommitOffset`，只提交从当前水位开始连续成功的最大 offset；遇到失败暂停该 partition 或重试/DLQ，不能越过洞。
3. 检查 `CommitMessage` 错误并做有界重试、告警；提交状态不明时按重复处理设计。
4. 以 `topic/partition/offset` 或业务事件 ID 建 inbox 去重表；数据库变更与 inbox 标记在同一事务内。
5. 用故障注入验证：让 offset N 阻塞、N+1 先完成，再触发 rebalance，确认 N 不丢；同时覆盖 DB 成功/commit 失败和进程崩溃窗口。

**面试结论**：当前亮点是“版本化状态幂等”；当前缺陷是“并发消费与 offset 提交没有形成严格交付协议”。主动把两者分开讲，比使用“实用 exactly-once”更可信。

# §7 · 短板与改进

## §7.1 已知短板

**S1 · 版本检查与更新不是原子 CAS** ⚠️ P0
- 两条并发事件可能都通过 `BeforeUpdate`，较旧事件后写覆盖较新事件
- `BuildVersionedUpdateSQL` 目前只有定义和测试，生产更新链未使用
- **修法**：单条条件 UPDATE + `RowsAffected` 裁决

**S2 · partition 内并发提交可能越过失败 offset** ⚠️ P0
- 50 协程池没有连续完成水位，且忽略 `CommitMessage` 错误
- **修法**：partition 内串行或连续水位提交，失败重试/DLQ

**S3 · event_time 依赖 NTP**
- 数据源侧时钟漂移 → 假的"新事件反而 sync_version 更小" → 被跳过
- **修法**：`ingest_time` 兜底（Kafka broker 侧时间）

**S4 · DELETE 当前没有版本保护** ⚠️ P0
- `BeforeDelete` 直接返回 true，旧删除可能删除已更新对象
- **修法**：版本化软删/墓碑，原子比较后删除

**S5 · AttributeConverter 转换失败处理未标准化**
- **修法**：死信队列 + log 详细字段

**S6 · SuperCache / ModelRegistry 刷新存在窗口**
- SuperCache 是全局缓存，如果 ModelRegistry 更新（新增 model），缓存刷新有延迟
- **修法**：缓存 invalidation 事件

**S7 · Kafka session.timeout=10s 需要基于处理与网络分布校准**
- 网络抖动 → session 超时 → rebalance → 消费停顿几秒
- **修法**：先观测 heartbeat/rebalance 分布，再联调 session/max poll；不能直接拍脑袋改成 30s

## §7.2 演进方向

- **短期**：修 §7.1 短板
- **中期**：切换到 FlinkCDC（阶段 6）
- **长期**：**基于 Watermark 的乱序处理**（Flink 生态引入 HLC 或 Vector Clock 语义）
