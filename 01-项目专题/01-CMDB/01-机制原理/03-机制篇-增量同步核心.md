# §1 · 统一消息协议 SyncMessage

## §1.1 Protobuf 定义（`INCR_SYNC_DESIGN §2.1`）

```protobuf
message SyncMessage {
  string trace_id = 1;                          // 全链路追踪
  OperationType operation = 2;                  // 操作类型
  string model_type = 3;                        // 对应数据库表
  google.protobuf.Timestamp event_time = 4;     // 数据源侧事件时间
  string source = 5;                            // 数据源标识
  
  oneof payload {
    CreatePayload create = 10;
    UpdatePayload update = 11;
    DeletePayload delete = 12;
    BatchPayload batch = 13;
  }
}

enum OperationType {
  CREATE = 0;
  UPDATE = 1;
  DELETE = 2;
  BATCH_UPSERT = 3;
}
```

## §1.2 字段设计深度

**每个字段的存在理由**：

| 字段 | 存在理由 |
|---|---|
| `trace_id` | 跨系统追踪（云产品 → Kafka → CMDB → 消费方） |
| `operation` | 决定走哪个 handler（Create/Update/Delete/Batch）|
| `model_type` | **表驱动核心** —— 决定路由到哪个表 handler |
| `event_time` | **乐观锁版本号** —— 数据源侧事件发生时刻 |
| `source` | 数据源标识（区分同一 model_type 的多个来源）|
| `payload oneof` | 不同操作类型不同载体 |

**为什么用 Protobuf 而不是 JSON**：
- **二进制紧凑** —— Kafka 消息体积小
- **强 schema** —— 字段变更需要显式定义
- **版本兼容** —— proto 保留字段号
- **性能** —— 反序列化比 JSON 快 10 倍

## §1.3 消息示例（`INCR_SYNC_DESIGN §6.3` 原文）

**创建消息**：
```json
{
  "trace_id": "tid-abc-123",
  "operation": "CREATE",
  "model_type": "tcs_redis_entity_instance",
  "event_time": "2025-11-26T10:00:00Z",
  "source": "redis-cvm-sync",
  "create": {
    "data": {
      "id": 12345,
      "tenant_id": "cvm",
      "instance_name": "redis-prod-001",
      "port": 6379,
      "status": "RUNNING"
    }
  }
}
```

**更新消息**：类似但用 `update.id + update.updateFields`

**关键设计 2 · Kafka 配置**（`:56-70`）：

```go
kafkaConfig := &kafka.ConfigMap{
    "bootstrap.servers":  config.Cfg.Kafka.IncrSyncConsumerServers,
    "group.id":           config.Cfg.Kafka.IncrSyncConsumerGroupId,
    "auto.offset.reset":  "latest",                  // ★ 从最新开始
    "security.protocol":  "plaintext",
    "session.timeout.ms": 10000,                     // 10s
    "request.timeout.ms": 30000,                     // 30s
    "socket.timeout.ms":  30000,                     // 30s
    "enable.auto.commit": false,                     // ★★★ manual commit
}
```

**六个配置的深度分析**：

**配置 A · `auto.offset.reset: latest`**
- 新 consumer 加入 group 时**从最新开始消费**（不回溯历史）
- **含义**：新 consumer 启动时会丢失历史消息 —— **对增量同步是正确策略**（历史通过全量同步兜底）
- 反例：如果是 `earliest`，consumer 重启会重新消费所有历史消息 → 冲击 DB

**配置 B · `enable.auto.commit: false`** ⭐ 最重要
- **手动提交 offset**
- **必须在消息处理成功后才 commit**
- **失败时不 commit** → 消息重新消费（at-least-once）
- **配合乐观锁幂等** → 实用 exactly-once

**配置 C · `session.timeout.ms: 10000`**
- Consumer 与 broker 心跳超时 10s
- 超过 10s 无心跳，broker 认为该 consumer 挂，触发 rebalance
- **权衡**：调低 → 快速故障发现但网络抖动误判；调高 → 反之

**配置 D+E · `request.timeout.ms / socket.timeout.ms: 30000`**
- 单次 Kafka 请求超时 30s
- 略大于 session.timeout 保证网络请求不会拖累心跳

## §2.4 主消费循环（推演 `:110-272`）

**Kafka 消费的标准模式**：

```go
func (u *UnifiedIncrSyncConsumer) Run(ctx context.Context) error {
    // 订阅 topic
    err := u.KafkaConsumerService.consumer.SubscribeTopics(u.KafkaConsumerService.topics, nil)
    if err != nil {
        return err
    }

    for {
        select {
        case <-ctx.Done():
            return u.KafkaConsumerService.consumer.Close()
        default:
            // 拉取消息（1 秒超时）
            msg, err := u.KafkaConsumerService.consumer.ReadMessage(time.Second)
            if err != nil {
                continue  // timeout 是正常的
            }

            // 处理消息
            if err := u.processMessage(msg); err != nil {
                // 失败：不 commit，消息会重新消费
                el.Errorf(ctx, "process message error: %v", err)
                continue
            }

            // 成功：手动提交 offset
            _, err = u.KafkaConsumerService.consumer.CommitMessage(msg)
            if err != nil {
                el.Errorf(ctx, "commit offset error: %v", err)
            }
        }
    }
}
```

**关键设计**：
- **超时读取（1s）** —— 不阻塞主循环
- **失败不 commit** —— 消息重新消费（at-least-once）
- **成功后 commit** —— 保证正常场景下不重复

## §2.5 消息处理（`processMessage`）

**核心流程**（推演）：
```go
func (u *UnifiedIncrSyncConsumer) processMessage(msg *kafka.Message) error {
    // 1. 反序列化
    var syncMsg pb.SyncMessage
    if err := proto.Unmarshal(msg.Value, &syncMsg); err != nil {
        return err
    }
    
    // 2. 消息过期检查
    if time.Since(syncMsg.EventTime.AsTime()) > config.Cfg.IncrSync.MessageExpireTime {
        // 过期消息丢弃
        return nil
    }
    
    // 3. 通过 model_type 找 ModelRegistry
    model, ok := u.SuperCache.GetModel(syncMsg.ModelType)
    if !ok {
        return fmt.Errorf("unknown model_type: %s", syncMsg.ModelType)
    }
    
    // 4. 调用 IncrSyncService（走 AOP + DAO）
    return u.IncrSyncService.Handle(&syncMsg, model)
}
```

# §3 · AOP 版本控制中间件三钩子

## §3.1 三钩子定义（`INCR_SYNC_DESIGN §4.2` 原文）

```go
// 创建前 - 无需版本检查
BeforeCreate(ctx, tableName, data, version)

// 更新前 - 版本检查
shouldUpdate := BeforeUpdate(ctx, tableName, id, updateFields, version)
if !shouldUpdate {
    return // 跳过更新
}

// 删除前 - 版本检查（可选）
shouldDelete := BeforeDelete(ctx, tableName, id, version)
```

## §3.2 为什么用 AOP 而不是每个 DO 加字段

**INCR_SYNC_DESIGN §2.3 原文**：
> "**非侵入式**：CMDB 内部维护版本信息，不依赖外部系统提供版本字段，使用 AOP 切面方式统一处理"

**四大优势**：
1. ✅ **一次开发全部生效**：一次实现 AOP，50+ 个 model 都受益
2. ✅ **不改动每个 DO**：DO 结构保持业务导向
3. ✅ **不依赖外部**：数据源方不用改 schema 加 `version` 字段
4. ✅ **可选启用**：某些 DO 可以关闭版本控制（比如日志表）

## §3.3 版本控制的可选化演进

**iwiki 4013029956 明示的演进**（对齐机制篇 B §5）：
> "✅ **版本控制现在是可选的**！系统会自动检测 DO 是否有版本字段
> ✅ 支持多种时间字段：`sync_version`, `last_update_time`, `updated_at`, `update_time`
> ✅ 没有版本字段的 DO 将跳过版本控制，直接修改数据"

**这是产品化演进**：早期强制所有 DO 加 `sync_version` 侵入性太强，改为**可选**后新老 DO 都能接入。

# §4 · 三大冲突场景 + 乐观锁 SQL

## §4.1 场景 1：全量同步时收到增量

**风险**：增量数据被全量覆盖

**解法 SQL**（增量）：
```sql
UPDATE tcs_redis_entity_instance
SET instance_name = ?, port = ?,
    sync_version = ?, sync_source = 'INCR_SYNC',
    last_sync_time = NOW()
WHERE id = ?
  AND (sync_version < ? OR sync_version IS NULL);
```

**关键**：`WHERE sync_version < ?` —— **只覆盖旧版本**

## §4.2 场景 2：增量消息乱序

**风险**：旧数据覆盖新数据

**推演场景**：
- T0：event_time=100 UPDATE A 到达
- T0+3s：event_time=90 UPDATE B 到达（乱序）

**处理**：
1. 消费 A：sync_version 100 → 200（假设 B 更晚 event_time=200）
2. 消费 B：`WHERE sync_version < 90` → 当前是 200 → **跳过**

**结果**：以 event_time=200 的数据为准 ✓

## §4.3 场景 3：全量覆盖增量

**风险**：全量执行时用旧数据盖了新数据

**全量 SQL**：
```sql
UPDATE table SET ...
WHERE id = ? AND (sync_version < 全量启动时间 OR sync_version IS NULL);
```

**关键**：全量的 `sync_version = 同步开始时间`。如果增量已经写入更新的 sync_version，全量 UPDATE 会跳过。

# §6 · manual commit + 幂等的正确性证明

## §6.1 语义等价

**Kafka 官方 exactly-once**（走 producer id + transaction）：
- 复杂度高
- 性能开销大
- 需要 broker 支持 transaction

**TCUM 走"manual commit + at-least-once + 幂等 = 实用 exactly-once"**：
- 消息可能被重复消费（at-least-once）
- **但幂等处理**：`WHERE sync_version < event_time` 保证重复消费**结果不变**
- **语义等价于 exactly-once**

## §6.2 边界场景

**边界 1 · 处理成功但 commit 失败**
- 消息重新消费 → 走乐观锁 → 跳过（sync_version 已经 = event_time）
- ✓ 无副作用

**边界 2 · 处理失败**
- 不 commit → 消息重新消费
- 下次消费如果处理成功 → commit
- ✓ 无副作用

**边界 3 · 处理成功但 process 中间挂**
- 消息重新消费
- 同边界 1
- ✓ 无副作用

**结论**：**乐观锁 + at-least-once = 实用 exactly-once** ✓

# §7 · 短板与改进

## §7.1 已知短板

**S1 · event_time 依赖 NTP**
- 数据源侧时钟漂移 → 假的"新事件反而 sync_version 更小" → 被跳过
- **修法**：`ingest_time` 兜底（Kafka broker 侧时间）

**S2 · DELETE 语义未文档化**
- INCR_SYNC_DESIGN 提"BeforeDelete (可选)"，但具体规则未明确
- **修法**：明确"event_time >= current sync_version 才删"

**S3 · AttributeConverter 转换失败处理未标准化**
- **修法**：死信队列 + log 详细字段

**S4 · SuperCache 一致性**
- SuperCache 是全局缓存，如果 ModelRegistry 更新（新增 model），缓存刷新有延迟
- **修法**：缓存 invalidation 事件

**S5 · Kafka session.timeout=10s 可能过短**
- 网络抖动 → session 超时 → rebalance → 消费停顿几秒
- **修法**：调到 30s（代价：故障发现慢）

## §7.2 演进方向

- **短期**：修 §7.1 短板
- **中期**：切换到 FlinkCDC（阶段 6）
- **长期**：**基于 Watermark 的乱序处理**（Flink 生态引入 HLC 或 Vector Clock 语义）
