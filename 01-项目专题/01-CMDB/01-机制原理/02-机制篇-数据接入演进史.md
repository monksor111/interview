# §1 · 命题：为什么数据接入需要六阶段演进

## §1.1 CMDB 的"接入焦虑"

云产品持续增加时，如果每个模型都编写专用表、同步代码和查询接口，平台团队的交付速度会随模型数线性下降。

而且不接入的代价更大：
- 监控系统查不到元数据 → tag 补全失败 → 数据丢弃
- 告警系统不知道对象归属 → 无法通知
- AI Agent 拓扑查询空白

**核心矛盾**：**接入速度 vs 接入质量**。

## §1.2 六阶段的驱动力

每个阶段都是被**具体现象逼出来**的：

| 阶段 | 被什么逼出来 | 解了什么 | 新问题 |
|---|---|---|---|
| 1 单表 | 起点 | 简单能用 | 字段爆炸、类型冲突 |
| 2 元模型 | 字段爆炸 | 类型安全 | 静态定义、演进僵化 |
| 3 直连 DB | 接入慢 | 接入快 | 强耦合、DBA 半夜改表 |
| 4 SPI+Kafka | 强耦合 | 接入解耦、事件到达即处理 | 版本管理、消息乱序、可靠提交 |
| 5 多 region | 单 region 崩 | 跨地域、就近读写 | region 一致性、脑裂 |
| 6 FlinkCDC | SPI 需要云产品配合 | 降低业务方推送开发，平台治理 CDC 制品 | 权限、Flink 状态、资源和运行治理 |

## §1.3 完整叙事（面试话术模板）

> "TCUM CMDB 的数据接入经历了 6 个阶段。**每个阶段都是被具体现象逼出来的**：
> - 阶段 1 是单表模式，接一个产品加几十个字段——字段炸了
> - 阶段 2 引入抽象元模型，每类实体独立表——但静态定义演进僵化
> - 阶段 3 直连他人 MySQL，接入快——但**他人 DBA 半夜改表结构，早上告警一片红**
> - 阶段 4 是**我 2025 年主导的 SPI + Kafka 方案**，把周期等待改为事件驱动——但引入了乱序、版本管理和 offset 提交问题；`event_time` 乐观锁解决状态覆盖，不能替代可靠交付协议
> - 阶段 5 多 region 数据库，跨地域容灾——但要处理 region 一致性
> - 阶段 6 是 FlinkCDC + AI 辅助制品治理：代码已覆盖脚本渲染/Lint/版本/灰度和 Oceanus 作业编排；生产覆盖率和 SLA 需另行举证。
>
> **价值边界**：接入逐步从“每模型编写专用代码”转成“配置模型、映射和同步制品”。没有历史工单、人天或生产统计时，我不会虚构具体降幅；FlinkCDC 只是把成本从业务方推送开发转移到源库权限、平台资源和持续运行治理。"

# §2 · 阶段 1：单表模式（起点）

## §2.1 形态

```sql
CREATE TABLE ci_asset (
    id BIGINT PRIMARY KEY,
    ci_type VARCHAR(64),        -- CVM / CDB / Redis / ...
    -- CVM 相关字段
    instance_id VARCHAR(64),
    region VARCHAR(64),
    status VARCHAR(32),
    -- CDB 相关字段
    db_name VARCHAR(128),
    port INT,
    -- Redis 相关字段
    memory_size VARCHAR(32),
    ... 
    -- 一张表几百个字段
);
```

**接入方式**：每接入一个新云产品 = 加几十个 CVM/CDB/Redis 独有字段 + 改所有查询。

**典型代码痕迹**：`cmdb.isd.com` 老仓库（部分逻辑还在）

## §2.2 三大痛点

**痛点 1 · 字段爆炸**
- 接 10 个云产品 → 表有几百个字段
- `ALTER TABLE` 加字段要锁表几分钟
- 查询 `SELECT *` 返回一堆 NULL 字段

**痛点 2 · 类型冲突**
- 同名字段（比如 `status`）在不同产品里有不同枚举值
- 类型系统失效——用户查 `status='RUNNING'` 拿到一堆无关数据

**痛点 3 · 多产品共享表锁**
- CVM 大规模变更 → `UPDATE` 触发表锁
- CDB 团队的写入被阻塞

## §2.3 成本为什么会随模型数增长

静态阶段每接一个模型都可能新增 Schema、DO/Service、映射、查询接口、测试和发布协调。源码能证明这些工作项存在，但不能证明统一的“3～5 人月”耗时；如果没有历史工单和人天台账，面试只讲成本组成，不报具体数字。

# §3 · 阶段 2：抽象元模型（第一次抽象）

## §3.1 形态

**ModelRegistry 引入**（`cmdb-core`）：
```
model_type=cvm_instance → 表 tcs_cvm_entity_instance + DO 类型 CvmInstance
model_type=cdb_instance → 表 tcs_cdb_entity_instance + DO 类型 CdbInstance
```

**每类实体一张独立表**：
```sql
CREATE TABLE tcs_cvm_entity_instance (
    id BIGINT PRIMARY KEY,
    tenant_id VARCHAR(50),        -- ★ 强制多租户隔离
    sync_version BIGINT,           -- ★ 乐观锁版本号
    sync_source VARCHAR(20),       -- FULL_SYNC / INCR_SYNC
    last_sync_time DATETIME,
    -- CVM 独有字段
    instance_id VARCHAR(64),
    region VARCHAR(64),
    status VARCHAR(32),
    ...
);
```

## §3.2 元模型的核心组件（`INCR_SYNC_DESIGN §5`）

**ModelRegistry**（§5.1）：注册"model_type → 表 + DO"映射

**AttributeConverter**（§5.2）：Protobuf attributes → DO 字段转换

**元字段规范**：所有实体表都必须有 `id / tenant_id / sync_version / sync_source / last_sync_time / created_at / updated_at`

**iwiki 4013370589 强制约束**：**"所有资源实体必须有 tenant_id 做逻辑隔离"**

## §3.3 解决的问题

- ✅ 字段爆炸：每类实体独立表
- ✅ 类型冲突：DO 类型化
- ✅ 共享表锁：写入分散到不同表

## §3.4 引入的新问题

- ❌ **静态定义**：新增字段仍需 `ALTER TABLE`
- ❌ **模型演进僵化**：改字段类型需要迁移所有数据
- ❌ **跨产品关系仍难描述**：CVM 属于哪个 App？外键？关系表？
- ❌ **接入还是要写代码**：每接一个新产品要建表 + 定义 DO + 写映射

## §3.5 单产品接入成本

**降到 ≈ 1 人月**：
- schema 设计：3 人日
- 建表：1 人日
- DO 定义：2 人日
- 映射代码：10 人日
- 测试：4 人日

**仍然痛点**：**跨团队协调**依然是主要成本（20~50% 的时间）。

# §4 · 阶段 3：直连他人数据库（重耦合的教训）

## §4.1 形态

**为了加速接入**，CMDB 直接连各云产品的 MySQL replica：

```yaml
# CMDB 侧配置
data_sources:
  - name: cvm_direct
    type: DIRECT_DB           # ★ 代码中的枚举（iwiki 4024143170 明示 DataSourceType.DIRECT_DB）
    dsn: "user:pwd@tcp(cvm-replica.woa.com:3306)/cvm_prod"
  - name: cdb_direct
    type: DIRECT_DB
    dsn: "user:pwd@tcp(cdb-replica.woa.com:3306)/cdb_prod"
```

**代码证据**（`controller/company_cmdb_proxy_controller.go` + `controller/companycmdbcontroller/`）：TCUM CMDB 直接代理到公司 CMDB。

## §4.2 一段时间的甜蜜期

**接入方式**：
- 云产品给个 read-only replica 账号
- CMDB 侧写 SQL 映射到本地表
- **接入时间：3 天到 1 周**

**收益**：
- 接入极快
- 数据实时性好（replica 有几秒延迟）

## §4.3 然后陷阱一个一个来

**陷阱 1 · 他人 DBA 半夜改表结构**

**真实案例**（推演）：
- 12:00 AM：CVM DBA 加了个 `gpu_type` 字段（正常运维）
- 4:00 AM：CVM DBA 把 `status` 字段类型从 `VARCHAR(32)` 改成 `INT`（业务重构）
- 7:00 AM：TCUM 值班收到"CMDB CVM 数据全部无法解析"告警
- **根因**：CMDB 侧代码期望 `status` 是字符串，突然变 INT 崩溃

**教训**：**直连他人 DB = 与他人 schema 强耦合**。他人升级即断链。

**陷阱 2 · 跨部门权限治理**

- 每个云产品的 replica 账号要跨部门审批
- 权限变更、密码轮换、DBA 换人都要重新申请
- **接入 10 个云产品 = 10 套账号 = 10 倍权限运维**

**陷阱 3 · 性能相互干扰**

- CMDB 侧对 CVM replica 跑大聚合查询
- CVM 的其他消费方（比如 CVM 前端）也在读同一个 replica
- **一个大查询 → 全体消费方卡顿**

**陷阱 4 · 无幂等保证**

- CMDB 侧读到的是"当前时刻的数据快照"
- 中间可能 in-flight transaction 未提交
- **CMDB 拿到的数据可能是"脏读"**

**陷阱 5 · 无变更事件**

- 直连 replica 只能"轮询变化"（`WHERE updated_at > last_sync`）
- **无法感知 DELETE**（记录已经不在了）
- 需要业务侧配合软删除标记

## §4.4 单产品接入成本

**表面上降到 3~5 人日**——但**隐藏成本极高**：
- 长期运维成本（他人升级即断链）
- 跨团队权限成本
- 数据质量成本（脏读、DELETE 感知）

## §4.5 阶段 3 的历史遗迹

**代码里仍然存在**：
- `controller/company_cmdb_proxy_controller.go` —— 公司 CMDB 代理
- `controller/companycmdbcontroller/` —— 公司 CMDB 交互
- `service/kafka/consumer/company_cmdb_kafka_consumer.go`（246 行）—— **老一代 Kafka 消费者，用于处理公司 CMDB 直连场景**

**面试可以讲**：**"这是历史包袱，老 case 还在跑，新数据源都走阶段 4 的统一 SPI + Kafka"**。

# §5 · 阶段 4：SPI + Kafka（本人主导·2025 年）

## §5.1 形态

**核心设计**（`INCR_SYNC_DESIGN.md` 本人 813 行文档）：

### 全量同步（SPI Pull）
```
CMDB → GET /cmdb/spi/entities?type=X&updated_since=Y&page=Z
云产品侧返回统一 JSON
CMDB doDiff(local, remote) → insert/update/delete
```

### 增量同步（Kafka Push）
```
云产品变更 → 生产 SyncMessage (Protobuf) → Kafka
CMDB UnifiedIncrSyncConsumer 消费
AOP 版本控制中间件检查 event_time > current sync_version
DAO 执行 SQL (带 WHERE sync_version < ? 兜底)
manual commit Kafka offset
```

**Kafka Consumer 配置**（`unified_incr_sync_consumer.go:56-70`，代码级证据）：
```go
kafkaConfig := &kafka.ConfigMap{
    "bootstrap.servers":  config.Cfg.Kafka.IncrSyncConsumerServers,
    "group.id":           config.Cfg.Kafka.IncrSyncConsumerGroupId,
    "auto.offset.reset":  "latest",           // 从最新开始，不回溯历史
    "security.protocol":  "plaintext",
    "session.timeout.ms": 10000,
    "request.timeout.ms": 30000,
    "socket.timeout.ms":  30000,
    "enable.auto.commit": false,              // ★★★ 明确 manual commit
}
```

**这些参数值都是可背下来的**——面试问 "Kafka 消费者怎么配的" 有具体答案。

## §5.2 四大设计支柱（`INCR_SYNC_DESIGN §二`）

**支柱 1 · 统一消息协议**（§2.1）
```protobuf
message SyncMessage {
  string trace_id = 1;
  OperationType operation = 2;     // CREATE/UPDATE/DELETE/BATCH_UPSERT
  string model_type = 3;
  google.protobuf.Timestamp event_time = 4;
  string source = 5;
  oneof payload {
    CreatePayload create = 10;
    UpdatePayload update = 11;
    DeletePayload delete = 12;
    BatchPayload batch = 13;
  }
}
```

**支柱 2 · 表驱动架构**（§2.2）
- `model_type` → ModelRegistry → 表名 + DO 类型
- Kafka 解码、路由、批量写等公共流程可以复用；静态模型仍需要 DO/映射，动态模型才使用字段定义 + map 降低编译期代码量
- 代码证据：`ModelTypeMap`、`ModelRegistry.Register` 与 `RegisterDynamic`

**支柱 3 · 版本控制**（§2.3）
- 设计目标是用事件版本阻止旧状态覆盖新状态
- 当前代码有 `BeforeCreate/Update/Delete` 接口，但 Create 不比较、Delete 直接放行，Update 是先读后写
- `BuildVersionedUpdateSQL` 展示了原子 CAS 的正确方向，但尚未接入生产写主路径

**支柱 4 · 状态收敛目标**（§2.4）
- 设计文档选择版本控制而非逐资源分布式锁
- 版本号用于过滤已观察到的旧更新，但当前预检查与更新不原子，不能单独保证最终一致性
- 还需要可靠消息交付、全量回放与独立对账共同兜底

## §5.3 三大问题场景（`INCR_SYNC_DESIGN §4.1`）

| 场景 | 描述 | 风险 |
|---|---|---|
| 1 | 全量同步时收到增量消息 | 增量数据被全量数据覆盖 |
| 2 | 增量消息乱序到达 | 旧数据覆盖新数据 |
| 3 | 全量同步覆盖更新的增量数据 | 丢失最新变更 |

**设计文档给出的目标解法是原子版本条件更新**：

```sql
-- 关键 SQL（§4.3 原文）：
UPDATE tcs_redis_entity_instance
SET instance_name = ?, port = ?,
    sync_version = ?, sync_source = 'INCR_SYNC', last_sync_time = NOW()
WHERE id = ?
  AND (sync_version < ? OR sync_version IS NULL);   -- ★ 关键护栏
```

如果上述 SQL 真正用于最终写操作，乱序场景会这样收敛：
- T0：event_time=100 UPDATE 消息 A
- T0+3s：event_time=90 UPDATE 消息 B（乱序）
- 消费 A：sync_version → 100
- 消费 B：`WHERE sync_version < 90` → 当前是 100，跳过
- **目标结果**：以最新（event_time=100）的数据为准。当前生产路径仍需把版本条件并入最终 UPDATE 才能严格成立。

## §5.4 全量与增量共存

当前 SPI 全量不是只靠一个 `syncVersion=time.Now()`：它先按 `model_type` 获取 30 分钟分布式锁，设置 35 分钟增量暂停标记；增量消息暂存在每模型 Redis List。全量完成后清除暂停、取出并删除暂存列表，再逐条回放，由版本规则尝试过滤旧事件。

这条链的主要短板是：pause 设置失败仍继续；任务超过 TTL 会失去保护；`PopAll` 后回放失败没有 ACK/DLQ；回调未注册会丢弃消息。因此可靠性改进重点是 durable queue + ACK、lease 续租和明确的全量水位，而不是继续宣传一段未接入主路径的伪代码。

## §5.5 五大核心组件（`INCR_SYNC_DESIGN §五`）

| 组件 | 文件 | 职责 |
|---|---|---|
| **ModelRegistry** | `incr_sync_service/model_registry.go` | `model_type` → 静态 DO 或动态表/字段定义 |
| **AttributeConverter** | 增量同步服务 | SyncMessage attributes → DO/map 字段 |
| **VersionControlMiddleware** | 版本控制服务 | 写前检查骨架；最终 CAS 尚需补齐 |
| **IncrSyncService** | bizservice/incr_sync_service/ | 增量同步业务逻辑 |
| **UnifiedIncrSyncConsumer** | kafka/consumer/ | **本人代码，272 行** |

## §5.6 单产品接入成本

SPI + Kafka 把 CMDB 侧公共消费、路由和写入流程复用起来，但云产品方仍需实现 SPI/消息生产，双方还要完成字段映射、唯一键、版本语义和联调。价值是**协议解耦和公共能力复用**，不是可由源码证明的固定“5～10 人日”。

## §5.7 阶段 4 引入的新问题

- ❌ SPI 版本管理（如 SPI 定义升级，老适配层失效）
- ❌ Kafka 消息乱序（乐观锁解，但极端场景仍有边界）
- ❌ event_time 依赖数据源 NTP
- ❌ 单 region Kafka 集群（跨 region 需要阶段 5）

# §6 · 阶段 5：多 region 数据库（跨地域）

## §6.1 形态

**代码证据**（iwiki 4024143170 明示）：`DataSourceType` 枚举包含 **`REGION_DB`**——**多 region 数据库**。

**多 region 场景**：
- 一个云产品在多个 region 都有 MySQL
- CMDB 需要**同时消费多个 region 的数据**
- 数据落到 CMDB 后还要**跨 region 展示**

**关键 SQL 特征**（`t_cmdb_custom_flink_cdc_script.covered_regions`）：多 region UNION ALL

```
covered_regions = "ap-guangzhou,ap-beijing,ap-shanghai"
```

## §6.2 挑战

**挑战 1 · region 数据一致性**
- 一份数据在 3 个 region 都存
- 靠 TDSQL DCN 跨地域复制（iwiki 4018944587 底座卷提及）
- **短板**：DCN 有秒到分钟级延迟

**挑战 2 · 脑裂预防**
- region 网络抖动 → 两个 region 都认为自己是主
- 数据分叉

**挑战 3 · 路由复杂度**
- CMDB 读时从哪个 region 读？就近？主 region？
- 需要路由表

**挑战 4 · 跨 region 写冲突**
- 同一实体在两个 region 同时被更新
- **依然靠 sync_version 乐观锁**

## §6.3 与阶段 4 的关系

阶段 5 **不是替代阶段 4，是叠加**：
- 同步机制仍是 Kafka + AOP + 乐观锁
- 只是数据源和目标都变成多 region
- Kafka 集群需要按 region 部署或跨 region 复制

# §7 · 阶段 6：FlinkCDC + AI 辅助制品治理

## §7.1 战略动机

**为什么需要 FlinkCDC**：
- 阶段 4 需要**云产品方配合**（写 SPI + 生产 SyncMessage）
- 一些云产品**不愿意/不能配合**（团队人力不足、技术栈不匹配）
- FlinkCDC = **无侵入**（直接读他人 MySQL binlog，云产品完全不参与）

## §7.2 当前代码中的设计演进

**关键设计原则**（可背，iwiki 原文）：
> ① DataSourceType 枚举**不新增 FLINK_CDC**，FlinkCDC 是模型上的 SyncMode（DIRECT / FLINK_CDC）
> ② 灰度以"脚本版本（ScriptVersion）+ CoveredRegions"为载体，不再有"批次（Batch）"
> ③ 一个模型最多 1 条 ACTIVE 脚本；旧 ACTIVE 在新版本保存时被置 SUPERSEDED（事务内）
> ④ 脚本仍是一等版本化制品，但当前控制器已经具备 Oceanus folder/job/config 的创建、查询、运行、修改、停止、激活与恢复能力，不能再说“CMDB 完全不调用 Flink 平台”

当前职责可以拆成两层：

1. **制品层**：生成/预览/Lint Flink SQL 和 sink DDL，保存版本、hash、server-id、灰度地域及审计；
2. **运行层**：通过 Oceanus 服务创建和控制作业、管理运行配置、查询任务状态并支持恢复。

两层分开仍有价值：脚本版本是期望状态，Oceanus task 是实际状态。但二者跨系统，不能靠单库事务保证一致；应以 operation/attempt 状态机、幂等请求和定期 reconcile 收敛。

**核心字段解读**：
- **`script_version` + `parent_script_id`**：版本树（可回溯演化）
- **`covered_regions`**：多 region 灰度粒度
- **`gray_region_states`**：JSON 里每个 region 的灰度状态
- **`lint_status`**：SQL Lint（PENDING/PASS/WARN/FAIL）
- **`script_status` 状态集合**：`DRAFT / VALIDATED / ACTIVE / PAUSED / SUPERSEDED`；允许迁移不是单向直线，且 `SaveScript` 会直接创建 `ACTIVE` 版本

## §7.4 AI 生成 FlinkCDC 脚本的独特价值

**场景**：用户接入一个新数据源
- **传统方式**：用户手写 Flink SQL（100~500 行）——门槛高
- **AI 方式**：用户上传数据源信息（xlsx / csv / 文本描述） → tcum_cmdb_expert Agent 解析 → 生成完整 Flink SQL + CMDB sink DDL

**AI 生成的 SQL 会记录 Lint 状态**（PENDING/PASS/WARN/FAIL），`SaveScript` 对 FAIL 做硬阻断。它能拦截已编码的静态规则错误，但不能单独保证 SQL 在真实 catalog 和数据上正确。

数据模型明确预留 `ai_dialog_id`、Agent/Skill 名、模型与 Token 审计字段，可承载 TCUM-AI 生成链路。面试时要区分“表结构与服务支持”以及“每次生产请求都实际走该 Agent”的运行证据；后者需 Trace 或配置证明。

## §7.5 提单注意事项（iwiki 原文明示的踩坑）

**坑点**（iwiki 4024143170 原文）：
> 1. 提单时请勾掉「动态检查」选项；ALTER 已改为**非幂等的直接 DDL**，仅在未变更过的库执行一次。
>    **原 PREPARE+INFORMATION_SCHEMA 的幂等写法被平台动态预检识别为 zichu.columns（库名错位）触发 1146 错误**。
> 2. flink_sql / cmdb_ddl 必须保留 MEDIUMTEXT：业务上需存储完整 Flink SQL 与建表 DDL（多 region UNION ALL 后可达 ~50KB）

**这是"工程实施踩坑"的教训** —— 面试可以讲：
> "我们在工蜂 SQL 审核平台踩过一个坑：原本想写幂等 DDL（PREPARE + INFORMATION_SCHEMA），但平台的动态预检把 information_schema.columns 识别成 zichu.columns（库名错位）触发 1146 错误。最后改成非幂等直接 DDL，只跑一次。"

## §7.6 单产品接入成本

不能写“接近 0 人月”。CDC 减少业务方编写推送代码，但仍需要源库权限、schema/主键确认、数据映射、预检、灰度、Flink/Oceanus 资源和运行治理。成本从业务侵入开发转移到平台接入与持续运维，而不是消失。

## §7.7 阶段 6 的新问题

- Flink 状态大（每个模型一个 Flink 任务）
- 成本高（Flink 集群 vs Kafka 消费者）
- 运维复杂度（Flink 任务监控、checkpoint、savepoint）
- 他人 binlog 权限（需要跨部门审批）

# §8 · 演进曲线：成本没有消失，只是转移

| 阶段 | 主要成本落点 | 获得的收益 | 新增治理成本 |
| --- | --- | --- | --- |
| 单表/静态模型 | 平台逐模型开发 | 简单直接 | 字段与发布耦合 |
| 直连 DB | 接口开发减少 | 快速查询源数据 | 权限、Schema 漂移、源库压力 |
| SPI + Kafka | 双方维护协议与生产逻辑 | 全量与增量解耦 | 版本、offset、回放和对账 |
| 动态元模型 | 配置和 DDL 治理 | 减少编译期模型代码 | 动态类型、审批和缓存生效 |
| FlinkCDC + AI | 平台接入与运行治理 | 减少业务方推送开发 | binlog 权限、Oceanus 资源、checkpoint、灰度和 AI 质量 |

没有量化工单和成本台账时，只讲“成本结构变化”和可验证的代码能力，不画虚假的人月曲线。
