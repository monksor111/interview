> **定位**：用三条链路把增量同步、全量协调和 FlinkCDC 脚本治理串起来。它们是基于源码构造的能力推演，不冒充生产事故或实测时延。

## 场景 A：一条资源状态变更如何进入 CMDB

### A1. 问题

上游把资源状态变化编码为 `SyncMessage` 后，TCUM CMDB 如何识别模型、抵抗乱序并更新本地状态？

### A2. 源码可验证链路

```text
Kafka Message
  → UnifiedIncrSyncConsumer.MessageFilter
  → protobuf.Unmarshal(SyncMessage)
  → IncrSyncService.ProcessSyncMessage
  → 全量同步暂停检查
  → ModelRegistry.Get(model_type)
  → AttributeConverter / DynamicAttributeConverter
  → event_time 转版本号
  → BeforeCreate / BeforeUpdate / BeforeDelete
  → DAO 写入
  → 业务成功后尝试 CommitMessage
```

关键事实：

- 消息协议包含 `trace_id`、`operation`、`model_type`、`event_time`、`source` 和不同操作 payload。
- `model_type` 负责路由到具体模型元数据；动态模型会周期性从 `SuperCache` 刷新进 `ModelRegistry`。
- 对支持版本字段的实体，旧版本更新会在业务层被跳过；部分 SQL 路径还带版本条件。
- Kafka 配置关闭 auto commit，基础消费者在处理成功后调用 `CommitMessage`。

### A3. 必须主动说的边界

这条链路不能直接回答“端到端几秒”。源码没有 CVM 上游耗时、Kafka 排队分布或下游感知时间，合理的线上指标应至少包括：

- `source_event_time → consume_time` 的 Kafka lag；
- `consume_time → db_commit_time` 的处理 P50/P95/P99；
- 按 `model_type/partition/result` 切片的失败率；
- CMDB 状态变化到下游重新读取之间的传播延迟。

更重要的是，当前 50 协程池没有保证 partition 内有序完成。高 offset 可能先提交并越过低 offset 的失败消息，因此面试中不能说“失败一定重放”或“已经 exactly-once”。版本控制解决的是状态覆盖，不是 offset 交付。

### A4. 可直接作答

> “从 CMDB 的边界开始，一条状态变更先以 Protobuf `SyncMessage` 进入 Kafka 消费者，`model_type` 找到模型定义，payload 经静态或动态转换器映射，`event_time` 再作为版本依据执行创建、更新或删除。亮点是版本化状态更新能抵抗大量重复和乱序。当前短板是消费并发与 offset 提交没有形成严格协议：同 partition 消息进 50 协程池，可能越洞提交，所以我会先改成 partition 内串行、partition 间并行，再谈 at-least-once。”

## 场景 B：SPI 全量同步与 Kafka 增量如何避免互相覆盖

### B1. 问题

全量扫描持续时间较长，期间新的增量消息仍在到达。如果两条链路直接并发写，同一资源可能反复覆盖，删除判断也可能基于不一致快照。

### B2. 当前实现不是“纯靠版本号同时跑”

最新源码已经加入显式协调：

```text
SPISyncEngine.Execute(model_type)
  → 获取 model_type 粒度分布式锁（30 分钟）
  → 设置增量暂停标记（Redis，35 分钟）
  → 执行 SPI 全量拉取、Diff 和写入
  → 清除暂停标记
  → PopAll 暂存增量消息
  → 逐条调用 IncrSyncReplayFunc 回放
  → 版本控制过滤已经被全量覆盖的旧事件
  → 释放分布式锁
```

增量侧在 `ProcessSyncMessage` 开头检查暂停标记；若命中，会把序列化后的消息推入按 `model_type` 隔离的 Redis 队列并返回成功。全量结束后先清标记，再取出队列回放，避免回放消息再次入队。

这比旧文档描述的“全量与增量完全同时写，只靠 `sync_version` 决胜”多了一层流量协调：

- 分布式锁防止同一模型出现两个全量任务；
- 暂停标记缩小全量与增量的写冲突窗口；
- Redis 队列保留窗口内增量；
- 回放阶段再用版本规则处理时序冲突。

### B3. 源码暴露出的失败窗口

| 失败点 | 当前行为 | 风险 | 建议 |
| --- | --- | --- | --- |
| 设置暂停标记失败 | 只记错误，继续全量 | 全量与增量重新并发写 | 对要求一致性的模型应 fail closed；或显式降级为仅版本控制并告警 |
| 全量超过暂停 TTL | 标记可能先过期 | 增量在全量结束前恢复直写 | watchdog 续租，并让 TTL 与任务 lease 绑定 |
| `PopAll` 后部分回放失败 | 统计 `replayFail`，主流程仍完成 | 已弹出消息可能不再重试 | 使用可靠队列/processing list，逐条 ACK；失败进入 DLQ |
| 回放函数未注册 | 日志明确写“已丢弃” | 暂存消息永久丢失 | 视为全量任务失败，禁止静默成功 |
| 清暂停标记失败 | defer 再尝试，但期间行为不确定 | 后续增量继续堆积 | 幂等清理 + 告警 + 独立补偿任务 |

### B4. 可直接作答

> “我们不是让全量和增量毫无协调地同时写。当前 SPI 全量会按模型拿分布式锁并设置 Redis 暂停标记，增量消息先暂存；全量结束后清标记、回放增量，再由版本控制过滤旧事件。这个设计把互斥、缓冲和冲突处理分成三层。它的主要缺口是回放队列还不是可靠消费协议：`PopAll` 后失败消息缺少 ACK/DLQ，暂停标记设置失败也会继续执行，所以我会把这两点作为 P0。”

## 场景 C：FlinkCDC 脚本从生成结果变成可治理版本

### C1. 问题

AI 可以帮助生成 Flink SQL，但“生成一段文本”不等于“可以运行”。真正需要治理的是数据源约束、Lint、版本、灰度地域、server-id、sink DDL、当前生效版本和回滚关系。

### C2. 保存链路的当前事实

`ScriptService.SaveScript` 的主链路是：

1. 校验输入；`LintStatus=FAIL` 直接拒绝保存。
2. 开启数据库事务，读取当前最大 `script_version` 并计算新版本。
3. 将旧 `ACTIVE` 脚本改为 `SUPERSEDED`。
4. 插入新 `ACTIVE` 脚本，记录 Flink SQL、SHA-256、模板版本、父版本、覆盖地域和灰度状态。
5. 为各地域分配 server-id，避免 binlog 订阅冲突。
6. 更新模型的 `active_script_id`。
7. 执行受生成器约束的 sink DDL，并更新执行标志。
8. 任一步失败则事务回滚。

状态模型包含 `DRAFT / VALIDATED / ACTIVE / PAUSED / SUPERSEDED`；但要注意 `SaveScript` 本身会直接创建 `ACTIVE` 记录，不能仅凭实体注释就说所有请求都严格走完整的五状态迁移。

### C3. 设计亮点与需要继续验证的地方

亮点：

- 版本、当前指针、server-id 和 sink DDL 被放进同一数据库事务域；
- Lint FAIL 是硬阻断，不是提示；
- `FlinkSqlHash` 和 `TemplateVersion` 支持审计生成结果；
- 灰度地域不是一个布尔值，而是 `pending/effective/removed` 的结构化状态。

需要继续验证：

- 注释称最大版本读取使用 `SELECT FOR UPDATE`，当前查询代码片段没有显式 locking clause；并发保存主要依赖唯一索引冲突回滚，需要通过并发测试确认行为。
- 实体注释明确 `PAUSED` 只是 CMDB 状态；是否联动真实 Flink/Oceanus 任务，要看任务服务调用链，不能从状态字段自行推断。
- “AI 生成正确”不能由 Lint PASS 单独证明；还需要 parser、catalog 校验、测试数据回放和运行时 checkpoint/lag 指标。

### C4. 可直接作答

> “我们把 AI 生成结果当成待验证制品，而不是直接执行。保存前 Lint FAIL 会硬阻断；保存时在事务里处理旧版失效、新版生效、server-id、模型 active 指针和 sink DDL，同时记录 SQL hash、模板版本和灰度地域状态。这个设计解决了版本和审计问题，但我不会把 Lint PASS 等同于生产正确：下一步还要补真实 catalog 校验、测试回放和运行指标门禁。”

## 三个场景如何串成一条项目主线

```text
模型与脚本治理
  → 定义“什么数据可以进入、怎样映射”
    → SPI 全量建立基线，暂停并缓冲增量
      → 回放 Kafka 增量，版本规则收敛最终状态
        → 下游通过 CMDB 查询统一资源事实
```

这条主线的面试价值不在于背某个类名，而在于能说清四类不同问题：模型契约、批流协调、消息交付和生成制品治理。每一类都有已经实现的机制，也都有源码可见的失败窗口。
