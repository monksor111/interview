> **本章定位**：3 个真实 case 串讲，把机制篇的所有理论落到"一次真实事件的完整链路"。

# 场景 A · CVM 关机事件的 4 秒传递

## Situation

用户在腾讯云控制台**关机**一个 CVM 实例 `ins-abc-123`。这个"关机"事件如何最终反映到 TCUM CMDB？

## 时间线

| 时刻 | 事件 |
|---|---|
| T+0 | 用户点击关机按钮 |
| T+1s | CVM 后端下发 hypervisor 关机指令 |
| T+3s | 关机完成，CVM 后端 DB status='stopped' |
| T+3s | CVM 侧生产 SyncMessage → Kafka |
| T+3.5s | `UnifiedIncrSyncConsumer` 消费消息 |
| T+3.6s | AttributeConverter 反序列化 payload |
| T+3.6s | AOP `BeforeUpdate` 版本检查：event_time > current sync_version ✓ |
| T+3.7s | `UPDATE tcs_cvm_entity_instance SET status='stopped', sync_version=..., sync_source='INCR_SYNC' WHERE id=? AND (sync_version < ? OR sync_version IS NULL)` |
| T+3.8s | 下游消费：监控（不再对该实例告警）、TCUM-AI（获得最新状态） |

## 机制串讲

- 数据源生产 SyncMessage ✓（阶段 4）
- Kafka `enable.auto.commit=false` 保证 at-least-once ✓
- ModelRegistry `tcs_cvm_entity_instance` 路由 ✓（表驱动）
- AOP 版本检查 ✓（乐观锁）
- SQL 兜底 `WHERE sync_version < ?` ✓

**端到端延迟 ≈ 4 秒** —— 面试可背。

## 面试追问

**追问 1**：4 秒延迟对告警意味着什么？
- 4 秒内告警系统对已停机实例可能仍发告警——**"CMDB 与监控的时序耦合"**

**追问 2**：Kafka 挂 30 分钟怎么办？
- cmdb-check 兜底。凌晨全量对账时发现差异 → 自动修复
- 代价：30 分钟内数据陈旧

**追问 3**：能做到秒级吗？
- 能，靠增量同步理论 1 秒内
- 当前 4 秒主要来自 Kafka 消费的批处理和 AOP 层
- 可优化到 1~2 秒

# 场景 B · CVM 表结构升级的全量重灌

## Situation

CVM 库结构升级，新增 `gpu_type` 字段。**全量重灌**一次 CVM 表数据到 CMDB。

## 时间线

| 时刻 | 事件 |
|---|---|
| T+0 | DBA `ALTER TABLE tcs_cvm_entity_instance ADD COLUMN gpu_type VARCHAR(50)` |
| T+1min | 触发全量同步 Job：`FullSyncMode` 启动 |
| T+1min | 记录 `syncVersion = time.Now().UnixMilli()` |
| T+1min | 从 CVM SPI 拉全量（游标分页） |
| T+2min~T+10min | `doDiff(local, remote)` 计算 insert/update/delete 列表 |
| T+10min~T+30min | 逐条写入（sync_source='FULL_SYNC'） |
| **同时期** | 增量消息持续到达 |

## 关键冲突场景

- 时刻 X：全量 Job 写 CVM-abc 的旧字段
- 时刻 X+100ms：增量消息说 CVM-abc.status 变了

**冲突解决**（靠 sync_version 乐观锁）：
- 全量 Job sync_version = T+1min
- 增量 sync_version = X+100ms（当前时间 >> T+1min）
- 全量 UPDATE 的 `WHERE sync_version < 全量启动时间` → **跳过**（因为已被增量更新）
- 增量数据保留 ✓

## 面试追问

**追问 1**：全量 Job 期间 SPI 挂了怎么办？
- 分页游标断点续传——重启后从游标继续

**追问 2**：全量重灌会误删数据吗？
- **doDiff 产出的 delete 列表要二次校验**——比如"如果发现要删除 > 总数 10%"停止并告警

# 场景 C · 消息乱序 + AI FlinkCDC 生成的组合场景

## Situation

一个复杂业务变更：
1. 用户接入新数据源（未覆盖的云产品）
2. 通过 AI Agent 生成 FlinkCDC 脚本
3. 脚本激活，但 Kafka 中同时有旧协议消息乱序到达

## 时间线

| 时刻 | 事件 |
|---|---|
| T+0 | 用户上传数据源信息（xlsx） |
| T+30s | `tcum_cmdb_expert` Agent 解析 → 生成 model 定义 + column mapping |
| T+1min | 用户 review + 保存到 `t_cmdb_custom_model_definition` |
| T+2min | 用户上传 FlinkCDC 脚本（AI 生成 v1） |
| T+2min | 脚本走 Lint（PENDING → PASS） |
| T+3min | 用户激活脚本：`script_status = DRAFT → VALIDATED → ACTIVE` |
| T+3min | 旧 ACTIVE 脚本（如果存在）→ SUPERSEDED（**事务内**） |
| T+5min | Flink 平台侧提交任务，开始消费 binlog |
| T+6min | Flink 写入 sink 表 |
| T+7min | **同时期**：另一个 Kafka 老协议消息乱序到达（event_time 更早） |
| T+7min | UnifiedIncrSyncConsumer 消费：AOP 版本检查失败 → 跳过 ✓ |

## 机制串讲

- 阶段 6 独立 SQL 状态机（DRAFT → VALIDATED → ACTIVE → SUPERSEDED）
- AI 生成 + Lint 校验
- 事务内 SUPERSEDED 旧 ACTIVE
- 乐观锁保证乱序不影响新数据

## 面试追问

**追问 1**：AI 生成的 SQL 有 bug 怎么办？
- Lint 状态 FAIL 会拦截
- 用户 review 后手动确认
- 版本可回滚（`parent_script_id`）

**追问 2**：脚本从 ACTIVE → PAUSED 是什么场景？
- 灰度出问题、成本控制、临时下线
- **推演**：不删除数据，只停止 Flink 任务

**追问 3**：多 region 灰度失败怎么回滚？
- `gray_region_states` JSON 里每个 region 独立状态
- 单 region 失败可以只回滚该 region
