## A · 数据同步层（6 条）

**A1 · partition 内并发处理会破坏可靠提交语义** ⚠️ P0
- 代码虽明示 `enable.auto.commit=false`，但 `base_kafka_consumer.go` 把消息投到 50 协程池，并在每条成功后直接 `CommitMessage`。
- 同一 partition 的高 offset 可能先提交并越过低 offset 的失败消息；commit 返回错误也没有处理。
- 影响：不能严格证明 at-least-once，更不能宣称 exactly-once；失败消息可能只靠后续巡检发现。
- 修法：partition 内串行、partition 间并行；或维护连续完成水位，只提交没有洞的最大 offset；提交失败需重试/告警。
- 验收：构造 N 阻塞、N+1 成功后 rebalance 的故障注入，确认 N 必须被重放。

**A2 · 版本预检查与最终更新存在 TOCTOU** ⚠️ P0
- `BeforeUpdate` 先 SELECT 当前版本，随后 `BaseBatchUpdate`；版本条件没有进入最终 UPDATE。
- `BuildVersionedUpdateSQL` 只有定义和测试，生产调用数为 0；两个并发事件可同时通过检查。
- 修法：`UPDATE ... WHERE sync_version < new_version` 原子 CAS，以 `RowsAffected` 判定是否生效。

**A3 · event_time 依赖 NTP** ⚠️ P1
- 现象：数据源 NTP 漂移 → 新事件反而 sync_version 更小 → 被跳过
- 修法：ingest_time fallback
- 改动量：<100 行

**A4 · 全量暂停/回放队列不是可靠 ACK 协议** ⚠️ P0
- 暂停标记设置失败仍继续全量；`PopAll` 后部分回放失败只记统计；回放函数缺失时日志写明会丢弃。
- 修法：可靠 processing queue + ACK/DLQ；暂停失败按模型风险 fail closed；任务运行时续租暂停 lease。

**A5 · DELETE 当前绕过版本控制** ⚠️ P0
- `BeforeDelete` 直接返回 true，旧删除事件可能删除更新对象。
- 修法：版本化软删/墓碑，使用原子版本比较。

**A6 · Kafka session.timeout 10s 需要校准** P2
- 是否过短取决于 heartbeat、网络和 rebalance 实测，不能只凭常量下结论。
- 修法：观察 rebalance/heartbeat 分布后联合调参；代价是故障发现速度与误判率的权衡。

## B · 元数据 SPI（3 条）

**B1 · Pull 周期盲区** P1
- 现象：新扩容资源 10 分钟才可见（云梯甚至一天）
- 修法：Push 通道 + 分级拉取

**B2 · SPI 版本管理缺失** ⚠️ **P0**
- 现象：无版本号，升级卡壳
- 修法：`/v1/entities` 版本号 + 多版本并存
- 改动量：<100 行

**B3 · 分页 offset 而非 cursor** P2
- 现象：分页期间数据变动导致重复或漏
- 修法：游标分页

## C · 巡检层（3 条）

**C1 · 多副本没有可靠任务所有权** ⚠️ P0
- `JobList` 是进程内 map，每个实例都可能从 DB 加载并执行同一任务；启动前的状态读写也不是 CAS。
- 修法：DB lease + owner + fencing token，原子抢占并按 attempt_id 落终态。

**C2 · 任务取消与定时器生命周期不完整** P1
- 刷新周期时直接替换 `time.Tick`；超过两小时只把 DB 状态改失败，不能取消仍在运行的 Handler。
- 修法：`time.NewTicker/Stop`、`context.WithTimeout`、attempt 隔离和退出清理。

**C3 · Handler 覆盖与自动处置门禁不足** P1
- 新任务框架只实现 `module_host_config + db`；上报告警使用全局自动更新/忽略/人工规则，未见通用差异量与速率门禁。
- 修法：插件契约测试；按模型/字段/来源分级，默认 dry-run，影响面熔断、限速、审批、快照和二次校验。
