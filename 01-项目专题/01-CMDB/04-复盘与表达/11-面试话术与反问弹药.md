# §1 · 3 分钟自述稿

> "我在 TCUM CMDB 做了两年，负责的是**腾讯云内部所有云产品的统一元数据管理**。这个系统的特殊之处在于——**它不是一个单体应用，而是 11 个代码仓的组合体**：包括主 CMDB（cmdb + cmdb-core）、图数据库版（nebula_cmdb，基于 Nebula Graph 面向业务功能）、一致性校验（cmdb-check）、增量同步（tcum-cmdb-global，我主导的）、以及场景化的 paas-cmdb / xingyun-cmdb-op 等。
>
> **我最深度参与的是增量同步系统的设计与落地** —— 就是 `tcum-cmdb-global/INCR_SYNC_DESIGN.md`（本人 813 行设计文档）和 `unified_incr_sync_consumer.go`（272 行代码，`@author yaao`）。**核心设计有 4 点**：
> - **统一 Protobuf 消息协议 SyncMessage**（trace_id / operation / model_type / event_time / payload oneof）
> - **表驱动架构**（`model_type` → ModelRegistry → 表 + DO 类型，50+ 云产品实体各一个 service）
> - **版本控制骨架**（增量更新前比较版本；但当前读后写存在 TOCTOU，条件更新 SQL 尚未接入主路径）
> - **全量/增量协调**（同模型分布式锁 + Redis 暂停暂存 + 全量后回放；`cmdb-check` 提供独立校验入口）
>
> **数据流向**：**云产品侧 → Kafka SyncMessage → UnifiedIncrSyncConsumer（enable.auto.commit=false 手动提交）→ AOP 版本检查 → DAO → MySQL**。这套机制解决了三个真实问题：**全量与增量并存的数据覆盖、消息乱序、多云产品接入成本**。
>
> **数据接入模式的演进有 6 个阶段**：单表 → 抽象元模型 → 直连他人 DB → SPI+Kafka（我主导的）→ 多 region → FlinkCDC + AI 辅助。接入从“每模型写专用代码”逐步变成“配置模型、字段、数据源和同步制品”；没有工单或统计证据时，不报具体人月降幅。
>
> **短板必须坦白 3 条**：
> - 第一，**event_time 依赖数据源 NTP**，时钟漂移会导致新事件被跳过；
> - 第二，**SPI 无版本管理**，升级时会卡壳；
> - 第三，**权威源矩阵未代码化**——星云 CMDB 与公司 CMDB 冲突时靠约定。"

# §3 · 20 反问清单

## 组 1 · 架构与选型（5 问）

**Q1**. 你们的 CMDB 是单体还是多系统组合？团队怎么治理边界？
🔗 *我这边是 11 仓组合体。*

**Q2**. 图数据库 vs 关系型选型？读写比多少？
🔗 *我这边双写：MySQL 主库 + Nebula 只读图查询。*

**Q3**. 元数据 SPI 用什么协议？REST/gRPC/自定义？分页策略？
🔗 *我这边每条 SPI 配置定义 endpoint、超时、原生/自定义映射和 OFFSET/CURSOR 分页；不能概括成固定的 updated_since API。大模型优先用 cursor，避免拉取期间变更导致 offset 漂移。*

**Q4**. 多 CMDB 生态时（比如你们和公司 CMDB 并存）权威源怎么划分？
🔗 *我这边分维度权威源：设备 → 公司 CMDB / 业务 → 星云 CMDB。*

**Q5**. Flink CDC 在你们技术栈的位置？
🔗 *它是 DIRECT_DB/REGION_DB 模型的一种 SyncMode。当前不只保存 SQL/DDL，还提供 Oceanus 作业创建、运行、停止、配置激活与恢复；脚本期望状态和作业实际状态跨系统，需要幂等与 reconcile。*

## 组 2 · 数据一致性（5 问）

**Q6**. 增量同步用 Kafka 吗？at-least-once 还是 exactly-once？commit 策略？
🔗 *代码里关闭了 auto commit，并在处理成功后手动提交；乐观锁提供最终状态幂等。但当前同 partition 消息会进入并发池，高 offset 可能先提交，所以我不会把它叫 exactly-once，严格 at-least-once 也需要先修复连续 offset 水位。*

**Q7**. 消息乱序怎么处理？版本号还是时间戳？依赖时钟怎么应对漂移？
🔗 *我这边 event_time 乐观锁，NTP 漂移是短板，考虑 ingest_time fallback 或 HLC。*

**Q8**. 全量与增量共存怎么保证不打架？
🔗 *当前是三层：同模型全量先加分布式锁；用 Redis 暂停标记把增量暂存；全量结束后回放，再用版本规则过滤旧事件。短板是暂停设置失败仍继续、PopAll 后回放失败缺少可靠 ACK/DLQ。*

**Q9**. 一致性巡检的策略是什么？发现大差异时怎么办？
🔗 *当前是周期任务校验和上报冲突处置两条链；源码没有通用差异阈值门禁。我的改进是默认 dry-run，按模型/字段风险、差异比例和历史基线熔断，审批后限速修复并二次校验。*

**Q10**. AOP 中间件的落地形态？拦截器/decorator/代理？
🔗 *代码定义了 BeforeCreate/Update/Delete 钩子，但目前只有 Update 做读前版本检查，Delete 放行、Create 不比较，而且最终 UPDATE 没带版本 CAS；所以我会把它叫版本控制骨架，不说“一次开发全部生效”。*
