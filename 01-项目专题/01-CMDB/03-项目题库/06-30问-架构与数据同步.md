# 主题 A · 架构与选型

## ★ Q1. TCUM CMDB 为什么是 11 个仓的组合体

### 命题
ServiceNow 单体、Netflix Edda 单体、TCUM 11 仓——分工哲学是什么？

### 分析逻辑
考察对**"服务切分"**的判断。

### 四方对比

| 方案 | 架构 | 优势 | 劣势 |
|---|---|---|---|
| **ServiceNow** | 单体大平台 | 一致性强 | 演进慢、成本高 |
| **Netflix Edda** | 单体（stopped 项目）| 简单 | 已废弃 |
| **DataHub** | 多子系统（GMS + Kafka + 前端）| 生态丰富 | 复杂度高 |
| **TCUM** | **11 仓组合**（业务/PaaS/图/校验/同步分离） | 场景针对性优化 | 治理税重 |

### 差异本质
- **单体**：**一致性 > 灵活性**
- **多仓**：**灵活性 > 一致性**

TCUM 选多仓：**腾讯云内部多团队协作 + 场景异质性大**

### 亮点+短板
- 亮点：场景针对性、团队独立发布节奏、故障隔离
- 短板：跨仓治理复杂、口径不统一风险

### 改进思路
- Q1.1（P1）**统一 SPI 接口**让 11 仓外部看起来是一个 CMDB

## ★ Q2. 图数据库 vs 关系型 · 选型判断

### 命题
Neo4j 全图、Nebula Graph、TCUM Nebula 只读 + MySQL 写入——哪种？

### 四方对比

| 方案 | 存储 | 读性能 | 写性能 |
|---|---|---|---|
| **Neo4j 全量** | 图 | 极强 | 中 |
| **TigerGraph** | 图 | 极强 | 中 |
| **DataHub** | 关系型主 | 中 | 强 |
| **TCUM** | **双写** MySQL + Nebula | 强 | 强 |

### 差异本质
- **全图**：读多跳快 / 写慢

**TCUM 走双写**：写入走 MySQL 主库，异步同步到 Nebula 供只读查询。

### 改进思路
- Q2.1（P1）明确"权威源"矩阵
- Q2.2（P2）Nebula 数据自动异步同步 + 一致性巡检

## Q4. 权威源模糊怎么办

### 命题
星云 CMDB 和公司 CMDB 都有 CVM 数据——以谁为准？

### 四方对比

| 方案 | 策略 |
|---|---|
| **ServiceNow** | 强权威源（配置项发起方）|
| **Netflix** | 弱权威源（谁写谁负责）|
| **TCUM** | **分维度权威源**（`nebula_cmdb/README.md` 明示）|

**TCUM 权威源矩阵**：
- 设备属性（IP、机架、IDC）→ 公司 CMDB
- 业务扩展属性（模块、产品树）→ 星云 CMDB
- 云梯资源（es/clb/cdb）→ 星云 CMDB

### 亮点+短板
- 亮点：分维度清晰
- 短板：**代码里未强制约束** —— 冲突时靠约定

### 改进思路
- Q4.1（P1）**权威源矩阵代码化**：每个字段带 owner 属性

# 主题 B · 数据同步

## ★ Q7. 乐观锁 vs 悲观锁

### 命题
ServiceNow 悲观锁 + version、DataHub 乐观锁 aspect version、TCUM 乐观锁 event_time——分歧本质？

### 四方对比

| 方案 | 版本号 | 冲突处理 |
|---|---|---|
| **ServiceNow** | 递增 ID | 悲观锁（阻塞）|
| **GitHub-style** | 递增 ID | 乐观锁（重试）|
| **DataHub** | aspect version | 乐观锁 |
| **TCUM** | **event_time**（毫秒时间戳）| 乐观锁 |
| **Redis distlock** | 无版本 | 分布式悲观锁（重）|

### 差异本质
- **悲观锁**：**性能差但强一致**
- **乐观锁**：**性能好但需要重试机制**

**TCUM 选乐观锁**：分布式场景乐观锁 + 幂等 = 高性能 + 最终一致

### 改进思路
见第 03 章 §6

## ★ Q8. 版本号选型 · 递增 ID / logical clock / event_time / HLC

### 命题
四种版本号方案的取舍？

### 四方对比

| 方案 | 优势 | 劣势 |
|---|---|---|
| **递增 ID** | 简单单调 | 需要中心生成器 |
| **Vector Clock** | 分布式无中心 | 存储/比较开销大 |
| **event_time**（TCUM） | 自解释、无中心、天然单调 | 依赖 NTP |
| **HLC**（Hybrid Logical Clock）| 兼具时间 + 逻辑单调 | 实现复杂 |

**TCUM 选 event_time**：**在监控 / CMDB 场景 NTP 稳定，简单胜出**

### 改进思路
- 长期看 HLC 应对 NTP 漂移

## Q9. 全量与增量共存的三种解法

### 四方对比

| 方案 | 举例 |
|---|---|
| **停机时间窗** | 老派方案（半夜停服务全量） |
| **双写切流** | 新库切换（阿里蚂蚁） |
| **TCUM sync_version 并存** | **本人主导的核心亮点**（`INCR_SYNC_DESIGN`）|
| **Debezium snapshot mode** | 一次快照 + 后续增量 |

**TCUM 亮点**：全量和增量**同时跑**，靠 sync_version 决定谁保留。**无停机时间**。
