# 主题 A · 架构与选型

## ★ Q1. TCUM CMDB 为什么是 11 个仓的组合体

### 命题
ServiceNow 单体、Netflix Edda 单体、TCUM 11 仓——分工哲学是什么？

### 分析逻辑
考察对**"服务切分"**的判断。

### 四方对比

| 方案 | 架构 | 优势 | 劣势 |
|---|---|---|---|
| **ServiceNow** | 单体大平台 | 一致性强 | 演进慢、成本高 |
| **Netflix Edda** | 单体（stopped 项目）| 简单 | 已废弃 |
| **DataHub** | 多子系统（GMS + Kafka + 前端）| 生态丰富 | 复杂度高 |
| **TCUM** | **11 仓组合**（业务/PaaS/图/校验/同步分离） | 场景针对性优化 | 治理税重 |

### 差异本质
- **单体**：**一致性 > 灵活性**
- **多仓**：**灵活性 > 一致性**

TCUM 选多仓：**腾讯云内部多团队协作 + 场景异质性大**

### 亮点+短板
- 亮点：场景针对性、团队独立发布节奏、故障隔离
- 短板：跨仓治理复杂、口径不统一风险

### 改进思路
- Q1.1（P1）**统一 SPI 接口**让 11 仓外部看起来是一个 CMDB

## Q4. 权威源模糊怎么办

### 命题
星云 CMDB 和公司 CMDB 都有 CVM 数据——以谁为准？

### 四方对比

| 方案 | 策略 |
|---|---|
| **ServiceNow** | 强权威源（配置项发起方）|
| **Netflix** | 弱权威源（谁写谁负责）|
| **TCUM** | **分维度权威源**（`nebula_cmdb/README.md` 明示）|

- 设备属性（IP、机架、IDC）→ 公司 CMDB

- 云梯资源（es/clb/cdb）→ 星云 CMDB

### 亮点+短板
- 亮点：分维度清晰
- 短板：**代码里未强制约束** —— 冲突时靠约定

### 改进思路

# 主题 B · 数据同步

## ★ Q7. 乐观锁 vs 悲观锁

### 命题
ServiceNow 悲观锁 + version、DataHub 乐观锁 aspect version、TCUM 乐观锁 event_time——分歧本质？

### 四方对比

| 方案 | 版本号 | 冲突处理 |
|---|---|---|
| **ServiceNow** | 递增 ID | 悲观锁（阻塞）|
| **GitHub-style** | 递增 ID | 乐观锁（重试）|
| **DataHub** | aspect version | 乐观锁 |
| **TCUM** | **event_time**（毫秒时间戳）| 乐观锁 |
| **Redis distlock** | 无版本 | 分布式悲观锁（重）|

### 差异本质
- **悲观锁**：**性能差但强一致**
- **乐观锁**：**性能好但需要重试机制**

**TCUM 的设计方向是乐观版本控制**：它适合读多写少和乱序更新，但必须把版本条件放进最终 UPDATE，并配合可靠消息、删除墓碑、全量回放和对账，才能讨论状态收敛。当前代码还是部分实现，不能用“乐观锁 + 幂等 = 最终一致”作等式。

### 改进思路
见第 03 章 §6

## ★ Q8. 版本号选型 · 递增 ID / logical clock / event_time / HLC

### 命题
四种版本号方案的取舍？

### 四方对比

| 方案 | 优势 | 劣势 |
|---|---|---|
| **递增 ID** | 简单单调 | 需要中心生成器 |
| **Vector Clock** | 分布式无中心 | 存储/比较开销大 |
| **event_time**（TCUM） | 自解释、无中心、天然单调 | 依赖 NTP |
| **HLC**（Hybrid Logical Clock）| 兼具时间 + 逻辑单调 | 实现复杂 |

**TCUM 选 event_time**：**在监控 / CMDB 场景 NTP 稳定，简单胜出**

### 改进思路
- 长期看 HLC 应对 NTP 漂移

## Q9. 全量与增量共存的三种解法

### 四方对比

| 方案 | 举例 |
|---|---|
| **停机时间窗** | 老派方案（半夜停服务全量） |
| **双写切流** | 新库切换（阿里蚂蚁） |
| **TCUM 暂停/缓冲/回放 + 版本收敛** | 最新源码中的 SPI 全量与增量协调 |
| **Debezium snapshot mode** | 一次快照 + 后续增量 |

**TCUM 当前做法**：同一模型全量开始时拿分布式锁并设置 Redis 暂停标记，增量消息先入待回放队列；全量完成后清标记、回放增量，再由版本规则过滤旧事件。它不要求业务停机，但暂停标记失败、TTL 到期和回放失败仍是需要治理的窗口。

## Q10. 消息乱序处理

### 命题
Kafka 分区内有序、TCUM 乐观锁跳过、TiCDC 精确保序、HLC 排序——哪种？

**TCUM 的状态冲突处理**选择乐观锁跳过：`event_time` 不大于当前版本时不覆盖。它能限制重复/乱序更新对最终状态的影响，但不要把它说成 exactly-once；消息交付还受 partition 内并发提交影响（见机制篇 C §6）。

## ★ Q12. manual commit + 幂等能否等价 exactly-once？

### 命题
关闭 auto commit、成功后手动提交，再加乐观锁幂等，能否保证 at-least-once 或 exactly-once？

**回答**：不能直接保证。当前基础消费者将消息投到 50 协程池，同一 partition 的高 offset 可能先完成并提交，越过低 offset 的失败消息；`CommitMessage` 错误也被忽略。乐观锁解决的是数据库最终状态的重复/乱序覆盖，不是 Kafka offset 的可靠交付。

### 亮点+短板
- 亮点：版本化状态更新能吸收大量重复和乱序消息，依赖简单。
- 短板：partition 内并发提交可能产生 offset 洞；event_time 还依赖数据源时钟。
- 修法：partition 内串行、partition 间并行；或维护连续完成水位，禁止越洞提交，并检查 commit 错误。严格场景再增加事务 inbox/outbox。
