## ★ Q25. 影响面分析 · 多跳查询

### 命题
故障时"哪些下游受影响"需要 5~10 跳查询——业界怎么做？

### 四方对比

| 方案 | 性能 |
|---|---|
| **MySQL JOIN** | 几跳就慢（10s+） |
| **Neo4j** | 秒级（图算法优化） |
| **Nebula Graph**（TCUM） | 类同 Neo4j |
| **TigerGraph** | 类同 |
| **BFS 客户端** | 慢，网络往返多 |

### 改进思路
- Q25.1（P2）**影响面预计算**：热点实体的影响面提前算好

## Q28. 关系类型的标准化

**常见类型**：
- 部署关系（Pod → Cluster → Region）
- 所属关系（Pod → App → Business）
- 依赖关系（Service A → Service B）

## Q29. 循环依赖处理

**方案**：
- 写入时检查（预防）
- 查询时 visited set（兜底）
- 深度限制（10 跳）

**TCUM 走查询侧 visited set + 深度限制**——写入侧未防（短板）

## ★ Q30. AI Agent 消费 CMDB 数据

### 命题
TCUM-AI 通过 MCP 调用 CMDB——接口设计上要注意什么？

### 关键点
- **只读 API**（不允许 AI 写 CMDB）
- **语义化查询**（不只是 SQL）
- **限流**（AI 消费可能爆量）
- **成本审计**（LLM token 追溯，见 iwiki 4024143170 t_cmdb_custom_ds_parse_record）

### 改进思路
- Q30.1（P2）**为 AI 提供"语义化描述"接口**——AI 拿到实体时能看到业务含义
