## 证据规则

每个结论使用以下标签：

- **[已实现]**：可定位到 Global 调用链；例如“批量出队后写 XStor 与 VM”。
- **[受配置控制]**：代码有分支，是否在生产启用要看环境变量或数据库配置；例如 ClickHouse 查询。
- **[历史背景]**：来自 iWiki 或其他仓库，解释为什么要设计，但不能证明 Global 已运行。
- **[未证实/未实现]**：未在 Global 中找到；不能在面试中说成已有能力。

## 代码基线

源码根目录：`/Users/yaao/Documents/code/tcum-yunshao-global`。

最重要的入口和边界如下：

```text
Prometheus remote write
  -> VictoriaMetricsService.BuildTsDatas
  -> MetricsService.WriteTimeSeries
  -> TsCache（XStor 分片队列）
  -> TsStorageTaskManager（100 worker）
  -> XStor HTTP batch write + VM remote write

同一批规范化结果
  -> MetricStreamingService（流式指标）
  -> SloProcessService（实时 SLI）
  -> MetricCkKafkaService（CK Kafka 输出）

PromQL API
  -> MetricMetaService 选 XStor/CK
  -> PromqlProxy
  -> 存储专属 Physical Planner
```

核心文件：

- `service/bizservice/gwservice/gw_service.go`：接入后处理、存储入队、SLO/流/CK 分支。
- `service/cache/tscache/ts_cache.go` 与 `task/local_task/ts_storage_task.go`：写入削峰和 worker。
- `service/integration/influxdb/influxdb_write_service.go`：XStor 分库批写、有界重试。
- `service/integration/victoria_metrics/*.go`：Prometheus remote-write 解码与 VM 代理写入。
- `service/bizservice/pqlqueryservice/**`、`service/integration/promql-proxy/**`：查询路由、下推与 CK 计划。

## 已纠正的旧口径

旧稿大量引用 `metric-filter`、Grafana Agent、VM 集群参数、单 orgID=88、`persistentqueue.FastQueue` 和 VM 流式聚合。这些并不在 `tcum-yunshao-global` 源码调用链中，故不能再描述为该项目的实现。它们最多是历史系统或上游产品背景。

同样，iWiki《[Xstor 读写优化总体设想](https://iwiki.woa.com/p/4016226228)》中的“TSID 并行查询、MessagePack、集中 series-key cache、多值指标”是设计设想；本卷会明确指出哪些被 Global 吸收、哪些没有落地。

## 如何使用本卷

先读 01、02，建立“数据进入、如何被路由、怎样落库和查询”的主线；再读 03、04 理解同一批数据如何分叉到 SLO、流指标与告警；最后用 06–11 准备面试。回答时优先说实现、开关和边界，再说历史设计与下一步。
