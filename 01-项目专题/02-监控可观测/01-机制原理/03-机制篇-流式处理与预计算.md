# 机制篇 C：Global 的流式分叉、实时 SLO 与有限计算下推

> **结论先行**：Global 代码中存在两类“实时计算”：一类是把匹配到配置的原始指标转换后投递流式平台；另一类是 SLO/SLI 的实时匹配、标签注入和 Kafka 输出。它不是 Flink，也没有证据表明项目在使用 VM streaming aggregation 或 vmalert recording rules。PromQL 的计算下推属于查询路径，且只支持很小的安全子集。

## 1. 三条实时分叉的职责不同

```text
规范化后的 TsData
 ├─ TsCache -> XStor / VM：原始存储路径
 ├─ MetricStreamingService：选中 ArkStreamConfig 的指标 -> Kafka
 ├─ SloProcessService：匹配 SLI -> 业务语义转换/注入 -> SLO Kafka
 └─ MetricCkKafkaService：配置 Ck 的指标 -> CK Kafka
```

入口在 `service/bizservice/gwservice/gw_service.go:200-214`。因此不能把三者统称为“预聚合”：流指标和 CK 输出主要是格式/路由转换，真正具有 SLO 语义计算的是 `SloProcessService`；存储端聚合是另一条查询路径。

## 2. 流式指标：配置筛选、800 KB 切批、异步 Kafka

`MetricStreamingService.WriteStreaming` 先从 `SuperCache` 的 `RawMetric2MetricMap` 找指标模型，只对 `ArkStreamConfig.Enabled=true` 且 label matcher 命中的指标输出。它还支持一个可注册 filter 链，任一 filter 返回 false 即丢弃这条时序，并记录按 filter 维度的计数。见 `service/bizservice/metricstreamingservice/metric_streaming_service.go:122-242`。

每条 `TsData` 会展开为消息格式的 metric；保留原始 sample 时间，补充处理时间和 period，并将 tag 名 `period` 重命名，避免与流平台的保留字段冲突。见同文件 `285-340`。批次按 protobuf 序列化后的估算大小限制为 800 KB。

真正避免同步 Kafka 发送的是 `sendQueue`：启动时根据配置创建有界 channel 和 worker；`sendBatch` 正常情况下仅入 channel，由 worker 调 `ProduceMessage`。但队列满时会退化为**同步发送**，而非丢弃，见 `245-282`。这是可靠性优先的反压策略，代价是 Kafka 慢会回传为网关请求变慢。该队列进程退出时最多 drain 10 秒，超过则仅记录错误，因此也不是持久化重放机制。

## 3. SLO：实时“匹配—转换—注入—输出”，不是查询时回算

`SloProcessService.Submit` 对每条时序提交一个 `metric-slo-pool` 任务，池大小硬编码为 20000。任务依次：

1. 从 `SloCacheData.SliMetricMap` 以指标三元组定位候选 SLI；
2. 用白/黑标签规则过滤；
3. 按 YunAPI、实例自定义、VPC probe、域名内部等 SLO 类型转换成下游 metric；
4. 应用注入规则；
5. 将原始 SLI 结果与注入结果按 800 KB 批量写 SLO Kafka。

处理骨架在 `service/bizservice/sloservice/slo_process_service.go:24-111`，匹配和类型转换在 `slo_sli_process_service.go:35-180`，输出在 `slo_output_service.go:43-110`。

它的优点是把复杂的业务对象、用户、地域、实例映射固定在数据进入时完成，后续 SLO 查询不必反复做同样的元数据 join。代价是规则或映射更新不会重算历史结果；若实时处理漏掉数据，不能靠查询时重新聚合自动修复。

## 4. 缓存是实时计算的前提，而不是附属优化

SLO 和流处理的每条数据都要查指标、SLI、租户、存储节点等配置。Global 通过 `SuperCache` 一次性构建新快照，完整加载成功后整体替换 `superCacheData` 指针；后台每 10 秒尝试刷新，而不同子缓存通常按 60 秒粒度复用旧值。见 `service/cache/supercache/super_cache.go:180-359`。

这种 copy-and-swap 的意义是读路径无需锁、不会看到半更新的组合配置。缺点是配置生效存在刷新延迟，且关键缓存加载失败会保持旧快照或阻断本轮更新；业务必须接受短暂陈旧读。

## 5. 查询计算下推：和流处理完全不同

PromQL proxy 会针对简单聚合生成远端物理计划：XStor/CK 先做部分聚合，PromQL engine 负责最后的合并和表达式语义。支持 `sum/count/min/max`，`avg` 可改写为 `sum/count`；某些 `sum_over_time/count_over_time` 仅在窗口等于 step 时允许。见 `service/integration/promql-proxy/influxdb-base/logical-optimizer/distribute.go:23-166`。

在 CK 路径，物理计划直接生成 `GROUP BY` SQL；在 XStor 路径，由 Influx planner 生成后端查询。它的目标是少传原始点、少在 Go 进程聚合，而不是提供一个通用流计算框架。

## 6. 明确未证实的能力

- **VM streaming aggregation / vmalert recording rule**：本仓库没有将其接入到 Global 主链路的调用证据。
- **“三层预聚合指标模型已经运行”**：可作为历史设计语言，但不能据此声称 Global 已实现三个可回溯聚合层。
- **Exactly-once 流处理**：当前 Kafka 发送失败仅记录或返回错误；未见 transactional producer、outbox 或消费 offset 协同。

## 7. 面试回答

“我们没有为了监控场景额外引入 Flink。Global 的做法是把已经规范化的指标做事件式分叉：配置命中的指标异步送入流平台，SLO 路径在 2 万容量 worker pool 内完成 SLI 匹配、业务维度转换和注入，再批量写 Kafka。这样把查询时重复的元数据关联前置，但接受了结果随配置版本演进、历史不自动回算的代价。另一类优化是 PromQL 的有限下推，只对可安全下推的简单聚合使用存储端 `GROUP BY`。”
