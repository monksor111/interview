# 机制篇 B：不是“理论三引擎”，而是 Global 的存储路由与查询执行器

> **结论先行**：Global 的写入层同时保留 XStor、VM 和 ClickHouse Kafka 输出；查询层目前只在 XStor 与 ClickHouse 间按指标元数据路由。VictoriaMetrics 的读接口在项目中存在，但不是这条 PromQL proxy 的主查询后端。三种引擎并非按一个硬编码的“百万时间线阈值”自动选型，而是由指标配置、指标形态和环境开关共同决定。

## 1. 先把“存什么”和“从哪里查”分开

| 引擎 | Global 写入事实 | Global 查询事实 | 不应夸大的部分 |
|---|---|---|---|
| XStor/Influx | [已实现] 以 `XstorSharding` 聚合 Line Protocol 后 HTTP 批写 | [已实现] 默认 PromQL proxy 后端 | 未见 MessagePack 返回或 TSID fan-out 查询 |
| VictoriaMetrics | [受配置控制] Prometheus remote-write 代理写 | [已实现接口] 有普通 `QueryRange` 客户端 | PromQL proxy 路由不指向 VM |
| ClickHouse | [受配置控制] 指标转 protobuf 后写 Kafka | [受配置控制] 具备完整 CK physical planner | 默认环境可能根本不启 CK 查询 |

历史 iWiki 的“XStor + CK 分层”解释了引入 CK 的动机，但 Global 代码体现的是**指标级配置分流**，不是运行时统计 series 数后自动迁移。

## 2. 写入侧：XStor 与 VM 是不同目标，CK 是 Kafka 下游

XStor 按 `XstorSharding` 分库批写，详见 [01](./01-机制篇-数据面全链路.md)。VM 仅在全局 `VmProxyWrite` 和节点 `PreComputeWrite` 同时开启时写入；同时，当前转换代码只接收 `storageId == 1` 的数据。这说明 VM 写入是一个受到迁移/灰度约束的代理路径，不应笼统说“所有数据都写 VM”。

CK 不在 `TsStorageTaskManager.SaveTs` 内直接写，代码还保留 `//ck TODO`；真正的 CK 路径在网关完成处理后，调用 `MetricCkKafkaService.WriteCkKafka`。它会检查每条指标的 `MetricStoreConfigModel.Ck` 与 `CkTableName`，为每个 sample 构造一条 metric，按 800 KB 切成 Kafka 消息。见 `service/bizservice/metric_ck_kafka_service/metric_ck_kafka_service.go:44-181`。

这意味着 CK 的可靠性、落表延迟与重放语义至少跨越 Kafka 和消费端；消费端不在本仓库中，不能从 Global 推导为“已经写入 MergeTree Part”。

## 3. 查询路由：元数据而非实时基数决定后端

`MetricMetaService.GetQueryStoreConfigByMetricName` 的规则顺序是：

1. `log_monitor`、`probe` 前缀固定走 XStor；
2. 流指标拥有专用 XStor 配置时也固定走 XStor；
3. 非标准指标名、指定强制回退的 stackCode 走 XStor；
4. 有 `RangeConfigs` 的指标走 XStor，因为 CK 路径不支持；
5. 其余标准指标依据 `MetricStoreConfigModel.StoreInClickhouse()` 决定。

见 `service/bizservice/metricservice/metric_meta_service.go:279-332`。因此正确说法是：**CK 由指标模型的显式存储配置选择，且存在兼容性回退**，不是“高基数指标一律自动写/查 CK”。

即使一个指标配置为 CK，`PromqlForceToQueryDefaultStorage` 为 true 时仍强制回到 XStor；默认值就是 true。CK client 还要求 `Clickhouse.Enable > 0` 才初始化。见 `common/env/env.go:50-76`、`service/bizservice/pqlqueryservice/service.go:113-148`。生产是否真的启用 CK，必须查看部署环境和指标元数据。

## 4. XStor 查询：PromQL 代理负责语义，物理计划负责下推

查询请求先解析 PromQL、提取 metric name、选择 proxy。`PromqlProxyQueryable.Select` 将 Prometheus selector/hints 交给存储专属 physical planner，再将返回 matrix 交还 PromQL 引擎。见 `service/integration/promql-proxy/queryable.go:37-68`。

对于 XStor，优化器仅尝试安全的简单聚合：`sum`、`count`、`min`、`max`；`avg` 改写为 `sum/count`；只在简单 selector 下允许。`sum(sum_over_time())` 与 `sum(count_over_time())` 还要求 range 等于 query step。复杂 binary/unary、`without`、offset、`@` 时间、直方图均不在支持集合中。见 `service/integration/promql-proxy/influxdb-base/logical-optimizer/distribute.go:23-166`。

这是“计算下推”的真实边界：把可交换、可结合的部分聚合交给存储，最终语义仍由 PromQL engine 合并；不是把任意 PromQL 都翻成 InfluxQL。

## 5. ClickHouse 查询：有两种物理计划

### 5.1 普通 selector：数据与元数据并发扫描

CK scan plan 发出两条查询：

- 数据表取 `tsid, timestamp, value`；
- 元数据表取 `tsid, any(ts_key)`，按 `tsid` 聚合。

两个任务由 `errgroup` 并发运行，然后按 `tsid` 恢复 Prometheus labels。见 `service/integration/promql-proxy/clickhouse-base/physical-plan/scan_plan.go:46-180`、`physical-planner/scan_plan_builder.go:135-232`。

这部分吸收了 iWiki 中“TSID 是内部关联键”的思想，但没有出现“先列举所有 TSID，再把 TSID 分成 N 段并行查询”的调度器。这里的并行度是**数据扫描和元数据扫描两路并发**，而不是按时序分片 fan-out。

### 5.2 简单聚合：在 CK 做 SQL `GROUP BY`

聚合计划把 `sum/count/min/max` 翻译为 SQL 聚合，按 PromQL grouping label 和时间桶 `GROUP BY`，随后用 stepper 对齐回 Prometheus 时间步。见 `service/integration/promql-proxy/clickhouse-base/physical-planner/aggr_plan_builder.go:221-433`。

例如 `sum by(region)(cpu_util)` 不需要把每条原始 series 拉回 Go 后聚合；返回的只是一组 region、bucket、sum。这既减少网络传输，又借用了 CK 的向量化聚合能力。风险是 PromQL 的 lookback、首个 bucket 和窗口边界很容易算错，代码专门向前扩展 SQL start time，并在本地对齐，正是为处理这个问题。

## 6. 正则与结果规模保护

高基数系统中，正则不是“小语法糖”。Influx 路径限制单个 tag 正则 24 KB、有限枚举展开最多 3000 个值，超过则拒绝而非下发病态查询；可枚举模式被改写为等值 OR。见 `service/integration/promql-proxy/influxdb-base/matcher_regex.go:1-180`。

CK 路径也会保守地将 exact、enum、contains、prefix、suffix 等模式改写为较轻的谓词，其他模式保留 `match()`。此外，PromQL 字符串上限为 1 MB，处理样本默认上限为 600 万。见 `service/integration/promql-proxy/proxy.go:23-115`、`common/env/env.go:21-143`。

## 7. “分布式执行”为什么还不能说已实现多分片并行

代码确有 `DistributedExecutionOptimizer`，名称容易让人误以为已经对多个存储分片并行发查询。但每个 `PromqlProxy` 只注册了一个 `PromqlProxyRemoteEngine` 到 static endpoints；优化器源码也注明当前只有一个 remote backend。见 `promql-proxy/proxy.go:118-125`、`influxdb-base/logical-optimizer/distribute.go:39-42`。

因此目前它的主要价值是构造“远端部分聚合 + 本地合并”的逻辑计划，并为未来多 endpoint 预留接口；不是 iWiki 中的多 TSID worker 查询引擎。

## 8. 面试回答

“Global 的多引擎不是一个硬编码的高基数阈值路由器。写入侧，XStor 是按分库批量 HTTP 写，VM 是配置门控的 remote-write 代理，CK 经 Kafka 输出；查询侧，指标元数据会根据指标类型、RangeConfig 和显式 store config 在 XStor/CK 间选路，且有全局回退开关。CK 路径已经实现 selector 的数据/元数据并发扫描和简单聚合 SQL 下推；XStor 路径也只对可证明安全的聚合下推。TSID 多分片并行、MessagePack 返回这类历史设想没有看到在 Global 落地，我会把它们作为下一步而非现状。”
