# 面试话术：基于 Global 代码的诚实表达

## 3 分钟项目介绍

“我负责的 `tcum-yunshao-global` 是监控核心后端。它接收 Prometheus remote-write，把数据统一成内部时序模型后完成元数据、标签和指标配置处理。写入主链路会按 XStor 分库进入本地队列，后台用 100 个 worker 批量写 XStor；VM 是一条配置门控的 remote-write 代理写路径。与此同时，同一份数据还可以进入流处理、实时 SLO 计算以及 ClickHouse 的 Kafka 输出。

查询侧我们做了 PromQL proxy：先按指标元数据决定查 XStor 还是 ClickHouse；对简单的 `sum/count/min/max` 做存储端下推，CK 路径能够把数据扫描和元数据扫描并行，并直接以 SQL `GROUP BY` 返回聚合结果。为了防止高基数查询拖垮存储，还做了正则枚举改写、正则大小限制、1 MB query 上限和最大样本数限制。

我认为项目最真实的优点是性能和风险都写在了代码里：对象池、分库批处理、削峰、连接复用、Kafka 800 KB 切批；同时我会主动说明短板——当前 XStor/VM 是顺序双写，写失败没有持久重放，CK 读写存在异步可见延迟。这是我最想继续补齐的可靠性闭环。”

## 被追问时的关键句

- **“你们是否所有数据都写 VM？”**：不是。VM 代理写受全局和节点开关控制，当前转换还只放行指定 storageId；不能泛化为全量 VM 主写。
- **“三存储如何按基数自动路由？”**：当前不是自动阈值路由，查询依据指标元数据和兼容性；高基数只是配置 CK 的业务动机。
- **“是否已实现分布式并行查询？”**：已有 optimizer 框架，但 proxy 目前只注册一个 remote endpoint；CK 真实并行是数据/元数据两条扫描并发。
- **“双写如何保证一致？”**：不保证事务一致，只是顺序调用；我会用 outbox、目标独立队列和重放补齐。
- **“流计算是 Flink 吗？”**：不是。当前是网关内配置匹配、格式转换、Kafka 异步投递；SLO 是实时匹配和转换，不依赖外置状态计算引擎。

2. 多存储异步写入后，面板读己之写和回填策略如何设计？
3. 规则评估、静默和通知的副作用如何做补偿与审计？
4. 高基数治理是靠 schema 准入、标签配额，还是事后路由？
5. 复杂 PromQL 的下推一致性测试覆盖到什么粒度？
