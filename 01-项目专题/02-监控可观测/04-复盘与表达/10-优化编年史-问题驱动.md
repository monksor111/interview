# 优化演进：只记录代码已经留下的答案

> 无法从 Git 历史和需求单精确还原“何时发生”，因此本章按问题→现有实现→遗留问题组织，不伪造时间线。

## 1. 高频 remote-write 的对象分配

**问题**：Snappy 解压和 protobuf 解析在接入峰值下产生大量短命对象。  
**现有答案**：5 MB 解压 buffer pool、`WriteRequest` pool、8000 timeseries 预分配。  
**遗留**：必须持续审计池对象逃逸与大对象滞留。见 `victoria_metrics_service.go:202-250`。

## 2. 多分库写入相互拖累

**问题**：不同 XStor 分库吞吐和故障不同。  
**现有答案**：按 `XstorSharding` 分队列；按库合并 HTTP body；100 worker 和 `OutputDataSleep` 削峰。  
**遗留**：worker 内仍串行写 XStor/VM，失败无可靠重放。见 `ts_cache.go`、`ts_storage_task.go`、`influxdb_write_service.go`。

## 3. 下游短时故障导致无限阻塞

**问题**：慢库会造成积压。  
**现有答案**：仅白名单库重试，限网络/5xx/429，最多 3 次、总预算 5 秒。  
**遗留**：这是损失优先/可用性优先策略，需要把最终失败纳入数据完整性 SLO。见 `influxdb_write_service.go:141-303`。

## 4. 查询从单后端走向可路由多后端

**问题**：不同指标形态不适合共用同一个查询路径。  
**现有答案**：用指标元数据、指标兼容性和全局开关选择 XStor/CK；CK 有独立 physical planner。  
**遗留**：默认仍强制回 XStor；多 endpoint 并行尚未落地。见 `metric_meta_service.go`、`promql-proxy/**`。

## 5. 大量原始点回传导致查询压力

**问题**：简单聚合不应全部在 Go/PROMQL 层处理。  
**现有答案**：XStor/CK 的 `sum/count/min/max` 下推，CK 按标签和 bucket 聚合；正则有枚举改写和资源上限。  
**遗留**：支持范围小，必须持续做语义一致性测试。见 `distribute.go`、`aggr_plan_builder.go`、`matcher_regex.go`。

## 6. 每条数据做元数据 DB 查询不可接受

**问题**：网关热路径需要指标、SLI、静默、存储节点等配置。  
**现有答案**：SuperCache 建新快照后整体替换；Redis MGET 做 4 ms 合批。  
**遗留**：刷新延迟、加载错误以及缓存缺失的保守/激进降级要单独观测。见 `super_cache.go`、`redis_batcher.go`。
