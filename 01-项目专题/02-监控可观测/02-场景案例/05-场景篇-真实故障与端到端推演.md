# 场景篇：四个可由 Global 代码推导的故障与排查案例

> 本章不虚构“已发生的线上事故”。每个场景都是从现有调用链、注释和降级逻辑推导的真实风险，可作为面试中的技术推演题。

## 场景 1：某个 XStor 分库持续 5xx，为什么 VM 数据也开始延迟？

**现象**：`ts-save-pool` busy 指标升高，`TsCache.AllSize` 持续增长，XStor 写错误增加，随后 VM 写量下降或延迟上升。

**因果链**：

```text
XStor 某 db 5xx
-> 白名单库在单 worker 内重试，最长占用 5 秒
-> 同一 worker 还未执行后续 VM 写
-> 100 个 worker 被慢分库逐步占满
-> BatchPoll 继续拿数据或入队积压
-> VM 代理写被连带拖慢
```

证据：XStor 有界重试见 `influxdb_write_service.go:141-215`；XStor 后 VM 的串行调用见 `ts_storage_task.go:128-134`。

**先查什么**：按 XStor shard 统计 HTTP 状态/耗时，检查 worker busy、队列长度、VM 写成功数。不要先怀疑 VM 集群。

**改法**：将 XStor、VM 写拆为独立有界 worker 池或 durable outbox；给每个分片单独的并发预算和熔断；失败消息写可重放介质。这样能把“一个分库慢”限制在自己的隔离舱。

## 场景 2：流平台 Kafka 慢，为什么接入 API 的 P99 被拖高？

**现象**：`METRIC_STORAGE_KAFKA_QUEUE_FULL` 增加，网关 `WriteTimeSeries` 的 streaming cost 上升。

**因果链**：正常情况下流指标只入 `sendQueue`；队列满时，`sendBatch` 调用 `ProduceMessage` 同步发送。于是下游 Kafka 反压从 worker 传到网关请求。见 `metric_streaming_service.go:245-282`。

**这不是 bug，而是选择**：代码选择“不轻易丢流指标”，牺牲了接入延迟。若流指标并非主写路径的强依赖，应考虑队列满时按优先级丢弃、采样或写磁盘 outbox；若必须可靠，则应把网关 API 与 Kafka producer 完全异步解耦。

## 场景 3：指标已开启 CK，为何查询仍落到 XStor？

**排查顺序**：

1. 该指标名是否是 `log_monitor`/`probe`、流指标、非标准多段名称？这些固定回退 XStor；
2. 是否存在 `RangeConfigs`？当前 CK 路径不支持；
3. `MetricStoreConfigModel.StoreInClickhouse()` 是否为真；
4. 环境变量 `PromqlForceToQueryDefaultStorage` 是否仍为 true；
5. `Clickhouse.Enable` 是否开启，CK proxy 是否初始化。

证据：路由规则在 `metric_meta_service.go:279-332`，开关在 `env.go:50-76` 与 `pqlqueryservice/service.go:113-148`。

**结论**：CK 路由是兼容性优先的配置路由，不是只要写入 CK 就自动读 CK。

## 场景 4：某条大盘 PromQL 一直不能下推，如何解释而不是硬优化？

**现象**：带 `without`、binary expr、offset、复杂 range function 的查询仍在 PromQL engine 中做更多处理，或者无法走远端 aggregation。

**根因**：下推只支持满足代数条件和时序窗口边界要求的简单表达式。比如 `sum by(region)(x)` 可在后端先聚合；但 `a / b`、`sum without(instance)`、带 offset 的选择器并不能靠简单局部聚合保证相同语义。见 `influxdb-base/logical-optimizer/distribute.go:119-166`。

**正确改法**：先用 query 画像确认原始点数、标签基数和瓶颈；对稳定的大盘表达式增加显式预计算指标，或扩展 planner 并写 PromQL 一致性测试。不要以“把全部表达式翻译成 SQL”为目标。
