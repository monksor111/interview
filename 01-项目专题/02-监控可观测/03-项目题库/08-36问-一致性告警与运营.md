# 代码型面试题 C：一致性、告警与运营

## Q25. Global 的 XStor/VM 双写是强一致吗？

不是事务意义的强一致。代码在一个后台任务内按顺序先写 XStor、再写 VM；没有两阶段提交、outbox、幂等键协调或失败补偿。某一边成功、另一边失败时会永久分叉，除非上游重发同数据。应称为“配置门控的顺序双写”，不是强一致。代码：`ts_storage_task.go:128-134`。

## Q26. CK 写入和查询能保证读己之写吗？

不能从本仓库证明。网关将 CK 数据投递 Kafka，而消费者和 ClickHouse 入表在外部；查询 proxy 直接连 CK。Kafka 投递成功不等于 MergeTree 已可见，故天然存在异步可见延迟。代码：`metric_ck_kafka_service.go:119-138`。

## Q27. 静默告警会不会丢历史？

设计上不会：命中静默的告警会从 notification 剪掉，但历史分支将 active 与 silenced 合并后保存。这样“不给人发”与“不给系统留痕”被分开。代码：`alert_service.go` 中 `SaveAlerts` 和 `applySilence`。

## Q28. 静默缓存不一致时宁可多报还是少报？

当前 `applySilence` 在 SuperCache 或 silence snapshot 不可用时返回未静默，继续通知，即偏向多报。原因是未知状态下误吞真正告警的风险更大。代码：`alert_service.go` 的 nil guards。注意：这是从实现推导的失败策略，不代表所有告警配置都同样处理。

## Q29. 为什么历史保存和通知并行？

二者都是外部副作用，串行会让慢历史库拖通知。`errgroup` 并发减少延迟，但不提供原子性；任何一侧失败都可能出现通知有、历史无或反之。需要通过失败监控、重试/补偿任务治理。代码：`alert_service.go` 的 `errgroup.Group` 分支。

## Q30. SLO 实时处理的配置一致性如何保证？

SLO 匹配从 SuperCache 快照读取，整份快照构建完成再替换，单次处理不会混用一半新一半旧配置；但在刷新窗口内仍会使用旧规则，且历史输出不自动回算。代码：`super_cache.go:190-300`、`slo_sli_process_service.go:124-180`。

## Q31. 自动注册指标为什么会主动丢第一批数据？

未在缓存发现自动注册指标时，服务只向 Redis 写注册意图，本次数据直接返回；等待同步任务注册和 SuperCache 刷新后，下次上报才进入正常链路。这样避免热路径直接写元数据 DB，但有冷启动数据缺口。代码：`gw_auto_register_service.go:122-148`。

## Q32. 指标名/标签被改写的可观测性怎样做？

关键路径保留 debug 日志和各阶段 metrics，例如队列大小、poll 数、VM 写量/耗时、Kafka 队列满、SLO/告警耗时。面试中要强调“可配置 debug + 结构化监控”，而不是将完整标签无条件打印，后者会放大 I/O 和敏感数据风险。

## Q33. 多租户隔离能从代码证明到什么程度？

Global 有 tenant cache、通知配置和告警维度处理；但仅凭该仓库不能断言底层 VM/XStor 的物理租户隔离、orgID、磁盘目录隔离。面试应该只谈“应用层按租户取配置和处理通知”，底层隔离需部署资料佐证。

## Q34. 为什么需要 `PromqlForceToQueryDefaultStorage`？

它是数据一致性/功能兼容的运营开关。新 CK 读取路径出现错误或指标不兼容时，可全局回到 XStor；同时也可以按 stack code 强制回退。它在高风险存储迁移中比“只靠发版回滚”更快。代码：`env.go:50-76`、`metric_meta_service.go:300-305`。

## Q35. 正则拒绝会不会影响用户体验？

会，但这是可解释的资源隔离。无限/超大枚举正则可能把 XStor CPU 打满，伤害全部租户。项目对可识别的大集合给出明确上限，对不能安全展开的表达式回退原正则；应配合错误提示、查询模板和标签索引改进，而不是默默超时。

## Q36. 如何为这个项目建立正确的 SLO？

至少拆成：接入成功率、入队延迟/深度、XStor 与 VM 最终写成功率、流 Kafka queue-full、CK Kafka 投递、PromQL 拒绝/超时、静默命中、告警历史/通知失败。不能只盯 API 200，因为 200 可能只是异步入队成功。现有代码已埋了其中不少指标，缺的是端到端关联与最终落库确认。
