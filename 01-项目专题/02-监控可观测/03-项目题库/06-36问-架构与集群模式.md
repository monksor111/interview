# 代码型面试题 A：架构、路由与查询

> 每题都以 `tcum-yunshao-global` 源码为锚点。回答时先说调用链，再说取舍，最后说未解决边界。

## Q1. Global 是单体还是微服务？为什么还要在一条请求里分叉多条链路？

它是一个包含多个业务域的 Go 服务进程，而非把 XStor、VM、CK、SLO 全拆成独立服务。接收指标后，`WriteTimeSeries` 对同一份规范化数据依次入存储队列、提交 SLO、发送流平台、输出 CK Kafka。这样做的优势是 `TsData` 的清洗、元数据匹配只做一次；代价是同进程资源争抢和旁路慢链路影响请求尾延迟。适合解释为“逻辑上事件分叉，部署上仍是核心服务”。代码：`gw_service.go:165-235`。

## Q2. 为什么 XStor 写入按 `XstorSharding` 分队列？

一个全局 FIFO 会让慢分库把其他业务拖住。`TsCache.QueueMap` 以分片名创建独立队列，再让后台批量消费。它实现了分片级隔离，但没有完整的每分片 worker 配额：`BatchPoll` 仍在一轮遍历所有队列。因此这是“减少邻居干扰”，不是严格 QoS。代码：`ts_cache.go:44-108`。

## Q3. 多存储是怎样路由的？

不要回答“按高基数自动分流”。查询路由由指标元数据决定：特殊指标、流指标、带 RangeConfig 的指标回 XStor；标准指标再看显式 CK 配置；环境变量还可将所有查询强制回默认 XStor。代码：`metric_meta_service.go:279-332`、`proxy_manager.go:171-194`。写入路由又是另一套：XStor/VM/CK 各有开关和输出路径。

## Q4. 为什么 CK 的普通查询要同时查数据表和元数据表？

数据表读取只需要 `tsid、时间、value`，避免每一行重复传完整标签；元数据表用 `tsid -> ts_key` 还原 labels。两者由 `errgroup` 并发执行，随后在 Go 内 join。这是用一次额外元数据查询换取时序数据扫描更小的列读取。风险是元数据写入延迟或 `tsid` 不一致会让点无法正确还原。代码：`clickhouse-base/physical-plan/scan_plan.go:46-180`。

## Q5. PromQL 下推的正确性如何保证？

不是先追求覆盖率，而是先限定可交换、可结合的聚合。项目只允许简单 selector 上的 `sum/count/min/max`；`avg` 被分解为 `sum/count`；range function 也受 range=step 等限制。复杂表达式不下推或回退 PromQL engine。这样把错误风险限制在小集合内。代码：`influxdb-base/logical-optimizer/distribute.go:23-166`。

## Q6. “DistributedExecutionOptimizer” 是否等于分布式查询已经上线？

不等于。它提供多 remote engine 的逻辑框架，但 `NewPromqlProxy` 当前只构造一个 static endpoint。因而没有按 TSID 或按后端分片 fan-out 的实际并行查询。应回答“接口已经为多 endpoint 预留，当前只是一后端的部分聚合计划”。代码：`promql-proxy/proxy.go:118-125`。

## Q7. 为什么 CK 查询还要提供全局强制回退到 XStor 的开关？

CK planner 有语义覆盖边界，例如带 `RangeConfigs` 的指标不能走 CK；新路径还要灰度、回滚。默认 `PromqlForceToQueryDefaultStorage=true`，且 CK client 只在关闭该开关并启用 CK 配置时创建。它是部署级 kill switch。代码：`env.go:50-76`、`pqlqueryservice/service.go:113-148`。

## Q8. 查询层有哪些准入控制？

PromQL 文本超过 1 MB 在解析前拒绝；查询 engine 有 timeout、lookback、最大处理样本，默认 max samples 为 600 万；XStor 正则还有长度与枚举上限。它们不是优化性能的锦上添花，而是避免单条恶意/误用查询耗尽解析内存、CPU 或存储端资源。代码：`promql-proxy/proxy.go:23-115`、`matcher_regex.go:1-180`。

## Q9. 为什么不把所有正则改成 OR？

有限字面量集合可以安全改为等值 OR；通配、重复、超大字符集无法有限枚举。项目对可枚举集合最多 3000 个值，超限直接拒绝；复杂模式回退原正则。原因是上千 OR 和上千正则分支都可能拖垮 XStor。这个答案应强调“语义保留与资源上限”。

## Q10. 项目实际怎样将 CK 聚合结果恢复为 Prometheus 结果？

CK SQL 按标签与时间 bucket 返回聚合值；`ClickhouseAggrPhysicalPlan` 从列协议缓冲构造 series，再由 stepper 对齐到 PromQL step。不是把 CK JSON 原样透传。代码：`clickhouse-base/physical-plan/aggr_plan.go:32-212`、`physical-planner/aggr_plan_builder.go:221-433`。

## Q11. VM 在这个项目中是什么角色？

代码事实是：Global 能接收和发出 Prometheus remote-write，也提供 `QueryRange` 客户端；后台任务可按配置把数据代理写到 VM 节点。不能从此仓库推导 VM 集群拓扑、orgID、复制因子或“它是唯一主存储”。这些属于部署/其他仓库事实。代码：`victoria_metrics_service.go`、`victoria_metrics_proxy_service.go`。

## Q12. 最重要的架构改进是什么？

把写入目标从一个 worker 内的串行 XStor→VM 调用改为独立的、可持久重放的 outbox/worker 域。这样才能让 XStor 故障不拖 VM、让重试从临时 goroutine 行为升级为可观测的可靠投递。现有代码已明确 TODO 指出失败会丢数据：`ts_storage_task.go:128`。
