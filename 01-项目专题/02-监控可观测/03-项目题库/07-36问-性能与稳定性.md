# 代码型面试题 B：性能、背压与稳定性

## Q13. 接入 remote-write 最直接的性能优化是什么？

`BuildTsDatas` 将 Snappy 解压 buffer 和 protobuf `WriteRequest` 放入 `sync.Pool`；前者初始 5 MB，后者的 timeseries slice 预分配 8000。高频请求避免申请和清理大量短命对象。代码：`victoria_metrics_service.go:202-250`。池化的代价是必须严守对象归还后的引用生命周期。

## Q14. 为什么要按数据库聚合 XStor 写请求？

每条数据各发 HTTP 会让连接、Header、调度成本主导。代码按 `XstorSharding` 合并 Line Protocol，一库一个 body，并复用 `bytes.Buffer`。这同时减少 RPC 数和 GC。代码：`influxdb_write_service.go:43-100`。

## Q15. XStor 重试为什么设置最多 3 次、最多 5 秒？

监控写链路最怕一个故障库无限占满 worker，后续正常数据全部积压。代码只对网络、5xx、429 重试，白名单库才启用，硬上限 3 次、总预算 5 秒。它牺牲部分数据完整性，换系统存活与可恢复性。代码：`influxdb_write_service.go:141-303`。

## Q16. 100 worker 和 20000 worker 是否越大越好？

不是。`ts-save-pool=100` 面向慢 I/O 批写，`metric-slo-pool=20000` 面向逐条轻量业务计算。前者的瓶颈是下游连接与写入，后者意在消化大量独立 SLI 任务。两者都需要根据 CPU、队列长度、GC、外部 Kafka/DB 延迟压测；代码常量本身不是容量承诺。代码：`ts_storage_task.go:38-63`、`slo_process_service.go:24-49`。

## Q17. 流式 Kafka 队列满了发生什么？

正常时 producer payload 入有界 `sendQueue`，由配置数量 worker 异步发送。队列满时不丢，退化为同步 `ProduceMessage`，将背压反射给调用方。这提升投递机会，但拖高请求 P99。代码：`metric_streaming_service.go:65-107`、`245-282`。

## Q18. CK Kafka 为什么按 800 KB 切批而不是按条数？

标签长度和 sample 数导致单条 protobuf 大小差异极大，按条数无法约束消息大小。代码以 `proto.Size(metric)` 累加，超过 800 KB 就先发送当前批。SLO 和流指标也采用同样阈值。代码：`metric_ck_kafka_service.go:44-138`、`slo_output_service.go:43-110`。

## Q19. VM 写客户端如何避免频繁建连？

`VictoriaMetricsProxyService` 以 storage node ID 缓存 client 与 endpoint，读锁查找，endpoint 未变化直接复用；变化才重建并写回 map。代码：`victoria_metrics_proxy_service.go:100-160`。它降低连接创建开销，但没有保证 endpoint 切换期的请求重放。

## Q20. 为什么需要标签长度和数量上限？

高基数风险首先由无界 label value/label count 触发。写 VM 转换中，标签值截为 100 字符、最多 60 个标签，再按 key 排序。排序保证序列身份稳定；限制保护索引；但截断会带来碰撞和语义损失。代码：`ts_data.go:273-335`。

## Q21. SuperCache 如何把 DB 读取从热路径移走？

启动时全量加载，后台每 10 秒刷新；每个子缓存按自己的时间戳决定是否复用旧值，多数为 60 秒。加载完成后将新 `SuperCacheData` 整体替换，因此读路径无锁。代码：`super_cache.go:180-359`。代价是配置最多一分钟陈旧，以及加载失败时的降级语义要逐项审计。

## Q22. Redis batching 有什么收益和风险？

初始化为 1000 请求/4 ms 窗口。多个 MGET 请求收集唯一 key 后合成一个 Redis MGET，再按请求拆回结果。收益是降低 RT；风险是额外 4 ms 排队、队列满时调用阻塞，以及 batch processor 为每个 batch 起 goroutine，极端压力需要限并发。代码：`main/main.go:124`、`redis_batcher.go:52-180`。

## Q23. 为什么查询限制文本大小还不够？

1 MB 文本可以表达指数级展开的正则或命中千万 series 的 selector；真正的资源消耗由匹配结果和采样点决定。所以还需要 regex 枚举限制、最大处理 samples、后端 timeout 和指标级回退。代码：`matcher_regex.go`、`env.go:21-143`。

## Q24. 当前最危险的可靠性空洞是什么？

存储后台任务在写失败后只是记日志/指标，没有 durable retry。进程崩溃、队列溢出或最终失败都可能造成数据缺口；源代码已直接备注该问题。修复优先级高于继续微调 worker 数。代码：`ts_storage_task.go:128-135`。
