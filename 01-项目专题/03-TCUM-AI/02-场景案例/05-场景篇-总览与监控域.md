### 从这张表能提炼的三句话（面试收尾用）

1. **优化点不是随机的，是被任务模式逼出来的**：聚合类 Agent（汇总/SLO）必然逼出 COS+沙箱；生成类 Agent（PromQL/InfluxQL/看板）必然逼出"执行验证闭环"或"代码保结构"；关联类 Agent（CMDB/变更）必然逼出"部分成功语义"和"按工具定制上下文预算"。
2. **同一类问题在不同 Agent 上的解法可以不同，取决于数据能不能降级**：普通指标数据可以截断+COS 卸载；但**拓扑数据丢字段就直接产生错误答案，所以宁可放宽阈值也不降级**——这是"上下文预算按语义分配"而非"一刀切64KB"的真实依据。
3. **三个 Agent 的配置质量问题（排障专家描述全空、看板专家 `a2a_endpoint` 端口写错、AI 助手 token 明文）恰好说明平台缺配置校验**——这比任何"我们还有优化空间"的空话都具体。

## 0.3 从这张表能读出的四个架构事实（面试可以直接讲）

**事实一：`order` 字段暴露了产品运营策略**

`supervisor` 的 `order=3`、`sre_expert=4`、`tcum_ai_assistant=5`、`prometheus_alert_diagnose_expert=10`、`prometheus_metric_expert=30`，而 `obs_summary_analysis_expert`/`tcum_cmdb_expert`=1000、`change_analysis_expert`=9002、`digital_twin_agent`=9000。

**解读**：**总入口和高频专家排在最前，垂直/新上线的排后面**。这不是随意的数字——它反映"用户不知道该问谁时先看到 supervisor"的产品思路，也就是**用排序做人工兜底路由**，弥补LLM 路由不可控的那部分。

**事实二：`endpoint` 的三种形态对应三种接入模式**

| 形态 | 实例 | 含义 |
|---|---|---|
| `30.172.92.173:8083`（共享） | 10 个 Agent | **同一个 `obs_agent` 进程内多 Agent**，靠 `gorilla/mux` 按 `/{agent_code}` 路径分发 |
| `21.117.141.204:8883` / `30.172.92.192:8083` |排障专家、数字分身 | **独立部署**——排障专家因为要访问不同网络域；数字分身因为是共享实例服务 N 个人格，隔离故障域 |
| `localhost:8083` | `supervisor` | **进程内自引用**——它是请求时动态生成后注册进本进程 `AgentManager` 的，所以 endpoint 指回自己 |

`supervisor` 那个 `localhost` 特别值得讲：它说明**总入口 Agent 不是一个独立服务，而是一个"运行时装配出来的虚拟 Agent"**——每次请求查库拉全量子 Agent 现场组装，构建后注册进本进程（同名则热更新），下次同进程请求复用。

**事实三：`agui_endpoint` 与 `a2a_endpoint` 端口分离（8083 / 8082）**

大部分 Agent 同时暴露两个协议：8083 走 AGUI（面向前端，SSE 流式 + 富事件），8082 走 A2A（面向 Agent 间调用）。**同一个 Agent 实例、两套协议出口**——这是 `AgentManager` 为每个 Agent 同时注册 AGUI Server 和 A2A Server 的结果。

例外：`grafana_dashboard_expert` 的 `a2a_endpoint` 也写成 8083（疑似配置错误或有意统一），`tcum_ai_assistant` 的 `agui_endpoint` 为空但 `a2a_endpoint` 指向 `21.168.173.207/agents/{uuid}`。

**事实四：`config_items` 的膨胀记录了业务扩张**

同一个"业务空间（tenants）"下拉配置，在不同时期上线的 Agent 里选项数量完全不同：

| Agent | 上线 | tenants 选项数 |
|---|---|---|
| `prometheus_alert_diagnose_expert` | 2025-12 | **9 个**（tcs/cvm/cbs/cls/tcum/msg/tsf/monitor/demo） |
| `prometheus_promql_expert` | 2026-02 | **15 个**（+cdb/tke/csm/net/capi/bigdata） |
| `grafana_dashboard_expert` | 2026-03 | **30+ 个**（+cvm-c/tione/customer/TokenHub/lighthouse/dns/cos/CBS-c/znyw/dts/ckafka/rocketmq/rabbitmq/pulsar/tdmqcmq/TCR/codebuddy） |

**这是一个非常有说服力的技术债例子**：三个 Agent 的 `config_endpoint` 都指向 `.../v1/agent/prometheus_metric_expert/config_items`（**复用同一个配置端点**），但 `config_items` 字段里又各存了一份**快照**，导致同一份"业务空间列表"在库里有三个不同版本。

> **正确做法**：`tenants` 这类枚举应该**运行时从 CMDB 动态注入schema**（第一篇之二 §3.5 提到的"动态枚举注入"），而不是每个 Agent 存一份 JSON 快照。这也直接解释了为什么"动态枚举注入"在我们这里是真需求而非教科书条目。

# 1. `prometheus_alert_diagnose_expert` · 告警诊断专家

**上线最早（2025-12），`order=10`，是整个平台的第一个生产 Agent。**

## 1.1 业务痛点

告警是运维的主要入口，但一条Prometheus 告警到手后，值班同学要做的事非常机械且易错：

1. 拿告警 ID 去告警平台查详情（触发时间、触发值、涉及实例、告警规则表达式）；
2. 看懂告警规则里的 PromQL——**这是最大门槛**，`rate(x[5m]) / on(instance) group_left ...` 这类表达式很多人读不懂；
3. 用这个 PromQL（或改造后的）去查触发前后的指标曲线，判断是真异常还是抖动；
4. 横向对比同类实例，判断是单点还是面；
5. 写结论。

**痛点本质**：这套流程知识密集但推理简单，是典型的"专家经验能被固化"的场景。

## 1.2 输入形态（从 `query_examples` 反推）

```json
[
  {"Query": "告警 ID: ab644332cb58dd33:20260109030300；分析告警情况", "AgentConfig": "{\"tenants\":\"tcs\"}"},
  {"Query": "分析告警策略，id 为107", "AgentConfig": "{\"tenants\":\"tcs\"}"},
  {"Query": "分析最近一天的告警信息","AgentConfig": "{\"tenants\":\"tcs\"}"}
]
```

三种输入对应三个不同复杂度的任务：

| 输入 | 任务性质 | 轮次量级 |
|---|---|---|
| 具体告警 ID | **点查+ 深度分析**（确定性最高） | 5~10 轮 |
| 告警策略 ID | **配置解读**（要读PromQL、判断阈值合理性） | 3~8 轮 |
| "最近一天的告警" | **聚合分析**（数据量最大，最容易撞上下文上限） | 15~30 轮 |

**注意 `AgentConfig` 是必填的 `tenants`**（`Required: true`）——这是一个重要设计：**业务空间不让模型猜，由用户在UI 上显式选**。因为 TCS 底座和 CVM 计算的指标命名、Prometheus 实例、标签体系完全不同，模型猜错就是全盘错。这体现了一个判断：**"能用确定性输入解决的，绝不交给模型推断"**。

## 1.3 能力构成

- **工具**：来自 `monitor` 子 MCP（34 个工具）的告警相关子集——`GetAlertById`、告警策略查询、`PrometheusQuery`、`PrometheusQueryRange`、指标元数据检索等；
- **Skill**：`obs/monitor/` 下的 `alarm-id-analysis`（告警 ID 分析）、`alarm-configure-basic`（告警配置基础）等 13+ 个；
- **RAG**：监控指标元数据 RAG（自建 ES8，索引 `metric_meta`）——用于把用户口语（"CPU 高不高"）映射到真实指标名；
- **上下文注入**：`time_inject`（相对时间"最近一天"要转绝对时间）、`tenants_inject`（业务空间编码）、`entity_tag_inject`（让告警实例可点击）、`user_inject`。

## 1.4 执行链路（以"告警 ID"为例）

```
用户 Query + AgentConfig{tenants: tcs}
  → agent_access API → 查库拿 endpoint(30.172.92.173:8083/prometheus_alert_diagnose_expert)
  → AGUIClient.Call → obs_agent 进程内 AgentManager 路径命中
  → ChatModelAgent.Run（新 goroutine）
  → BeforeAgent: skill 中间件注入 skill 工具 + skill_exec
  → BeforeModelRewriteState: time/tenants/entity_tag/user 四注入（哨兵去重，仅首轮）
  → 第 1 轮 LLM: 识别出"这是告警 ID 分析" → 调 skill(alarm-id-analysis) 加载 SOP
  → 第 2 轮 LLM: 按 SOP Step1 → GetAlertById(告警ID)
  → 第 3 轮 LLM: 从告警详情里提取 PromQL + 时间窗 → 并发调
       PrometheusQueryRange(触发前后曲线) + PrometheusQuery(当前值) + 同类实例对比查询
     ← ToolsNode 并发执行（3 个 goroutine），wg.Wait() 一次性返回
       ⚠️ 此处是 token 跃迁点：3 个时序JSON 可能几百 KB
       → middleware_truncator逐个判断 >64KB？→ 上传 COS + 结构化截断 + WarnMsg
  → 第 4~6 轮 LLM: 分析趋势；若需要全量数据 → 写 Python 脚本 → skill_exec 沙箱下载 COS 分析
  → 第 N 轮: 无 tool_calls → END，输出诊断报告（含 entity:// 链接）
  → SSE 流式回传，前端渲染工具调用卡片 + 结论
  → 异步：dialog_history_service.MaybeSummarizeAndSave + skill_cache 更新
```

## 1.5 工程难点与解法

| 难点 | 解法 |
|---|---|
| **"最近一天的告警"数据量爆炸** | 这是 COS 卸载机制的**主要触发场景**。一天的告警可能上千条，全量 JSON 远超 64KB → 上传 COS + 返回前 N 条样例 + 引导写脚本统计。**关键是模型拿到的是"结构样例 + 数据总量+ 分析指令"，足以写出正确的聚合脚本** |
| **相对时间歧义** | `time_inject` 注入当前绝对时间；SKILL.md 里明确"时间标准化"规则（`desc` 里也写了"具备时间标准化能力"）。这是防幻觉的一环——模型自己算时间极易错|
| **PromQL 语法正确性** | 拆分出独立的 `prometheus_promql_expert`（见之二），本Agent 可通过 `task` 委派或直接复用其skill |
| **告警数据与指标数据的口径一致** | 告警规则里的 PromQL 必须**原样**或**受控改造**后用于查询，不能模型重写。SKILL.md 铁律："所有工具返回结果是唯一数据来源，禁止编造指标" |
| **工具失败不能中断** | `toolErrorHandlerMiddleware`：Prometheus 查询超时/语法错误转成 `[TOOL_ERROR]` 文本 + 三条行动指引，模型可改参数重试或降级 |

## 1.6 度量与不足

**不足**：
1. **无引用溯源强制**——报告里说"CPU 使用率 95%"，没强制标注 `[tool:PrometheusQuery, ts]`，用户无法验证。运维场景一个编造的数值可能导致错误决策，这是最该补的一条；
2. **无不确定性表达**——模型倾向给确定答案，但"我不确定，建议人工确认 X"往往才是正确输出；
3. **无准确率评测集**——"告警分析准确率"若无评测集，任何数字都站不住脚。这个 Agent 上线最久、样本最多，**应该是第一个建评测集的对象**（数据来源现成：线上真实会话 + 历史故障复盘）；
4. **RAG 相似度无阈值**——`ScoreThreshold` 未设置意味着永远返回满 TopK 条指标元数据（`FindMetrics` 是两路各 20 条），**哪怕全不相关**，是幻觉直接来源。RAG 完整机制见本篇 **§8**。

# 2. `prometheus_metric_expert` · 指标分析专家

**`order=30`，与告警专家同期上线，是"主动分析"侧的入口。**

## 2.1 业务痛点

告警是被动的（阈值触发才有），但运维还需要**主动**回答："这个实例现在健康吗""这批实例哪个异常""这个看板整体什么情况"。这类问题的门槛在于：

1. 数千个指标，用户不知道该看哪几个；
2. 不同产品（CVM 母子机、TSF 实例、Pod）指标体系完全不同；
3. "健康"是个综合判断，要多指标交叉。

## 2.2 输入形态（`query_examples` 展现了四种典型任务）

```
1. "分析 ins-5acbf58b 实例的健康状态"                        → tenants: tsf
2. "分析 0000036b-...-... cvm子机实例和其母机近1天的CPU使用率情况"  → tenants: cvm
3. "分析监控看板 db-f059..., db-4f52... 在近6小时的监控数据，
    分析异常实例，输出整体总结，使用表格形式列举汇总异常实例"      → tenants: cvm
4. "查看 tce 命名空间下内存利用率前3 的 pod，
    并查看这些 pod 过去十分钟的内存变化趋势，给出诊断结论"→ tenants: tcs
```

这四条能看出**任务复杂度跨度极大**：

| 例| 任务模式 | 关键挑战 |
|---|---|---|
| 1 | 单实例多指标健康诊断 | 要知道"该实例类型看哪些指标" |
| 2 | **母子机关联分析** | 要先查拓扑关系（子机 → 母机），再双侧查指标 |
| 3 | **多看板批量异常筛查+ 表格输出** | 数据量最大；且要求特定输出格式 |
| 4 | **TopN +趋势追踪（两阶段查询）** | 第一次查询结果决定第二次查询参数 |

**例 4 是 ReAct 循环价值的最佳证明**：必须先查 TopN 拿到 pod 名单，才能构造第二次趋势查询——这是**工作流写不出来、必须靠多轮推理**的场景。

**例 2 是跨数据源关联的证明**：CVM 母子机关系在 CMDB/架构拓扑里，指标在 Prometheus里，必须两边打通。

## 2.3 能力构成

- **工具**：`monitor` 子 MCP 全量（34 个）+ `cmdb` 子 MCP（11 个，查实例/架构拓扑）+ `dashboard` 相关（看板查询）；
- 代码位置：`usercases/obs_agent/tools/monitor/`（58 个 Go 文件）、`tools/cmdb/`（13 个）、`tools/dashboard/`（17 个）；
- **`QueryArchTopology` 工具有专门的 2倍截断阈值**（`register.go:57`）——因为架构拓扑数据天然大且结构化，砍太多就失去意义。**这是"按工具语义定制上下文预算"的实例**；
- **RAG**：指标元数据检索（把"内存利用率"映射到 `container_memory_working_set_bytes` 之类）；
- **`desc` 里明确的能力边界**："实例健康诊断、监控面板分析、指标分析、时间标准化、实例信息及架构信息获取"。

## 2.4 执行链路（以例 4 "TopN + 趋势" 为例）

```
第 1 轮 LLM: 需要先知道"内存利用率"对应哪个指标 → RAG 检索指标元数据
             （或调 ListMetricLabels 探查）
第 2 轮 LLM: 构造 PromQL topk(3, container_memory_working_set_bytes{namespace="tce"})
             → PrometheusQuery
             ← 返回 3 个 pod 名
第 3 轮 LLM: 用这3 个 pod 名构造第二次查询
             → PrometheusQueryRange(pod=~"a|b|c", 过去10分钟)  ← 三个并发或一个正则
             ← 时序数据（可能超 64KB → COS 卸载）
第 4 轮 LLM: 分析趋势（是否持续上涨、是否有突刺）→ 输出诊断结论
```

**这里体现了一个重要工程判断**：例 4 的第2→3 轮是**数据依赖**，不能并发；而例 3 的多看板查询是**无依赖**，可以并发。**eino 的 ToolsNode 天然支持后者**（一轮内 N 个 tool_calls 并发），前者则依赖 ReAct 的多轮迭代——两种能力配合才能覆盖真实场景。

## 2.5 工程难点与解法

| 难点 | 解法 |
|---|---|
| **多产品指标体系差异** | `tenants` 强制选择 + `tenants_inject` 注入业务空间编码；不同tenants 对应不同 Prometheus 实例与指标命名规范 |
| **看板批量分析的数据量** | 这里要区分两条实现，不能笼统写成 `MetricData`：`PrometheusQueryRange` 一类时序工具若输出 `metrics`，L1 会沿 `data.data.result[*]` 做结构化截断；而 `QueryGrafana` 的契约是 `raw_grafana`（原始 Grafana 响应），L1 只识别 ds_query 的 `frames[*].data.values` 列式和 CLS proxy 的三种行式数组。`BatchQueryGrafana` 又是独立路径：每个 panel 的原始响应会在工具内部尝试上传 COS，面向模型返回 `table` 行（panel、resultCount、cosUrl、error 等，可选 analysis），不应误说成 `MetricData`。三者共同目标都是“保结构/给出回捞入口”，但触发条件和返回契约不同；COS client 不可用或上传失败时 URL 为空，不能假设总能回捞。 |
| **表格输出格式** | SKILL.md 的"输出格式规范"类规则约束 |
| **母子机等关联关系** | `cmdb` 工具 + `QueryArchTopology`（专门放宽截断阈值） |
| **多轮依赖查询容易超轮次** | `MaxStep` 配置为 25~30（`prometheus_expert: 25`）；但**轮次耗尽报错**是已知缺陷（应改强制收敛） |

## 2.6 不足

- **无语义感知的采样截断**：例 3 的多看板异常筛查，被截断到"前 N 条"，但**对排障最有价值的往往是异常聚集段而非头部**。应改为"错误级别优先 + 时间分桶均匀采样 + 异常聚集段完整保留"，指标类保留极值点与拐点、中段降采样；
- **无 `StreamableTool`**：大范围指标查询耗时长，用户只能干等，无进度反馈；
- **例 3 这种任务最容易撞上下文上限**，是 `AdaptiveContextRetry` 的高频触发场景，但**压缩触发率没有埋点**，不知道实际发生频率。

# 3. `supervisor` · 可观测联合专家（总入口）

**`order=3`，`endpoint=localhost:8083`，全平台唯一的动态装配 Agent。**

## 3.1 业务痛点

用户的真实提问是模糊的："帮我看下这个告警"可能涉及告警诊断、指标分析、日志检索、CMDB 资产、变更关联多个专家。让用户自己在 15 个 Agent 里挑，产品体验极差；而做一个"全能Agent"又会因工具过多导致选择准确率下滑。

`desc` 写得很直白：*"能够基于多智能体协作平台，突破传统确定性工作流限制，智能分析用户问题并跨产品调度智能体联动分析"*，`use_cases` 里写 *"适用于不明确具体智能体的复杂场景"*。

**注意 `query_examples` 只有一条**：`"你有哪些能力？"`——这条示例问句本身就说明了它的定位：**它是"我不知道该问谁"时的默认落点**。

## 3.2 实现机制（第一篇之三 §4.1 已详述，此处讲场景侧含义）

每次请求命中 `req.Agent == "supervisor"` 时：

```go
_, agents, _ := s.agentOperator.ListAgents(ctx, po.AgentFilter{Enabled: []int64{1}})
for _, item := range agents {
    if item.Endpoint == "" { continue }
    subAgent, _ := NewSubAgent(ctx, item)
    subAgentDescs = append(subAgentDescs,
        fmt.Sprintf("名称: %s\n描述: %s\n使用示例: %s", item.Code, item.Profile, item.UseCases))
}
sa.SystemPrompt = fmt.Sprintf("<角色定义>%s</角色定义><子Agent列表>%s</子Agent列表>", ...)
```

**场景侧的三个关键含义**：

1. **`profile` 和 `use_cases` 是路由的"训练数据"**。CSV 里那些精心写的多语言 `Desc`/`Tags`/`Features`/`query_examples`，不只是前端展示——它们**直接决定 LLM 的路由准确率**。这就把"运营维护 Agent 描述"变成了一项**有技术含量的工作**：描述写得含糊，路由就错。
2. **零发版扩展**。2026-04 上线 `tcum_cmdb_expert`、2026-05 上线 `tianxun_inspect_expert`/`change_analysis_expert`，`supervisor` **不需要任何改动**就自动获得了调度它们的能力。这是"平台"而非"应用"的关键特征。
3. **`enabled=1` 是唯一开关，没有白名单**。代码里是全量遍历——意味着**任何一个新入库的 Agent 都会立刻进入 supervisor 的候选池**。这既是优点（自动化）也是风险（一个描述写得很宽泛的新 Agent 会抢走大量路由）。

## 3.3 工程难点与解法

| 难点 | 解法 / 现状 |
|---|---|
| **子 Agent 全是跨进程远程调用** | `A2AAgent`/`AGUIAgent` 远程壳，`Streaming: true` 流式收集；子 Agent 的完整 ReAct 循环在**对端进程**跑 |
| **异构协议** | `NewSubAgent` 按 `protocol_type` 分派（tcum_agui / knot_agui 带 token / sre_agui / A2A） |
| **子 Agent 上下文隔离** | Deep 模式天然隔离——子 Agent 只收到`task(description)` 这一段文本，**看不到主会话历史**。优点是干净、可并行；缺点是"前因后果"传不过去（例：用户前面说过"我关注的是深圳区域"，委派时若LLM 没写进 description 就丢了） |
| **长耗时子 Agent** | ⚠️ `idleTimeout = 60s`偏短，跨产品根因定位可能超时被误判空闲 |
| **热更新** | 构建后注册进 `AgentManager`，同名则 `UpdateAgentWithNewConfig`，同进程后续请求复用 |

## 3.4 最值得讲的一个设计张力

**`supervisor` 暴露了 Deep 模式的核心权衡**：

| | Deep（当前） | Supervisor/transfer（未用） |
|---|---|---|
| 子 Agent 看到什么 | 只有一段 `description` | 共享完整上下文 |
| 并发 | ✅ 可并行多个子 Agent | ❌ 串行 |
| 上下文成本 | 低（隔离） | 高（共享历史） |
| 信息保真| ❌ 依赖 LLM 把关键上下文写进 description | ✅ 完整 |

**运维场景选Deep 是对的**——因为跨产品分析天然需要并行（同时查 CVM 和 CBS），且各专家的关注点不同、共享全量历史反而是噪音。但**代价是"description 写不全就丢信息"**，这解释了为什么 `supervisor` 的 System Prompt 需要精心设计"如何写委派描述"的规则。

## 3.5 不足

1. **路由不可度量**（第一篇之三 §4.2）——最该建的是"200+ 条『用户问题 → 正确 Agent』标注样本"纳入 CI；
2. **无置信度兜底**——分类不确定时应反问用户，当前只能硬选；
3. **子Agent 结果无结构化证据链**——只回文本，主Agent 汇总时无法保留"哪个专家用哪个工具查到了什么"；
4. **`use_cases` 无质量校验**——描述写得好坏直接影响路由，但没有 lint/评测反馈机制。

# 4. `obs_summary_analysis_expert` · 可观测汇总分析专家

**`order=1000`，2026-01 上线。`desc` 值得原文引用**：

> *"我的核心能力是整合告警数据与巡检数据。我的工作方式不是简单的罗列，而是基于 产品/监控栈 维度对数据进行集合分类，并执行差异化的分析策略"*

## 4.1 业务痛点

这是一个**典型的"日报/周报"类场景**，但难点不在数据获取，而在**分析范式**：

- 告警数据和巡检数据是两个系统、两种结构；
- 简单罗列 500 条告警 + 300 条巡检隐患，对读者毫无价值；
- 真正需要的是"**按产品/监控栈聚类 → 找出集中爆发的类别 → 对不同类别用不同分析策略**"。

例如：TCS 底座的告警要看集群维度，CVM 的要看母子机维度，消息中间件的要看队列堆积维度——**同一份数据在不同产品语境下的分析方法完全不同**。

## 4.2 能力构成与执行特点

- 这是典型的 **Deep Agent** 场景，很可能配置了子 Agent 或大量 skill；
- `config_items` 里`tenants` 是 `Required: true` 但**没有 `DefaultValue`**（对比告警专家有 `DefaultValue: tcs`）——说明汇总分析**必须显式指定范围**，不给默认值防止误用；
- `query_examples` 为空，`use_cases.Features` 只有一条 *"获取可观测分析报告"*——说明它主要不是给用户在 UI 上自由问的，而是**被 `supervisor` 委派或被定时任务调用**的。

## 4.3 工程难点与解法

| 难点 | 解法 |
|---|---|
| **两类数据源整合** | 告警工具 + 天巡巡检工具（`tianxun` 14 个 + `tianxun-access` 22 个子 MCP 工具） |
| **数据量必然超限** | 这是 **COS 卸载 +沙箱聚合分析的最佳适配场景**：全量告警/巡检数据传 COS，LLM 写 Python 做聚类/分布/趋势统计，只把统计结论带回上下文。**"分析范式"这种需求恰好是"代码算得比模型准"的典型** |
| **差异化分析策略** | 靠 SKILL.md 按产品/监控栈分别定义分析规则；模型先分类再按类加载对应 skill |
| **报告格式稳定** | SKILL.md 输出格式规范 |

## 4.4 这个场景最能证明 COS + 沙箱机制的价值

一份"全平台近一天告警 + 巡检汇总"的原始数据可能几 MB。三种做法对比：

| 做法 | 结果 |
|---|---|
| 全量塞上下文 | 直接超限，或压缩后信息全失真 |
| 只取前 N 条 | 结论**必然错**——聚类分析对采样极其敏感 |
| **COS 卸载 +沙箱 Python 聚合** | 模型看到结构样例 + 总量，写 `pandas` 分组统计，拿到**精确的聚类/分布/趋势数字**，再基于这些数字做定性分析 |

**这就是"数据留在对象存储、算力放到沙箱、只有结论进 token"的完整价值体现**——而且它顺带解决了"LLM 不擅长精确计数"这个根本缺陷。

## 4.5 不足

- **无 COS 使用率度量**：不知道模型实际有多少比例真的用了 COS_URL 去下载分析，还是"看着样例就编了个结论"。**这是最该埋的一个指标**（"截断发生率"与"COS_URL 后续被访问率"），若后者很低说明卸载机制形同虚设；
- **沙箱不可用则数据彻底丢失**，无降级路径。

# 5. `cloud_product_slo_analysis_expert` · 云产品可用性分析专家

**`order=1001`，2026-02 上线。定位：*"基于云产品 SLO 数据，生成汇总性的聚类/分布/趋势分析结论"*，`Features` 写*"专注于云产品可用性的影响面/诊断分析"*。**

## 5.1 业务痛点

SLO（服务等级目标）分析是云厂商的核心运营动作，但难点在：

1. SLO 数据是**多维度交叉**的（产品 × 地域 × 时间 × 客户），维度组合爆炸；
2. 关键问题不是"SLO 是多少"，而是"**哪些维度组合拉低了整体 SLO**"和"**影响面有多大（多少客户/实例受影响）**"；
3. 这类分析人工做要拉数、透视、画图，一次几小时。

## 5.2 能力构成与执行特点

- 工具来自 `assess` 子 MCP（5 个）+ `monitor`；`tools/monitor/` 里有 `tool_query_sli_list.go`（SLI 列表查询，注意它是**手写 JSONSchema** 路径）；
- 与 `obs_summary_analysis_expert` 同属"汇总分析"族，共用同一套 COS + 沙箱聚合范式；
- `config_items` 为空——不需要选业务空间，因为 SLO 分析天然是**跨产品**的。

## 5.3 工程难点

| 难点 | 解法 |
|---|---|
| **多维交叉分析** | 必须走沙箱 Python（`pandas` 多维透视），模型直接推理必然算错 |
| **影响面评估需关联 CMDB** | 从 SLO 异常维度反查受影响实例/客户，需 `cmdb` 工具配合 |
| **趋势判断需时间序列** | Prometheus/Barad 时序查询 |

## 5.4 这个场景的独特价值：证明"Agent 能做数据分析师的活"

传统 BI 做不到的是"**基于分析结果继续追问**"：SLO 下降 → 定位到某地域 → 再查该地域的具体产品 → 再查该产品的具体实例。**这条追问链每一步的查询参数都依赖上一步结果**，这正是 ReAct 循环不可替代的地方，也是它和"固定报表"的本质区别。

## 5.5 不足

- 与 `obs_summary_analysis_expert` 功能边界模糊（都是"汇总性聚类/分布/趋势"），**`supervisor` 路由时容易混淆**——这是"Agent 粒度划分"的经典问题：切太细则路由难，切太粗则工具膨胀。当前缺少路由评测集来验证这两个是否真的能被正确区分。

# 6. `prometheus_promql_expert` · PromQL 生成专家

**`order=1005`，2026-02 上线。`desc` 是 `NULL`（配置不完整），`use_cases` 只有 *"专注PromQL的设计和编写"*。**

## 6.1 业务痛点与设计判断

**这个 Agent 的存在本身就是一个重要的架构决策，值得单独讲。**

PromQL 生成是告警诊断、指标分析、Grafana 看板三个场景的**公共子能力**。三种处理方式：

| 方式 | 问题 |
|---|---|
| 每个 Agent 各自实现 | prompt 重复、优化不同步 |
| 做成一个 Skill | 无法独立迭代评测，且PromQL 生成需要多轮（查指标名 → 查label → 组装 → 语法校验） |
| **拆成独立 Agent** ✅ | 可被多方委派、可独立评测、可独立换模型 |

选第三种，本质是把**"高频、高门槛、可独立验证"的子能力升级为独立 Agent**。这是 Agent 粒度划分的一个好范例：**判断标准不是"业务是否独立"，而是"是否需要独立的多轮推理 + 是否能独立验证正确性"**。

## 6.2 能力构成

- 工具：指标元数据检索（RAG）+ `ListMetricLabels`（探查可用 label）+ `PrometheusQuery`（**语法校验兼试跑**）；
- `config_items` 的 `tenants` 有 **15 个选项**（比告警专家多 6 个），`DefaultValue: tcs`，`Required: true`——因为不同业务空间的指标命名规范不同，PromQL 必须针对具体空间生成；
- `config_endpoint` 复用 `prometheus_metric_expert` 的端点。

## 6.3 执行链路的核心：闭环验证

```
第 1 轮: 理解需求（"CVM 的 CPU 使用率超过 80% 的实例"）
第 2 轮: RAG 检索 → 找到候选指标名
第 3 轮: ListMetricLabels(指标名) → 拿到可用 label（instance/region/zone…）
第 4 轮: 组装 PromQL
第 5 轮: PrometheusQuery(生成的 PromQL) ← 【关键】拿真实执行结果验证
         → 语法错？→ 读[TOOL_ERROR] 提示改写→ 重试
         → 返回空？→ 判断是"确实没有"还是"表达式写错了"→ 调整
第 6 轮: 输出验证过的 PromQL + 说明
```

**第 5 轮是这个 Agent 的灵魂**：它不是"生成一段看起来对的 PromQL"，而是**真的跑一遍**。这利用了 `toolErrorHandlerMiddleware` 把语法错误转成带指引的文本这一机制，形成"生成 → 执行 → 读错误 → 修正"的闭环。

> **这一点可以拔高**：Agent 相比纯 LLM 生成的最大优势就是**能够验证自己的输出**。凡是"输出可被程序验证"的场景（SQL/PromQL/InfluxQL/配置文件/代码），都应该把验证工具给模型，让它自己闭环。这也是 Claude Code 能做对代码的根本原因（能跑测试）。

## 6.4 不足

- `desc` 为 `NULL`——**这会直接影响 `supervisor` 的路由**（`profile` 有内容但 `desc` 缺失），是一个真实的配置质量问题；
- 无"生成正确率"评测集（这类场景**极易建评测集**：给定需求 → 期望 PromQL 语义等价，可用执行结果比对自动判定）。**这是我认为最应该第一批建评测的 Agent**，因为判定可自动化。

# 7. `barad_influxql_expert` · Barad InfluxQL 生成专家

**`order=1006`，2026-03 上线。与 PromQL 专家是同一模式的复刻**：*"Barad 系统的 InfluxDB 查询专家，擅长 InfluxQL 的设计和编写"*。

## 7.2 设计上的复用与差异

| 维度 | PromQL 专家 | InfluxQL 专家 |
|---|---|---|
| 模式 | 生成 → 执行验证 → 修正闭环 | 同 |
| 索引 | `metric_meta` | **`barad_metric_meta`**（独立索引） |
| `config_items` | 15 个 tenants | **空** |
| 工具 | monitor 子 MCP | barad 子 MCP |

## 7.3 不足

- 与 PromQL 专家**大量重复的实现模式**，但没有抽出公共的"查询语言生成 Agent"基类/模板——新增第三种查询语言（如 CLS 日志检索语法、ClickHouse SQL）时还要再复制一遍；

# 8. 横切能力详解：指标元数据 RAG（5 个 Agent 共用）

> 前面 §1/§2/§6/§7 都提到"RAG 检索指标元数据"，但没展开。它是监控域**最核心的横切能力**——告警诊断、指标分析、PromQL/InfluxQL 生成、Grafana 看板全都依赖它。这一节完整讲清"怎么做的"。

## 8.1 业务痛点：口语与指标名之间的鸿沟

用户问"**这个 Pod 内存高不高**"，而真实指标名是 `container_memory_working_set_bytes`；用户问"**磁盘IO 压力**"，可能对应 `node_disk_io_time_seconds_total`。中间这层映射有三重难度：

1. **量级**：TCUM 侧指标数以千计（三层结构：技术栈 → 指标类型 → 指标），没人记得住；
2. **异构**：TCUM/Prometheus 栈、Barad（InfluxDB）栈、CLS 日志三套体系命名完全不同；
3. **不能猜**：模型编一个指标名出来，查询返回空，**它会误判成"没有异常"** —— 这是最危险的失败模式（比报错更糟）。

所以这层映射必须做成**可召回、可过滤、带元信息**的检索能力，而不是塞进 prompt 里。

## 8.2 整体架构：两条链路 + 三个同构索引

```
【灌库链路】定时任务，每 5 分钟
  QueryMStacks(技术栈)
    └→ QueryMStackMetricTypes(指标类型)
         └→ QueryMStackMetrics(指标)        ← 三层嵌套 CAPI 遍历
              → MetricDefine{三元组 + 名称/描述/单位/Prometheus 类型}
              → EmbedContent()（整个结构体 JSON 序列化）
              → ES8 Indexer（BatchSize=10，Embedding 组件自动向量化）
                 写入 content（原文）+ content_vector（向量）+ 过滤字段

【检索链路】Agent 每次需要指标时
  FindMetrics 工具（LLM 调用）
    → tenant 解析 → QueryTenantConfig → mstackCodes（支持 "*" 展开全量）
    → 【双路检索】ListSimilarMetrics(原始query, topK=20,过滤)
                ListSimilarMetrics(LLM 改写 query, topK=20, 过滤)
    → 交替穿插 + MetricFullName 去重
    → BaseOutput{type: table, columns: 固定 7 列}
```

**三个同构索引**（同一套 `esindexer`/`esretriever`/`embedder` 复用三次，只有索引名与过滤字段不同）：

| 索引 | 数据来源 | 过滤字段 | 服务 |
|---|---|---|---|
| `metric_meta` | TCUM 指标定义（CAPI） | `metric_stack_code` | `rag/service/metric/meta` |
| `barad_metric_meta` | Barad 指标定义 | `namespace` | `rag/service/barad/meta` |
| `cls_topic_meta` | CLS 日志主题 | `tenant_code` | `rag/service/cls/meta` |

> **可讲的设计点**：三条业务线的RAG 只有"索引名 + 过滤字段 + 数据源"三处不同，公共部分（ES 客户端、检索模式、embedder 选型、Document 转换）全部复用。**新增一种知识域的成本是一个 `meta_service.go`**。

## 8.3 数据建模：两个真正影响效果的细节

###① `ai_description > description > name` 三级取值优先级

灌库时每一层（栈 / 指标类型 / 指标）的描述都按这个优先级取：

```go
stackDesc := stackName                // 兜底：名称
if stack.Description != nil && *stack.Description != "" { stackDesc = *stack.Description }
if stack.AiDescription != nil && *stack.AiDescription != "" { stackDesc = *stack.AiDescription }  // 最优先
```

**`AiDescription` 是TCUM 后端专门为 AI 场景维护的字段**。意义很大：人看的描述（"CPU 使用率"）和给检索用的描述（"CPU 使用率，反映计算资源繁忙程度，常用于判断实例负载与扩容决策，单位 %"）**诉求不同**。把它做成独立字段，等于**把"检索语料质量"变成业务侧可运营的资产**，而不是算法侧的黑盒。

> 面试讲法：*"RAG 效果的上限由语料质量决定，而语料质量不该由 AI 团队一个人扛。我们让业务侧能单独维护 `ai_description`，等于把最影响效果的那一环交给最懂指标的人。"*

### ② `PrometheusMetricType` 专为 LLM 而存在

```go
// Prometheus 指标类型（counter/gauge/histogram/summary），用于 LLM 生成 PromQL 时
// 选择正确的聚合方式；TCUM 后端未定义时此处为空字符串，下游默认按 gauge 处理
```

这个字段不参与检索，但**跟着检索结果一起返回给模型**。原因很实际：`counter` 必须套 `rate()`/`increase()`，`gauge` 直接取值，`histogram` 要用 `histogram_quantile()`。**模型不知道类型就会写错聚合函数**，而这类错误 PromQL 往往能跑通、只是结果没意义 —— 又一个"比报错更危险"的失败模式。

> **一般结论**：**RAG 返回的不该只是"找到了什么"，还要包含"怎么正确使用它"**。

## 8.4 检索侧最值得讲的设计：双路 query + 交替穿插融合

`FindMetrics` 工具**强制要求两个 query 参数**（`jsonschema` 描述都是 `required`）：

```go
type FindMetricsInput struct {
    LLMRewrittenQuery string  // "经过大模型提取指标信息的请求文本，包含指标描述和产品信息等"
    Query             string  // "用户请求的全文，不经过大模型处理，要求将用户的请求全部传入"
    Tenantstring  // "强烈建议显式传入；为空时退化为全量检索，结果相关性会下降"
}
```

然后**两路各检索 20条，交替穿插合并去重**：

```go
metricsInfoRaw, _ := ListSimilarMetrics(ctx, rawQuery, 20, mStackCodes...)          // 原文路
metricsInfo, _    := ListSimilarMetrics(ctx, llmRewrittenQuery, 20, mStackCodes...) // 改写路
// 交替取：raw[0], rewritten[0], raw[1], rewritten[1], ... 按 MetricFullName 去重
```

**为什么这么做**（这是一个很好的"问题→优化"故事）：

| 单用哪一路 | 失效场景 |
|---|---|
| 只用 LLM 改写后的 query | 改写会**丢信息**：用户说"帮我看看深圳这批 ckafka 消费堆积严重不严重"，模型可能改写成"消息堆积"，丢掉了产品和地域线索 |
| 只用用户原文 | 原文含大量噪音（寒暄、上下文、多个子问题），向量被稀释；且用户口语与指标描述**词面差距大** |

所以**两路都要，且用"交替穿插"而不是"按分数排序"合并** —— 因为两路的分数**不可比**（不同 query 打出的分不在同一个尺度上）。交替穿插本质是**按排名位次融合（RRF 的极简形式）**：两路的第1 名一定都进结果，第 2 名紧随其后。

> **这一点可以拔高**：ES 商业版的 RRF 用不了（见下），团队在**应用层用"交替穿插"实现了等价效果**——这是"受限条件下用最简手段拿到主要收益"的典型。**RRF 的核心价值就是"用位次而非分数融合"，交替穿插保留了这个核心。**

## 8.5 tenant 过滤：三段式取值 + 通配符展开

```go
// tenant 取值优先级：agent 上下文（agent 直连场景）> 入参（skill→MCP 调用场景）。
// 之所以保留 ctx 优先，是为了让 agent 直连时无需 LLM 显式传参即可生效；
// 而 skill→MCP 链路 ctx 中不含 tenant，必须由调用方在入参里显式传入。
tenantCode, _ := utils.GetTenants(ctx)
if tenantCode == "" { tenantCode = input.Tenant }
```

**这段注释本身就是一个很好的面试素材**：同一个工具有**两条调用链路**（Agent 直连 →ctx 里有 `tenants_inject` 注入的值；skill → MCP → ctx 丢失），所以必须**双来源 + 优先级**。这类"同一能力被多条链路复用导致上下文不等价"的问题，在 Agent 平台里非常普遍。

拿到 tenant 后：`QueryTenantConfig(tenant)` → `Config.MstackCodes` → 若含 `"*"` 则**展开为全量栈列表** → 构造 ES `terms` 过滤：

```go
Terms: {"metric_stack_code": [...]}
```

**过滤在 ES 层做而非返回后过滤**，且——这点很重要——`knn.Filter` 和 `query.bool.filter` **两路都应用了这组过滤条件**（`approximate.go:87` / `:123`），所以**向量召回不会跨租户漏数据**。

## 8.6 精确的技术真相：`Hybrid: true` + `RRF: false` 到底发生了什么

这是最该说准的地方（我在第三篇 Q18 里原本的措辞"RRF 关闭致向量检索失效"**不够准确，已修正**）。

配置：

```44:53:usercases/obs_agent/rag/retriever/es/es8_retriever.go
		SearchMode: search_mode.SearchModeApproximate(&search_mode.ApproximateConfig{
			QueryFieldName:  fieldContent,
			VectorFieldName: fieldContentVector,
			Hybrid:          true,
			// RRF only available with specific licenses
			// see: https://www.elastic.co/subscriptions
			RRF:             false,
			RRFRankConstant: nil,
			RRFWindowSize:   nil,
		}),
```

实际发给 ES 的请求（据 `eino-ext` 源码 `approximate.go:84-144` 推导）：

```json
{
  "knn":  [{ "field": "content_vector", "query_vector": [...], "filter": [terms 过滤] }],
  "query": { "bool": { "filter": [terms 过滤], "must": [{ "match": { "content": "<query>" }}]}},
  "size": 20
}
```

**注意没有 `rank.rrf` 节点**。ES 在 `knn` 与 `query` 同时存在、且无 `rank` 时的语义是：**两路都执行，最终得分 = BM25 得分 + kNN 得分（直接相加）**。

所以准确的问题描述是：

> **不是"向量检索没执行"，而是"向量得分被 BM25 得分的量纲淹没"** —— BM25 无上界（受词频/IDF/文档长度影响，常见量级 5~30+），而 ES 对 cosine 的 kNN 打分归一化在 **0~1**。两者直接相加，**向量那一路的实际权重接近可忽略**，混合检索退化为"BM25 为主 + 向量微调"。

配套的三个"没设"（都在同一段配置里）：

| 参数 | 现状 | 影响 |
|---|---|---|
| `Similarity`（kNN 最小相似度） | `nil` | 向量侧无相关性门槛 |
| `K` / `NumCandidates` | 都 `nil` | 走 ES 默认（k取 size、候选数默认推导），**未按数据规模调优** |
| `ScoreThreshold` | 未设 → `MinScore` 不下发 | ⚠️ **永远返回满TopK 条，哪怕全不相关** —— 20 条不相关指标进上下文，是幻觉的直接来源 |

**还有两个需要与 ES 侧确认的点（仓库内没有 mapping 定义，只有 `indexer.Store`）**：

1. `content` 字段的analyzer：若是 ES 自动映射（standard analyzer），**中文会被按字切分**（"内存利用率" → 内/存/利/用/率），BM25 质量会明显下降 —— 而上面刚说BM25 是实际主导路，所以这条影响很大；
2. `content` 存的是**整个 `MetricDefine` 的 JSON 序列化结果**（`EmbedContent()` 就是 `json.Marshal(md)`），意味着 **`"MetricStackCode"`/`"MetricTypeName"` 这些英文字段名也进了 embedding 文本和 BM25 语料**，属于纯噪音。

| # | 问题 | 说明 |
|---|---|---|
| 1 | **每 5 分钟全量重建** | 三层嵌套 CAPI 遍历（栈 × 指标类型 × 指标）+ **对全部指标重新 embedding**。指标元数据是**低频变化**数据，5 分钟全量的性价比极低；`BatchSize=10` 还意味着大量小批次embedding 调用 |
| 2 | **`AlwaysTrueCondition()` = 所有节点都跑** | 多实例部署时**每个实例都做一遍全量重建**，成本 ×N 且互相覆盖写 |
| 3 | **无变更检测 / 无版本切换** | 全量重写同一个索引，没有"影子索引 + 别名切换"。若某次 CAPI 返回不完整，**索引会被写成不完整状态且无回滚** |

**改造建议（按 ROI）**：
1. **P0**：`Interval` 拉长到小时级+ `Condition` 改为单实例执行（选主）；
2. **P0**：`ScoreThreshold` 设一个值（先按线上分数分布取分位数），把"永远返回 20 条"改成"不相关就返回空" —— 配合 `FormatFindMetricsOutput` 已有的 `CodeNotFound`+`"no relevant metrics were found"` 分支，**模型能明确知道"没找到"而不是拿到 20 条噪音**；
3. **P1**：把 `EmbedContent` 从"整个结构体 JSON"改成**为检索优化的自然语言模板**（如 `"{栈描述} / {类型描述} / {指标名}：{指标描述}，单位 {unit}"`），去掉字段名噪音；
4. **P1**：按 `MetricFullName` 做**增量 upsert + 变更检测**（内容 hash 比对），只对变化项重新 embedding；
5. **P1**：`embedder` 三选一（`cloud_hunyuan`/`venus_proxy_api`/`openai`）**切换时无守卫** —— 新旧向量来自不同模型、语义空间不同，检索会**静默变差不报错**。应把 embedder 标识与向量维度写进索引元信息并在启动时校验（当前"5 分钟全量重建"意外地缓解了这个问题，但切换窗口内仍是混杂状态）；
6. **P2**：BM25 侧确认 `content` 的中文 analyzer（ik / smartcn），否则主导路的分词就是错的。

## 8.8 一段可以直接讲的总结

> *"指标元数据 RAG 是我们监控域 5 个 Agent 的公共底座。灌库侧是三层 CAPI 遍历拿到指标定义，做成 `metric_meta`/`barad_metric_meta`/`cls_topic_meta` 三个同构索引；检索侧封成一个 `FindMetrics` 工具给 LLM 调。*
>
> *我觉得做对了三件事：**① 双路 query（用户原文 + LLM 改写）交替穿插融合** —— 因为改写会丢产品/地域线索、原文又有噪音，且两路分数不可比，所以按位次融合而不是按分数排序，这本质是 RRF 的极简实现；**② 语料质量做成业务可运营的资产** —— `ai_description > description > name` 三级优先级，让最懂指标的人去写给 AI 看的描述；**③ RAG 返回的不只是"找到什么"还有"怎么用"** —— 带上 `PrometheusMetricType`，因为 counter 不套 `rate()` 会写出能跑但没意义的 PromQL。*
>
> *也有几个我很清楚的问题：**最严重的是没设 `ScoreThreshold`，永远返回满 TopK**，20 条不相关指标进上下文就是幻觉来源；其次是 **ES 商业版 RRF 用不了，`Hybrid` 下BM25 与 kNN 得分直接相加，而 BM25 无上界、cosine 归一化到 0~1，所以向量那一路的实际权重接近可忽略**——混合检索退化成了 BM25 为主；还有灌库任务**每 5 分钟全量重建、且所有节点都跑**，对低频变化的元数据来说性价比很差。这三条我会按ScoreThreshold → 灌库频率与选主 → embedding 语料模板 的顺序改。"*
