# 8. `grafana_dashboard_expert` · Grafana 监控面板配置专家

**`order=1010`，2026-03 上线。定位：*"根据用户资源自动生成可导入的 Grafana 监控看板 JSON 配置"*。这是全平台工程复杂度最高的 Agent 之一。**

## 8.1 业务痛点

配一个像样的 Grafana 看板需要：选对指标 → 写对 PromQL/InfluxQL → 设计 panel 布局（row/panel/变量）→ 配数据源 → 调图表类型与单位 → 导出 JSON。一个 20 panel 的看板人工配置 1~2 小时，而且**新开一个产品/地域就要重复一遍**。

**核心难点是输出物的结构复杂度**：Grafana Dashboard JSON 是一个深度嵌套结构（dashboard → templating.list → panels[] → targets[] → fieldConfig），**LLM 直接生成整份 JSON 极易出结构错误**，而结构错一处整个看板就导入失败。

## 8.2 关键设计：不让 LLM 直接生成 JSON，而是给它"组装工具"

代码结构印证了这个判断：

```
usercases/obs_agent/service/grafana_dashboard/     ← 组装核心渲染引擎
  ├── core/                     ← Dashboard 结构组装
  ├── datasource/{prometheus,influxdb}/  ← 数据源适配
  └── flavor/{tcum,barad}/← 不同监控栈的"风味"
usercases/obs_agent/tools/dashboard/               ← 17 个面向 LLM 的工具
  ├── tool_build_tcum_dashboard.go
  ├── tool_build_barad_dashboard.go
  ├── tool_build_zhiyan_dashboard.go
  ├── tool_edit_panel.go / tool_edit_row.go / tool_edit_variable.go
  ├── tool_search_dashboard.go
  ├── tool_flush_dashboard.go
  └── tool_restore_dashboard_version.go
```

**三层设计的意义**：

| 层 | 职责 | 为什么这么分 |
|---|---|---|
| `core/` 渲染引擎 |保证输出的 JSON **结构永远合法** | 结构正确性由**代码**保证，不交给模型 |
| `datasource/` + `flavor/` | 适配 Prometheus/InfluxDB、TCUM/Barad/智研三套栈 | 同一份"看板意图"可渲染成不同栈的实现 |
| `tools/dashboard/` 17 个工具 | 暴露**语义级操作**给 LLM：`build`/`edit_panel`/`edit_row`/`edit_variable`/`flush`/`restore_version` | 模型只需表达"加一个 CPU 面板"，不需要知道 JSON 长什么样 |

> **这是本项目"人机分工"最清晰的一个例子，非常值得在面试讲**：
> **LLM 负责"该看什么指标、怎么组织"（语义决策）；代码负责"生成合法 JSON"（结构正确性）。** 凡是"结构复杂但规则确定"的输出，都应该这样切——给模型语义级工具，而不是让它吐结构化文本。这比"用 JSON Schema 约束模型输出"更可靠，因为后者仍有出错概率。

## 8.3 `tenants` 30+ 选项：技术债的活化石

这个 Agent 的 `config_items.tenants` 有 **30+ 个选项**，是全表最多的：

```
tcs, cvm, cbs, cls, tcum, msg, tsf, monitor, cdb, tke, demo, csm, net, capi, bigdata,
cvm-c, tione, customer, TokenHub, lighthouse, dns, cos, CBS-c, znyw, dts,
ckafka, rocketmq, rabbitmq, pulsar, tdmqcmq, TCR, codebuddy
```

对比 2025-12 上线的告警专家只有 9 个。**同一份"业务空间列表"在库里有三个不同版本的快照**（告警专家 9 个、PromQL 专家 15 个、Grafana 专家 30+ 个），而三者的 `config_endpoint` 又都指向同一个 `.../prometheus_metric_expert/config_items`。

**这个例子在面试里有三重价值**：
1. 证明业务是真在快速扩张（15 个月从 9 个产品域到 30+ 个）；
2. 暴露了一个真实的一致性问题（快照 vs 端点，两个来源）；
3. 直接支撑"**动态枚举注入**"这个改造提议——枚举应该运行时从 CMDB拉，而不是每个 Agent 存一份。

## 8.4 执行链路

```
第 1 轮: 理解需求（"给CVM 的这批实例做一个监控看板"）
第 2 轮: 查资源（cmdb 工具拿实例列表）+ RAG 检索该产品常用指标
第 3 轮: 委派/调用 PromQL 能力生成各panel 的查询表达式
第 4 轮: tool_build_tcum_dashboard(结构化参数) → 代码渲染出合法 JSON 骨架
第 5~N 轮: tool_edit_panel / tool_edit_variable 逐步细化
最后: tool_flush_dashboard 落库/生成可导入 JSON
（出错可tool_restore_dashboard_version 回滚）
```

**`tool_restore_dashboard_version` 值得注意**——它给了模型"**撤销**"的能力。这是 Agent 设计里常被忽略的一点：**当Agent 会修改状态时，必须给它回滚工具**，否则一次错误操作无法恢复。

## 8.5 不足

- **`a2a_endpoint` 配成了 8083**（应是 8082），疑似配置错误——说明**Agent 配置缺少校验**（应在启动/入库时校验端口与协议匹配）；
- `use_cases` 只有 `"Grafana看板配置专家"` 一句，`Tags` 是 `[{}]` 空对象——**配置质量差直接影响 supervisor 路由**；
- 没有"生成的看板是否真的能导入 Grafana"的自动化验证（这个**完全可以自动化**：调Grafana API 试导入）。

# 9. `tcum_cmdb_expert` · CMDB 资产专家

**`order=1000`，2026-04 上线。这是唯一一个"非监控"域的核心 Agent，`desc` 信息量很大。**

## 9.1 业务痛点

`desc` 原文的能力清单：*"查询和分析企业 IT 资产信息，包括服务器信息和 PaaS 资源。支持按类型、名称、VIP 地址、地域、负责人、业务模块等多维度查询过滤……**具备业务模块层级自动识别能力，自动解析层级关系并关联查询对应的资产数据**"*。

痛点：CMDB 是运维的"事实底座"，但查询门槛高——业务模块是**多级树形结构**（如 `[CDB冷备中转_深圳金融][其他]`），用户往往只记得部分层级名；且资产维度多（类型/地域/IP/负责人/模块），SQL/API 参数组合复杂。

## 9.2 `query_examples` 揭示的四类任务

```
1. "查看我名下机器的地域分布情况"                      → 隐式身份 + 聚合统计
2. "查询业务模块[CDB冷备中转_深圳金融][其他]中的支撑域名"  → 层级解析+ 关联查询
3. "分析 ins-05416f7f 这个 Polaris 实例的架构拓扑"      → 拓扑分析
4. "分析 10.132.28.197、10.132.28.203 两台母机所涉及的客户" → 反向影响面分析
```

**这四条每一条都揭示一个技术点**：

| 例 | 技术点 | 说明 |
|---|---|---|
| 1 | **"我"的身份解析** | 需要 `user_inject` 注入当前用户 ID，然后按 `负责人=当前用户` 过滤。**这直接关联到"身份透传"这个安全缺口**——如果工具用服务身份查询，"我名下"就查不对；如果不做 AuthZ，用户可能查到别人名下资产 |
| 2 | **业务模块层级自动识别** | `[父][子]` 这种嵌套记法需要解析成结构化查询参数。`desc` 里专门强调这是一项能力，说明这块做了专门处理 |
| 3 | **架构拓扑** | 对应 `QueryArchTopology` 工具（**有2 倍截断阈值**的那个） |
| 4 | **反向影响面分析** | 从物理机反查受影响客户——这是**故障影响面评估**的核心能力，也是最有业务价值的一条 |

## 9.3 例 4 的价值：把"影响面评估"自动化

传统流程：母机故障 → 人工查该母机上有哪些子机 → 查每个子机属于哪个客户 →汇总。这个过程在故障处理的黄金5 分钟里极其耗时。

Agent 化后：一句话拿到"受影响客户清单"。**这是 AI Agent 在运维场景最直接的价值体现**——不是"更聪明"，而是**把跨系统的多跳查询压缩成一次自然语言交互**。

## 9.4 工程难点与解法

| 难点 | 解法 |
|---|---|
| **CMDB 数据量大** | `cmdb` 子 MCP 11 个工具，`tools/cmdb/` 13 个 Go 文件；`QueryArchTopology` 专门放宽截断阈值到 128KB |
| **多维过滤参数组合** | 工具 schema 用 `XxxInput` struct 反射生成，参数清晰；但**地域/类型这类枚举应该动态注入** |
| **"我"的解析** | `user_inject` 中间件 |
| **层级路径解析** | 专门的模块层级解析逻辑 |
| **实体链接** | `entity_tag_inject` 让返回的实例 ID 变成可点击 `entity://` 链接——CMDB 场景这个体验价值最大（用户要跳去看详情） |

## 9.5 不足与风险

- ⚠️ **这是"身份透传缺失"风险最高的 Agent**：CMDB 资产数据天然有归属和权限边界。若工具用服务身份查询，则 A 用户可通过 Agent 查到 B 业务的资产——**这是多租户合规红线**（第一篇之四 §7.10）；
- **无审计**：谁在什么时候通过 Agent 查了哪些资产，没有记录；
- 只读场景相对安全，但**如果未来加入 CMDB 写操作（改负责人、改模块归属），必须先有权限体系**。

# 10. `tianxun_inspect_expert` · 天巡巡检专家

**`order=1000`，2026-05 上线。`use_cases` 写得最完整（4 条 Features），是配置质量的正面样本。**

## 10.1 业务痛点

`desc` 把能力清晰分成两类：

> *"一是**分析类**，涵盖集群总览分析、巡检控制分析、巡检报告解读、巡检插件解读；二是**配置类**，协助用户设计并落地新的巡检项配置。"*

痛点在README 里也点明了：*"巡检脚本维护成本高、扩展性差，巡检报告生成繁琐，人工配置效率低"*。

## 10.2 `query_examples` 的四条对应四种完全不同的任务模式

```
1. "分析当前巡检隐患的全局分布情况和最近 1 天的变化趋势"        → 聚合分析（数据量大）
2. "解读 ID 为 22404 的报告"                                → 点查解读
3. "集群为 tcs-test-set2，检查 tce 命名空间容器 ocloud-ckafka-oss-monitor
    运行状态为 running，且 monitor-cluster 进程存在。帮我生成巡检项"  → 【配置生成】
4. "帮我解读 K8sStatefulSetReplicasCheck 插件"               → 知识解读
```

**例 3 是全平台最特殊的一类任务**：它不是"查询/分析"，而是**从自然语言描述生成一份可执行的巡检配置**。

## 10.3 例 3 的深层意义：从"读"到"写"的跨越

| | 前面所有 Agent | 巡检项生成 |
|---|---|---|
| 操作性质 | 只读（查询、分析） | **写**（生成配置并落地） |
| 出错后果 | 结论不准，用户可判断 | **配置错误会导致误告警或漏检** |
| 是否需要审批 | 否 | **应该需要** |

**这就是"权限体系缺失"最具体的风险落点**：一个能"落地新的巡检项配置"的 Agent，如果没有人工确认环节，模型理解偏差就会直接产生一条错误的巡检规则。

> 面试可以这样讲：*"我们现在有一个 Agent 已经跨过了『只读』边界（巡检项生成），这让我意识到权限体系不是『将来要做』而是『已经欠着』。它的正确形态应该是：生成配置 → interrupt 挂起 → 前端展示『将要创建的巡检项：检查对象/阈值/覆盖范围/预期告警』→ 用户确认 → resume 落地。技术底座（`CompositeInterrupt`）已经有了，缺的是配 `CheckPointStore` 和前端交互。"*

## 10.4 能力构成

- 工具：`tianxun`（14 个，巡检数据）+ `tianxun-access`（22 个，巡检接入/配置）——**加起来 36 个，是最大的工具组**；
- Skill：`obs/inspection/` 6 个技能；
- 与 `obs_summary_analysis_expert` 有数据重叠（后者整合"告警 + 巡检"），但分工是：**天巡专家做巡检域的深度（报告/插件/配置），汇总专家做跨域的广度**。

## 10.5 例 4 "解读插件"揭示的一个能力：内部知识的 Agent 化

`K8sStatefulSetReplicasCheck` 这类巡检插件有几百个，每个都有自己的执行逻辑、参数、适用场景。这些知识散落在代码、文档、老同事脑子里。

把它Agent 化的价值：**新人不需要读插件源码就能理解巡检结果**。这属于 README 里"知识沉淀困难、专家经验难以传承"痛点的直接解法。

## 10.6 不足

- **36 个工具是工具膨胀的重灾区**——巡检专家的工具描述全量进 prompt，占用可观；应做意图内的二级裁剪（分析类 vs 配置类加载不同工具子集）；
- **配置生成类任务无 dry-run 验证**：应该像 PromQL 专家那样"生成 → 试运行 → 看结果 → 修正"闭环，而不是直接落地；
- **无审批环节**（见 §10.3）。

# 11. `change_analysis_expert` · 变更分析专家

**`order=9002`，2026-05 上线。`query_examples` 用的是简单字符串数组格式（与其他 Agent 的 JSON 结构不同），说明是较晚且较快上线的。**

## 11.1 业务痛点

业界共识：**大部分生产故障由变更引起**。所以"这次变更有没有引起问题"是运维最高频的问题之一。

`desc`：*"通过变更单关联的监控面板数据，分析变更前后的指标变化，评估变更对系统的影响，生成变更分析报告"*。

`query_examples`：
```
"分析 cos 租户的变更单 test-kakalin-2"
"帮我看下这个变更的影响"
"变更单 92235 的分析报告"
"分析最近这次发布变更对系统的影响"
```

## 11.2 关键设计：变更单 → 监控面板的自动关联

`Features` 明确三条：
1. *"支持通过变更单号自动关联监控面板"*
2. *"支持变更前后指标对比分析"*
3. *"支持变更影响评估和运维建议生成"*

**第1 条是最有价值的工程点**：变更单在变更平台，监控面板在 Grafana/TCUM，两者靠什么关联？只能靠**变更单里声明的服务/模块/实例 → CMDB → 对应的监控看板**这条链路。这是一个**三跳关联**：

```
变更单号 → 变更平台 API →涉及的服务/实例
        → CMDB 查该服务对应的业务模块
        → 查该模块绑定的监控看板 / 关键指标
        → 取变更时间窗前后的指标数据
        → 对比分析
```

**这条链路是"Agent 优于工作流"的又一个证明**：变更单的形态千差万别（有的写实例 ID，有的写模块名，有的只写服务名），固定工作流无法覆盖，需要模型根据实际拿到的内容决定下一跳怎么查。

## 11.3 "变更前后对比"的分析方法论难点

这是一个统计问题，不只是查数：

| 难点 | 说明 |
|---|---|
| **时间窗选择** | 变更后 5分钟？1 小时？不同指标生效时间不同（内存泄漏要几小时才显现） |
| **基线选择** | 对比"变更前同长度窗口"还是"上周同时段"？前者受当时业务波动影响，后者受周期性影响 |
| **区分因果与相关** | 变更后 CPU 涨了，可能是变更导致，也可能恰好流量高峰 |
| **多指标综合判断** | 单指标涨跌不能定论 |

**当前实现大概率靠 SKILL.md 的分析规则约束**（"必须对比变更前同长度窗口""必须至少检查 N 个核心指标""指标变化超过 X% 才认定异常"）。这是把统计方法论固化进 prompt 的典型做法。

## 11.4 不足

- **无因果判定能力**——只能给"变更后指标变化了"，不能给"变更导致了指标变化"。改进方向是引入对照组（同类未变更实例的同期指标）；
- **无引用溯源**（同告警专家）——变更分析报告的结论直接影响"是否回滚"的决策，**数值必须可验证**。这个 Agent 是"强制引用溯源"最该优先落地的对象；
- `order=9002` 排在很后面，`config_items` 为空但`config_endpoint` 复用 `prometheus_metric_expert` 的——**配置有冗余/不一致**。

# 12. `tcum_tcs_error_debug_expert` · TCUM 统一运维排障专家

**`order=1000`，2026-03 上线。全表配置最"空"的一个：`desc` 空、`profile` 空、`use_cases` 空、`config_items` 空。但它有一个独特特征：`endpoint = 21.117.141.204:8883`（AGUI）/ `:8882`（A2A）——**独立部署在完全不同的网段**。**

## 12.1 从"独立部署"能读出什么

其他 10 个 Agent 都在 `30.172.92.173:8083`（同一 obs_agent 进程），只有它在 `21.117.141.204`。**独立部署通常只有三个原因**：

1. **网络域隔离**——它要访问的目标系统（TCS 底座日志、TCE 集群）在另一个网络域，obs_agent 所在网段访问不到；
2. **依赖冲突**——需要特定的工具链/客户端；
3. **故障域隔离**——排障场景可能执行较重的操作，不想影响其他 Agent。

对应到 README 里的技能库：`ops/tcumtcs/` 有一个 "TCS 系统错误分析" 技能，`ops_agent` 服务也存在——说明**排障能力可能跑在 `ops_agent` 进程而非 `obs_agent`**，这解释了不同的端口（8883/8882 而非 8083/8082）。

## 12.2 配置全空暴露的问题

`profile` 和 `use_cases` 为空意味着：

```go
subAgentDescs = append(subAgentDescs,
    fmt.Sprintf("名称: %s\n描述: %s\n使用示例: %s", item.Code, item.Profile, item.UseCases))
// → "名称: tcum_tcs_error_debug_expert\n描述: \n使用示例: "
```

**`supervisor` 拿到的是一个只有名字、没有描述的子 Agent**——LLM 只能靠 code 里的字面意思（`tcum_tcs_error_debug`）猜它能干什么。**这直接导致路由准确率下降，且这个 Agent 很可能基本不会被 supervisor 选中。**

> **这是一个可以直接讲的"配置即代码质量"问题**：在 LLM 驱动路由的架构下，**Agent 的 `profile`/`use_cases` 字段的地位等同于函数的 doc comment——它不是文档，它是被执行的输入。** 应该在入库时做校验（profile 非空、长度下限、必须含"何时使用"描述），甚至用 lint 检查描述质量。

## 12.3 排障场景本身的特点

排障是**最需要长程可靠性**的场景：

- 轮次多（要看日志、看指标、看配置、看拓扑，逐层排除）；
- 数据量大（日志尤其）；
- 最容易撞上下文上限和轮次上限。

**所以它也是"轮次耗尽应改为强制收敛"最受益的场景**——排障排到第 29 轮才报错，前面 28 轮的发现全部作废，用户体验极差。

## 12.4 不足（最严重的配置质量问题）

1. `desc`/`profile`/`use_cases` 全空 → 无法被有效路由；
2. 独立部署但**未在文档中记录原因**——后续维护者不知道能不能合并回主进程；
3. 日志类数据的截断应用"语义感知采样"（错误级别优先 + 异常聚集段完整保留），当前是通用截断策略。

# 13. `tcum_ai_assistant` · 统一运维 AI 助手（外部平台接入）

**`order=5`，2026-01 上线。是第一个"非自研"接入的 Agent。**

## 13.1 接入形态：`knot_agui`协议

```
endpoint:      http://knot.woa.com/apigw/api/v1/agents/agui/c08a217a2d6646e8bcc8d9ffb9707bdc
a2a_endpoint:  http://21.168.173.207/agents/628508cd-f774-45ac-b9b5-3f210943b67a
protocol_type: knot_agui
auth_config:   {"token":"a4dd8fc0075d4c779135290b83800fa1"}
agui_endpoint: （空）
```

**四个技术细节值得讲**：

1. **endpoint 里是一个 UUID**——说明 Knot 平台上每个 Agent 有独立 ID，TCUM 只是它的一个消费方；
2. **`auth_config` 存 token**——对应 `sub_agent_factory.go`里的 `parseKnotToken(ag.AuthConfig)` 和 `WithKnotToken` option。**这是唯一一个需要独立鉴权的 Agent**；
3. **`agui_endpoint` 为空但 `endpoint` 有值**——说明 `endpoint` 是主字段，`agui_endpoint`/`a2a_endpoint` 是补充；
4. **`protocol_type` 是第三种值**（tcum_agui / sre_agui / knot_agui）——协议适配层的价值就在这里。

## 13.2 ⚠️ 一个必须指出的安全问题

**`auth_config` 里的 token 是明文存在数据库里的，而且出现在了数据导出 CSV 中。**

这违反了"Secrets: env-only"的基本原则。正确做法：
- DB 只存**凭证引用**（如 `secret_ref: "knot/tcum_ai_assistant"`）；
- 真实 token 放密钥管理系统（或至少环境变量），运行时按引用解析；
- 数据导出/日志中自动脱敏（项目在 `pkg/rag/trag/client.go` 里已有 token 脱敏的先例，说明团队知道这个做法，只是没覆盖到这里）。

> 面试提这一条的价值：**主动发现并指出自己系统的安全问题，比宣称"我们很安全"可信度高得多。** 而且这是一个"发现即修复"的低成本项。

## 13.3 业务价值：产品知识问答

`desc`：*"基于平台官方文档知识，提供从基础概念到复杂场景实践的全方位技术问答支持，以及产品使用引导"*，`query_examples`：`"统一运维权限申请流程是怎样的?"`。

**这是典型的文档 RAG 场景，被"外包"给了 Knot 平台**——这是一个正确的判断：**通用文档问答不是 TCUM 的差异化能力，用现成平台即可；TCUM 应聚焦在"需要调工具查真实数据"的场景。**

**分工边界很清晰**：

| | `tcum_ai_assistant`（Knot） | 自研 Agent |
|---|---|---|
| 数据来源 | 静态文档 | **实时工具调用** |
| 能力 | 知道"怎么做" | 知道"现在是什么状态" |
| 例 | "权限申请流程是怎样的" | "这个告警为什么触发" |

## 13.4 不足

- token 明文存储（§13.2）；
- 外部 Agent 的**可观测性断链**——Langfuse trace 到`AGUIAgent.Run` 就断了，对端 Knot 平台内部的 LLM 调用/工具调用看不到。**这是所有跨平台 Agent 协作的通病**，理论上应通过 trace context 传播（W3C Trace Context / `traceparent` header）打通，当前未做；
- 外部平台的可用性直接影响本平台（无熔断降级）。

# 14. `sre_expert` · AICoop 智能运维专家（跨团队多 Agent 嵌套）

**`order=4`，2026-01 上线。全表最有意思的一个——它本身就是一个多 Agent 系统。**

## 14.1 它是"Agent 中的 Agent 平台"

`desc` 原文：

> *"我是 AICoop 智能运维伙伴，**支持 MultiAgent 智能协作，可协同多位专家为您解决问题**。我支持的能力包括：微服务公有云运维专家（TSF、TSE、Service Mesh、服务治理、ZK，支持知识库查询、监控指标分析、拓扑结构查看）；Linux 系统专家（命令使用、性能调优、进程管理、文件系统、shell 脚本）"*

`use_cases.Desc`：*"AiCoop 多Agent调度，让 AI 像真正的 SRE 团队一样思考、协作、决策"*，`Features`：根因推理/ 容量评估 / 机房裁撤 / 公有云开区 / 日常智能问答。

**所以这里有三层 Agent 嵌套**：

```
TCUM supervisor（Deep, task 工具委派）
    └─ sre_expert（AGUIAgent 远程壳 → sreagent.woa.com）
            └─ AICoop 自己的 MultiAgent 调度
                    ├─ 微服务公有云运维专家
                    └─ Linux 系统专家
```

**这在真实工程里意义重大**：它证明 **A2A/AGUI 协议能让不同团队的 Agent 系统互相嵌套，而不需要对方暴露内部结构**。TCUM 的 supervisor 只知道"有个 sre_expert 能干这些事"，完全不知道对端还有一层调度。

## 14.2 `config_items` 是全表最复杂的：三个配置项

```json
[
  {"Key":"scenario","Type":"select","DefaultValue":"tcsOpsTeam","Options":[
      {"Value":"tcsOpsTeam","Name":"公有云 TCS"},
      {"Value":"hotTraceReasoningTCS","Name":"公有云 TCS 告警根因推理"},
      {"Value":"tsfOpsTeam","Name":"公有云 TSF"},
      {"Value":"hotTraceReasoningTSF","Name":"公有云 TSF 告警根因推理"},
      {"Value":"tceOpsTeam","Name":"私有云 TCE"},
      {"Value":"pulseviewOps","Name":"PulseView"}]},
  {"Key":"reasoning","Type":"switch","Name":"深度思考","DefaultValue":"false"},
  {"Key":"planning","Type":"switch","Name":"规划模式","DefaultValue":"false"}
]
```

**这三个配置项揭示了三个能力，恰好都是 TCUM 自有 Agent 缺失的**：

| 配置| 对应能力 | TCUM 自有 Agent 现状 |
|---|---|---|
| `scenario`（6 个运维域） | **域路由由用户显式指定** | 类似 `tenants` 的思路 |
| `reasoning`（深度思考） | **Effort 分级 / 推理深度可调**（对标 CC 的 `thinking.ts`） | ❌ 无 |
| `planning`（规划模式） | **显式 Plan-then-Execute** | ❌ 无（只有 deep 内置的 `write_todos`） |

> **这一点在面试里可以这样用**：*"我们平台接入的外部 Agent（AICoop）已经把『深度思考』和『规划模式』做成了用户可控开关，这反过来提醒我：Effort 分级和显式规划是我们自研 Agent 缺的两块。特别是 planning——运维根因分析天然适合『先出排查计划、再逐条执行、最后汇总』，而我们现在是让模型在ReAct 循环里边想边做，中间过程用户看不到计划全貌。"*

**`config_items` 通过 `parseAgentConfigItems(ag.ConfigItems)` 传给 `AGUIAgentConfig.AgentConfig`**，即用户在 TCUM UI 上选的 scenario/reasoning/planning 会**透传到对端平台**。这是跨平台参数传递的实际机制。

## 14.3 `query_examples` 的一条很典型

```
"集群是 Upgrading 状态，查看详情是 region-dns 状态是 Failed ；如何排查处理？"
```

这是**纯排障问句**——没有 ID、没有精确参数，全靠自然语言描述现象。这类输入对Agent 的要求最高：要从现象描述反推可能原因，再逐一验证。

## 14.4 不足

- **跨平台 trace 断链**（同 §13.4）；
- **跨平台上下文丢失**：`task(description)` 只传一段文本，用户在 TCUM 侧的会话历史对端看不到；
- **外部依赖的可靠性无兜底**：`sreagent.woa.com` 挂了或慢了，TCUM 侧只能超时（且 `idleTimeout=60s` 对"根因推理"这类任务偏短）。

# 15. `digital_twin_agent` · 数字分身

**`order=9000`，2026-06 上线（最新）。`visible=0` —— **唯一一个对用户不可见的 Agent**，独立部署在 `30.172.92.192:8083`。**

## 15.1 `visible=0` 的含义

`ListAgents` 工具会过滤 `visible=1`，且代码里明确过滤掉 `supervisor`/`digital_twin_agent`——所以它**不出现在用户可选的 Agent 列表里，也不进 supervisor 的候选池**。

原因：它不是一个"能力型Agent"，而是**所有数字分身的运行时载体**。用户面对的是"某个具体分身"（如"运维值班助手"），而不是 `digital_twin_agent` 本身。

## 15.2 场景：把专家经验变成 7×24 数字员工

README 描述的执行流程：

```
配置数字分身 → 注入历史记忆 → 设置定时任务 → 调度器触发执行
→ 查询记忆/偏好 → 创建对话 Session → Agent 推理生成报告 → 推送企业微信通知
```

关键特性：
- **画像**：`Soul` 字段定义分身身份与行为风格（注入 `<soul>`）；
- **记忆注入**：`TwinMemory` 表 + LLM Rerank 精选（候选池 50 → 截 200 字节 → Top-10 → 注入 `<memories>`）；
- **偏好**：`Preferences` 注入 `<preferences>`；
- **定时调度**：cron + once 两种模式；
- **分布式锁**：防多实例重复执行 + 锁续约。

## 15.3 技术实现（第一篇之三 §4.3 已详述，此处讲场景含义）

**"一个实例服务 N 个人格"的场景价值**：

假设有 500 个数字分身，如果每个分身都构建一个独立 Agent 实例：
- 内存爆炸（每个实例带自己的 ReAct 图、工具列表、prompt）；
- 分身配置变更需要重建实例；
- 无法应对分身数量增长。

**运行时装配的方案**：一个实例 + 每次请求按 `TwinInfo` 现造工具集。代价是每次请求多一次 DB 查询（`TwinInfoResolver`）和一次图重建（`rebuildGraph`），收益是**线性扩展 + 配置即时生效**。

## 15.4 主动式任务：Agent 从"被动应答"到"主动工作"

这是数字分身最有价值的一点，也是 `docs/arch/数字分身Agent主动式任务处理方案.md` 的主题。

**与被动对话的三个本质差异**：

| | 被动对话 | 主动定时任务 |
|---|---|---|
| 触发 | 用户提问 | cron / webhook |
| 失败可见性 | 用户立即看到 | **无人看着，失败可能静默** |
| 上下文 | 用户会补充 | **必须自包含**（prompt 里要写全） |
| 权限 | 用户在场可确认 | **无人可确认** → 对应 CC 的 `dontAsk` 模式 |

**所以主动任务对可靠性要求最高**：
- 分布式锁 + 锁续约（防重复执行）✅ 已做；
- 执行失败必须告警（否则静默失败）⚠️ 需确认；
- **绝不能有需要人工确认的操作**（无人在场）→ 应强制 `readonly` 或预授权白名单 ⚠️ 未做。

## 15.5 不足

- **权限体系是这个场景的硬需求而非可选项**：数字分身 = 无人值守+ 有工具 + 有权限边界。当前虽有 `TwinSoulMiddleware` 的 `adminOnlyTools` 过滤和 `DynamicTaskTool` 的授权 map，但**没有"写操作"维度的分级**；
- **`ExecuteSQL` 在 `adminOnlyTools` 名单里** ——说明分身工具集里确实存在高危工具，只靠 "是否 admin" 一个布尔量控制太粗；
- 记忆机制的问题（无冲突消解、无显式记忆提取规则、LLM rerank 每轮成本高）见第三篇 Q20。

# 16. 场景层横向总结

## 16.1 15 个 Agent 的四种"能力原型"

抽象出来只有四类，每类的工程重点完全不同：

| 原型 | 实例 | 核心挑战 | 关键机制 |
|---|---|---|---|
| **A. 点查 + 深度分析** | 告警诊断、指标分析、报告解读、变更分析 | 多跳依赖查询、时间标准化 | ReAct 多轮迭代 + `time_inject` + skill SOP |
| **B. 聚合分析** | 可观测汇总、SLO 分析、巡检全局分布 | **数据量很容易超限 + LLM 不擅长精确计算**；“很容易”不等于每次都会超过 L1 字节阈值 | **可走 COS 卸载 + 沙箱 Python 聚合**。只有具体工具结果超过各自有效阈值、且 COS 上传成功时才会出现 L1 的 COS_URL；`BatchQueryGrafana` 则在自身路径中逐 panel 尝试上传 |
| **C. 结构化生成** | PromQL、InfluxQL、Grafana 看板、巡检项 | **输出结构正确性** | 语义级工具（代码保结构）+ **执行验证闭环** |
| **D. 平台/载体** | supervisor、digital_twin_agent | 动态装配、权限隔离 | 请求期装配 + `BeforeAgent` 链 + rebuildGraph |

**这个分类的价值**：它说明**不能用同一套工程标准衡量所有 Agent**。B 类的关键指标是"COS_URL 使用率"，C 类是"生成物验证通过率"，A 类是"引用溯源完整性"，D 类是"权限隔离正确性"。**评测集也必须按原型分别设计。**

## 16.2 从 15 个 Agent 的演进读出的产品策略

```
2025-12  告警诊断 + 指标分析 + supervisor       ← 先做最高频的两个 + 总入口
2026-01  AI助手(外接) + SRE专家(外接) + 汇总分析   ← 广度扩张：能外接的就外接
2026-02  SLO 分析 + PromQL 专家                ← 抽出公共子能力
2026-03  InfluxQL + Grafana看板 + 排障          ← 覆盖第二套监控栈 + 从"读"到"生成"
2026-04  CMDB 资产                ← 跨出监控域
2026-05  天巡巡检 + 变更分析                    ← 覆盖运维全生命周期
2026-06  数字分身                              ← 从"工具"到"数字员工"
```

**四条清晰的策略线**：
1. **先高频后长尾**（告警/指标 → SLO/变更）；
2. **能外接就外接**（AI助手、SRE专家不自研）；
3. **公共子能力上升为独立 Agent**（PromQL/InfluxQL 从内嵌能力抽出）；
4. **从只读到生成再到自主**（分析 → 配置生成 → 数字分身无人值守）——**风险等级也是这个顺序递增的，而权限体系没有跟上这条曲线，这是最大的失衡**。

## 16.3 场景层最该补的五件事（按优先级）

| # | 事项 | 理由 | 受益 Agent |
|---|---|---|---|
| 1 | **工具风险分级 + HITL 审批** | 已有 Agent 跨过"只读"边界（巡检项生成、看板落库、数字分身无人值守） | 天巡、Grafana、数字分身 |
| 2 | **身份透传 + AuthZ + 审计** | CMDB 资产、多租户数据有权限边界，当前很可能用服务身份 | CMDB、全部 |
| 3 | **强制引用溯源 + 数值校验** | 运维决策依赖数值，编造一个指标值可能导致错误回滚 | 告警诊断、变更分析、SLO |
| 4 | **分原型评测集** | A/B/C/D 四类原型判定方式不同；C 类（PromQL/InfluxQL/看板）**可自动化判定**，应最先做 | PromQL、InfluxQL、Grafana |
| 5 | **Agent 配置质量 lint** | `tcum_tcs_error_debug_expert` profile 全空导致无法被路由；`grafana`的 a2a 端口配错；token 明文入库 | supervisor 路由质量 |

## 16.4 一个可以直接讲的"场景驱动技术决策"叙事

> *"我们的技术选择基本都是被场景逼出来的，不是先有方案再找场景：
>
> - **COS 卸载 + 沙箱聚合**是被『可观测汇总分析』逼出来的——一天的全平台告警 + 巡检数据几MB，全塞上下文必死，只取前 N 条则聚类结论必错，所以只能走『数据留 COS、算力放沙箱、只回结论』；
> - **AdaptiveContextRetry** 是被『看板批量分析』逼出来的——一轮并发查 3~5 个看板，token 跃迁式暴涨跳过 summarization 安全区，且这批结果全是未读tool 无法 elide，只能在模型调用层拦 400 兜底；
> - **PromQL/InfluxQL 独立 Agent** 是被『三个场景都要写查询语言』逼出来的——不抽出来就是三份重复 prompt；抽出来后还顺带获得了『生成→执行→修正』的验证闭环；
> - **Grafana 看板的语义级工具**是被『JSON 结构太复杂』逼出来的——让模型直接吐 JSON 必然出结构错，所以改成代码保结构、模型只做语义决策；
> - **数字分身的运行时装配**是被『一个实例服务 N 个人格』逼出来的——构建期焊死能力集就无法做细粒度授权。
>
> 反过来说，我们没做的那些（权限体系、评测集、prompt cache）也是因为还没有场景把它逼到必须做——但巡检项生成和数字分身已经把权限这件事逼到台面上了，这是我判断它是下一阶段 P0 的依据。"*
