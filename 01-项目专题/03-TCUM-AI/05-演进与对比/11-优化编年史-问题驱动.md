# 第五篇 · 优化编年史：我们遇到了什么问题，为什么这么优化

> **这一篇是给面试用的"弹药库"**。前四篇讲的是"我们做了什么机制"，这一篇讲**每个机制是被什么具体问题逼出来的**。
>
> 为什么这最值钱：面试官对"我们做了自适应压缩"无感，但对"**一轮并发 5 个工具让 token 从 18k 跃迁到 128k，summarization 因为全是未读tool 无内容可压，直接把超限请求发出去撞400，会话当场中断**"会立刻追问下去。**能说出问题的人才像真的干过。**
>
> 每条统一四段：**【现象】→【根因】→【优化动作】→【代价 / 权衡】**，并标注代码位置作为证据。

# 一、上下文类（4 条）

## 1.1 会话在"一轮并发多工具"之后当场中断

**【现象】** 告警诊断/汇总分析这类 Agent，前面十几轮都正常，某一轮突然返回 `400 ContextWindowExceededError`，**整个会话直接终止**，用户看到的是报错而不是降级结果。而且这一轮之前的 token 明显低于 summarization 的触发阈值（模型上限的一半）。

**【根因】** 两个机制的盲区正好叠在一起（`adaptive_context_retry.go` 文件头注释把这个复盘写进了代码）：

1. eino 的 `ToolsNode` 对一轮 N 个 `tool_calls` 是**并发执行 + `wg.Wait()` 一次性全部返回**（`compose/tool_node.go:751-783`）。所以 token 不是渐增而是**跃迁式暴涨**——完全可能从远低于 50k 一步跳到超过 100k，**整个"安全区"被跳过**，summarization 的"轮次之间判断阈值"根本没有介入机会；
2. 更致命的是：这一批结果全是**"未读 tool"**（当前推理轮的原始输入，后面还没有 assistant 消费过）。而 summarization 的压缩策略**必须保留未读 tool**（否则模型这轮就拿不到自己刚要的数据）→ **无elidable 内容** → 它只能把超限的 messages 原样发出去 → 400。

**【优化动作】** 在 `WrapModel` 层加`AdaptiveContextRetry`：从 400 错误里 **parse 出真实 `(currentTokens, maxTokens)`**（4 条正则覆盖 litellm/OpenAI/Anthropic/通用格式）→ 算出 `needSave` → 按"已读优先、低密度优先、体积大优先"排序 → tool 走 T1 采样/T2 丢 data/T3 引用占位、assistant 走 T4 头尾截断 → **round 递进解禁**（第 1 轮绝不动未读、第 2 轮才允许动未读和 T3、第 3 轮才允许 T4）→ 压缩后本地重算，**不达标就不发请求**（fail-fast）→ 达标才重试 `Generate`。

**【代价 / 权衡】**
- 只覆盖 `Generate`，**`Stream` 直接透传**，而 AG-UI 主链路是流式 → **这条兜底在生产主链路上基本没被触发过**（第一篇 §1.1 L4 已详述，是当前 P0）；
- 压缩本身有信息损失，所以做了"COS_URL 必须穿透每一档"来保住数据回捞入口。

> **讲法**：*"并发是因，超限兜底是果。"* 这句话能一次性证明你读懂了框架源码、看懂了两个机制的交界处、并且是从线上现象倒推回去的。

## 1.2 压缩请求自己把自己撑爆了

**【现象】** 触发 summarization 后，报错变成 `failed to generate summary`——**压缩这个动作本身失败，然后会话照样中断**。

**【根因】** 压缩要把一大堆历史喂给压缩模型，这个请求自己也可能超限。而且 `chars/4` 的本地估算对中文/JSON **低估 1.5~2 倍**，代码注释写得很直白：*"实际 tokenizer 可能把 90k 字符估算算成 120k+ tokens"*——所以静态预算裁剪（`0.9 × maxTokens`）算出来"没超"，实际发出去就超。

**【优化动作】** 两层：
1. `GenModelInput` 做静态预算裁剪（未读保护 + 最近 2 条保护 + 已读最旧优先 elide）；
2. **压缩模型自己也被 `adaptiveContextModel` 包一层**（`summarization_handler.go:69`），形成**递归自保**——压缩请求超限时也能原地压缩重试。

**【代价 / 权衡】** 结构上有点绕（压缩器内部套了压缩重试器），必须在注释里写清动机，否则后人会以为是重复包装。

> 这条的价值在于展示"**防御要覆盖防御自身**"的思维。

## 1.3 走Deep 模式的 Agent 静默地失去了压缩能力

**【现象】** 同样的会话长度，普通 Agent 好好的，Deep Agent（带子 Agent 委派的）却更容易超限。

**【根因】** 两处构建路径分叉：`BuildDeepAgent` 走的是另一条装配流程，如果不显式挂上 summarization，它就**没有**——而且**不报错、无日志，纯静默**。同类问题还有一个更隐蔽的版本：`ToolCallMiddlewares` **必须在存入 `agentCfgMap` 之前注入，否则 deep 模式新建 `ToolsNode` 时会丢掉截断中间件**（这条踩坑记录直接留在代码注释里）。

**【优化动作】**
- 收敛为唯一入口 `BuildSummarizationHandler(ctx, cm)`，所有 Agent（Default / Deep）都必须从这里拿压缩能力，注释里写明动机就是"避免 `BuildDeepAgent` 路径静默失去压缩能力"；
- 截断中间件的注入时机在代码里留了显式注释坑位。

**【代价 / 权衡】** 这类"多构建路径能力不一致"的问题**没有测试能兜住**，只能靠"唯一入口 + 注释"。**更彻底的做法是把能力清单做成断言**（构建完检查必需中间件是否都在），目前没做。

> **讲法**：*"最危险的 bug 不是报错，是静默降级。"*

## 1.4 本地估算说"没超"，模型说"超了"

**【现象】** 压缩后重算发现"应该没问题"，发出去还是 400；重试几轮都在浪费真实的模型调用。

**【根因】** `chars/4` 是英文经验值。中文一字常 1~2 token，JSON 结构字符 token 密度也远高于英文。**而且更隐蔽的第二个因素**：所有本地估算都**只累加 `len(m.Content)`**——完全没计入工具 schema（每轮全量发送，20+ 工具可达数千 token）、`ToolCalls.Arguments`、`ReasoningContent`。所以低估是**两个因素叠加**。

**【优化动作】** 引入 litellm 的 `/utils/token_counter`（真tokenizer，不推理不计费，响应带 `tokenizer_type`），封成三级：`LocalTokenCounter` / `LitellmTokenCounter` / `FallbackTokenCounter`。**克制的地方是关键**：
- **只在"已经超限、必须精确算压缩量"的重试路径调远端**，正常请求零额外延迟；
- 800ms 短超时 + **连续 3 次失败熔断 60s**；
- primary 成功时顺带算一次本地值打`ratio=%.2fx` 偏差对比日志（**自带效果度量**）；
- `ADAPTIVE_TOKEN_COUNTER_DISABLE` 一键回滚纯本地。

**【代价 / 权衡】** 多一次HTTP 调用（P95 观察~365ms）。**判断依据是成本比较**：一次 300ms 的分词调用，远比"压缩不到位 → 再发还超限 → 又浪费一次大模型调用"便宜。

# 二、工具可靠性类（4 条）

## 2.1 一个 MCP 工具报错，整个会话挂掉

**【现象】** 真实 trace：某个 MCP 工具返回 error → `ToolNode` 状态 ERROR → ReAct 图 ERROR → **整个会话终止**。用户前面二十轮的分析成果全部作废。

**【根因】** eino 的图执行语义里，节点返回 error 就是终止信号。而工具报错在运维场景**极其常见且大多可恢复**（参数写错、后端限流、临时超时、指标不存在）——把它当致命错误是不合理的。

**【优化动作】** `toolErrorHandlerMiddleware`：把工具 error 转成**正常的 `[TOOL_ERROR]` 文本**返回给模型，并附**三条明确行动指引**（改参数重试 / 临时错误可重试一次 / 连续失败 2 次就换别的工具），错误文本截断 2000 字符防撑爆。两个精准的例外**必须原样抛**：
- `IsInterruptRerunError`（human-in-the-loop 依赖，兜底会破坏中断恢复语义）；
- `ctx.Err()`（请求已取消，兜底毫无意义）。

挂在 Handlers 链**最前（最外层）**，因此连 `BeforeAgent` 动态注入的 MCP 工具也一起被兜住。

**【代价 / 权衡】** 模型可能在错误上纠缠多轮（所以指引里明确写了"连续失败 2 次改用别的工具"这条**退出条件**）；且工具失败被"正常化"后，**没有指标统计工具失败率**——这是缺口。

## 2.2 模型调用了一个不存在的工具

**【现象】** 模型幻觉出一个工具名，图直接报错终止。

**【优化动作】** `UnknownToolsHandler` 返回 `"unknown tool: %s"` **文本**而非 error，让模型自己看到"没这个工具"并改用真实工具。

**【权衡】** 与 2.1 同源思路：**凡是模型能自我纠正的失败，都不应该是终止信号**。

## 2.3 拓扑数据被截断后，Agent 给出了错误答案

**【现象】** CMDB 架构拓扑分析，30 个实体批量查询后结果超 64KB 被结构化截断，**Agent 基于不完整的拓扑给出了错误的影响面结论**——这比报错更糟，因为它看起来是对的。

**【根因】** 通用的"64KB 截断 + COS 卸载 + 沙箱回捞"范式对**大多数**数据成立，但对拓扑不成立：
- 拓扑是星型/分叉结构，30 实体单批 fan-out 后天然超限；
- **拓扑分析对字段完整性极度敏感，丢一个 `DotEdge` 就等于丢一条依赖关系，直接产生错误答案**；
- 而且它不适合走沙箱降级——沙箱能算聚合，但拓扑推理是模型要做的。

**【优化动作】**（`register.go:49-59` 的注释把这个判断完整记录了）
- 给 `QueryArchTopology` **单独 2× 阈值**，且用 `2 * middleware.DefaultToolResultMaxSize()` **表达为倍数而非绝对值** —— 这样 `TOOL_RESULT_MAX_SIZE` 环境变量调整时相对比例保持稳定；
- 配合 **v3 列存 + 元组压缩**从源头把体积压下来，让 30 实体（<60 硬上限）的典型场景能完整返回所有 `dots` + `edges`。

**【代价 / 权衡】** 引入了 per-tool 配置这一层复杂度。**但这条给出的一般结论很有价值**：**上下文预算必须按数据语义分配，不能一刀切**——"能降级的数据给紧预算 + 卸载通道，不能降级的数据给宽预算 + 源头压缩"。

## 2.4 批量查询里一个失败，整批都拿不到

**【现象】** 批量按名称查 30 个巡检项 / 批量查30 个实体拓扑，其中 1 个名称不存在，**整个调用失败返回**。

**【优化动作】** 统一改成**部分成功语义**：
- `GetInspectItems`：先一次 `ListInspectItems(Names=...)` 解析 ID，再逐个取详情；**任一名称的解析或详情失败不中断其他**，错误逐项挂在 `InspectItemResult.Err`；
- `ArchTopologyResp`：`Graph` 只含成功子图的合并结果，`Failures` 列出失败项及原因枚举（`not_exists` / `duplicate` / `render_error`）。

**【权衡】** 返回结构更复杂，但**对 Agent 极其重要**：模型拿到"28 个成功 + 2 个 not_exists"可以继续推理并在结论里说明缺口；拿到一个整体error 就只能重试或放弃。**"部分成功 + 结构化失败原因"是 Agent 友好型 API 的关键特征。**

# 三、模型行为跑偏类（最鲜活的一组：每条禁令都是一次跑偏的化石）

> 这一组特别适合面试讲，因为它证明你**看过真实会话日志**而不只是写代码。
> 素材来源：`skill_content_compactor.go` 的精简版 SKILL.md、`skill_exec.go` 的参数描述——**这些"禁止/必须"每一条背后都是一次线上跑偏**。

| # | 【现象】模型干了什么 | 【优化动作】加了什么约束 | 为什么这么改 |
|---|---|---|---|
| 3.1 | 把 `skill_name` **嵌进 `command` 字符串内部**（如 `skill_exec("skill_name=xx python3 a.py")`），导致参数解析失败 | 参数 Desc 直接写：*"⚠️ 必填，**必须作为独立的顶层 JSON 字段传入，不要嵌入 command 字符串内部**"* | 模型对"哪个参数放哪"的判断不可靠，**Schema 描述里要写反例**而不只写正例 |
| 3.2 | 在沙箱里 `which` / `ls` / `cat` / `find` **到处探测环境**，白烧好几轮 | 精简版 SKILL.md 明令：*"禁止 which、ls、cat、find 等探测"* | 模型有"先探环境"的本能，但 skill 已经把路径和用法写清了，探测纯浪费轮次与 token |
| 3.3 | 工具失败后**反复换参数重试**，卡在同一个工具上不动 | 明令：*"工具失败或空数据不要反复换参数重试"*；配合 `toolErrorHandler` 的"连续失败 2 次改用别的工具" | 必须给模型**显式的退出条件**，否则它会一直"再试一次" |
| 3.4 | 为了算"总对话量环比"，**多查一次上一周期**的聚合数据 | 明令：*"不要为了总对话量环比补查上一周期；该字段没有上一周期时显示『未提供』或『—』"* | 模型会为了"报告完整"自行增加调用。**"缺就写缺"必须显式许可**，否则它会去凑|
| 3.5 | 数据被采样截断（`sampled=true`）后，**照着采样值报了个错误的总量** | 明令：*"若 `sampled=true`，报告顶部必须提示『数据存在采样截断，实际总量可能更高』"* | 这是**数据可信度必须冒泡到结论层**的典型：底层标记了采样，上层不说就等于骗人|
| 3.6 | 反馈只有 1 条好评时，算出 **"好评率 100%"** | 明令：*"反馈总数 <5 时好评率显示 N/A（样本不足）；**分母为 0 时不要编造百分比**"* | 统计常识对模型不是常识。**小样本比例、零分母**是必须硬约束的两个坑 |
| 3.7 | 为了"更全面"去拉**原始对话/消息明细**，一次撑爆上下文 | 明令：*"标准报告禁止调用 `QueryDialogs` / `QueryDialogMessages`"*；`QueryFeedbacks` 限 `ratings=[0]`、`has_comment=1`、`limit<=5`，反馈为 0 时**禁止调用**；执行日志 `Limit<=3`、只展示统计不展示全文 | **上下文治理不能只靠事后压缩，要在"允许模型调什么、调多少"上前置约束** |
| 3.8 | 某个 SKILL.md 本身太大，**每轮都全量进上下文** | 用**人工手写的行为等价精简版**替换返回给模型的文本（`compactSkillContentForLLM`），**`BaseDirectory` 保持完整**让 `skill_exec` 仍能读原始目录 | 说明书的每轮固定开销常比数据还大；且**"给模型看的"和"给执行用的"可以是两份** |
| 3.9 | 时间/用户/租户/实体规则等信息**每轮被重复注入**，上下文越堆越大 | 4 个 inject 中间件用 `adk.GetRunLocalValue` 打**哨兵**，只在第一轮真跑 | `BeforeModelRewriteState` 是**每轮都调**的，"一次性注入"必须自己实现幂等 |
| 3.10 | ReAct 下 assistant 发起 tool_calls 时 `content` 天然为空，litellm 后端**严格要求 content 非空** → 压缩请求被 400 拒绝 | `fixEmptyContentMessages` 把这类消息补成 `[调用工具: A, B]` | 协议兼容性问题，且补的占位文本**顺带帮压缩模型理解这轮调了什么工具**（一举两得） |

**还有一个特别有意思的细节**：精简版 SKILL.md 结尾要求 *"报告结尾必须包含 `[OPTIMIZE-V3]`"*。

>这是一个 **prompt 生效性探针**：看输出里有没有这个标记，就知道模型**实际读到的是哪一版 skill**。`V3` 也说明这份精简版已经迭代了三轮。**这是在没有评测集的情况下，一个极低成本的"prompt 版本可观测"手段**——面试讲这个细节很能体现工程直觉。

# 四、数据正确性类（5 条）

## 4.1 阈值推荐把"差值/比率"误判成吞吐量

**【现象】** 告警模板阈值推荐，对形如 `A - B > ${x}`（差值）或比率类表达式，**推荐出的阈值量级完全不对**。

**【根因】** 指标类型分类器（`tagger.go`）会用主指标名 + 主查询文本去匹配关键词（`rate/throughput/latency/...`）。但当主查询含**顶层算术运算符**时，**主指标名不代表整体语义**——`request_count_a - request_count_b` 的语义是"差值"，不是"count"。

**【优化动作】** `gatherText` 加判断：`hasTopLevelArithmetic(b.MainQuery)` 为真时**跳过 `MetricName` / `MainQuery`，只用变量元数据**（变量名 + Description + DisplayName）。注释写明动机：*"避免把差值当 throughput、比率当 count 之类的误判"*。

**【权衡】** 依赖变量元数据的质量。**这条的一般结论**：**基于文本关键词的分类器，必须识别"文本不代表语义"的场景并主动放弃该信号**——盲目多用信息反而更错。

## 4.2 阈值推荐上线后误报率偏高

**【现象】** 推荐出的阈值太贴近正常波动，实际告警误报多。

**【优化动作】** 一次**全局调参**（注释原文："整体调优方向：三档（strict/balance/loose）均适当放宽，降低误报率"）：`std_offset` 模式 **KStd 各档 +0.5**（偏移更大、阈值离 P50 更远）、`rel_factor` 模式 `RelFactorHigh +0.5` / `RelFactorLow -0.1`、`absolute` 模式 Default 适当增大。

**【权衡】** 放宽必然牺牲灵敏度（漏报↑）。**值得学的是把调参方向和理由写进代码注释**——否则半年后没人知道这些魔数为什么是这个值。

## 4.3 用户无法判断推荐结果可不可信

**【现象】** 阈值推荐给了一个数，用户不知道该不该信、要不要人工复核。

**【优化动作】** 一套**确定性的置信度体系**（不用 LLM）：
- `scoreConfidence` 按 warnings **逐条降档** high→medium→low：样本不足 / `std=0` / drift 过大 / `unexpected scale` / **门控失败（用了未过滤序列）** / `ConsistencyChecker` 未能完全修正冲突；
- `Explanation.Details` 分七类结构化解释（`feature`/`prior`/`heuristic`/`gate`/`unit`/`consistency`/`provider`）；
- `buildOverallSummary` 面向用户直说："本次共推荐 N 个变量…**其中 X 个置信度较低，建议重点确认**"。

**【权衡】** 只活在这一个垂直场景，**没上升为平台能力**（第四篇 §1.4 启示 4 建议泛化为 `pkg/confidence`）。

> **讲法**：*"我们不追求模型永不出错，而是追求让系统知道自己什么时候可能错，并显式说出来。"* 这个立意在运维场景比"准确率 95%" 有说服力得多。

## 4.4 同一个工具的返回结构有两种形态，截断逻辑失效

**【现象】** `QueryGrafana` 类工具，一部分数据源截断正常，另一部分（CLS 日志数据源）**截断不生效**，结果原样超限进上下文。

**【根因】** `raw_grafana` 实际有两种完全不同的响应形态：Grafana `/api/ds/query` 标准响应是`results.{refID}.frames[*].data.values` **列式**；CLS 数据源 proxy 是`Response.AnalysisRecords / Results / AnalysisResults` **行式**（连大小写风格都不同）。原实现只认第一种。

**【优化动作】** `truncateRawGrafanaData` 改为**按序试探两种形态**，命中即返回；行式那条按 `AnalysisRecords → Results → AnalysisResults` 优先级找第一个非空数组截断（优先截体积大头）；两种都不匹配才降级 raw 截断。同时给模型的`dataPath` 提示也**同时说明两种形态**，让它自己看样例判断。

**【权衡】** 这类"同名类型多形态"是对接遗留系统的必然复杂度，**只能靠试探 + 兜底降级**，不可能靠类型系统解决。

## 4.5 工具报业务错误，却也被上传 COS 并污染了 COS_URL

**【现象】** 工具返回业务错误（如"实例不存在"），错误响应体积不大但也走了完整流程，`metadata.COS_URL` 被写入一个**指向错误信息的链接**，模型后续可能拿它去"下载完整数据"。

**【优化动作】** 截断中间件前置判断 `isBaseOutputError(result)`：`ErrorCode` 非 0 且非 2xx，或 `ErrorCode` 成功但 `ErrorMsg` 非空 → **直接跳过 COS 上传与截断**，原样返回。

**【权衡】** 判定依赖 `BaseOutput` 结构，非该结构时返回 false 走普通流程。**一般结论**：**任何"自动增强"逻辑都要先判断输入是否值得增强**，否则会给下游制造误导性线索。

# 五、生产护栏类（3 条，含一条最像事故的）

## 5.1 ⭐ 大盘名称丢失、并被移到根目录

**【现象】** 更新 Grafana 大盘后，**大盘名称丢了，而且从原文件夹被移到了根目录**。

**【根因】**（`monitor_capi_service.go:2092-2098` 的注释完整记录了这次复盘）`UpdateDashboard` 是**原样覆盖**语义——会把 `Name` / `ParentFolderUid` 等字段整体写回。而上游 `QueryDashboard` 有时返回**不完整的 meta**（`Name` 为空），空Name 被原样写回 → 名称清空 + 归属丢失 → 大盘"跑到根目录"。

**【优化动作】** 加**兜底护栏直接拒绝**：

```go
if strings.TrimSpace(meta.Name) == "" {
    log.ErrorContextf(ctx, "update dashboard rejected: empty Name, tenant: %s, grafana_dashboard_id: %s", ...)
    return fmt.Errorf("update dashboard: meta.Name is empty, refuse to overwrite (...)")
}
```

注释里明确写了判断依据：*"合法大盘必有名称，这里直接拒绝，避免任何调用方误传空值把大盘写坏。"*

**【代价 / 权衡】** 这是**"宁可失败，不可写坏"**的取舍。三条一般结论，都很值得讲：
1. **对"原样覆盖"型的下游 API，必须在写入前做完整性护栏**——Agent 场景尤其危险，因为参数最终来自模型；
2. 护栏要放在**最靠近副作用**的那一层（service 层），而不是工具层——因为可能有多个调用方；
3. **这也是"会改状态的 Agent 必须有回滚工具"的由来**（`tool_restore_dashboard_version`）。

## 5.2 看板布局重叠/越界，但不能因此拒绝生成

**【现象】** LLM 给出的 panel 布局有重叠、越界、`W/H` 非正数等问题。

**【优化动作】** `ValidateLayout` 做**软校验**：发现问题只打 warn 日志，**不阻断**大盘生成。注释写明理由：*"第二版基于已生成大盘的修复 Skill 会负责修正问题"*。而且专门写了测试保证它**既不 panic 也不返回error**。

**【权衡】** 与 5.1 的"直接拒绝"形成有意的对照——**判断标准是"能不能事后修"**：布局丑可以下一轮修（可逆），空Name 覆盖是不可逆的数据损坏。**同一个系统里两种相反的策略，恰恰说明取舍是想过的而不是拍的。**

## 5.3 多租户凭证缓存无上限

**【现象】** 按租户构造的 CAPI service 实例缓存会随租户数增长。

**【优化动作】** *"简单容量控制：超过上限时清空（**避免锁竞争的复杂 LRU 实现**）"*，构造失败时**返回全局单例兜底**（让错误在云API 侧暴露，而不是在这里 panic）。

**【权衡】** 明确**放弃精细 LRU 换实现简单 + 无锁竞争**。这种"显式记录为什么不做更优方案"的注释，在面试里比"我们实现了 LRU 缓存"更有说服力。

# 七、怎么把这些故事讲好（模板 + 提炼）

## 7.1 讲单个优化点的四句话模板

> **① 现象**：线上出现了什么用户可感知的问题（要有数字/具体报错）
> **② 根因**：为什么会这样（**最好能指出"两个机制的交界处"**，这是深度的体现）
> **③ 动作**：我们怎么改的（讲清关键取舍，不要罗列细节）
> **④ 代价**：这么改牺牲了什么、还有什么没解决（**主动说代价最能建立可信度**）

反例（不要这样讲）：*"我们做了自适应上下文压缩，支持五级压缩策略。"*
正例：*"一轮并发 5 个工具让 token 从 18k 直接跳到 128k，跳过了 summarization 的安全区；而这批结果全是未读tool，压缩阶段必须保留，所以它无内容可压、只能把超限请求发出去撞400，会话当场中断。所以我们在 WrapModel 层做了从 400 错误里 parse 真实 token、按信息密度分档压缩、压缩后自查不达标就不发请求的兜底。代价是它目前只覆盖非流式，而我们主链路是流式的——这是我现在排第一优先的待办。"*

## 7.2 从这些问题里提炼出的六条通用范式（面试收尾金句）

| 现象类型 | 提炼出的范式 |
|---|---|
| 会话因超限中断 | **并发是因，超限兜底是果**——两个机制的盲区叠加处才是真问题 |
| Deep 路径悄悄没有压缩 | **最危险的 bug 不是报错，是静默降级**——多构建路径必须收敛为唯一入口 |
| 工具报错炸掉会话 / 幻觉工具 | **凡是模型能自我纠正的失败，都不该是终止信号**；但要给显式退出条件 |
| 拓扑被截断产生错误答案 | **上下文预算按数据语义分配**：能降级的给紧预算+卸载通道，不能降级的给宽预算+源头压缩 |
| 批量查询一败全败 | **部分成功 + 结构化失败原因**是 Agent 友好型 API 的关键特征 |
| 空 Name 写坏大盘 vs 布局重叠只warn | **取舍标准是"能不能事后修"**：可逆的问题软校验，不可逆的数据损坏直接拒绝 |

## 7.3 还有一类问题我们**没有**解决（主动说）

|问题 | 现状 |
|---|---|
| 这些优化**有没有效果，没有任何指标能回答** | 压缩触发率、各档命中率、工具失败率、COS_URL 后续访问率、模型跑偏率——**全部没有埋点**。所有"优化有效"目前只能靠个案观察 |
| 模型跑偏类问题**靠 prompt 补丁逐条堵**，没有回归保护 | 每条禁令都是一次跑偏的补丁，但**没有测试/评测集保证下次改prompt 不会退化**。`[OPTIMIZE-V3]` 探针是唯一的低成本版本可观测手段 |
| 缺"事故→ 护栏"的机制化 | 5.1 那种护栏是个案添加的，没有"所有原样覆盖型写操作都必须过完整性校验"的统一约束 |

> **收尾讲法**：*"这些问题的解法我认为都是对的，但整体上我们停留在『**逐个问题打补丁**』阶段，缺的是两样东西：**度量**（不知道优化有没有效）和**回归保护**（不知道下次改动会不会退化）。所以我把『埋三个指标 + 建第一批可自动判定的评测集（PromQL/看板 JSON/巡检项）』排在下一阶段的最前面——它们不解决新问题，但让前面所有优化变得可验证。"*
