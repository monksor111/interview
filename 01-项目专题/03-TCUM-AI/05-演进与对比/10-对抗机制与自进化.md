# 第四篇 · 多智能体对抗 与Agent/用户级自进化

> 这是前三篇缺失的一块。前面讲的是"怎么把事做完"（循环、上下文、工具、协作拓扑），这一篇讲两个更高阶的问题：
> - **对抗**：谁来证明"做完的事是对的"？—— 决定系统的**可信度上限**
> - **自进化**：这个系统用得越久会不会越好用？—— 决定系统的**长期价值曲线**
>
> 面试价值：这两块是区分"做过Agent"和"想过 Agent"的分水岭。绝大多数候选人在这两个问题上只能说"我们让模型自己检查一下"。

---

# 一、多智能体对抗（Adversarial Multi-Agent）

## 1.1 先把问题问清楚：为什么需要"对抗"而不是"检查"

LLM 自查有一个根本缺陷：**同一个模型、同一段上下文、同一个目标函数，让它检查自己刚写的东西，它会倾向于确认自己是对的**（自洽偏差）。所以"让模型再看一遍"几乎无效。

真正有效的对抗必须满足**三个前提**——这是理解 CC 全部对抗设计的钥匙：

| 前提 | 含义 | 反例 |
|---|---|---|
| **① 利益隔离** | 审查者的成功标准 ≠ 执行者的成功标准。执行者的目标是"完成"，审查者的目标必须是"**找出它没完成**" | 同一个 Agent 追加一句"请自查" |
| **② 能力不对称** | 审查者要有执行者没有的**独立证据来源**（能跑测试、能实测接口、能看真实数据），而不只是重读文本 | 让模型凭上下文判断"我这个 PromQL 对不对" |
| **③ 判决可执行** | 审查结论必须能**真实阻止**流程，而不是一段建议文本 | 输出"建议复核"然后照常返回给用户 |

CC 的所有对抗机制都可以映射到这三条上。下面逐个拆。

## 1.2 Claude Code 的六类对抗机制

### ① Verification Agent —— 目标函数被显式逆转为"Try to break it"

这是 CC 六个内建 Agent 之一（`generalPurpose` / `explore` / `plan` / **`verification`** / `shell` / `browser-use`），也是最能体现"对抗"的设计：

```
Verification Agent 的职责（report/06-多Agent蜂群架构.md §6.4）:
- 强制运行 Build、测试套件、Linter、类型检查
- 前端改动 → 浏览器自动化验证
- 后端改动 → curl 实测响应
- 主动进行对抗性探测（Adversarial probes）
- 最终判决：PASS / FAIL / PARTIAL
- 与写代码的 Agent 利益彻底隔离
```

四个关键设计点：

1. **目标函数逆转**：它的 system prompt 目标不是"确认代码可用"，而是 **"Try to break it"** —— 这直接实现了前提①。它交出PASS 是"没能破坏成功"，而不是"我认为没问题"。
2. **强制外部证据**：Build / 测试 / Linter / 浏览器自动化 / curl 实测 —— 全部是**程序化、可复现、与模型判断无关的证据**（前提②）。这一条是最容易被忽略但最本质的：**对抗的力量不来自"另一个模型"，来自"另一个证据来源"**。
3. **三值判决而非二值**：`PASS / FAIL / PARTIAL`。`PARTIAL` 这个档非常关键——它承认"部分完成"这个在真实工程里最常见的状态，避免"为了给出 PASS 而放宽标准"或"为了严谨而全盘 FAIL"。
4. **利益隔离是结构性的**：不是靠 prompt 说"你要客观"，而是**不同的 Agent 实例、不同的上下文、不同的成功定义**。

### ② Coordinator 的四阶段：把验证提升为独立阶段

```
Phase 1 Research（Worker 并行）→ Phase 2 Synthesis（Coordinator 亲自做）
→ Phase 3 Implementation（Worker）→ Phase 4 Verification（Worker）
```

要点：**Verification 是一个由独立 Worker 执行的阶段，不是 Implementation 阶段的收尾动作**。写代码的 Worker 完成即退出，验证由另一个进程/上下文进行——它看不到写代码 Agent 的推理过程，只能看代码和运行结果。**"看不到你怎么想的"本身就是对抗性的信息隔离。**

### ③ 角色隔离：用能力剥夺代替行为约束

```typescript
const EXPLORE_AGENT: BuiltInAgentDefinition = {
  agentType: 'Explore',
  disallowedTools: [AGENT_TOOL_NAME, FILE_EDIT_TOOL_NAME, FILE_WRITE_TOOL_NAME, ...],
  model: 'haiku',         // 更快更便宜
  omitClaudeMd: true,// 只读搜索不需要提交规范/代码风格
  getSystemPrompt: () => '... READ-ONLY MODE - NO FILE MODIFICATIONS ...',
}
```

- `Explore` / `Plan` 被**硬禁写工具**（不是 prompt 里写"请不要修改文件"，而是工具根本不在集合里）；Bash 被限制为 `ls`、`git status` 等安全操作；
- **"计划与实现彻底分离"**：做计划的 Agent 没有能力实现，做实现的 Agent 拿到的是别人的计划 —— 这样"计划里的自我合理化"没法在实现阶段被偷偷修正；
- 顺带一个惊人的工程数据：仅 `omitClaudeMd` 一项，**在全量用户上每周节省数十亿 token**。

> **这一条对 tcum 最有借鉴价值**：TCUM 的权限设计其实已经用了同一个哲学——数字分身场景下"未授权的子 Agent 从一开始就不在 `dynamicTaskTool.subAgents` map 里"，"非 admin 分身直接过滤 `ExecuteSQL` 等 5 个高危工具"。**能力剥夺 > 行为约束**，TCUM 在权限上想通了，但在**质量对抗**上还没用这个思路。

### ④ 反惰性委派与反偷懒：把"人性弱点"写进 prompt 约束

CC 在 Coordinator/子 Agent 的 system prompt 里做了两件很"不体面"但极有效的事：

```
// 反模式 —惰性委派（系统提示中明确反对）
Agent({ prompt: "Based on your findings, fix the auth bug" })

// 正确 — 综合后的具体规格
Agent({ prompt: "Fix the null pointer in src/auth/validate.ts:42.
  The user field on Session is undefined when sessions expire but the
  token remains cached. Add a null check before user.id access —
  if null, return 401 with 'Session expired'." })
```

- **禁止模糊指令**：派发任务必须给出具体路径和行号，Coordinator 必须**亲自理解 Worker 的研究结果并写出实现规格**，而不是"转发"（"Workers 无法看到你的对话，每个 prompt 必须是自包含的"）；
- **子 Agent 启动注入**："你是一个被 Fork 出来的工人，不是经理。不要交流提问，直接使用工具干活，**严禁再生成子 Agent**。"

这两条解决的是多Agent 系统最典型的失效：**层层转发导致信息熵递减、以及无限递归派生**。

### ⑤ Stop 钩子的 `agent` 类型 —— 裁判 Agent 的**否决权**

这是 CC 最精巧的对抗设计，也是 TCUM 完全没有的：

```
模型输出完成
  ↓
执行 Stop / SubagentStop 钩子（所有匹配钩子并行）
  ↓
如果有 blockingError → 将错误消息注入模型，模型继续推理
如果 preventContinuation → 终止推理循环
```

- `agent` 类型的 Stop 钩子会**启动一个独立的 Agent 子会话来验证"能不能停"**（`execAgentHook`：新 agentId、过滤掉不允许的工具、追加 `structuredOutputTool`）；
- 裁判说不行 → `blockingError` **被注入回主模型，主模型必须继续干**（前提③：判决可执行）；
- 还有更轻量的 **函数钩子（Function Hook）** 版本：

```typescript
addFunctionHook(setAppState, sessionId, 'Stop', '',
  (messages) => hasSuccessfulToolCall(messages, 'StructuredOutput'),
  'You MUST call the StructuredOutput tool to complete this request.')
```

即：Stop 时检查历史里有没有成功调用指定工具，没有就注入错误**强制模型继续**，直到满足条件。

> **这就是"完成定义"（Definition of Done）的可执行化**：不是让模型自己判断"我做完了吗"，而是由外部条件判定，判定不通过就不允许结束。

### ⑥ LLM 审 LLM：YOLO 权限分类器的两阶段对抗

`classifyYoloAction` 用一个模型审查另一个模型将要执行的命令，设计上处处体现"对抗预算分配"：

**第一阶段（Fast）**：精简提示 + 附加 `"Err on the side of blocking. <block> immediately."` + `max_tokens=64` + `stop_sequences=['</block>']`。**判定"允许"就快速通过；判定"阻止"或无法解析，才升级。**

**第二阶段（Thinking）**：完整提示 + `"Review the classification process and follow it carefully..."` + `max_tokens=4096` + 允许 CoT，解析 `<thinking>`与 `<block>yes/no</block>`。

三个可讲的点：
1. **不对称的错误代价被显式编码进 prompt**："宁可误杀"（`Err on the side of blocking`）——因为漏放一个 `rm -rf` 的代价远大于误拦一次；
2. **两阶段是成本优化而非能力提升**：绝大多数命令在64 token 内就能放行，只有可疑的才花 4096 token 做 CoT；
3. **系统提示与 CLAUDE.md 打`cache_control`**（1 小时 TTL），让高频分类调用复用 prompt cache。

### ⑦（补充）对抗性输入的确定性防御

严格说这属于安全而非多 Agent，但它是"对抗思维"最彻底的体现，值得一起讲：

- **不用正则解析 Shell，改用 AST**：因为 `cd src&& python3 hello.py` 这类输入正则不可靠；
- **`validateObfuscatedFlags`**：检测通过 shell 引号机制隐藏危险标志位，如 `find . -name '*.tmp' "-exec" rm {} \;`（把 `-exec` 藏进引号）、`jq $'-f' evil_script`（ANSI-C 引号编码）；
- **解析器超时即判敌**：`PARSE_ABORTED → 'too-complex, reason: Parser aborted — possible adversarial input'`，保守拒绝；
- **构建性证明思想**：不试图证明"不存在攻击"，而是证明"这条命令等价于这组 argv"——**不需要知道所有攻击手段，只需要确保完整理解了命令结构**；
- **权限聚合不变量**：`deny > ask > allow`，且**钩子的 `allow` 不能绕过 settings.json 的 deny/ask** —— 防止"裁判被说服"；
- 源码大量安全注释引用 **HackerOne 报告编号** —— 安全代码是攻防对抗中演化出来的，不是设计出来的。

## 1.3 TCUM-AI 的对抗现状：有雏形，没有体系

诚实盘点，**TCUM 有 5 处真实的对抗/自检机制，但全部集中在"单Agent 内的确定性校验"，一个"独立审查 Agent"都没有**：

| # | TCUM 已有 | 位置 | 对应哪个前提 | 评价 |
|---|---|---|---|---|
| 1 | **阈值推荐的置信度降档 + 结构化解释** | `tplthreshold/confidence.go` | ②③部分 | ⭐**最强的一处，甚至超过 CC**：`scoreConfidence` 按 warnings（样本不足 / `std=0` / drift 过大 / `unexpected scale` / **门控失败（用了未过滤序列）** / `ConsistencyChecker` 未能完全修正冲突）**逐条降档** high→medium→low；`Explanation.Details` 分`feature/prior/heuristic/gate/unit/consistency/provider` 七类结构化解释；`buildOverallSummary` 直接告诉用户"其中 N 个置信度较低，**建议重点确认**" |
| 2 | **PromQL/InfluxQL 生成 → 执行验证 → 修正闭环** | `prometheus_promql_expert` / `barad_influxql_expert` | ② | 把"验证工具"交给模型，让语法/语义错误被**真实执行**打回。这是"独立证据来源"的正确用法 |
| 3 | **工具错误转文本 + 行动指引** | `tool_error_handler_middleware.go` | ③弱 | 错误变成 `[TOOL_ERROR]` + 三条指引（改参数重试 / 临时错误重试一次 / 连续失败 2 次换工具），让模型自纠而非中断 |
| 4 | **幻觉工具兜底** | `UnknownToolsHandler` | ③弱 | 返回 `"unknown tool: %s"` 而非 error，模型可自我纠正 |
| 5 | **压缩后fail-fast 自查** | `adaptive_context_retry.go` | ② | 压缩完本地重算token，不达标**就不发请求** —— 一种"确定性自我验证" |
| 6 | **权限落在"工具存在与否"** | `dynamic_task_tool_middleware.go`等 | ①② | 与 CC 的 `disallowedTools` 同哲学：未授权子 Agent 不在 map 里，prompt 注入也调不到；非 admin 分身过滤 `ExecuteSQL` 等 5 个高危工具；`filteredSkillBackend` allowlist + 拒绝审计日志 |

**明确缺失的**（面试要主动列，这比被问出来好）：

| 缺失 | 严重度 | 说明 |
|---|---|---|
| **无 Verification/Critic Agent** | 🔴 P0 | 15 个生产 Agent 里**没有一个的职责是"审查另一个 Agent 的产出"**。`rules_analysis_agent` 的 Chain 里虽有两段ChatModel，但第二段是**总结**（`summarySystemPrompt`）不是校验 |
| **无"完成定义"的可执行判定** | 🔴 P0 | eino 的 `AfterModelRewriteState` 扩展点是 **0 实现**（`eino扩展点全景清单.md` 已标注）——而这正是 CC `Stop hook` 的等价位置。所以 TCUM **无法阻止一次不合格的收尾**：模型说完就完了 |
| **无 LLM 审 LLM 的高危动作拦截** | 🔴 P0 | `skill_exec` 沙箱里是**自由 bash/python**，没有 YOLO 分类器等价物、没有 AST 解析、没有危险模式检测 |
| **无角色隔离的只读子 Agent** | 🟡 P1 | 没有 `Explore`/`Plan` 等价物；子 Agent 拿的是完整工具集，"分析型"与"变更型"能力未分离 |
| **无反惰性委派约束** | 🟡 P1 | `task` 工具的 description 未强制"派发必须自包含 + 给出具体对象"，也未注入"严禁再生成子 Agent" |
| **置信度只存在于一个垂直场景** | 🟡 P1 | `tplthreshold` 的 confidence 机制**没有上升为平台能力**，告警诊断/根因分析/变更影响这些更需要标注不确定性的场景全都没有 |

## 1.4 给 TCUM 的启示（按 ROI 排序，都给具体落点）

### 启示 1（P0，最高 ROI）：把 `AfterModelRewriteState` 用起来做"输出守门人"

**这是一个已经存在、链路完整、但 0 实现的扩展点**——等价于 CC 的 Stop hook。最小实现（无需LLM，纯确定性）：

```go
// pkg/agent/output_guard_middleware.go（新增）
func (h *outputGuard) AfterModelRewriteState(ctx, state *adk.ChatModelAgentState, mc *adk.ModelContext) (...) {
    last := state.Messages[len(state.Messages)-1]
    if last.Role != schema.Assistant || len(last.ToolCalls) > 0 { return }  // 只管最终回答

    var violations []string
    // ① 数字断言必须有工具来源：出现百分比/阈值但本轮没有任何 tool 消息
    if hasNumericClaim(last.Content) && !hasToolEvidence(state.Messages) {
        violations = append(violations, "回答中包含具体数值但本次会话未调用任何数据查询工具，请先取数再结论")
    }
    // ② 实体引用格式校验：声明了 entitylink 的 Agent，输出里的实体必须用 entity:// 语法
    // ③ 关键字段缺失：告警诊断类必须包含"影响面/根因/建议"三段
    // ④ 幻觉指标名：把输出里的指标名与本轮工具返回过的指标名做集合校验

    if len(violations) > 0 {
        // 注入一条 user 消息强制模型重做 —— 等价于 CC 的 blockingError
        state.Messages = append(state.Messages, schema.UserMessage(
            "[OUTPUT_GUARD] 你的回答未满足完成标准：\n- " + strings.Join(violations, "\n- ") +
            "\n请修正后重新给出最终回答。"))
    }
}
```

**成本**：一个中间件文件 + 注册进 `ChatModelAgentMiddlewareManager`（已有注册表，配置里加个字符串名即可）。
**收益**：把"完成定义"从"模型自觉"变成"平台强制"，且**零 LLM 成本**。这是 TCUM 当前最缺、最容易补、最容易讲的一块。

> ⚠️ 实现注意：必须**限制重做轮次**（如最多 1 次），否则会与 `MaxStep` 相互作用形成死循环；且要跳过 `interrupt` 场景。

### 启示 2（P0）：给"可自动验证"的场景配Verifier Agent

TCUM 有一个 CC 没有的优势：**运维域的很多产出是可以被程序判定的**。这正是 Verifier 最容易落地的地方：

| 场景 | Verifier 的"独立证据来源" | 判决 |
|---|---|---|
| PromQL/InfluxQL 生成 | **真实执行**（已有工具）+ 结果非空 + 时间范围合理 + label 存在性 | PASS / FAIL / PARTIAL |
| Grafana看板 JSON | **JSON Schema 校验 + Grafana 试渲染 API + panel 数量/datasource 引用检查** | 同上 |
| 天巡巡检项 | 在样本集群上**试跑**，比对期望| 同上 |
| 阈值推荐 | 已有 `confidence` + `ConsistencyChecker`，**再加一步"用历史数据回放：这个阈值在过去 7 天会产生多少次告警"** | 同上 |
| 告警诊断结论 | 弱可验证：至少校验"引用的每个指标/变更单号在工具返回里真实存在" | PARTIAL 为主 |

**关键是照抄 CC 的三个前提**：Verifier 用**独立 Agent**（不是同一个 Agent 加一步）、**必须调工具拿外部证据**（不许只读文本判断）、**判决进入流程**（FAIL 时把失败原因回注让主 Agent 重做，而不是附在报告末尾）。

**先做哪个**：Grafana 看板（判定最确定、最容易做，且当前正是幻觉高发区）。

### 启示 3（P0）：`skill_exec` 沙箱要补"动作分类器"

当前沙箱里是自由 bash/python，而Agent 已经从"只读分析"走到"配置生成 + 无人值守执行"。照抄 CC 的**两阶段 + 不对称代价**：

- **第一阶段（零 LLM）**：确定性规则先过——命令 AST 解析（Go 可使用 `mvdan.cc/sh`）+ 危险模式规则（递归删除、`curl | sh`、写系统目录、访问云元数据地址或企业内网网段）+ 引号和编码混淆检测；具体网段从安全策略配置加载，不写死在面试文档中；
- **第二阶段（LLM，仅可疑时）**：精简 prompt + `max_tokens=64` + 附加"宁可拦截"；
- **解析失败即拒绝**（`possible adversarial input`），不要"看不懂就放过"；
- 结合已有的 `ExecutionContext`（`Executor`/`Authorizer` 双主体已经在 ctx 里了）做**分身/用户维度的分级策略**。

### 启示 4（P1）：把 `confidence` 从一个垂直场景升为平台能力

`tplthreshold` 的做法完全可以泛化成一个 `pkg/confidence` 包：

```go
type Assessment struct {
    Level    string          // high | medium | low
    Warnings []string        // 触发降档的原因
    Details  []Explanation   // feature/prior/heuristic/gate/unit/consistency/provider
    Summary  string          // 面向用户的一句话
}
```

**降档信号在运维域到处都有**：数据采样截断（`AggregateDialogStats.sampled=true` 已经在做提示了）、查询时间窗过短、指标序列数为 0、工具重试过、走了兜底路径、上下文被极限档压缩过（**这条尤其重要：被极限档压缩过的会话，其结论置信度必然下降，而当前完全没有告知用户**）。

**讲法**：*"我们不追求模型永不出错，而是追求**让系统知道自己什么时候可能错，并显式说出来**。"* 这个立意在运维场景比"我们准确率 95%" 有说服力得多。

### 启示 5（P1）：角色隔离 —— 拆出"只读分析型"子 Agent

按 CC 的 `EXPLORE_AGENT` 思路，给`task` 委派增加一个只读档：
- 子 Agent 类型分`analysis`（只读工具集 + 更便宜的模型 + 不注入变更类 prompt）与 `action`（完整工具集）；
- 用**工具集裁剪**实现，而不是 prompt 约束（TCUM 的`dynamicTaskTool` 已经有"按权限过滤 subAgents map"的现成机制，扩展成"按档位过滤工具"是同一套代码）；
- 顺带能拿到 CC 那个副作用收益：只读子 Agent 可以用更小的模型 + 省掉大段变更规范 prompt，**成本直接下降**。

### 启示 6（P1）：`task` 工具补"反惰性委派"约束

在 `task` 工具的 description 里明确（这是纯 prompt 改动，成本近零）：
- 派发必须**自包含**：子 Agent 看不到你的对话，必须给全信息（具体集群/实例/指标名/时间范围，而不是"基于上面的发现继续分析"）；
- 给出**反模式 vs 正确**的双示例（CC 的做法，实测比抽象要求有效）；
- 注入"你是被派发的执行者，**不要再派发子任务**"—— TCUM 的Deep Agent 是支持嵌套的，没有这条约束就有递归风险。

# 二、Agent 级 / 用户级自进化

> 记忆专题已重组为独立章节：[《Agent 记忆协同体系：TCUM-AI、Codex、Claude Code、DSH 的实现对读与面试题库》](13-记忆协同体系-四家实现与面试题库.md)。其中按当前源码/官方公开文档重新核验了 TCUM-AI、Codex、Claude Code、DSH 的事实边界，并完整回答 Q1～Q30；本节保留“自进化”视角的历史概览与路线讨论。

## 2.1 先把"自进化"拆成四个可回答的问题

"Agent 会不会越用越好"这个问题太虚，面试要拆成四问：

| 问题 | 本质 |
|---|---|
| **① 学什么** | 什么信息值得沉淀？什么信息不该沉淀？ |
| **② 谁来写** | 人写（用户级）还是 Agent 自己写（Agent 级）？ |
| **③ 怎么用** | 沉淀下来的东西如何在恰当时机被召回、且不撑爆上下文？ |
| **④ 怎么退化** | 错的、过时的、没人用的知识怎么淘汰？—— **绝大多数系统死在这一问** |

CC 对四问都有明确答案，这也是它这块值得抄的原因。

## 2.2 CC 的 Agent 级自进化：Memory 系统

### ① 学什么：闭合的四类分类学+ 一条极关键的排除原则

```
user用户角色、偏好、知识背景     "用户是数据科学家，专注于可观测性"
feedback   用户对工作方式的反馈         "集成测试必须使用真实数据库"
project    项目目标、里程碑、决策"3月5日起冻结非关键合并"
reference  外部系统的指针              "Linear 项目 INGEST 追踪管道 bug"
```

`parseMemoryType` 严格匹配、无效值优雅降级（返回 `undefined` 而非报错）。

**最值得抄的是排除原则**：

> 代码模式、架构、git 历史等信息是**可推导的**（通过 grep/git/CLAUDE.md 就能获得），**不应该存储为记忆**。只有那些**不可从当前项目状态推导**的信息才值得持久化。

这一条一句话解决了所有记忆系统的头号问题——**记忆膨胀**。记忆不是"日志"，是"无法重新获得的信息"。

### ② 谁来写：`extractMemories` —— 分叉 Agent 自主提取

```
extractMemories:
    // 只在完整查询循环结束时运行（模型给出最终回复、无工具调用）
    memories = scanMemoryFiles(autoMemDir)
    manifest = formatMemoryManifest(memories)
    runForkedAgent({
        system: buildExtractPrompt(manifest),      // 带上已有记忆清单 → 避免重复写
        messages: conversationHistory,
        allowedTools: [FileRead, FileWrite, FileEdit, Grep, Glob]
    })
```

三个设计点：
1. **时机**：只在一轮完整对话结束时跑，不干扰主流程；
2. **分叉 Agent 共享主对话的 prompt cache** —— 它"看到"完整上下文，判断准确，**而成本极低**（这是 CC 反复使用的技巧，Fork 子 Agent 统一用 `'Fork started — processing in background'` 前缀就是为了字节级前缀命中缓存）；
3. **带着已有记忆清单去提取** → 天然去重、天然增量。

> **这是真正的"自进化闭环"**：Agent 自己决定把什么写进长期记忆，而不是由人配置规则。

### ③ 怎么用：LLM 驱动的两阶段检索（没有向量库！）

```
第一阶段  scanMemoryFiles: readdir → 过滤 .md（排除 MEMORY.md）
          → readFileInRange(0, 30行)拿 frontmatter，single-pass 顺带取 mtimeMs
          → 按 mtime 降序取Top 200
第二阶段  sideQuery(Sonnet): system=SELECT_MEMORIES_SYSTEM_PROMPT
          输入= Query + memory manifest("- [type] filename (ISO ts): description")
                + Recently used tools
          max_tokens=256, output_format=json_schema({selected_memories: string[]})
          → validFilenames.has(f) 严格校验，防幻觉文件名
```

四个精妙处：
1. **不用向量库**，用"元信息清单 + LLM 语义选择"—— 对"几百条记忆"这个量级，这比维护 embedding 一致性更省心（也顺带避开了 TCUM 正在踩的 embedding 一致性坑）；
2. **single-pass 优化**：`readFileInRange` 内部 `stat` 顺带拿 `mtimeMs`，比"先 stat 排序再读"少一半系统调用；
3. **工具感知过滤**：正在用某MCP 工具 → **跳过该工具的 API 文档类记忆，但保留"陷阱/已知问题"类** —— *正在用的时候恰好是最需要警告的时候*。这个判断非常人性化；
4. **已展示过滤** `alreadySurfaced`：5 个名额只给新候选，避免每轮重复注入同样的记忆。

### ④ 怎么退化：新鲜度警告 + 双重大小限制

```
memoryFreshnessText(mtimeMs):
    days = floor((now - mtimeMs) / 86400_000)
    if days <= 1: return ''
    return '该记忆已有 {days} 天。记忆是时间点观察，而非实时状态。
            关于代码行为或文件位置的引用可能已过时。
            在将其作为事实断言前，请对照当前代码验证。'
```

- **不是删除，而是给模型"降权提示"** —— 源于真实用户报告：模型把已重命名的函数当作现状引用；
- 索引层 `MEMORY.md` 限 **200 行 + 25KB 双重限制**（源于"有用户创建了单行数百字符的条目"，只限行数拦不住），截断在换行处并附 `WARNING:... Only part was loaded.`；
- 两层存储：`MEMORY.md`（索引，自动进每次系统提示）+ 主题文件（详情，按需加载）+ `logs/2026/03/2026-03-31.md`（KAIROS 追加日志）。

> **"索引常驻 + 详情按需"这个结构，和 TCUM 的 skill 渐进披露是同一个模式**——可以在面试里主动把两者联系起来，显示你抓到的是模式而不是招式。

## 2.3 CC 的用户级自进化：把人的反馈固化成可执行规则

| 载体 | 机制 | 自进化含义 |
|---|---|---|
| **`CLAUDE.md`** | 项目级记忆文件，自动发现并加载 | **人可编辑、进 git、可 review/diff/回滚** —— 知识的演化过程本身被版本化 |
| **26 种 Hook 事件** | `SessionStart → Setup → [UserPromptSubmit → PreToolUse → (PermissionRequest) → 执行 → PostToolUse/PostToolUseFailure → (PermissionDenied) → Stop/StopFailure] → SessionEnd`，外加 `SubagentStart/Stop`、`PreCompact/PostCompact`、`FileChanged`、`TeammateIdle/TaskCreated/TaskCompleted` | 用户把"每次都要提醒 Agent 的事"变成**自动强制**：如 `PreToolUse` 拦截、`PostToolUse` 注入上下文、`Stop` 定义完成标准 |
| **matcher 细粒度路由** | `PreToolUse`→`tool_name`、`SessionStart`→`source`、`FileChanged`→`basename(file_path)`；无 matcher 则全触发 | 规则可精确到"只对 Bash 生效"，降低触发频率与开销 |
| **极简 IPC 协议** | 退出码 + stdin/stdout/stderr传结构化语义；退出码 2 = 阻塞错误；`asyncRewake` 后台执行且退出码 2 时通过通知队列**唤醒模型继续对话** | 任何语言写的脚本都能成为 Agent 的行为规则 |
| **信任门控+ 组织策略** | 用户未接受信任对话框则**所有钩子一律跳过**（源于真实漏洞：`SessionEnd`/`SubagentStop` 曾在拒绝信任后仍执行）；`policySettings.disableAllHooks` 组织级熔断 | **自进化能力必须可被治理** |
| **条件技能激活** | `activatedConditionalSkillNames` 一旦激活会话内始终可用（缓存清理也保留）；技能沿目录树向上发现 | 能力随上下文自动出现 |

**还有一件事值得单独说**：CC 明确把"更深的自进化"留在了**未实现**状态（chapter-16 思考题三）——`autoCompact` 是"原始的元认知"（Agent 意识到自己上下文将尽并主动压缩），`DreamTask` 暗示了空闲反思的可能，但"Agent 反思自己哪些工具调用冗余、哪些权限请求总被拒绝、哪些任务分解低效并据此改进策略"这个闭环**它自己也没做**。

> 面试用这一点收尾很有力：**"连Claude Code 都把行为策略级的自我改进留在思考题里，说明当前工业界的共识边界是'记忆与规则可自进化，策略不可自进化'。所以我们的路线选择也应该是先把记忆闭环和规则固化做扎实，而不是一上来搞'自主优化 prompt'。"**

## 2.4 TCUM-AI 的自进化现状：**表结构全对，闭环全缺**

这是本篇最有价值的一个发现。看 `TwinMemory` 表：

```18:29:usercases/agent_access/po/twin_memory.go
	Key            string     `gorm:"column:key;type:varchar(255);index:idx_key"`
	Content        string     `gorm:"column:content;type:longtext;not null"`
	Source         string     `gorm:"column:source;type:varchar(50);default:'manual'"`
	SourceDialogID int64      `gorm:"column:source_dialog_id;type:bigint;default:0"`
	Confidence     float64    `gorm:"column:confidence;type:decimal(3,2);default:1.00"`
	Enabled        int64      `gorm:"column:enabled;type:tinyint;default:1"`
	HitCount       int64      `gorm:"column:hit_count;type:bigint;default:0"`
	LastHitAt      *time.Time `gorm:"column:last_hit_at;type:datetime(3)"`
	TTL            int64      `gorm:"column:ttl;type:bigint;default:0"`
```

`Source` / `SourceDialogID` / `Confidence` / `HitCount` / `LastHitAt` / `TTL` —— **一个完整自进化闭环所需的字段一个都不缺**。但：

| 字段 | 设计意图 | 代码现状 |
|---|---|---|
| `Source`（默认 `manual`） | 区分人工录入 vs **Agent 自动提取** | 全仓**没有 `Source="auto"` 的写入路径** → 记忆只能人工录|
| `SourceDialogID` | 追溯这条记忆来自哪次会话 | 只在 PO↔PB 转换里出现，**无写入** |
| `Confidence`（默认 1.00） | 置信度衰减/提升 | `CreateTwinMemory` 时 `if Confidence == 0 { = 1.0 }`，**此后永不改变** |
| `HitCount` / `LastHitAt` | 命中统计 →冷门淘汰 | **rerank 命中后没有任何 +1 逻辑**，全仓只有 convert 转换 |
| `TTL` | 过期 | **没有任何清理任务读它** |

**对四问的回答**：

| 问 | TCUM 现状 |
|---|---|
| ① 学什么 | ❌ 无分类学（`category` 字段是自由字符串，无闭合枚举、无排除原则） |
| ② 谁来写 | ❌ 只有人工（`Source`恒为 manual）；`digital_twin_mcp_server.go` 只提供**查记忆**给分身用，不写 |
| ③ 怎么用 | ✅ **这一环做得不错**：候选 ≤50 → 每条截 200 字节 → LLM 语义 Rerank Top-10 → 去重 → 注入 `<memories>`，LLM 失败两处 fallback to recent |
| ④ 怎么退化 | ❌ 全缺：无新鲜度提示、无置信度衰减、无命中统计、无 TTL 清理 |

**另一条更可惜的**：TCUM 已经采集了**高质量的人类反馈信号**却完全不用——`UpsertMessageFeedback(Rating, Tags, Comment)`，聚合出 `LikeCount/DislikeCount/LikeTopTags/DislikeTopTags/AgentStats/Prev*` 环比。但这些数据**唯一的消费者是 `platform_ops_expert` 生成的运营周报**（给人看的PPT 素材），**没有一条回流到 Agent 的 prompt / 记忆 / 路由**。

> 一句可以直接讲的诊断：**"我们把反馈做成了报表，没做成回路。"**

## 2.5 给 TCUM 的启示（分三阶段，全部有现成落点）

### 阶段一（P0，两周内可做完，全是补 UPDATE）：把已有字段接上闭环

1. **`HitCount` / `LastHitAt` 回写**：`rerankMemoriesByLLM` 选中 Top-K 后，异步 `UPDATE hit_count = hit_count+1, last_hit_at = now()`。**这一步的价值是马上产出数据**——没有命中数据，后面所有淘汰策略都是拍脑袋。
2. **注入时带新鲜度提示**（照抄 CC）：`formatMemories` 里对`UpdatedAt` 超过 N 天的记忆追加 *"该记忆已有 X 天，是时间点观察而非实时状态；作为事实断言前请先用工具核实"*。**运维场景比代码场景更需要这条**——集群拓扑、容量、负责人变化远比函数改名频繁。
3. **TTL 清理定时任务**：数字分身已有定时任务框架 + 分布式锁 + 锁续约（`StartStaleTaskRecovery` 那套），复用即可。
4. **`Confidence` 衰减规则（确定性，无 LLM）**：`confidence = f(初始值, 命中率, 存活天数, 是否被用户点踩过)`；低于阈值自动 `Enabled=0` 而非删除（可回溯）。

### 阶段二（P1）：补"谁来写"—— 自动提取

照抄 `extractMemories`，但要用 TCUM 已有的零件：

- **时机**：`MaybeSummarizeAndSave` 已经有"会话结束/满10 条 → 异步 goroutine + 60s 超时"的现成骨架，**记忆提取挂同一个位置**，不需要新框架；
- **输入**：带上该分身已有记忆的 manifest（`category/key/description +更新时间`）→ 天然去重增量；
- **输出**：`Source="auto"`、`SourceDialogID=当前会话`、`Confidence=0.6`（自动提取的初始置信度**低于**人工录入的 1.0，这个不对称很重要）；
- **必须有闭合分类学 + 排除原则**（TCUM 版）：
  - ✅ 该存：用户的口头约定（"我们这边P0 告警只看 5分钟均值"）、租户/业务特有的命名习惯、历史事故结论、用户明确的偏好（"报告不要给建议只列问题"）；
  - ❌ 不该存：**任何能从 CMDB / 监控 / 变更系统重新查到的东西**（实例列表、指标名、当前阈值、拓扑）—— 直接照抄 CC 的"可推导即不存"原则。这一条能挡掉 80% 的记忆膨胀。
- **人审开关**：自动提取的记忆先进 `Enabled=0` 待审队列，分身 owner 在管理页一键采纳/丢弃 —— 既拿到自进化，又不失控。

### 阶段三（P1/P2）：反馈回路 + 用户级规则固化

5. **反馈→记忆**：`Rating=0`（点踩）+ `Tags`/`Comment` 非空的样本，异步跑一个提取器把可泛化的部分写成 `category=feedback` 的记忆（CC 的四类里正好有 `feedback` 这一类）。**这是把"报表"变成"回路"的最短路径**。
6. **反馈→路由**：`AgentStats` 里某Agent 的点踩率持续偏高 → 自动降低它在 supervisor `<子Agent列表>` 里的排序权重（**CSV 里那个 `order` 字段现在是人工兜底路由，正好可以变成"反馈驱动的自动权重"**）。
7. **`AGENTS.md` / `CLAUDE.md` 等价物**：把 Agent prompt 从 DB 迁到 git（`agents/{code}/PROMPT.md`），一次性拿到**版本管理 + review + 回滚 + 变更审计**。这条在第三篇也提过，但放在"自进化"视角下意义更明确：**知识的演化必须可追溯，否则"自进化"和"悄悄变坏"没法区分**。
8. **TCUM 版Hook 体系（P2，想清楚再做）**：TCUM 已经有 4 张注册表（Tool / AgentMiddleware / ChatModelAgentMiddleware / Skill），其中 **`AgentMiddleware` 的 5 个字段全 0 实现、两个服务的注册表都是空 map** —— 链路完整没人用。它就是天然的 Hook 承载点（`BeforeAgent`/`AfterAgent` 等价于 `SessionStart`/`SessionEnd`）。但要照抄 CC 的**信任门控 + 组织策略开关**：允许用户注入规则的同时，平台必须能一键禁用。

### 一条必须坚持的边界

照抄 CC 的克制：**记忆和规则可以自进化，Agent 的行为策略（prompt / 工具集 / 路由）不做自动改写**。理由：
- 运维 Agent 的动作有真实后果，行为策略被自动改写后**无法回滚到"上周那个好用的版本"**；
- 没有评测集的前提下（TCUM 当前 🔴 无任何评测集），任何自动优化都无法判断是变好还是变坏——**自进化的前置条件是可度量**。

> 这条边界本身就是很好的面试回答：*"我认为自进化的前置条件是评测能力。在没有评测集之前，我只会做'记忆闭环 + 反馈固化 + 人审采纳'，不会做'自动改prompt'——因为那是在没有仪表的情况下调发动机。"*

# 三、面试问答话术（可直接背）

**Q：你们做了多智能体对抗吗？**

> *"严格说没有形成体系，只有雏形，我可以说清边界。我们有的是**单 Agent 内的确定性自检**：阈值推荐场景做了 `confidence` 逐条降档（样本不足/门控失败/一致性冲突未修正各降一档）并把'哪几个置信度低、建议重点确认'直接告诉用户；PromQL/InfluxQL 走了'生成→真实执行→修正'闭环，让程序而不是模型判对错；上下文压缩后会本地重算 token，不达标就不发请求。*
>
> *但我们**没有独立的审查 Agent**，也没有'完成定义'的可执行判定——15 个生产 Agent 没有一个的职责是审查别人。对照 Claude Code，它的 `verification` Agent 把目标函数显式逆转成'Try to break it'，强制跑 build/测试/浏览器验证/curl 实测、做对抗性探测、给 PASS/FAIL/PARTIAL 三值判决，而且与写代码的 Agent **利益彻底隔离**；它的Stop hook 甚至能起一个独立 Agent 来判定'能不能结束'，判定不通过就把错误注入回主模型强制继续。*
>
> *我从中提炼的是三个前提：**利益隔离、能力不对称（要有独立证据源）、判决可执行**。我们最该先补的是第二条和第三条——而且我们有个别人没有的优势：运维域很多产出（PromQL、Grafana JSON、巡检项、阈值）**是程序可判定的**，Verifier 的证据来源天然存在。落点也很明确：eino 的 `AfterModelRewriteState` 扩展点我们目前是 0 实现，它正好是 CC Stop hook 的等价位置，补一个纯确定性的输出守门人（数值断言必须有工具证据、实体引用格式校验、关键字段完整性）零LLM 成本就能做。"*

**Q：你们的 Agent 会自我进化吗？**

> *"我会分四问回答：学什么、谁来写、怎么用、怎么退化。我们**第三问做得不错，另外三问基本是空的**。*
>
> *怎么用：分身记忆是候选池 50 条 → 每条截 200 字节降rerank 开销 → LLM 语义 Rerank Top-10 → 去重 → 注入 `<memories>`，LLM 失败两处 fallback。*
>
> *但学什么没有分类学、谁来写只有人工、怎么退化完全没有。最能说明问题的是：`TwinMemory` 表里 `Source`/`SourceDialogID`/`Confidence`/`HitCount`/`LastHitAt`/`TTL` 六个字段**一个不缺**，但全仓没有 `Source="auto"` 的写入、`HitCount` 命中后不+1、`Confidence` 创建后永不变、`TTL` 没有任何清理任务读它。**表结构全对，闭环全缺**。另一条更可惜：我们采集了点赞点踩 + 标签 + 评论，聚合出了环比和 TopTags，但唯一消费者是运营周报——**我们把反馈做成了报表，没做成回路**。*
>
> *Claude Code 这块给我三个直接可抄的东西：一是**'可从当前状态推导的信息不该存为记忆'**这条排除原则，一句话解决记忆膨胀；二是 `extractMemories` 用**分叉 Agent 共享 prompt cache** 在每轮对话结束时自主决定写什么记忆，成本极低；三是**新鲜度警告**——不删旧记忆，而是附上'这条已X 天，是时间点观察不是实时状态，作为事实前请核实'，这在运维场景比代码场景更需要，因为拓扑和容量变得更快。*
>
> *我的落地顺序是先补三个 UPDATE（命中回写、TTL 清理、置信度衰减），因为没有命中数据后面所有淘汰策略都是拍脑袋；再挂自动提取（复用现有的会话摘要异步骨架，自动提取的初始 confidence 给 0.6 低于人工的 1.0，且先进待审队列由owner 采纳）；最后做反馈回路。*
>
> *有一条边界我会坚持：**记忆和规则可以自进化，行为策略（prompt/工具集/路由）不做自动改写**。因为我们目前没有评测集——**自进化的前置条件是可度量**，没有仪表的时候不该去调发动机。顺便说，连Claude Code 自己都把'Agent 反思自己的行为模式并优化策略'留在书末的思考题里，说明这是当前工业界的共识边界。"*

**Q：如果只给你一个季度，这两块你先做什么？**

> *"三件事，按顺序：①`AfterModelRewriteState` 输出守门人（零 LLM、一个文件、马上拦住'没取数就下结论'和实体格式错误）；②Grafana 看板场景的 Verifier Agent（判定最确定，且是当前幻觉高发区，能直接拿到 PASS/FAIL数据）；③`TwinMemory` 三个 UPDATE + 新鲜度提示。*
>
> *这三件的共同点是：**都不需要新框架、都能在两周内看到数据**。而它们产生的数据（守门人拦截率、Verifier 判决分布、记忆命中率）恰好就是我们最缺的东西——**评测集的第一批种子样本**。所以这三件事既是补短板，也是为下一阶段的评测能力铺路。"*
