# 一、项目讲解与"你的贡献"（几乎每场必考）

小红书从 5.9 到 12.10 五个场次里，**每场都以"围绕简历项目问一些常规问题"开场**——业务背景、亮点、贡献、印象最深的技术问题。这是架构师面试的基本盘，也是淘汰率最高的一环："X 淘汰者共性——技术停留表面 / 场景 trivial / 未真正落地"。

## Q1. 请介绍一下你参与度最高的项目（业务架构 + 工程架构 + 亮点 + 挑战 + 个人职责）

**考察意图**：面试官在 3 分钟内判断三件事——① 你是否讲得出**业务价值**（不是"我做了个采集系统"，而是"我把可观测率从 55% 提到 85%"）；② 你的**架构感**（能不能画出坐标系）；③ 你的**Ownership 边界**（哪些是你做的、哪些是团队做的、哪些是走读的）。

**60 秒电梯稿**（用于开场）：

> "我在腾讯云负责统一运维底座 TCUM 的稳定性与 AI 平面，横跨四层：**监控数据面**（infrastore 系列 + VM/CK/XStor 三存储，日峰值 Y 亿数据点）、**元数据面**（Global CMDB，Flink CDC + Kafka 增量协议纳管 100+ 云产品）、**智能决策面**（TCUM-AI Agent，13+ 类 Agent / **51 Skill** / **10 MCP Server**，底模 **TCUM-Qwen3.5-397B-A17B**，覆盖 30 个云产品）、**控制面**（多租户、审批、发布、多地域）。我个人主要负责的是 **X**（此处替换为你真实做的那 1~2 段）。整个项目的核心业务价值是把故障可观测率从 55% 提到 85%，年度主动发现 25 个问题，告警准确率 70%。"

> **数字核验说明**："13+ 类 Agent" 包括静态注册（`cloud_native_expert` / `prometheus_expert` / `ops_expert`）+ 独立初始化（`digital_twin_agent`）+ **请求级动态装配**（`supervisor` 每次请求 `ListAgents(Enabled=1)` 现场组子 Agent，见 `usercases/agent_access/service/agent_service.go:112`）+ 数字分身若干。**面试时被追问细节要能讲清'静态 / 动态 / 数字分身'三种形态**，见本文 Q7 深度部分。

**架构师深度**：

小红书这个层级的面试官（尤其二三面）不会满足于业务描述，他一定追问的三条链：

1. **业务架构 vs 工程架构的区别**——很多人混着讲。业务架构是"客户从哪儿来、我为客户产出什么价值、上下游是谁"；工程架构是"进程/服务/数据流/存储的物理拓扑"。**要分开画两张图**：
   - 业务架构：`云产品接入 → SLI 计算 → SLO 视图 → 告警/工单 → 故障复盘`
   - 工程架构：`Agent 采集 → Kafka → infrastore-metric-filter → XStor/VM/CK → Grafana`
2. **亮点必须是"可迁移的方法论"，不是功能列表**。反面例子："我们做了拓扑图"。正面例子："我们把'什么是资源关系'从代码硬编码解耦到元模型，一个新云产品接入周期从周级降到小时级"——**方法论是"元模型驱动"，可迁移到小红书的任何中台**。
3. **贡献要按"层"讲**，不要按"任务"讲。四层贡献模板：
   - **协议/契约层**：我定义了 `SyncMessage` 统一增量协议（[proto 定义](/Users/yaao/Documents/code/tcum-cmdb-global/service/kafka/kafkapb/common_incr_sync_message.proto)），把 N 套异构 CMDB 收敛成 1 套；
   - **机制/实现层**：我在消费侧实现了 event_time 版本条件更新 + 唯一键提取（单键 / 组合键均覆盖测试）；
   - **治理层**：我推动了未知字段处理策略、毒消息隔离和数据新鲜度 SLO；
   - **运营层**：一致性延迟从小时级降到分钟级，成为客户可用性数据的基线。

## Q2. 项目里最印象深刻的技术问题是什么？怎么解决的？

**考察意图**：这题不是要听故事，而是判断你**遇到复杂问题时的方法论**——发现 → 定位 → 决策 → 验证 → 沉淀。5.13 场次专门单独列了这一题。

**60 秒电梯稿**（三选一，按岗位挑）：

**版本 A · 一致性版**（适合中台岗）：
> "最印象深刻的是 CMDB 增量同步的**乱序问题**。多数据源通过 Kafka 发增量消息，网络抖动或 producer 重启会导致同一资源的更新乱序到达 consumer——旧状态覆盖了新状态。我们最终用 `event_time` 作为版本号，在 DB update 时加 `WHERE event_time > current_event_time` 的条件写。它解决了 90% 的乱序，但我主动向你说明它**不能解决的三类边界**：① 时钟漂移；② 同一时间戳冲突；③ 跨资源事务。所以我们还叠了 `cmdb-check` 主动巡检做兜底。"

**版本 B · 上下文/AI 版**（适合 AI 岗）：
> "最深刻的是 Agent 上下文爆炸。运维场景一个工具返回可能是几 MB 时序 JSON，多轮又要累积 20+ 轮。我们最后做了**七层压缩**，核心洞察是——**能在便宜的层解决，就不要升级到贵的层**。L0~L2 是零 LLM 的表示层/结构层压缩（`compact_table` 列存、64KB 阈值截断 + COS 卸载、只针对 `operations-analysis` skill 的精简版替换），L3/L5/L6 才是花 LLM 的语义摘要（summarization / period 分层 / 场景化裁剪），L4 是最关键的**兜底层**——`AdaptiveContextRetry` 拦截 `Model.Generate` 返回的 `ContextWindowExceededError`，用**目标预算驱动的 T1→T5 递进压缩 + 极限档 fallback**（不是简单的 A/B/C/D 硬分档，而是从错误消息 parse 出真实 `(currentTokens, maxTokens)`、算出要节省多少 token、按'最胖 + 密度最低'优先压）。这个七层设计让我们在 TCUM-Qwen3.5-397B（128K context）下跑长排障对话时端到端成功率能上到我们的目标 SLO。我可以展开讲每一层的取舍，以及为什么 summarization 自己也要用同款 `adaptiveContextModel` wrapper 兜底（它自己也会撑爆）。"

**版本 C · 稳定性版**（适合基础架构岗）：
> "最深刻的是**告警风暴**。一次配置错误导致 30 分钟内 10w+ 条告警，把下游企微网关打挂。我做的关键决策是**在 Alert Controller 前置租户级 + 规则级双维限流**，并且限流态和阻塞态分离：命中限流阈值后进入 blocked 状态并维持 windowSize 时长，避免边界抖动。代码在 [alert_rate_limiter.go](/Users/yaao/Documents/code/tcum-yunshao-global/bootstrap/webserver/middleware/alert_rate_limiter.go)。这题的难点不是限流算法本身，而是**配置热变更时如何优雅重置**——我的实现是配置变化时清空规则表并同步删除指标，避免脏数据。"

**架构师深度**（三点通用心法）：

1. **别只讲"我解决了什么"，要讲"我识别到什么问题背后的模式"**。乱序问题的模式是"分布式系统里事件顺序 ≠ 时间戳顺序"，方法是"用向量时钟或全局单调递增版本收敛"；告警风暴的模式是"高扇出场景任何一次故障都是雪崩"，方法是"下游限流 + 上游反压"。**把具体问题抽象成模式，才配架构师这个 title**。
2. **主动暴露方案的边界**。"我做了 X，它解决了 A，但不能解决 B 和 C"——这个句式本身就能筛掉 80% 的候选人。因为面试官最怕的是"上线后才发现方案不 work"的人。
3. **给出验证方式**。方案好不好，看的是"你怎么证明它 work 的"。event_time 方案的验证是"冲突跳过率指标"；限流方案的验证是"下游企微网关 QPS 平滑"。**没有验证的架构决策都是拍脑袋**。

**项目锚点**：见 [项目驱动追问题库.md](../../00-导航与策略/项目驱动追问题库.md) Q8"仅靠 event_time 版本比较，哪些异常仍然解决不了"。

# 二、一致性、切流与迁移（12.10 二面重灾区）

12.10 二面明确问了三题：**跨系统一致性、迁移切流、中台如何支撑定制化**。这类题几乎是所有中台岗的必考。

## Q3. 中台怎么看待"定制化的业务诉求"？怎么支撑？

**考察意图**：这是**中台架构师的核心哲学题**。中台的天敌就是定制化——每个业务方都要"给我加个字段"，最后中台变成"看起来通用、其实一堆 if-else 的破布娃娃"。面试官在看你**有没有中台治理的产品 sense**。

**60 秒电梯稿**：

> "我把定制化诉求分成三档处理——**元数据层可扩展 / 插件层可注入 / Fork 层被拒绝**。第一档是 90% 的诉求：加字段、改关系、变展示——我们通过**元模型**（模型组/模型/字段/关系四级）让业务方自助配置，不改中台代码。第二档是 8%：业务方要在标准流程里插一段自己的逻辑——我们通过 **SPI/中间件/Skill** 提供插件点，中台只定义契约。第三档是 2%：真正需要 fork 分支的场景——我们**拒绝**，让业务方走上层业务系统，中台不为个例买单。这个策略让我们纳管了 100+ 云产品，同时保持核心代码可维护。"

**架构师深度**：

1. **中台的边界是"元模型 vs 业务规则"**。可迁移到小红书的方法论：任何一个"业务方要求"，先问一句"这是元数据问题还是业务规则问题？"——加字段是元数据，改工作流是业务规则。**元数据层做通用抽象，业务规则层做插件承载**。
2. **拒绝也是能力，不是缺陷**。真正的中台架构师会说"这个诉求不该在中台做，你应该在业务层做"，而不是全盘接单。TCUM CMDB 的 Flink CDC 和 SPI 就是典型：数据源位置（DIRECT_DB / REGION_DB）和同步方式（DIRECT / FLINK_CDC）**正交建模**，业务方组合出四种形态，中台不新增代码（[flink_cdc_entity.go](/Users/yaao/Documents/code/tcum-cmdb-global/service/dao/entity/custom_model_entity/flink_cdc_entity.go)）。
3. **可迁移的判断标准**：一个"定制化诉求"的复用度 ≥ 3 个业务方就应该沉淀到中台元数据；<3 就该在业务层做；正好 =3 时看趋势——**避免"一个客户一个特性"的陷阱**。

- 元模型驱动接入：[cmdb/02-机制篇-数据接入演进史.md](../../01-项目专题/01-CMDB/01-机制原理/02-机制篇-数据接入演进史.md) 的"接入周期从周级到小时级"；

## Q4. 跨系统一致性怎么保证？

**考察意图**：这是**分布式系统的核心题**。面试官不是要听"强一致 / 最终一致"的定义，他要听你**在真实项目里做过哪些一致性取舍**。

**60 秒电梯稿**：

> "跨系统一致性我从来不做'强一致'承诺——**分布式系统里凡是宣称强一致的中台，多半在骗自己**。我的三段式策略是：① **协议层收敛**——所有增量走同一份 `SyncMessage` 契约，带 `event_time` 版本号，consumer 侧做条件更新；② **补偿层兜底**——`cmdb-check` 做定期主动巡检，发现不一致触发补偿；③ **可见性 SLO**——把'资源变更到最终可见'的 P99 延迟当成中台的核心 SLI 来监控。这样我可以承诺'最终一致 + 分钟级新鲜度'，而不是空口说强一致。"

**架构师深度**：

1. **一致性不是二元的，是一个"承诺谱系"**：`强一致 → 顺序一致 → 因果一致 → 会话一致 → 最终一致`。**架构师的价值在于选对哪一档**：
   - 支付类：必须强一致，用 2PC/TCC/Saga；
   - 元数据类：最终一致 + 可见性 SLO 足够；
   - 缓存类：可以弱到"读己之写"甚至最终一致。
2. **主动暴露自家的"伪双写"**。TCUM 的 XStor/VM 是"顺序双写"——**同一个 worker 先写 XStor 再写 VM，任一失败没有事务性回滚**（[monitoring/08-36问-一致性告警与运营.md](../../01-项目专题/02-监控可观测/03-项目题库/08-36问-一致性告警与运营.md) 已经坦白）。这不是强一致，是"配置门控的顺序双写"。**能主动说出这个短板反而加分**——比"我们全强一致"可信 10 倍。
3. **一致性的三个成本维度**：延迟、可用性、复杂度。**CAP 不是选择题，是滑块**。架构师要能说清"我为了这个业务多降了多少延迟、多担了多少复杂度"。

**可迁移方法论**（小红书场景）：
- 用户内容双写 MySQL + ES：一定是最终一致，用 binlog + Canal + 补偿；
- 计数中台（一面系统设计题原题）：一定是最终一致 + Redis + 异步落 DB，宁可短暂不一致也要抗流量；
- 交易类：必须 Saga 或 TCC，不能靠最终一致。

**项目锚点**：
- 双写坦白：[monitoring/09-短板矩阵与自曝清单.md](../../01-项目专题/02-监控可观测/04-复盘与表达/09-短板矩阵与自曝清单.md)；
- event_time 条件更新：[项目驱动追问题库.md](../../00-导航与策略/项目驱动追问题库.md) Q8。

## Q5. 迁移切流项目怎么保障整体切流不出问题？

**考察意图**：这是**大公司必考题**——因为大公司几乎所有系统都在做迁移。面试官在看你有没有做过**真正带风险的切流**，而不是"新系统上线不算切流"。

**60 秒电梯稿**：

> "切流不出问题的关键是——**任何一步都能回滚**。我用的是'双轨并行 → 影子读 → 灰度写 → 全量切 → 反向兜底'五步法：① 新老系统双写双读并行，用旁路对账发现不一致；② 影子模式：读新系统结果只做校验不返回给用户；③ 按维度灰度写（region、租户、单元测试租户），每级观察 24 小时以上；④ 全量切换后老系统仍保留 30 天作为反向兜底；⑤ 每一步都有明确的回滚 SOP 和自动回滚触发条件（错误率、延迟、对账失败率）。核心心法是'**灰度粒度要小于灾难粒度**'——如果 1 个 region 切炸能全网救回来，那就一次切 1 个 region。"

**架构师深度**：

1. **切流失败的三大根因**：① **数据不完整**——老系统有的数据新系统没有；② **语义不一致**——同一个字段在新老系统含义不同；③ **依赖未收敛**——第三方还在调老系统。**每一条都要独立的检测手段**。
2. **对账是切流的生命线**。TCUM CMDB 的 `cmdb-check` 就是这个角色——切流期间对账频率提到分钟级，正常态降到小时级。**对账不是切完再做，是切之前就要做**。
3. **回滚触发条件必须"可编码"**，不能靠"运维觉得不对"。示例：`错误率 > 3× 基线 持续 5 分钟` 或 `P99 延迟 > 2× 基线 持续 10 分钟` 或 `对账不一致率 > 0.1%`——**代码里定义、自动触发**，不能人肉判断。
4. **反向兜底期至少 30 天**。因为你不知道多久后才会有一个"跨月对账才发现问题"的场景。

**可迁移方法论**（小红书场景）：
- 从 MySQL 迁 TiDB / OceanBase：双写 + Canal 增量 + T+1 全量对账 + 分表灰度；
- 从自研 RPC 迁 gRPC：Sidecar 双协议 + 影子请求对账 + 按接口灰度；
- 从 Redis 迁 Redis Cluster：双写 + 一致性 hash 迁移工具 + 读流量按 slot 灰度。

## Q6. 系统设计——设计一个计数中台

**考察意图**：**计数中台是分布式系统的"HelloWorld"**——它同时考察：读写分离、缓存一致性、防超卖、限流、幂等、监控、故障域隔离。面试官在 40 分钟里想看你**能不能像架构师一样打组合拳**。

**架构师视角的完整解法**（可套小红书场景：笔记点赞数、评论数、粉丝数）：

### 需求拆解（架构师必做的第一步）

**先反问面试官三个问题**（这是加分项，不是拖延）：
1. **读写比**？点赞是 100:1 读写比，粉丝数可能是 1000:1，直播打赏可能是 1:1；
2. **一致性要求**？点赞可以最终一致，但"我给博主打赏 100 元的到账数"必须准确；
3. **单点计数的量级**？王一博粉丝数 vs 小 V 粉丝数完全是两个系统。

### 分层架构

```
接入层：SDK / 网关（幂等 token、限流、租户隔离）
   ↓
计算层：Redis 集群（原子 INCR，热点分片）
   ↓                    ↓
持久化层：Kafka          实时读接口
   ↓
落库层：Flink 聚合 → MySQL 分库分表
   ↓
对账层：T+1 全量对账 + 分钟级增量对账
```

### 核心设计点

1. **幂等**：每次计数带 `request_id`，Redis SETNX 兜底 30 分钟，防止网络重试导致重复计数；
2. **热点打散**：单个 counter_id 拆成 16/64/256 个 slot（视热度），读时聚合。**动态热点识别**：用滑动窗口统计 QPS，超阈值自动升级 slot 数；
3. **写后读一致性**：写操作后返回 `latest_value` 直接从 Redis 读，避免"点赞后刷新还是旧数字"；
4. **持久化异步化**：Redis 是事实来源，Kafka + Flink 异步落 MySQL，MySQL 挂了不影响读写；
5. **反作弊挂载点**：在 Redis 前置一个规则层，识别刷量行为（同 IP/设备频次、时间分布），命中后写入影子计数器而不是主计数器；
6. **对账**：Kafka 消息数 vs Redis 增量 vs MySQL 增量三方对账，任一维度偏差 > 0.01% 报警。

### 演进路径（架构师视角必答）

- **阶段 1**（QPS < 1w）：单 Redis + 定时落 MySQL 足够；
- **阶段 2**（QPS 1w~10w）：Redis Cluster + Kafka 异步 + Flink 聚合；
- **阶段 3**（QPS > 10w，出现明星热点）：热点动态识别 + slot 打散 + 边缘缓存；
- **阶段 4**（跨地域）：多活写入 + CRDT 计数器（G-Counter）解决冲突。

### 主动暴露的风险

1. **Redis 集群脑裂时 INCR 可能丢失**——需要 AOF everysec + 主从半同步；
2. **热点计数迁移时窗口**——slot 数变化时需要"双读 + 单写 + 迁移完切读"，参考 Redis 渐进式 rehash；
3. **反作弊规则如何在线更新**——参考告警规则的热更新，不能重启服务。

**项目锚点**：
- 限流实现（可复用到接入层）：[alert_rate_limiter.go](/Users/yaao/Documents/code/tcum-yunshao-global/bootstrap/webserver/middleware/alert_rate_limiter.go)；
- 滑动窗口完整设计：[场景设计/分布式滑动窗口限流系统.md](../01-系统设计/分布式滑动窗口限流系统.md)；

## Q7. 系统设计——运动 App 的 Agent（异常检测 + 用户理解 + 运动评价）

**考察意图**：这题是**Agent 岗最有区分度的题**——它同时考察：Agent 架构、上下文管理、长期记忆、工具体系、评测、产品 sense。二面明确说"越聪明越好"，说明面试官在看你的**产品想象力**。

**架构师视角的完整设计**：

### 需求解构（先反问）

1. "打卡状态异常"是什么？是"用户 3 天没打卡"这种规则型，还是"用户今天心率异常但仍打卡"这种模式型？
2. "了解用户"到什么粒度？画像标签级还是叙事式记忆？
3. "评价运动表现"给谁看？给用户看要鼓励向，给教练看要专业向。

### 分层 Agent 架构（严格对标 TCUM-AI 的 Deep 模式 + Supervisor 动态装配）

这不是空想架构——**每一个组件我都能指到 TCUM-AI 的代码位置**：

```
                    ┌── Supervisor Agent (请求级动态装配)
                    │   → 每次请求 ListAgents(Enabled=1)
                    │   → 造 AGUI/A2A 双协议远程壳
                    │   → 子 Agent 描述拼进 <子Agent列表> prompt
     ┌──────────────┼──────────────┬──────────────┐
     ↓              ↓              ↓              ↓
  异常检测       用户画像        运动评价       数字分身
  Agent          Agent          Agent          Agent
  (静态)         (静态)         (静态)         (动态人格)
     │              │              │              │
     └──── 统一走 BuildDeepAgent ────┘
          （即使无子 Agent，也强制走 Deep 模式
            以保证中间件链一致——ToolErrorHandler、
            Skill、Summarization、AdaptiveContextRetry、
            TwinSoul、DynamicMcp、DynamicKb 全部装齐）
     ↓
  ── MCP 工具层（Provider）──
  ├─ 静态注册：{ServerName}_{ToolName}（下划线）
  └─ 动态注入：{ServerName}.{ToolName}（点号）
     ├─ DynamicMcpMiddleware：BeforeAgent 拉取分身 McpConfig
     ├─ 每次新建 client（TCUM_TOKEN JWT TTL 30min 强制保鲜）
     └─ 支持 streamable-http（默认）/ SSE 两种 transport
     ↓
  ── Skill 层（声明式 Prompt + 沙箱执行）──
  ├─ private / public 双产物（Bearer token 隔离）
  ├─ SKILL.md 语义化描述 + mcporter 调用规范
  ├─ skill_content_compactor：长 SKILL.md 用精简版
  └─ skill_exec_sandbox：沙箱执行 mcporter call
     ↓
  ── 数据层 ──
  ├─ 实时：Kafka（打卡事件流）
  ├─ 时序：VM/InfluxDB（心率、步数、GPS 轨迹）
  ├─ 关系：MySQL（用户档案、社交关系）
  └─ 向量：Milvus/COS（长期记忆语义检索 + 大结果卸载）
```

### 三个核心机制（这才是"聪明"的地方）

1. **异常检测 = 规则 + LLM 双通道**：
   - **规则通道**：连续 N 天未打卡、心率 > 基线 2σ、配速突降 → 触发第一层告警；对标 TCUM 的 vmalert 规则评估路径；
   - **LLM 通道**：把用户近 7 天数据 + 历史模式喂给 LLM，让它判断"是否异常"——**LLM 能识别规则识别不到的组合模式**（例如"这周训练量下降 + 睡眠差 + 心率高 = 疑似过度训练综合征"）；对标 TCUM 的 `prometheus_alert_diagnose_expert` Agent，能诊断规则告警背后的根因；
   - 两个通道结果不一致时优先 LLM，但记录人工反馈用于评测。

2. **用户理解 = 三层记忆**（对标 TCUM-AI 的实际记忆分层实现，不是空想）：
   - **短期（session context）**：走 eino ADK 的推理循环 + `AdaptiveContextRetry` 兜底——工具结果超 64KB 走 `middleware_truncator` 结构化截断 + COS 卸载，多轮累积超阈值走 `summarization` 主动摘要；
   - **中期（会话级摘要）**：每次对话结束调用 `BuildSummarizationHandler`，摘要格式硬编码要求"聚合 COS_URL 清单"，让下一次对话仍能驱动沙箱脚本重新分析历史大结果；
   - **长期（跨对话记忆）**：数字分身的 `Soul` 字段（`twin_soul_middleware.go`）+ 关联知识库（`KBRef.Type = internal / external_mcp`）+ 用户绑定的 `EnvVars`——**这套完整的"人格 + 知识 + 环境"三元组，就是运动 App 的"我的教练"雏形**；
   - **记忆更新触发条件**：训练模式变化 > 阈值 / 用户主动纠正 / 定期总结（对应 TCUM 数字分身的 admin 更新流程）。

3. **运动评价 = 多维度 + 对照组 + 叙事化 + 精简 SKILL**：
   - 维度：训练量、强度、多样性、恢复；
   - 对照组：自己的历史、同龄同性别人群、目标训练计划；
   - 叙事化：不是给"训练量 78 分"，而是给"这周你的长距离配速稳步提升，但力量训练缺席，建议下周加两次核心训练"——**这是产品 sense**；
   - **工程细节**：这类结构化报告在 TCUM 里就是通过 **Skill** 承载的——`operations-analysis` skill 的完整 SKILL.md 太大会撑爆每轮 context，所以有个专门的 `compactSkillContentForLLM(name, content)` 精简替换：**BaseDirectory 保留完整目录供 skill_exec 沙箱使用，只有喂给主推理模型的文本走精简版**。同样的思路可以用在运动评价——"训练评价指标定义"这种 3000 字的规则文档不需要每轮都塞进 context。

### 主动暴露的工程挑战（架构师加分项）

1. **幻觉风险**：LLM 可能编造用户"上周跑了 30km"——**三道防线**：
   - `ToolErrorHandler` 把工具错误转为模型可见的正常结果（`buildToolErrorResult`）但**不透传 `interrupt/rerun` 错误**（HITL 依赖）和 `context.Canceled/DeadlineExceeded`（会话已终止），避免过度兜底；
   - Function Calling 强制 grounding，评价 Agent 必须引用工具返回的原始数据；
   - 关键结论走 human-in-the-loop（`compose.IsInterruptRerunError`），教练审核后再发给用户。
2. **成本**：千万级用户 × 每日评价 = 天文数字 token——**分层触发**：
   - 普通用户走规则生成 + 静态模板；
   - 付费用户 / 训练模式变化时才调 LLM；
   - 大结果走 **COS 卸载 + 摘要保留 URL** 模式（`summarizeUserInstruction` 强制要求摘要末尾列出 "待用 COS 数据" 清单，每行 `- toolName: dataPath, N条, COS_URL`），下一次对话按需下载而不是每次都传输；
   - 底模选型：日常问答走小模型（TCUM 的 `TCUM-Qwen3.5-397B-A17B` 是 MoE，A17B active 参数便宜），深度分析才走大模型——通过 `BuildRuntimeModelSelectorIfEnabled` 中间件按 `forwardedProps.agent_config.chat_model` 动态切换。
3. **评测**：怎么证明 Agent 变聪明了？——**建立三层评测**：
   - 单元级：异常检测 Recall/Precision；
   - 任务级：评价报告人工打分 + Langfuse trace（TCUM 已接入）；
   - 业务级：用户次日留存、打卡率、付费转化——**这是全栈岗最看重的"产品 sense"**。
4. **配置热更新不影响在服请求**：对标 TCUM 的 `ReloadAgentIfChanged` 请求触发式热更新——**hash 驱动**（对比 `configHash`）、**先构建后切换**（rebuild 失败保留旧 Agent）、**精确路径注册**（不用 path prefix 避免被吞路由）。运动 App 的"训练规则 v2 上线"应该走同一模式，而不是全量重启。

### 为什么这道题能拉开档次

普通候选人只答"用 LLM + RAG 就行"；架构师答完架构后一定会追加**评测体系**、**成本控制**、**幻觉防御**、**热更新**——这四件事恰好对应小红书面评说的"通过者共性：三层评测体系、context 剪裁策略、失败处理/幻觉/context 管理"。

### 追问储备（面试官很可能深挖的三个方向）

**追问 1：为什么所有 Agent 都走 Deep 模式，即使没有子 Agent？**
> "这不是为了让架构看起来'多 Agent'，是为了**中间件链的一致性**。`agent_builder.go` 里 `buildAgentWithSubAgents` 明确注释：'统一走 BuildDeepAgent，确保 COS skill 后端等中间件被正确构建'。**如果不走 Deep，deep 模式下新建的 ToolsNode 会拿到 ToolCallMiddlewares 为 nil 的副本，全局结果截断中间件就失效了**——这是我们踩过的坑。"

**追问 2：Supervisor 为什么每次请求都要 ListAgents 重新装配？**
> "因为 TCUM 是**多租户开放平台**——不同 dialog 可能属于不同租户、允许调用的子 Agent 白名单不同（`SubAgentIDs`）；Supervisor 里子 Agent 是**远程壳**（AGUI 或 A2A），只承载"名称 + 描述 + Endpoint"，装配非常轻量。这样牺牲一次 DB 查询换取了'子 Agent 上线立即生效'和'租户级隔离'两个能力。
> 反面案例：如果每次请求不 ListAgents，就得走复杂的配置推送/订阅链路。当前设计的成本-收益比更好。"

**追问 3：动态 MCP 工具和静态注册的工具有什么区别？**
> "两个维度：
> ① **命名空间**：静态注册用下划线 `{Server}_{Tool}`，动态注入用点号 `{Server}.{Tool}`——**必须区分**，否则动态覆盖静态时会命名冲突；
> ② **client 生命周期**：动态 MCP **每次 BeforeAgent 新建 client**、不做池缓存——因为 TCUM_TOKEN 是 JWT、TTL 30 分钟，池化了反而会用到过期 token；用户可信边界内不校验 URL（可控 SSRF 面）。
> 这个设计我印象很深，是因为我们最初做过 client 池化，结果线上 40% 的调用因为 token 过期失败，反而不如每次新建。"

## Q8. 在基础项目上加一个用大模型辅助的功能（Agent PE 岗开放题）

**考察意图**：这是**开放式**题目，考察产品 sense + Agent 落地能力。面试官不会给你标准答案，他看你能不能**在一个既有业务里找到大模型的价值切入点**。

**通用答题模板**（我把它总结成"AI 切入四问"）：

1. **痛点**：现在这个业务里，用户 / 运营 / 客服每天最重复、最费时、最需要判断的动作是什么？
2. **数据**：这个动作背后有没有足够的历史数据 / 上下文可以给到模型？
3. **风险**：这个动作错了后果有多严重？（决定要不要 human-in-the-loop）
4. **验证**：怎么用小成本 A/B 证明加了 AI 之后更好？

**示例作答**（假设面试官问"在小红书商单业务里加 AI"）：

### 追问 E：`AdaptiveContextRetry` 是怎么工作的？和 `summarization` 什么关系？

**架构师作答**：
> "两者是**互补关系**，不是替代：
> - `summarization` 在**进入模型请求前**判断"累计 tokens > maxTokens/2"就主动摘要，**预防性**；
> - `AdaptiveContextRetry` 在**Model.Generate 返回 400 ContextWindowExceededError 后**才触发，**应急性**。
> summarization 有两个缺口，正是 AdaptiveContextRetry 要补的：① 阈值判定粒度是"轮次之间"，一轮并发 tool 结果可让 tokens 从远低于阈值直接跃迁到远高于模型上限；② 未读 tool 在压缩阶段强制保留，多个并发 tool_calls 都是未读时 summarization 无 elidable，直接把超限 messages 送给主 LLM。
>
> AdaptiveContextRetry 的**核心创新**是从"A/B/C/D 硬分档"升级为"**目标预算驱动的单次压缩循环**"：
> 1. 从错误消息 parse 出真实 `(currentTokens, maxTokens)`，精确算需要节省多少 tokens；
> 2. 消息分类打分（size / role / unread / batch / info density），按"最胖 + 密度最低"排序；
> 3. 每个候选按 5 级递进压缩（T1→T5），每一步都本地估算，一旦达标立即停止；
> 4. 仍无法达标走"极限档"（system 头尾采样 + 摘要占位 + tail），最大限度腾出空间；
> 5. **fail-fast**：每档结束都本地估算 tokens < targetTokens 才发请求，避免无效 400。
>
> 另一个精妙的地方——**summarization 自己也会撑爆**，所以它的压缩模型也套了同款 `adaptiveContextModel` wrapper 兜底。这是防御性编程的教科书案例。"

**代码锚点**：`pkg/agent/adaptive_context_retry.go`（816 行）、`pkg/agent/summarization_handler.go` 的 `compressAwareModel` 包装。

### 追问 F：工具结果超过 64KB 怎么处理？为什么不能一律截断？

**架构师作答**：
> "分四种情况：
> ① **白名单工具**（`browser_screenshot` 截图二进制、`skill` 文档正文、`task` 子 Agent 结论）**完全跳过截断**——`task` 的返回已经是压缩产物，再截会破坏结论完整性；
> ② **业务错误结果**（BaseOutput.ErrorCode 非 2xx 或 ErrorMsg 非空）**跳过 COS 上传和截断**——错误响应上传 COS 是浪费也会污染 metadata.COS_URL；
> ③ **结构化支持类型**（MetricData / TableData / AnalyzedMetricsOutput / raw_grafana）走**结构化截断**：`compact_table` 保留 columns 只截 rows，模型永远知道字段含义；

> 阈值三级配置：全局默认 64KB → 环境变量 `TOOL_RESULT_MAX_SIZE` 覆盖 → per-tool 覆盖用**倍数**而非绝对值（如 `QueryArchTopology` 给 `2 * DefaultToolResultMaxSize()`），保证调整默认值时相对比例稳定。"

**代码锚点**：`usercases/obs_agent/tools/common/middleware/middleware_truncator.go`（默认 `defaultToolResultMaxSize = 64 * 1024`）。

### 追问 G：Skill 和普通工具有什么区别？为什么要有 skill_exec 沙箱？

**架构师作答**：
> "**Skill 是'带指令的工具集合'**，比普通工具多三层：

### 追问 H：TCUM_TOKEN 为什么每次 BeforeAgent 都要重新签，不做池化？

**架构师作答**：
> "因为 TCUM_TOKEN 是 **JWT，TTL 30 分钟**。我们最初做过 client 池化，结果线上 **40% 的调用因为 token 过期失败**——池化的 client 里绑定了老 token，等下次用到时已经过期。
>
> 现在的策略：**每次 `BeforeAgent` 新建 client + 从 ctx 签新 JWT**（`signExecContextJWTFromCtx`），这样 token 永远 fresh。牺牲的是每次请求的 client 建立开销，但换来了 100% 的 token 有效率——**在'JWT TTL 短 + 请求 QPS 不高'的场景下这是最简单直接的正确解**。
>
> 更普适的方法论：**分布式系统里凡是有 TTL 的凭证，池化都要谨慎**。要么池化 + 定期主动刷 + 失败重签双保险，要么干脆不池化。我们选了后者。"

**代码锚点**：`pkg/agent/dynamic_mcp_middleware.go` 的 D2/D3/D4/D5 设计决策注释。

### 追问 I：Agent 配置热更新为什么不用监听推送，而用请求触发式？

**架构师作答**：
> "**"请求触发式"** 是主动的取舍：每次请求进来时，`ReloadAgentIfChanged` 会做：
> 1. 通过 `configLoader` 拿最新配置（可能是 DB + 文件合并）；
> 2. 计算 `newHash = newCfg.Hash()`；
> 3. 和 `agents[name].ConfigHash` 对比；
> 4. hash 变了 → `agentRebuilder` 重建，**先构建、再切换、旧的失败就保留**；
> 5. **AG-UI 路由用可变 handler（`mutable_handler.go`）**，路由本身只注册一次；且用**精确 path** 而不是 path prefix，避免相似路径被先注册的 handler 吞掉。
>
> **为什么不用推送？** 因为：
> ① Agent 定义变化频率低（每天几次），不需要实时；
> ② 推送需要维护订阅关系、心跳、断连重连——比 hash 对比复杂 10 倍；
> ③ **hash 对比是天然的"变更幂等"**——多个请求同时进来只有一次真正 rebuild；
> ④ 请求触发式意味着**没有请求就不重建**，节省资源。
>
> 反面情况：如果 Agent 配置变化每秒都在发生，就该改成推送。当前场景下的成本-收益比是请求触发式最优。"

**代码锚点**：`pkg/agent/manager.go:145`（`ReloadAgentIfChanged`）、`pkg/agent/mutable_handler.go`。

## Q9. 自己实现滑动窗口算法

**考察意图**：这题**同时考代码能力和架构感**。写不出代码直接淘汰（面评：code 是硬门槛）；写得出但讲不清"和固定窗口/漏桶/令牌桶的取舍"就是普通开发。

**60 秒电梯稿**：

> "滑动窗口有两种主流实现——**分片滑动窗口**（把大窗口切成 N 个小格子，每次前进一格）和 **精确滑动窗口**（记录每次请求的时间戳，滑动时踢掉过期的）。前者时间空间都是 O(1)，但精度取决于分片粒度；后者精度到毫秒但空间是 O(QPS × 窗口时长)。分布式场景我用 Redis ZSet 做精确版：score 是时间戳，ZREMRANGEBYSCORE 清理过期，ZCARD 得到当前窗口内计数。**我项目里的告警限流用的是简化版固定窗口 + blocked 状态兜底**，因为告警是尖峰型且不需要毫秒级精度。"

**架构师深度**：

**四种限流算法的选型矩阵**：

| 算法 | 精度 | 突发容忍 | 内存 | 分布式友好 | 适用场景 |
|---|---|---|---|---|---|
| 固定窗口 | 差（窗口边界抖动 2x） | 无 | O(1) | 好 | 告警、日志、宽松限流 |
| 分片滑动窗口 | 中 | 无 | O(片数) | 好 | 网关限流、API 调用 |
| 精确滑动窗口（ZSet） | 高 | 无 | O(N) | 好（Redis） | 反作弊、支付防刷 |
| 漏桶 | 高 | 固定速率整形 | O(1) | 需分布式漏桶 | 削峰、下游保护 |
| 令牌桶 | 高 | 允许突发 | O(1) | 需分布式令牌桶 | 用户体验优先场景 |

**项目里的真实取舍**（[alert_rate_limiter.go](/Users/yaao/Documents/code/tcum-yunshao-global/bootstrap/webserver/middleware/alert_rate_limiter.go)）：

我们用的是**固定窗口 + blocked 态**——不是最精确的，但为什么合适：
1. 告警是"名字维度"的分布式流量，不需要毫秒级精度；
2. blocked 态设计避免了固定窗口的"边界抖动"（窗口切换瞬间瞬时 2x 流量）——命中限流后强制静默 `windowSize`，直到下一个整窗；
3. 内存 O(租户数 × 规则数)，可控；
4. 配置变化时同步清空规则表和监控指标，避免脏数据。

**代码要点**（面试可以现场写）：

```go
// Redis ZSet 精确滑动窗口的核心逻辑
func (r *SlidingWindow) Allow(key string, limit int, window time.Duration) bool {
    now := time.Now().UnixMilli()
    windowStart := now - window.Milliseconds()
    pipe := r.rdb.Pipeline()
    pipe.ZRemRangeByScore(ctx, key, "0", strconv.FormatInt(windowStart, 10))
    countCmd := pipe.ZCard(ctx, key)
    pipe.ZAdd(ctx, key, &redis.Z{Score: float64(now), Member: uuid.NewString()})
    pipe.Expire(ctx, key, window)
    _, err := pipe.Exec(ctx)
    if err != nil { return false } // 保守拒绝
    return countCmd.Val() < int64(limit)
}
```

**要说明的三个坑**：
1. 上面这段**不是原子的**——高并发下会超发。真正生产用要 Lua 脚本包起来；
2. `uuid.NewString()` 是为了避免同一毫秒的请求 score 冲突被 ZSet 去重；
3. **失败时选择"拒绝"还是"放过"是产品决策**——反作弊拒绝，用户体验放过。

**项目锚点**：[场景设计/分布式滑动窗口限流系统.md](../01-系统设计/分布式滑动窗口限流系统.md) 有完整的分布式实现。

**考察意图**：**大数据量场景的必答题**。面试官在看你有没有**真正做过分库分表**（还是只看过文章）。

**60 秒电梯稿**：

> "分库分表要先想清楚**四个问题**：① 分片键是什么（决定 90% 的方案）② 是否跨片查询（决定要不要额外索引表）③ 扩容策略（决定要不要一致性 hash）④ 迁移方式（决定业务无感还是要停机）。我实际做过的是**监控时序数据的分表**：分片键是 `storage_id + metric_id`，扩容用一致性 hash + 双写迁移。分布式事务上，**元数据变更用 Saga**（可回滚）、**告警去重用幂等 + 补偿**（不要用 2PC，太重）、**支付类才用 TCC**——一句话：**能用最终一致就不用分布式事务，能用 Saga 就不用 TCC，能用 TCC 才不得已用 2PC**。"

**架构师深度**：

**分片键选择的"三宁三不"**：
- 宁选自然键（user_id、order_id），不选代理键（自增 id）——扩容时代理键要全库重排；
- 宁选高基数键（user_id），不选低基数键（region_id）——低基数会造成热点；
- 宁选查询友好键（订单表用 user_id），不选写入友好键——90% 的性能问题是读放大。

**跨片查询的三种解法**：
1. **索引表**：为非分片键建独立索引表，先查索引拿分片键；
2. **广播查询**：所有分片并行查然后合并（TCUM 监控查询走的就是这条）；
3. **实时同步到 OLAP**：分库写 → CDC → ClickHouse 做分析——分片解决 OLTP，OLAP 用列存。

**分布式事务的选型矩阵**：

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|---|---|---|---|---|
| 2PC/XA | 强 | 差（阻塞） | 高 | 银行核心 |
| TCC | 强 | 中 | 高（要三接口） | 支付、库存 |
| Saga | 最终 | 好 | 中 | 长事务、跨服务 |
| 本地消息表 | 最终 | 好 | 低 | 大多数中台场景 |
| 事务消息（RocketMQ） | 最终 | 好 | 低 | 有 MQ 基建时首选 |

## Q11. Redis 持久化方案 + bgsave 对内存影响 + 哈希槽 + 集群扩容

**考察意图**：**Redis 深度必考题**。5.13 场次单独问了"zset 查询分数 10 到 n 的时间复杂度"——考细节；二面则问了这套组合拳——考全局。

**架构师视角的关键点**：

1. **持久化选型**（真实生产不会只选一个）：
   - **RDB**：全量快照，恢复快，但可能丢失最后一次快照后的数据；
   - **AOF**：追加日志，最多丢 1 秒（everysec），但恢复慢；
   - **混合持久化（4.0+）**：RDB 全量 + AOF 增量，是**当前生产的默认最佳实践**。

2. **bgsave 对内存的影响**（这是深挖点）：
   - fork 后子进程和父进程**共享内存页**（COW，写时复制）；
   - 父进程持续写入 → 触发页复制 → 内存占用**理论上可翻倍**；
   - **实际生产观察**：写密集场景 bgsave 期间内存可能涨 30~50%——**所以生产环境必须留 50% 内存 buffer**，且业务高峰不做 bgsave；
   - **RSS ≠ INFO used_memory**：bgsave 后 RSS 长期偏高，因为 malloc 归还内存不及时。

3. **哈希槽 + 渐进式 hash**：
   - Redis Cluster 16384 槽，key 分片 = `CRC16(key) mod 16384`；
   - **渐进式 hash 指的是 dict 的 rehash，不是集群 rehash**——两者别混；
   - dict rehash：ht[0] + ht[1] 并存，每次访问顺便迁移一个 bucket，避免 stop-the-world；
   - **集群扩容才是"槽迁移"**：`CLUSTER SETSLOT ... MIGRATING/IMPORTING`，配合 ASK 重定向，客户端要能处理 MOVED 和 ASK。

4. **集群动态扩容**：
   - 添加新节点 → `CLUSTER MEET`；
   - 分配槽：`redis-cli --cluster reshard`，会一批一批迁 key；
   - 迁移期间：源节点收到 GET 返回 ASK 让客户端去目标节点重试；
   - **风险**：大 key 迁移会阻塞（migrate 是同步的）——**大 key 治理必须在扩容前做**。

**架构师深度**（超出面试题的加分点）：

- **哪些场景不适合 Redis Cluster**：需要 multi-key 事务、Lua 脚本跨 slot、大 key 场景——这时候更适合**代理层（Codis / Twemproxy）**；
- **主从 vs Cluster 的取舍**：小规模用哨兵 + 主从，读写分离靠客户端；大规模用 Cluster；
- **持久化对性能的影响**：AOF everysec 场景下写入延迟 P99 可能被 fsync 影响——生产要**独立 AOF 磁盘**。

**项目锚点**：[middleware/Redis-专项.md](../../02-框架和中间件/01-中间件与语言/Redis-专项.md) 有完整的持久化和集群章节。

## Q12. Redis zset 查询分数 10 到 n 的时间复杂度

**60 秒电梯稿**：

> "`ZRANGEBYSCORE` 或 `ZRANGE ... BYSCORE` 的复杂度是 **O(log N + M)**——log N 是跳表定位区间起点，M 是返回结果的数量。所以如果 n 很大导致 M 接近 N，复杂度退化到 O(N)。**生产使用一定要带 LIMIT**，避免大结果集拖垮 Redis 主线程。"

**架构师视角的追问储备**：

- **为什么是 log N？**——zset 底层是跳表（skiplist）+ 哈希表；跳表的 range 查询依靠索引层跳跃到起点，O(log N)；然后顺序扫描直到结束条件，O(M)；
- **压缩列表阈值**：小 zset 用 ziplist（元素少 + 值短），大了才升级 skiplist——**关注 `zset-max-ziplist-entries` 和 `zset-max-ziplist-length` 配置**；
- **相关命令的复杂度速查**：
  - `ZADD`：O(log N)
  - `ZRANGE`（by index）：O(log N + M)
  - `ZRANGEBYSCORE`：O(log N + M)
  - `ZRANK`：O(log N)
  - `ZINCRBY`：O(log N)
  - `ZUNIONSTORE`：O(N) + O(M log M)——**慎用**。

# 五、MySQL 深度题（一面二面都问）

## Q13. 联合索引失效的情况（5.13 明确问）

**60 秒电梯稿**：

> "联合索引失效的**六种典型场景**——① 违反最左前缀；② 中间列用范围查询导致后续列不走索引；③ 索引列上用函数或运算；④ 隐式类型转换；⑤ OR 连接的非索引列；⑥ `LIKE '%xxx'` 前置通配。**背这些是新手，架构师视角要说：'索引失效的根因是查询计划器认为全表扫描更便宜'**——所以有时候手动 `FORCE INDEX` 反而更慢，因为你不理解统计信息。"

**架构师深度**：

**联合索引设计的"三原则"**：
1. **等值在前、范围在后**：`WHERE a = 1 AND b > 2` → 索引 `(a, b)`；
2. **区分度高的在前**：区分度低的列放前面会让扫描的行数不减少；
3. **覆盖索引优先**：`SELECT` 的列都在索引里，避免回表。

**面试官可能追问的深度题**：

- **为什么范围查询后的列不走索引？**——因为 B+Tree 是有序的，一列范围后下一列在物理上已经无序；
- **索引下推（ICP）**：MySQL 5.6+ 特性，即使不能用索引精确匹配，也能在 InnoDB 层用索引过滤——**减少回表**；
- **前缀索引怎么选长度？**——`SELECT COUNT(DISTINCT LEFT(col, N)) / COUNT(*)` 接近 1 时的最小 N。

## Q14. MVCC + 锁 + 索引组合拳（二面明确问）

**架构师视角的一句话总结**：

> "MVCC 让**普通读**不加锁（快照读），锁只出现在**写操作**和**加锁读**（`SELECT ... FOR UPDATE`）。MVCC 的核心是每行的 `trx_id` + `roll_pointer` 版本链 + Read View，实现了'读不阻塞写、写不阻塞读'。但这不代表没有并发问题——**幻读**在 RR 隔离级别下靠 Next-Key Lock 解决，但 `SELECT ... FOR UPDATE` 才会加，普通 SELECT 只用 MVCC 快照可能还是能看到不一致。"

**架构师深度**：

1. **Read View 的生成时机**：
   - RC：每次 SELECT 都新建 → 每次都能看到最新提交；
   - RR：事务开始第一次 SELECT 时建，之后复用 → 可重复读；
2. **锁的分类三维度**：
   - 粒度：表锁 / 行锁 / gap 锁 / next-key 锁；
   - 类型：S / X 锁；
   - 意向：IS / IX——**表级锁的元数据加速**；
3. **死锁**的常见原因：
   - 不同事务以不同顺序更新多行 → 用同一顺序解决；
   - `INSERT` 触发唯一键冲突后升级为 X 锁 → 用批量 upsert 降低概率；
   - `SELECT ... FOR UPDATE` 后再执行其他操作 → 用 `SELECT` 快照读 + 版本号乐观锁替代。

**项目锚点**：[middleware/MySQL-专项.md](../../02-框架和中间件/01-中间件与语言/MySQL-专项.md)。

## Q15. HashMap / ConcurrentHashMap 原理

**60 秒电梯稿**：

> "HashMap 是 **数组 + 链表 + 红黑树（8+）**，扩容 2 倍，负载因子 0.75。ConcurrentHashMap 1.7 是分段锁（Segment），1.8 后改成 **CAS + synchronized 锁桶头**——粒度更细。核心变化是从'分段并行'到'桶级并行'，并发度从 16 提升到 O(桶数)。"

**架构师视角的追问储备**：

1. **HashMap 死循环**：JDK 1.7 头插法在扩容时可能形成环，导致 CPU 100%——**这是"面试装逼常识"，但架构师要知道 1.8 尾插法 + tab 复用已经解决**；
2. **红黑树退化条件**：当桶内元素 < 6 时退回链表——避免频繁在链表/红黑树间抖动；
3. **ConcurrentHashMap 的 size() 不是精确值**——它用 CounterCell 数组减少竞争，size() 遍历累加是"最终一致"的；
4. **为什么容量必须是 2 的幂？**——`(n-1) & hash` 代替 `hash % n`，位运算比取模快，且 n 为 2 的幂时结果等价。

## Q16. ReentrantLock / 线程池 / CountDownLatch

**架构师视角**：

1. **ReentrantLock vs synchronized**：
   - 前者可中断、可超时、可公平、可条件变量分离——**用于复杂并发协调**；
   - 后者语法糖简单、JVM 优化好（锁升级：偏向 → 轻量 → 重量）——**用于简单同步**；
   - **默认选 synchronized**，只有需要高级特性才用 ReentrantLock；

2. **线程池的四大参数决策**：
   - `corePoolSize`：常驻线程数，按 CPU 密集（N+1）或 IO 密集（2N）判断；
   - `maximumPoolSize`：最大线程数，防止极端流量；
   - `workQueue`：SynchronousQueue（直接交付）/ LinkedBlockingQueue（无界慎用）/ ArrayBlockingQueue（有界推荐）；
   - `RejectedExecutionHandler`：AbortPolicy（抛异常）/ CallerRunsPolicy（调用者跑，天然反压）/ DiscardOldest；
   - **架构师常用 CallerRunsPolicy 做反压**——上游发起方被强制减速，比丢任务更安全；

3. **CountDownLatch vs CyclicBarrier vs Semaphore**：
   - CountDownLatch：一次性倒计时，主等从；
   - CyclicBarrier：可复用栅栏，从等从；
   - Semaphore：信号量，限流用。

## Q17. Spring：BeanFactory vs FactoryBean

**60 秒电梯稿**：

> "**BeanFactory 是 IoC 容器**，管理所有 Bean 的生命周期；**FactoryBean 是一种特殊的 Bean**，它的 getObject() 返回值才是最终注入到容器的 Bean。前者是'容器'，后者是'工厂'——名字容易混但作用完全不同。FactoryBean 常见于需要复杂初始化的场景，比如 MyBatis 的 `SqlSessionFactoryBean`、Feign 的 `FeignClientFactoryBean`。"

**架构师视角**：

FactoryBean 存在的意义：
1. **屏蔽复杂构造**——SqlSessionFactory 需要数据源、mapperLocations、typeAliases 一堆配置，包成 FactoryBean 后使用方只 `@Autowired SqlSessionFactory`；
2. **动态代理注入**——Feign 客户端本质是接口，无法直接 new，通过 FactoryBean 生成 JDK Proxy；
3. **条件化构造**——根据配置返回不同实现（比如根据 `spring.profiles.active` 返回 Mock 或真实 client）；
4. **延迟初始化**——getObject() 是懒调用，可以在真正需要时才建。

## Q18. MyBatis 插件（拦截器）原理

**60 秒电梯稿**：

> "MyBatis 有**四大拦截点**——`Executor`（SQL 执行）、`ParameterHandler`（参数处理）、`ResultSetHandler`（结果集处理）、`StatementHandler`（SQL 语法构建）。插件通过 **JDK 动态代理 + 责任链** 实现：`Plugin.wrap()` 把目标对象包一层代理，所有对四大对象的调用都走 `Interceptor.intercept()`。生产常用场景是**分页插件**（PageHelper）、**SQL 打印**、**数据权限**、**读写分离路由**。"

**架构师深度**：

1. **拦截器的顺序**——多个 Interceptor 时后注册的先执行（洋葱模型），要注意副作用；
2. **哪些不能拦截**——原生 SQL 中的 `<foreach>` 等标签在参数处理阶段已经展开，`StatementHandler` 拿到的是最终 SQL；
3. **拦截性能**：每个 SQL 都过代理链，插件本身要非常轻量——**不要在拦截器里做 IO**；
4. **动态数据源切换**：结合 AbstractRoutingDataSource + ThreadLocal，不必写 MyBatis 插件；只有跨库 join 才需要在 SQL 层改写。

# 七、算法题速查（附思路模板）

## Q19. LeetCode 240 · 搜索二维矩阵 II

**思路**：**从右上角开始的"阶梯搜索"** —— target 大就往下走一格（行 +1），target 小就往左走一格（列 -1）。时间 O(m + n)，空间 O(1)。**不要用二分**（每行独立二分是 O(m log n)，比阶梯法慢）。

```go
func searchMatrix(matrix [][]int, target int) bool {
    if len(matrix) == 0 { return false }
    i, j := 0, len(matrix[0])-1
    for i < len(matrix) && j >= 0 {
        if matrix[i][j] == target { return true }
        if matrix[i][j] > target { j-- } else { i++ }
    }
    return false
}
```

**为什么从右上角？**——那个位置是**这一行的最大、这一列的最小**，比较结果能唯一决定往哪走。

## Q20. 全排列（46）

**回溯模板**：

```go
func permute(nums []int) [][]int {
    res := [][]int{}
    used := make([]bool, len(nums))
    path := []int{}
    var dfs func()
    dfs = func() {
        if len(path) == len(nums) {
            tmp := make([]int, len(path))
            copy(tmp, path)
            res = append(res, tmp)
            return
        }
        for i, n := range nums {
            if used[i] { continue }
            used[i] = true
            path = append(path, n)
            dfs()
            path = path[:len(path)-1]
            used[i] = false
        }
    }
    dfs()
    return res
}
```

**追问要点**：
- **有重复元素怎么去重？** → 先排序，剪枝 `if i > 0 && nums[i] == nums[i-1] && !used[i-1] { continue }`；
- **复杂度**：O(N × N!)——生成 N! 个排列，每个花 O(N) copy。

## Q21. 删除链表倒数第 N 个节点

**双指针一次遍历**：

```go
func removeNthFromEnd(head *ListNode, n int) *ListNode {
    dummy := &ListNode{Next: head}
    fast, slow := dummy, dummy
    for i := 0; i < n; i++ { fast = fast.Next }
    for fast.Next != nil {
        fast = fast.Next
        slow = slow.Next
    }
    slow.Next = slow.Next.Next
    return dummy.Next
}
```

**易错点**：不用 dummy 节点会在 `n == len(list)` 时崩——**链表题永远先加 dummy**。

## Q22. 二叉树层序遍历

```go
func levelOrder(root *TreeNode) [][]int {
    if root == nil { return nil }
    var res [][]int
    q := []*TreeNode{root}
    for len(q) > 0 {
        size := len(q)
        level := []int{}
        for i := 0; i < size; i++ {
            node := q[0]; q = q[1:]
            level = append(level, node.Val)
            if node.Left != nil { q = append(q, node.Left) }
            if node.Right != nil { q = append(q, node.Right) }
        }
        res = append(res, level)
    }
    return res
}
```

**变形题**：Z 字遍历（隔层反转）、右视图（每层最后一个）、锯齿形——**都是同一个模板 + 一个 flag**。

## Q23. 构建自平衡 BST

**从有序数组构建**：**取中点作为根 → 递归左右**，天然平衡。

```go
func sortedArrayToBST(nums []int) *TreeNode {
    if len(nums) == 0 { return nil }
    mid := len(nums) / 2
    return &TreeNode{
        Val: nums[mid],
        Left: sortedArrayToBST(nums[:mid]),
        Right: sortedArrayToBST(nums[mid+1:]),
    }
}
```

**从无序数组构建自平衡 BST**：要么**先排序**再上面的方法（O(N log N)），要么用 **AVL / 红黑树的插入 + 旋转**——面试时说清楚复杂度取舍即可。

## Q24. 多数字乘积（一面原题）

**题面歧义**：可能是"最大三个数乘积"（LeetCode 628）或"数组累乘"或"两数之积等于某值"——**架构师第一件事：反问澄清题意**。

**最大三个数乘积**：排序后要么是 `nums[n-1]*nums[n-2]*nums[n-3]`，要么是 `nums[0]*nums[1]*nums[n-1]`（考虑负数）——**O(N) 一次扫描找 top3 max + top2 min** 也可以。

- 反脆弱：主动暴露短板、把每次故障当成机会——CMDB 一致性 SLO、告警治理都是从故障里长出来的。

**人格版**：**"清晰 · 诚实 · 有耐心"**
- 清晰：任何复杂问题我都能拆到 3 层以内讲明白；
- 诚实：区分"设计目标"和"已上线"，不夸大项目；
- 有耐心：中台建设是慢功夫，我花了 X 年做这件事。

## 为什么离职（红线题）

**三条原则**：① 不吐槽前司；② 不说钱；③ 说成长/匹配度。

**推荐模板**：

> "在 TCUM 我完整经历了从 0 到 1 再到 N 的过程，把可观测平台建成体系。现在这个体系已经进入优化和运营阶段，团队也稳定了。我个人下一步想去一个**产品对 C 端用户直接可见**的场景，把架构能力用在离用户更近的业务上——小红书的 AI 场景刚好匹配。前司很好，但我在这里能学的边际收益在下降，这是个人选择。"

**为什么这段有效**：
1. 没吐槽；
2. 讲了自己的成长曲线（0→1→N→边际递减）；
3. 说明匹配点（C 端 + AI）；
4. 主动 close 掉"跳槽是不是不稳定"的猜疑。

## 个人未来规划

**架构师版本**：

> "3 年内我想在 AI × 中台 的交叉领域做出**行业能看到的东西**——比如'AI 原生的中台架构'到底应该长什么样。5 年内希望能带一个 20~30 人的团队，把这套方法论沉淀成可复用的产品。我不追求特别快的晋升，我追求**每年做的事情都能对得起自己的下一份简历**。"

**为什么这段有效**：

2. 讲清了组织路线（20~30 人团队）；
3. 讲了价值观（对得起下一份简历）——反脆弱思维；

# 九、面评共性——通过者/淘汰者的深层差异

原文的面评共性极其宝贵，我把它转成**可操作的行动清单**：

## ✅ 通过者三大特征 → 我该怎么落地

| 特征 | 我的准备 |
|---|---|
| **项目有实质落地**（不停留在概念） | 每个亮点都能追到代码行号 / iwiki URL / 简历数字——见 [00-总索引与能力地图.md](../../00-导航与策略/00-总索引与能力地图.md) 的"事实基线" |
| **对 Agent 核心问题有清晰认知** | 上下文管理七层、幻觉三道防御、评测三层——见 [TCUM-AI 项目题库](../../01-项目专题/03-TCUM-AI/03-项目题库/07-面试题库-tcum-ai项目30问.md) |
| **算法题能跑通** | 见本卷第七章"算法题速查"——回溯 / 双指针 / DFS+BFS / DP 各刷 5 题模板即可 |
| **沟通主动、表达顺畅** | 每个问题准备 60 秒电梯稿——本卷所有 Q 都有 |

## ❌ 淘汰者三大陷阱 → 我该怎么规避

| 陷阱 | 规避方式 |
|---|---|
| **技术停留表面**（被深挖时讲不清底层） | 每个技术点准备三层：现象 → 机制 → 源码——本卷所有"架构师深度"部分 |
| **Agent 场景 trivial / 只在 POC 阶段** | 每次讲 Agent 都带上"月活 UV 100+、诊断覆盖率 85%、30 个云产品"这类真实规模数字 |
| **code 写不出**（最硬门槛） | 每周至少 5 题手写代码，保持手感 |

## 全栈岗的独特要求 → 我该怎么表达

面评提到"全栈岗对**业务思考深度 + 技术落地 + 产品 Sense**都有要求"，这是"聪明"的具体化：

- **业务思考深度**：不要只讲"我做了 X"，要讲"X 解决了什么客户痛点、给业务带来什么价值"；
- **技术落地**：**"我做了 X，验证方式是 Y，效果是 Z"**——三段式必答；
- **产品 Sense**：主动提出"这个功能应该做但没做" / "这个方案在客户视角有 A 缺陷"——**用户视角**而不是技术视角。

## 一句话总结小红书面试的"通关密码"

**"每个技术点都要有代码、每个业务点都要有数据、每个决策都要有取舍、每个短板都要主动认。"**
