## 一句话定位

Eino（发音近 "i know"）是字节跳动开源的 Go 语言 LLM 应用开发框架：用**静态类型的组件抽象**统一 ChatModel / Tool / Retriever 等原子能力，用**图编排（Chain/Graph/Workflow）**在**图构建/`Compile()` 阶段做类型检查**、**执行期自动处理流式拼接/合并/复制**、**统一注入 Callback 切面**；在此基础上用 **ADK** 提供 ReAct、多 Agent、Human-in-the-loop 和长任务预置模式。这里的 `Compile()` 是 Eino 构造运行图的框架阶段，不等于 Go 编译器在 `go build` 时完成全部接线检查。

  ChatModel / ChatTemplate / Tool / Retriever / Embedding / Indexer

        │  统一 Option 模式（抽象 Option + 实现专属 Option）
        ▼

  Chain（简化链式封装，Pregel 引擎）

## 读前纠偏：Eino 不是“一个 ReAct + 一堆工具”

理解 Eino 时必须拆开三层运行时，否则很容易把 Graph、ADK 和 DeepAgent 混为一谈：

| 层次 | 核心抽象 | 谁决定下一步 | 适合的问题 | TCUM-AI 用法 |
|---|---|---|---|---|
| Component | `ChatModel`、`Tool`、`Retriever`、`Lambda` | 调用者 | 原子能力与可替换实现 | 模型、工具、Embedding、ES Retriever/Indexer |
| Compose | `Chain`、`Graph`、`Workflow`、`Runnable` | 边、分支函数和固定 DAG | 可预测的业务流程、类型安全数据流 | 工作流 Agent、底层 ReAct 图、Callback |
| ADK | `Agent`、`AgentEvent`、`Runner`、Middleware、Transfer | 模型、预置拓扑或确定性流程 | 自主循环、多 Agent、恢复、事件流 | `ChatModelAgent`、`DeepAgent`、SubAgents、Handlers |

关键判断是：

- **Graph 是执行图，不天然等于 Agent**。只有图中存在“模型判断是否调用工具并回环”的决策环，才形成 ReAct Agent。
- **ChatModelAgent 是 Eino v0.8.0 的主力 ReAct Runtime**。旧的 `flow/agent/react` 仍存在，但 TCUM-AI 当前直接依赖的是 ADK `ChatModelAgent` 和其上的 `DeepAgent`。
- **多 Agent 不只是“父 Agent 调子 Agent”**。Eino 同时提供固定顺序、并行、循环、自由移交、中心 Supervisor、Agent-as-Tool、Plan-Execute-Replan 和 DeepAgent 等不同控制模型。
- **Middleware 不只是日志切面**。它可以修改 instruction、动态增删工具、重写消息历史、替换模型、包裹工具调用，因此事实上承担上下文工程、工具治理、Skill、动态 MCP、压缩、重试和模型路由。

## 专题一：Eino 提供了哪些多 Agent 架构

### 1. 架构总表

| 架构 | 路由者 | 拓扑 | 上下文/结果传递 | 并发 | 最适合 | 核心风险 |
|---|---|---|---|---|---|---|
| Sequential Agent | 框架 | 固定线性 | 前一个事件/状态继续进入后一个 | 否 | 审核流水线、生成→检查→修订 | 某一步失败阻断全链路 |
| Parallel Agent | 框架 | 固定扇出/汇聚 | 各子 Agent 独立运行，事件汇聚 | 是 | 多源调研、多专家并行 | 成本放大、结果冲突、取消传播 |
| Loop Agent | 框架 + Agent Action | 固定循环 | 循环状态记录迭代和子 Agent 下标 | 通常否 | 生成-评审-修订、执行-校验 | 无限循环，必须设置上限/退出动作 |
| Transfer/Handoff | LLM 调 `transfer_to_agent` | 可配置网络 | Runner 根据 `AgentAction` 切换当前 Agent | 取决于路由 | 意图路由、专家接力 | 路由漂移、乒乓转移、上下文污染 |
| Supervisor | Supervisor LLM | 星型、中心化 | 子 Agent 被强制确定性返回 Supervisor | 可由 Supervisor 调度 | 权限集中、统一口径、复杂协调 | 中心瓶颈、Supervisor prompt 负担 |
| Agent-as-Tool | 父 Agent LLM 调 Tool | 嵌套调用树 | 子 Agent 结果作为一次 ToolResult 返回 | 工具节点可并发 | 封装专家能力、不移交控制权 | 子运行不可见、递归和预算失控 |
| Plan-Execute-Replan | Planner/Executor/Replanner | 先顺序后循环 | 结构化 Plan + ExecutedSteps | 默认逐步 | 长任务、需要显式计划和纠偏 | 规划陈旧、每步重规划成本高 |
| DeepAgent | 主 Agent + task tool/子 Agent | 层次式任务委派 | 任务描述与子 Agent 结果回主 Agent | 可并行任务 | 通用复杂任务、研究/编码型 Agent | 抽象较重、事件与成本治理更难 |
| Compose 自定义图 | 开发者 | 任意 DAG/有环图 | 强类型边/字段映射/本地状态 | 显式设计 | 强业务约束、审批和补偿 | 开发成本高，不是通用自治路由 |

这几类不是“谁更高级”的关系，而是**控制权放在哪里**：固定 Workflow 把控制权交给代码；Transfer/Supervisor/Agent-as-Tool 把部分控制权交给模型；Plan-Execute 把控制拆成规划、执行和纠偏三个角色；自定义 Graph 则允许把确定性边界画到最细。

### 2. Sequential、Parallel、Loop：确定性 Workflow Agents

[`adk/workflow.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/workflow.go) 的 `workflowAgent` 只有三种 mode：Sequential、Parallel、Loop。它们的路由不是模型临场决定的，因此可预测、好测试。

- Sequential 按 `SubAgents` 顺序执行，维护 `InterruptIndex`，恢复时从被中断的子 Agent 继续。
- Parallel 为每个子 Agent 保存事件列表；任一分支中断时需要保存所有分支状态，恢复复杂度高于串行。
- Loop 保存 `LoopIterations` 和 `SubAgentIndex`；停止条件来自最大迭代数或事件里的 `BreakLoop` action，而不是靠“模型应该知道何时停”。
- 三者都会维护 `RunPath`，使嵌套 Agent 的事件能够标明调用路径，而不是只有一个模糊的 agent name。

它们适合业务协议明确的流程。例如“生成 PQL → 语法校验 → 语义校验 → 风险审查”应优先用 Sequential/Graph，而不是让 Supervisor 自由决定是否执行校验。

### 3. Transfer/Handoff：模型驱动的控制权移交

`adk.SetSubAgents` 会建立父子关系。`ChatModelAgent` 根据可达 Agent 生成转移说明并注入内置 `transfer_to_agent` 工具；模型调用后，工具通过 `SendToolGenAction` 产生 `AgentAction.TransferToAgent`，Runner/flow 再切换当前执行 Agent。

这和 Agent-as-Tool 的区别非常重要：

```text
Transfer:
  Agent A --transfer action--> Agent B
  当前控制者变为 B，适合“接力”

Agent-as-Tool:
  Agent A --tool call--> [Agent B 完成一个子任务] --tool result--> Agent A
  当前控制者始终是 A，适合“委派”
```

Transfer 适合客服意图路由、领域专家接管；Agent-as-Tool 适合主 Agent 保持全局计划，只把检索、代码审查等子问题交给专家。

### 4. Supervisor：中心化星型拓扑

[`adk/prebuilt/supervisor/supervisor.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/prebuilt/supervisor/supervisor.go) 并没有实现另一套神秘循环。它做了两件关键事情：

1. 每个子 Agent 用 `AgentWithDeterministicTransferTo(... supervisorName)` 包装，子 Agent 完成后只能回 Supervisor，不能彼此自由跳转。
2. 外层 `supervisorContainer` 提供单一 trace root，让 Supervisor 与所有子 Agent 的 Callback 落在同一调用树下。

因此 Supervisor 的价值是**拓扑约束 + 统一观测**。它比自由 Handoff 更容易治理，但 Supervisor 会成为路由、上下文和成本中心。对于必须固定执行的合规步骤，仍应放到 Graph/Sequential，而不是仅写进 Supervisor prompt。

### 5. Agent-as-Tool：嵌套委派而不是 Handoff

`adk.NewAgentTool` 把 `Agent` 适配为标准 Tool。内层 Agent 的 Message/Tool 事件可以选择向外转发，但 `Exit`、`TransferToAgent`、`BreakLoop` 等 action 被限制在 Agent Tool 边界内，不能意外终止或劫持父 Agent。这个 action scoping 是生产多 Agent 必须有的隔离机制。

适用场景：

- 主 Agent 要维持总体计划和用户口径；
- 子 Agent 是可复用专家能力；
- 希望对子 Agent 设置独立模型、工具和预算；
- 子 Agent 失败可以作为工具失败由主 Agent 重试或降级。

### 6. Plan-Execute-Replan：显式长任务状态机

[`adk/prebuilt/planexecute/plan_execute.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/prebuilt/planexecute/plan_execute.go) 组合方式是：

```text
Sequential(
  Planner,
  Loop(
    Executor: 每次只执行计划的第一步,
    Replanner: 根据 Plan + ExecutedSteps 决定更新计划或最终响应
  )
)
```

Planner 可用结构化输出，也可强制调用 Plan Tool 生成可反序列化计划；Replanner 强制在“更新 Plan”和“Respond”两个工具中选择。它比单纯 ReAct 更适合几十步长任务，因为计划与已执行步骤成为显式状态；代价是多一次甚至多次模型调用，且计划 schema、幂等和步骤结果压缩需要额外治理。

### 7. DeepAgent：预置的复杂任务 Harness

[`adk/prebuilt/deep/deep.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/prebuilt/deep/deep.go) 最终仍创建 `ChatModelAgent`，并不是另一套主循环。它在其上组合：

- 文件系统/大结果卸载能力；
- TODO/计划类工具；
- Task Tool 和 SubAgents；
- 可选通用子 Agent；
- 用户传入的 `AgentMiddleware` 与 `ChatModelAgentMiddleware`。

所以 DeepAgent 的本质是“带长任务工作台的 ReAct Agent”。它适合通用研究和编码任务，但对严格业务流程不能只依靠 Task Tool；关键步骤仍需确定性编排、审批和权限校验。

## 专题二：ReAct 在 Eino v0.8.0 中到底怎么运行

### 1. 不是一段 while，而是一张有环 Graph

[`adk/react.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/react.go) 构建的核心图是：

```text
START
  │
  ▼
Init：把输入消息放入会话状态
  │
  ▼
ChatModel ──没有 ToolCalls──> END
  │
  └──有 ToolCalls──> ToolNode ──普通结果──> ChatModel
                         │
                         └──ReturnDirectly──> Converter ──> END
```

详细执行过程：

1. `ChatModelAgent.Run` 合成 instruction、历史消息、运行时 options 和工具列表。
2. `BeforeAgent` handlers 可以动态修改 instruction、可执行工具以及 `ReturnDirectly` 集合。
3. ReAct State 初始化 `Messages`、剩余迭代数、return-direct tool call id、tool-generated actions。
4. ChatModel 节点前置处理器检查并递减 `remainingIterations`；耗尽返回 `ErrExceedMaxIterations`。
5. 流式 Branch 消费模型输出；看到任意 `ToolCalls` 进入 ToolNode，否则结束。
6. ToolNode 可以并行执行同一模型消息中的多个 tool calls，并把 Tool Message 追加回状态。
7. 如果某工具配置 `ReturnDirectly`，只抽取对应 `ToolCallID` 的结果直接返回；否则回到模型，让模型观察工具结果再决策。
8. `transfer_to_agent`、`exit` 等工具除了文本结果，还会附带 `AgentAction`，由外层 Runner 解释控制语义。

### 2. ChatModelAgent 有工具和无工具走不同执行路径

[`adk/chatmodel.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/chatmodel.go) 会根据运行时工具集选择：

- 无工具：构建简单 Chain，只调用模型；
- 有工具：构建上述 ReAct Graph；
- `BeforeAgent` 若把零工具改成非零工具或反过来，会触发本次运行使用临时 graph/chain，而不是错误复用旧的执行器。

这正是动态 MCP、Skill 和 Task Tool 能在 `BeforeAgent` 注入的基础：工具列表不是只能在 Agent 初始化时固定。

### 3. ReAct 的终止条件必须工程化

Eino 提供的终止通道包括：

- 模型不再返回 tool call；
- `ReturnDirectly` 工具；
- `ExitTool` 产生 Exit Action；
- Transfer Action 把控制权交给其他 Agent；
- 达到 `MaxIterations`；
- context cancellation、模型/工具错误或中断。

生产系统还应补：重复工具调用检测、单工具超时、总 wall-clock deadline、token/费用预算、危险操作审批、相同参数幂等键。`MaxIterations` 只是最后一道保险，不能代表完整的循环治理。

## 专题三：Eino 的扩展点到底有哪些

### 1. 扩展点全景

| 扩展层 | 扩展点 | 能做什么 | 不适合做什么 |
|---|---|---|---|
| Component | 实现 Model/Tool/Retriever 等接口 | 接入新模型、新工具、新存储 | 跨调用状态治理 |
| Compose Node | Lambda、Graph、Workflow、Branch | 确定性业务逻辑、路由、并发 | 模型自治策略本身 |
| Call Option | `WithChatModelOption`、节点指定 | 请求级温度、工具选择、Callback | 长期共享配置 |
| Callback | Model/Tool/Retriever/Graph 生命周期 | Trace、指标、日志、成本 | 改写复杂 Agent 状态 |
| `AgentMiddleware` | instruction/tools、模型前后、工具 wrapper | 简单静态扩展、兼容旧代码 | 需要自定义状态和 context 传播的新能力 |
| `ChatModelAgentMiddleware` | 6 类 handler 方法 | 动态工具、上下文压缩、模型替换、治理 | 跨 Agent 全局调度本身 |
| Runner/AgentEvent | event、action、interrupt/resume | UI 流、Handoff、暂停恢复 | 修改组件内部实现 |
| Backend/Hub | Skill Backend、AgentHub、ModelHub | 外部存储、按名取 Agent/模型 | 未授权的任意动态执行 |

### 2. `ChatModelAgentMiddleware` 的六组切点

[`adk/handler.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/handler.go) 的接口不是普通 Before/After 两个钩子，而是：

1. `BeforeAgent`：每次 Agent Run 一次；可改 instruction、raw tools、ReturnDirectly，也可返回新 context。
2. `BeforeModelRewriteState`：每次模型调用前；可重写完整消息历史，最适合压缩、记忆注入和 prompt 防护。
3. `AfterModelRewriteState`：每次模型调用后；可检查/修正模型响应并写回状态。
4. `WrapInvokableToolCall` / `WrapStreamableToolCall`：包裹传统同步/流式工具。
5. `WrapEnhancedInvokableToolCall` / `WrapEnhancedStreamableToolCall`：包裹带结构化 ToolArgument/ToolResult 的增强工具。
6. `WrapModel`：替换或包裹每次实际调用的 BaseChatModel；适合动态模型路由、重试、限流、缓存和响应审查。

嵌入 `BaseChatModelAgentMiddleware` 可以只实现需要的方法。新功能优先用该接口；旧 `AgentMiddleware` 是封闭 struct，只适合附加静态 instruction/tool 或简单 closure。

### 3. 顺序决定语义，不是无关紧要的注册列表

模型调用链的关键顺序是：

```text
旧 Middleware.BeforeChatModel
  → Handler.BeforeModelRewriteState
  → 内部 Retry
  → Event Sender
  → Handler.WrapModel（先注册者在最外层）
  → Callback Injection
  → Model.Generate/Stream
  → Handler.AfterModelRewriteState
  → 旧 Middleware.AfterChatModel
```

工具调用链是：

```text
内部 Event Sender
  → ToolsConfig.ToolCallMiddlewares
  → 旧 Middleware.WrapToolCall
  → Handler 的 Tool Wrappers
  → Callback Injection
  → Tool.Run
```

因此“错误兜底要包住动态工具”“事件应记录改写前还是改写后输出”“模型切换和 context retry 谁在外层”都必须通过注册顺序明确设计。只说“框架支持 middleware”远远不够。

### 4. 动态工具有两种完全不同的改法

- 在 `BeforeAgent` 修改 `runCtx.Tools`：同时改变**发给模型的 schema**和**真正可执行的工具集合**，整个本次 Agent Run 生效。TCUM-AI 的 Skill、skill_exec、动态 MCP 都用这个方式。
- 在 `WrapModel` 修改 `model.WithTools(toolInfos)`：只改变本次模型请求能看到的工具 schema，不改变 ToolNode 真正拥有的工具。Eino 的 `toolsearch` middleware 用它实现“所有工具可执行，但只把已搜索到的动态工具展示给模型”。

若只隐藏 schema 却没有执行侧白名单，不能当作权限控制；真正的授权必须在工具执行边界再次校验。

## 专题四：TCUM-AI 实际使用了哪些 Eino 扩展点

### 1. 装配主链路

[`agent_builder.go`](/Users/yaao/Documents/code/tcum-ai/cmd/server/common/agentserver/agent_builder.go) 的真实装配是：

```text
配置文件/DB AgentConfig
  │
  ├─注册静态 Tools、旧 AgentMiddleware、ChatModelAgentMiddleware
  ├─构建 Skill Backend + skill/skill_exec handlers
  ├─注入 summarization、运行时模型选择、context overflow retry
  ├─解析 SubAgents/自定义 Provider
  ▼
deep.New(...)
  ▼
DefaultAgent（补 A2A / AG-UI / Langfuse 配置）
  ▼
AgentManager（注册、配置 hash、热重建）
```

项目当前有一个容易面试时说错的事实：**配置 Agent 最终统一走 `BuildDeepAgent`，即使没有子 Agent**。`NewDefaultAgent` 先构造基础协议对象，但最终注册时仍由 DeepAgent 包装，以保证 Skill 等中间件一致装配。

### 2. 使用映射

| TCUM-AI 能力 | Eino 扩展点 | 项目实现 |
|---|---|---|
| 基础 ReAct | `adk.NewChatModelAgent` / DeepAgent 内部 | `pkg/agent/default_agent.go`、`deep.New` |
| 多 Agent | `deep.Config.SubAgents`、Task Tool | `buildAgentWithSubAgents`、Provider 动态返回子 Agent |
| 固定工作流 | `compose.Chain` + 自定义 `adk.Agent` 适配 | `pkg/agent/workflow_agent.go` |
| Skill | `skill.Backend` + Skill Middleware | Local/COS/filtered backend、SkillManager |
| 脚本执行 | 自定义 `BeforeAgent` 注入工具 | `skill_exec` + AgentRun 沙箱池 |
| 动态 MCP | `BeforeAgent` 动态追加 Tools | `dynamic_mcp_middleware.go` |
| 动态知识库/任务工具 | `BeforeAgent` handler | `dynamic_kb_middleware.go`、`dynamic_task_tool_middleware.go` |
| 上下文压缩 | `BeforeModelRewriteState` | Eino summarization handler |
| 超限兜底 | `WrapModel` | `adaptive_context_retry.go` 渐进压缩后重试 |
| 运行时模型路由 | `WrapModel` | runtime model selector |
| 工具错误恢复 | Tool wrapper | `tool_error_handler_middleware.go` 把错误变成模型可读结果 |
| 全链路观测 | Callback + AgentEvent | Langfuse、AG-UI 事件转换、日志/指标 |
| 配置热更新 | 项目装配层 | AgentManager config hash + rebuild，不是 Eino 原生魔法 |

### 3. TCUM-AI 的 Handler 顺序及含义

DeepAgent 路径中大致按以下顺序追加：

1. `ToolErrorHandlerMiddleware`：放最前，意图是包住后续所有静态/动态工具。
2. 配置声明的 ChatModelAgentMiddlewares。
3. Skill middleware。
4. `skill_exec` middleware。
5. Eino summarization。
6. 运行时模型选择。
7. Adaptive context retry。
8. Provider 额外 handlers，例如 TwinSoul、DynamicSkill/MCP。

需要注意：Handler wrapper 的“先 append”通常意味着“更外层”，但 Before/After hook 又是顺序执行；评审中不能凭列表直觉判断，必须结合 Eino 的实际 wrapper 构造顺序验证。

### 4. 项目没有直接采用的能力

- TCUM-AI 当前主构建链没有直接使用 Eino `prebuilt/supervisor`。
- 没有把 `prebuilt/planexecute` 作为通用主 Agent。
- 固定业务工作流使用自定义 `WorkflowAgent` 包装 `compose.Chain`，不是 ADK Sequential Agent 的同义替换。
- MCP Server 主实现基于 `mark3labs/mcp-go`；Eino 在 Server 侧主要承担已有 Tool 的接口适配，不应说成“Eino 自带完整 MCP Server”。

## 专题五：Skill 的渐进式披露是怎么实现的

### 1. Eino 原生的两阶段披露

[`adk/middlewares/skill/skill.go`](/Users/yaao/go/pkg/mod/github.com/cloudwego/eino@v0.8.0/adk/middlewares/skill/skill.go) 定义 `Backend.List/Get`：

```text
Agent 启动/绑定工具
  └─ Backend.List() → 只取 FrontMatter(name/description/context/agent/model)
       └─ 形成一个 skill 工具的短描述

模型判断需要某项能力
  └─ 调 skill({skill: "prometheus-dashboard"})
       └─ Backend.Get(name) → 才读取完整 SKILL.md + BaseDirectory
```

这解决“几十个 Skill 全文常驻 prompt”问题：模型平时只看到目录级元数据，选中后才把正文作为 ToolResult 放进消息历史。

Skill 有三种执行语义：

- Inline：正文返回父 Agent，后续模型继续执行；可设置 skill-level model，影响后续模型调用。
- `context: fork`：用干净上下文启动子 Agent 执行 Skill。
- `context: fork_with_context`：复制父 Agent 消息历史，再把 Skill 内容作为 Tool Message 交给子 Agent。

Fork 解决“Skill 本身就是复杂任务”时的上下文隔离，但 TCUM-AI 当前构建 Skill middleware 时没有配置 `AgentHub/ModelHub`，因此项目主链主要使用 Inline 模式，不能把 Eino 支持的 fork 说成 TCUM 已经落地。

### 2. TCUM-AI 扩成了三层披露

[`local_skill_backend.go`](/Users/yaao/Documents/code/tcum-ai/pkg/agent/local_skill_backend.go) 又增加了模块/子 Skill 语义：

1. **L0 目录层**：`List()` 只返回 Agent 配置中显式声明的顶层 Skill FrontMatter。
2. **L1 Skill 正文层**：调用 `skill` 后 `Get()` 返回被 `compactSkillContentForLLM` 精简的 SKILL.md；完整目录仍由 `BaseDirectory` 保留。
3. **L2 资源执行层**：模块 Skill 的 `sub-skills/<name>/SKILL.md` 不进入 List，但会被后端纳入可访问集合；脚本和配置不注入 prompt，需要时通过 `skill_exec` 在对应目录执行。

这才是真正的渐进式披露：**目录可见 ≠ 正文加载 ≠ 附属资源加载 ≠ 脚本执行**。

### 3. Skill 为什么必须告诉模型“该调用哪个脚本”

框架只提供机制，不会从一个模糊 Skill 自动推断所有工作流。一个合格 `SKILL.md` 至少要写清：

- 触发条件与不触发条件；
- 先读哪个参考文件；
- 哪类输入调用哪个脚本；
- 脚本参数、stdin/stdout 契约和成功/失败判断；
- 生成 PQL 后调用哪个 parser/linter/preview 脚本验证；
- 失败时能否自动修复、最多重试几次；
- 哪些动作只读，哪些会修改外部系统并需要确认。

否则 `skill_exec` 只是一个任意命令执行入口，模型既不知道验证链，也无法稳定判断生成的 PQL 是否合规。渐进披露解决的是 token，不会自动解决过程正确性。

### 4. TCUM-AI 的 `skill_exec` 执行链

```text
skill(name)
  → 返回压缩后的 SKILL.md + BaseDirectory +（可选）MCP schema
  → 模型读取“脚本/命令调用契约”
  → skill_exec(skill_name, command, stdin?)
  → ResolveSkillDirectory
  → 按 ThreadID/RunID 绑定 AgentRun 沙箱
  → 上传/复用 Skill 目录，合并运行时 env
  → 执行命令并截断/格式化 stdout、stderr
  → 错误以正常 ToolResult 返回，允许模型修正后重试
```

沙箱层包含连接池、会话工作目录、setup 指纹、冷启动 adopt、空闲回收和连锁驱逐熔断。安全上仍应补或持续核验：命令 allowlist、网络 egress、CPU/内存/时长限制、secret 最小注入、输出脱敏和写操作审批。

### 5. Skill 中嵌套 MCP 的渐进披露

若 Skill 目录有 `config/mcporter.json`，`Get()` 时才在沙箱执行：

```text
mcporter list
mcporter list <server> --all-parameters
```

得到的工具 schema 追加到该 Skill 正文，并按 `sessionKey:skillName` 缓存。实际调用再由模型通过：

```bash
mcporter --config config/mcporter.json call <server>.<tool> --args '{...}'
```

这避免所有 MCP 工具 schema 常驻主 Agent prompt；代价是第一次加载 Skill 多一次 discovery 开销，而且 schema cache 要处理配置热更新和服务端 tools changed。

## 专题六：MCP Server 与 Client 在 TCUM-AI 中怎么实现

### 1. 先划清 Eino 与 MCP 的职责

| 能力 | 主要实现 |
|---|---|
| Agent 内 Tool 抽象、ToolNode 执行 | Eino |
| MCP Client Tool → Eino Tool 适配 | `eino-ext/components/tool/mcp` |
| MCP 协议 Client/Server、Streamable HTTP/SSE | `mark3labs/mcp-go` |
| 业务鉴权、路由、连接复用、命名空间、指标 | TCUM-AI 自研封装 |

因此准确表述是：TCUM-AI 同时使用 Eino 的 Tool/Agent 扩展点和 mcp-go 的协议实现，把两者在边界处适配起来。

### 2. Server 侧

[`pkg/mcp/server.go`](/Users/yaao/Documents/code/tcum-ai/pkg/mcp/server.go) 的链路：

```text
子 MCP 包 init() 注册 SubMCPEntry
  → 统一 bootstrap 遍历注册表
  → NewMCPServer(name/version/instructions)
  → 注册 ServerTools
  → NewStreamableHTTPServer(stateLess=true)
  → 每个子 MCP 挂载独立 /tcum-mcp/<domain> 路径
  → 鉴权 middleware
  → tRPC HTTP no-protocol service
```

工具有两种构建方式：

- `NewServerTool[TInput]`：mcp-go 原生泛型 schema 生成，业务 handler 与 Eino 无关；适合新的独立 MCP 工具。
- `AdaptEinoTool`：从 Eino `ToolInfo` 转 JSON Schema，把 `InvokableRun` 包成 MCP Handler；适合复用已有 Agent Tool。

Server 采用 stateless Streamable HTTP，但业务若需要“同一大盘连续编辑”仍通过 `X-Session-Id` 在应用层关联会话。协议无状态不等于业务绝对无状态。

### 3. Server 鉴权与 context 桥接

HTTP 链路先完成太湖签名、ExecutionContext JWT 或 legacy AKSK 鉴权，再把 Credential、CallerInfo、tenant、session id 注入 request context。由于 mcp-go Handler 内部会重建 context，`WithHTTPContextFunc` 再桥接这些字段，否则下游 Tool 看不到调用者身份。

错误语义也做了区分：参数/业务失败通常返回 `CallToolResult{isError}` 而不是 Go transport error，使 Agent 能看到错误并调整参数；真正的协议/网络失败才走 error。两者混用会导致整条 ReAct stream 被不必要地终止。

### 4. Client 侧实际上有三条链

**A. 直接业务调用客户端**

[`pkg/mcp/client.go`](/Users/yaao/Documents/code/tcum-ai/pkg/mcp/client.go) 按 `serverURL` 缓存 Streamable HTTP client，执行 `Initialize` 后复用连接，`CallToolViaMCP` 依次尝试 endpoint，并注入 ExecutionContext JWT/tenant/header。适合服务端代码明确知道工具名的调用。

**B. 动态 MCP Middleware**

[`pkg/agent/dynamic_mcp_middleware.go`](/Users/yaao/Documents/code/tcum-ai/pkg/agent/dynamic_mcp_middleware.go) 每次 `BeforeAgent`：

1. 从数字分身 `McpConfig` 解析多个 server；
2. 展开 `${TCUM_TOKEN}` 和业务 header；
3. 按配置选择 Streamable HTTP 或 SSE；
4. `Start → Initialize → ListTools`；
5. 用 `allowedTools` 白名单过滤；
6. 经 eino-ext 变成 Eino Tools；
7. 重命名为 `serverName.toolName` 后注入 `runCtx.Tools`。

这里刻意不复用 client，以保证短期 JWT 新鲜；但 Tool 持有 client，不能在 discovery 后立即 Close。工程上需要监控客户端生命周期和连接数，否则“等 GC”可能带来资源压力。

**C. Skill 内 mcporter 客户端**

它不把 MCP Tool 直接注册到主 Agent，而是通过 `skill → skill_exec → mcporter` 在沙箱里 discovery/call，适合大量低频、领域化工具的渐进披露。

三者的取舍：

| 方式 | Tool schema 对模型可见时机 | 连接复用 | 隔离 | 适合 |
|---|---|---|---|---|
| 直接调用 | 不一定给模型 | URL 级池化 | 主进程 | 固定服务间调用 |
| 动态 Middleware | Agent Run 开始时 | 当前实现不池化 | 主进程 | 每个数字分身自定义少量 MCP |
| Skill + mcporter | 选中 Skill 后 | 沙箱/会话级 | AgentRun 沙箱 | 大量低频领域工具、脚本组合 |

仅会讲 ReAct、多 Agent、Skill、MCP 仍不够。面试和架构评审通常还会追下面这些维度：

### 推荐的生产 Agent 分层

```text
入口协议层：AG-UI / A2A / HTTP，负责身份、会话、取消
    ↓
Agent 控制层：ReAct / Supervisor / Workflow / Plan-Execute
    ↓
上下文层：history、summary、memory、skill/tool disclosure
    ↓
能力层：Tool / MCP / Retriever / SubAgent
    ↓
执行治理层：auth、policy、timeout、retry、idempotency、sandbox、HITL
    ↓
证据层：event、trace、token/cost、eval sample、replay
```

如果一个设计只讲上面第二层，它只是 Demo Agent；能够把六层的边界、失败语义和证据闭环讲清楚，才接近生产 Harness。

## 一、Eino 是什么、为什么这样设计（10 问）

**Q1：Eino 要解决什么核心问题？**
大模型应用存在"可枚举的通用规律"：核心组件类型、数据类型、交互模式相对固定，可用有向图描述；模型输出天然是流式的，需要统一处理流的读取/复制/合并/拼接；由此衍生出并发处理、扇入扇出、横切面注入（Callback）、Option 分配等一批通用子问题。Eino 用明确的"组件"接口 + 强大的"图编排"系统性解决这些通用问题，而不是停留在单点功能封装。[开源背景](https://www.cloudwego.io/zh/docs/eino/overview/eino_open_source/)

**Q2：为什么用 Go 而不是延续 Python/LangChain 路线？**
Python 弱类型带来运行时才暴露的类型错误、长期维护成本高；字节内部大规模落地（豆包/抖音/扣子数百个服务）后发现，进入线上大规模运行阶段，**可靠性与可维护性**的价值远超"写起来灵活"。Go 的静态类型能把"上游输出能否作为下游输入"这一编排核心假设，在 `Compile()` 阶段（而非运行时）就检查出来。

**Q3：Eino 名字怎么来的，团队定位是什么？**
发音近似 "i know"。定位为"终极大模型应用开发框架"，追求简洁性（Simplicity）、可扩展性（Extensibility）、可靠性（Reliability）、有效性（Effectiveness），并遵循 Go 惯例（Idiomatic Go）。它借鉴 LangChain、LlamaIndex、Google ADK 等社区思想，但不是照搬。

**Q4：类型系统的核心取舍是什么？**
面对"上下游节点类型是否匹配"这一问题，Eino 评估过两种方案：①泛化类型（`any`/`map[string]any`，类似 LangChain，各节点用 key 从 map 里取值再做类型断言）；②让上下游类型保持开发者预期，在 Compile 阶段做类型检查（类似"搭积木"，规格匹配才能连接）。Eino 选择②：开发者不需要从一堆 `any` 中"猜"传过来的值对不对。[编排的设计理念](https://www.cloudwego.io/zh/docs/eino/core_modules/chain_and_graph_orchestration/orchestration_design_principles/)

**Q5：类型检查在什么时机发生，是否总能在图构建/Compile 阶段发现错误？**
分三种情形：①上下游类型完全相同——最强检查；②下游接收 interface、上游实现该 interface（或下游是 `any`）——仍可静态判断；③**上游是 interface、下游是具体类型**——这种情况 Compile 阶段无法确定，只能推迟到运行时做类型断言。Graph 在 `AddEdge()` 时即检查，Chain 在 `Compile()` 阶段统一检查；Workflow 在字段映射级别做同样的检查，若映射双方类型不确定则同样推迟到运行时。

**Q6：Eino 的框架结构（多仓库）是怎么划分的？**
- **Eino**（主库）：类型定义、流处理机制、组件抽象、编排引擎、ADK/Agent 实现、Callback 切面机制；
- **EinoExt**：各组件的具体实现（OpenAI/Claude/Gemini/Ark/Ollama/Elasticsearch/Redis 等）、Callback Handler 实现（对接 APMPlus、Langfuse）、评估器、提示优化器；
- **Eino Devops**：可视化开发调试（IDE 插件拖拽生成代码）；
- **EinoExamples**：示例应用与最佳实践。
这种切分让 core 库依赖最小化（每个组件实现是独立 go module），换模型 SDK 不牵连编排层。

**Q7：Eino 与 LangChain 相比的核心差异点是什么？**
| 维度 | LangChain (Python) | Eino (Go) |
|---|---|---|
| 类型 | 动态语言，运行时才报错 | 静态强类型，Compile 期检查 |
| 性能/并发 | 受 GIL 限制 | goroutine 原生高并发 |
| 编排单元类型对齐 | map/any + 断言 | 泛型 + 图构建/Compile 阶段匹配，Workflow 支持字段级映射 |
| 流式处理 | 需手工拼接判断 | 框架自动拼接/装箱/合并/复制，组件只需实现"有意义"的范式 |
| 部署形态 | 脚本/服务均可，弱类型下大规模服务化维护成本高 | 天然适配 Go 微服务体系，编译产物单二进制 |

**Q8：Eino 的落地证据/生产验证是什么？**
开源前已在字节内部使用迭代半年多，是内部大模型应用**首选全代码开发框架**，接入豆包、抖音、扣子等多条业务线、数百个服务。多个设计点（如 Workflow 的字段级映射）直接来自抖音的真实需求反馈，Message 结构体设计也吸收了豆包的实践痛点。

**Q9：Eino 最大的代价/学习成本在哪？**
四种流式范式（Invoke/Stream/Collect/Transform）+ 自动转换规则、Callback 的 5 个切点 + 3 种触发实体、CallOption 两级体系（组件级/编排级）+ 4 种分发粒度、Workflow 的多种 FieldMapping API，构成了不小的概念面。相比"发一个 HTTP 请求调模型"的最简单场景，Eino 的抽象在**简单单轮对话**场景上是"重"的，价值要在**多组件编排、需要类型安全、需要长期维护**的场景才能体现。

**Q10：一句话总结 Eino 的设计哲学？**
"用 Go 的静态类型把大模型应用中『组件怎么拼、流怎么传、切面怎么插』这三类通用问题，尽量收敛到图构建/Compile 阶段检查、执行期自动处理；ADK Agent 则复用这套组件和图运行时承载决策循环。"

## 二、怎么使用 Eino（15 问，含代码）

**Q11：最简单的用法——直接调用 ChatModel 是什么样的？**
```go
model, _ := openai.NewChatModel(ctx, config)
message, _ := model.Generate(ctx, []*schema.Message{
    schema.SystemMessage("you are a helpful assistant."),
    schema.UserMessage("what does the future AI App look like?"),
})
```
组件可以完全脱离编排单独使用；只有当需要多组件组合、类型检查、流式自动处理、统一 Callback 时才需要引入 `compose` 编排层。

**Q12：ChatModel 组件接口长什么样？**
```go
type BaseChatModel interface {
    Generate(ctx context.Context, input []*schema.Message, opts ...Option) (*schema.Message, error)
    Stream(ctx context.Context, input []*schema.Message, opts ...Option) (*schema.StreamReader[*schema.Message], error)
}
type ToolCallingChatModel interface {
    BaseChatModel
    WithTools(tools []*schema.ToolInfo) (ToolCallingChatModel, error) // 返回新实例，不修改自身，安全用于并发
}
```
`WithTools` 返回新实例而非原地修改，这个设计保证了同一个底层 ChatModel 可以在并发请求中被安全地"绑定不同工具集"复用。[ChatModel 使用说明](https://www.cloudwego.io/zh/docs/eino/core_modules/components/chat_model_guide/)

**Q13：Chain 的典型用法（模板 → 模型）？**
```go
chain, _ := compose.NewChain[map[string]any, *schema.Message]().
    AppendChatTemplate(prompt).
    AppendChatModel(model).
    Compile(ctx)
result, _ := chain.Invoke(ctx, map[string]any{"query": "..."})
```
Chain 是 Graph 的简化封装：接口更"链式"，但底层仍会转换/编译为 Graph 执行；内部也支持 `AppendBranch`（分支）、`AppendParallel`（并行）、`AppendGraph`（嵌套子图），不是纯线性流程的专属。

**Q14：Graph 的典型用法（模型 + 工具分支）？**
```go
graph := compose.NewGraph[map[string]any, *schema.Message]()
graph.AddChatModelNode("node_model", chatModel)
graph.AddToolsNode("node_tools", toolsNode)
graph.AddEdge(compose.START, "node_model")
graph.AddBranch("node_model", branch) // 根据是否有 tool_call 决定走 node_tools 还是 END
r, _ := graph.Compile(ctx)
```
`compose.START`/`compose.END` 是图的起止哨兵节点；`NewGraph[I, O]()` 的输入类型 `I` 必须匹配首节点入参、输出类型 `O` 必须匹配末节点返回值。

**Q15：Workflow 相比 Graph 的独特用法（字段映射）是什么？**
```go
wf := compose.NewWorkflow[Input, Output]()
wf.AddLambdaNode("c1", compose.InvokableLambda(wordCounter)).
    AddInput(compose.START,
        compose.MapFields("SubStr", "SubStr"),
        compose.MapFieldPaths([]string{"Message", "Content"}, []string{"FullStr"}))
wf.End().
    AddInput("c1", compose.ToField("content_count"))
```
Graph 要求前驱**整体输出类型**与后继**整体输入类型**对齐，若只想传某个字段，往往要牺牲强类型（退化成 map）或侵入业务代码（定义公共 struct）。Workflow 用 `FieldMapping` 直接做字段级映射，业务函数保持原始签名不受编排影响。

**Q16：Workflow 的字段映射有哪几类 API？**
| 映射类型 | API | 说明 |
|---|---|---|
| 顶层字段→顶层字段 | `MapFields(a, b)` | 常规同级映射 |
| 全部输出→顶层字段 | `ToField(f)` | 上游整体输出塞进下游某字段 |
| 顶层字段→全部输入 | `FromField(f)` | 上游某字段作为下游整体输入 |
| 嵌套字段→嵌套字段 | `MapFieldPaths(p1, p2)` | 任一方为嵌套结构时使用 |
| 全部→全部 | 直接 `AddInput`，不传映射 | 等价 Graph 里的默认边 |
可用 `AddInputWithOptions(from, mappings, compose.WithNoDirectDependency())` 做纯数据流（无控制依赖），或 `AddDependency(from)` 做纯控制流（无数据传递），实现控制流与数据流解耦。

**Q17：怎样用 Lambda 接入自定义函数？**
Lambda 支持四种形态对应四种流式范式：`InvokableLambda`（Invoke，普通函数）、`StreamableLambda`（Stream，产出流）、`CollectableLambda`（Collect，消费流产出非流）、`TransformableLambda`（Transform，流进流出）。通过 `AddLambdaNode`/`AppendLambda` 接入 Graph/Chain，使 Eino 编排可以承载任意自定义逻辑而不局限于官方组件。

**Q18：如何构建一个 ReAct Agent？**
```go
agent, _ := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
    Name:         "assistant",
    Instruction:  "你是一个专家",
    Model:        toolCallingModel,
    MaxIterations: 20,
    ToolsConfig: adk.ToolsConfig{
        ToolsNodeConfig: compose.ToolsNodeConfig{
            Tools: []tool.BaseTool{myTool},
        },
    },
})
runner := adk.NewRunner(ctx, adk.RunnerConfig{Agent: agent})
events := runner.Query(ctx, "写一个 hello world 程序")
```
在 v0.8.0 ADK 中，`ChatModelAgent` 才是主力入口。它在有工具时构建 `Init → ChatModel ⇄ ToolNode` 有环 Graph，无工具时退化为单模型 Chain；`MaxIterations` 默认 20，按**模型生成次数**递减，不是旧 `flow/agent/react` 的 Graph node step 计数。完整循环见前文“专题二”。旧 `react.NewAgent` 示例仍可用于理解历史 flow API，但不应拿来描述 TCUM-AI 当前路径。

**Q19：如何自定义一个 Tool？**
```go
myTool := utils.NewTool(
    &schema.ToolInfo{
        Name: "user_info",
        Desc: "查询用户信息",
        ParamsOneOf: schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
            "name": {Type: "string", Desc: "用户姓名"},
        }),
    },
    func(ctx context.Context, input *userInfoRequest) (*userInfoResponse, error) { ... },
)
```
只要实现 `BaseTool.Info()` + `InvokableRun`/`StreamableRun` 即可接入 ToolsNode；`utils.NewTool` 是把普通 Go 函数包装成标准 Tool 接口的辅助方法，免去手写 JSON Schema 解析。

**Q20：如何构建一个最基础的 ADK Agent？**
```go
chatModel, _ := openai.NewChatModel(ctx, &openai.ChatModelConfig{...})
agent, _ := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
    Name: "assistant", Model: chatModel, ToolsConfig: adk.ToolsConfig{...},
})
runner := adk.NewRunner(ctx, adk.RunnerConfig{Agent: agent})
iter := runner.Query(ctx, "问题内容")
```
`Agent.Run()` 本身就返回 `AsyncIterator[AgentEvent]`；Runner 的增量价值是统一创建 flow session、处理 Transfer/Exit 等 action、在 Interrupt 时保存 checkpoint，并提供 `Run/Query/Resume/ResumeWithParams`。当前 v0.8.0 `Runner` 源码没有这里旧稿所说的 `TurnLoop Push/Preempt/Stop` API，取消主要依赖 `context.Context`。

**Q21：如何用 DeepAgent 处理复杂多步任务？**
```go
deepAgent, _ := deep.New(ctx, &deep.Config{
    Name:        "ops-agent",
    ChatModel:   chatModel,
    ToolsConfig: toolsConfig,
    SubAgents:   []adk.Agent{researchAgent, codeAgent},
    Handlers:    handlers,
})
```
DeepAgent 最终仍创建 `ChatModelAgent`。它通过 middleware 注入 TODO/计划能力、文件系统能力和 `task` 工具；`task` 再把每个 SubAgent 包装成 Agent Tool，根据 `subagent_type + description` 执行。Shell、Python、搜索并非 DeepAgent 凭空自带，只有显式配置相应 Tool/文件系统 backend 后才存在。TCUM-AI 对所有配置 Agent 统一使用该装配路径。

**Q22：如何把"确定性流程"与"自主 Agent 决策"结合？**
```go
graph := compose.NewGraph[*Input, *Output]()
graph.AddLambdaNode("validate", validateFn)
graph.AddChatModelNode("generate", chatModel)
graph.AddLambdaNode("format", formatFn)
compiledGraph, _ := graph.Compile(ctx)
// 把编排产物包装成 Lambda/Tool 供 Agent 调用
graphTool := compose.AnyLambda(compiledGraph.Invoke, compiledGraph.Stream, nil, nil)
```
`compose` 先把强约束过程编译成 Runnable，再用一个 Eino Tool 适配器暴露 `Invoke/Stream`；父 Agent 只决定“是否调用该能力”，能力内部的校验、审批和步骤顺序仍由 Graph 保证。它与 Agent-as-Tool 的共同点是都经 ToolCall 委派，区别是前者内部是确定性 Runnable，后者内部仍是自主 Agent。[Graph Tool 章节](https://www.cloudwego.io/zh/docs/eino/quick_start/chapter_08_graph_tool/)

**Q23：如何在编排中动态调整某个组件的运行参数？**
```go
r.Invoke(ctx, input, compose.WithChatModelOption(model.WithTemperature(0.5)))
r.Invoke(ctx, input, compose.WithCallbacks(handler).DesignateNode("node_1"))
```
`WithXxxOption` 系列函数把组件级 Option 封装进 `compose.Option`，是连接"组件层 CallOption"与"编排层 CallOption"的桥梁；这是**请求级**参数注入方式，区别于创建组件实例时固定的 Config。

**Q24：如何实现流式输出并在前端逐字展示？**
```go
streamReader, _ := agent.Stream(ctx, messages)
for {
    chunk, err := streamReader.Recv()
    if err == io.EOF { break }
    // 推送 chunk 到前端
}
streamReader.Close()
```
`Stream`/`Transform` 范式返回 `*schema.StreamReader[T]`，通过 `Recv()` 循环读取直到 `io.EOF`；用完必须 `Close()`，否则底层资源（尤其被 Copy 给多个消费者的流）可能泄露。

**Q25：如何实现人工审批（Human-in-the-loop）后再执行工具？**
```go
func (t ApprovableTool) InvokableRun(ctx context.Context, args string, opts ...tool.Option) (string, error) {
    wasInterrupted, _, stored := compose.GetInterruptState[string](ctx)
    if !wasInterrupted {
        return "", compose.StatefulInterrupt(ctx, &ApprovalInfo{ArgumentsInJSON: args}, args)
    }
    isTarget, hasData, data := compose.GetResumeContext[*ApprovalResult](ctx)
    if !isTarget || !hasData { return "", compose.StatefulInterrupt(ctx, ..., stored) }
    if data.Approved { return t.InvokableTool.InvokableRun(ctx, stored, opts...) }
    return "disapproved", nil
}
```
配合 `WithCheckPointStore`，首次调用触发中断并持久化参数，恢复时通过 `ResumeWithData` 带回审批结果；这是 Eino Interrupt & CheckPoint 机制在工具审批场景的标准写法。

## 三、编排引擎实现原理（12 问）

**Q26：Compile() 到底做了什么？**
把节点、边、分支、并行结构、State 生成函数等固化为可执行的运行时对象 `Runnable[I,O]`，统一暴露四种运行方式（Invoke/Stream/Collect/Transform）。编译阶段完成类型检查（能确定的部分）、流式范式的自动补全策略确定、Callback 自动注入点确定；`WithGenLocalState[S]` 声明的状态生成函数也在此时固定，但每次实际调用会重新生成一份独立 State 实例（保证并发安全）。

**Q27：Graph 底层执行引擎是什么，如何选择？**
两种可选执行引擎：
- **Pregel 引擎**（`NodeTriggerMode == AnyPredecessor`）：支持有环图，以"SuperStep"批量执行，Chain 固定使用；
- **DAG 引擎**（`NodeTriggerMode == AllPredecessor`）：不支持环，语义更简单清晰，Workflow 固定使用。
Graph 可自由选择二者之一；这个设计把"要不要支持环（如 ReAct 循环）"和"要不要固定语义简单的无环执行"分离成显式配置，而不是隐藏在某个黑盒里。

**Q28：为什么 Chain 固定用 Pregel，Workflow 固定用 DAG？**
Chain 常需要表达"分支/回退"等简单循环语义，Pregel 的批步执行天然支持环；Workflow 定位是"确定性字段级数据流水线"，本身不需要环，DAG 引擎语义更简单、可预测性更强，因此 Workflow **不支持** `WithNodeTriggerMode` 和 `WithMaxRunSteps`（因为无环，没有"最大轮数"概念）。

**Q29：`WithOutputKey`/`WithInputKey` 解决什么问题？**
`WithOutputKey("outkey")`：把非 map 类型的上游输出包装成 `map[string]any{"outkey": value}`，常用于多路边汇聚成一个 map 场景；`WithInputKey("inkey")`：从上游 `map[string]any` 输出中取出某个 key 的 value 作为下游输入。这是在"强类型对齐"与"多路汇聚必须退化为 map"之间留的一个显式、局部的转换口子，而不是让整张图都退化为 `map[string]any`。

**Q30：StatePreHandler/StatePostHandler 与流式的关系？**
`StatePreHandler`/`StatePostHandler` 对齐节点的**非流式**输入/输出类型；`StreamStatePreHandler`/`StreamStatePostHandler` 对齐节点的**流式**输入/输出类型。State 被设计为线程安全，节点在并发执行时可以安全读写共享 State——这是编排层"并发管理"承诺的具体落点，用户不需要手动加锁。

**Q31：外部只读原则（不可修改引用类型输入）为什么重要？**
Node/Branch/Handler 内部不应修改传入的引用类型 Input（struct 指针、map、slice），对 StreamReader 的 Chunk 同样适用。因为在 Graph 内部，同一份数据可能被**扇出复制**给多个下游节点和多个 Callback Handler，若某个消费者原地修改了它，会造成其他并发读取者看到不一致的数据——这是"自动 Copy"机制能安全工作的前提假设，框架不会替你做深拷贝防御。

**Q32：Branch/分支节点如何与流式协作？**
```go
compose.NewStreamGraphBranch(func(ctx context.Context, sr *schema.StreamReader[*schema.Message]) (string, error) {
    msg, err := sr.Recv() // 只读首帧就能判断是否有 tool_call
    defer sr.Close()
    if len(msg.ToolCalls) == 0 { return compose.END, nil }
    return nodeKeyTools, nil
})
```
这体现了 Collect 范式的典型应用：不需要等流完全拼接完，读首帧就能做路由决策，降低分支判断的等待延迟（ReAct Agent 判断是否调用工具正是用这个机制）。

**Q33：并行节点（Parallel）如何组织？**
Chain 通过 `AppendParallel` + `compose.NewParallel()` 并行执行多个子任务，结果汇总为 map（各分支产出的 key 不能冲突）。Graph 层面的并行本质是多条边从同一节点扇出到多个下游节点，执行引擎（Pregel 的 SuperStep 或 DAG 的拓扑调度）天然支持并发执行互不依赖的节点，无需用户手写 goroutine/WaitGroup。

**Q34：嵌套子图（AppendGraph/AddGraphNode）解决什么问题？**
把一个已经 `Compile` 或未编译的 Chain/Graph 作为另一个 Graph 的一个节点整体嵌入，实现组合复用。子图内部拥有独立的编译选项（如自己的 `WithInterruptAfterNodes`），父图的 Callback/CallOption 可以通过 `DesignateNodeWithPath` 精确穿透到子图内部指定节点，这是"分层可组合而不是拍平成一张巨图"的关键机制。

**Q35：编排层对"类型不确定"场景（interface 到具体类型）的处理策略是什么？**
Compile 阶段无法判断的类型关系（上游是 interface、下游是具体类型），编排层选择**推迟到节点执行时做类型断言**而不是直接拒绝图编译。这是一个显式的权衡：完全拒绝会让很多合法但图构建时无法证明的场景（如插件化组件）无法使用；完全放行则会失去部分提前检查收益。Eino 选择"能检查就检查，不能检查就延后但仍检查（而非静默跳过）"。

**Q36：为什么说 Workflow 是"控制流与数据流解耦"的设计？**
默认情况下 Graph 的一条边同时承担"执行顺序"和"数据传递"两个职责。Workflow 通过 `AddInputWithOptions(..., WithNoDirectDependency())`（纯数据流，不建立执行依赖）和 `AddDependency(from)`（纯控制流，不传数据）把这两个职责拆开，使得"A 必须先于 B 执行，但 A 的输出不需要传给 B"或"B 需要 A 的某个字段，但不要求严格的执行顺序（如都依赖同一上游）"这类需求可以精确表达，而不必强行用一条边同时表达两件事。

**Q37：为什么组件实现只需要实现"有意义"的流式范式，其余靠框架补全？**
若强制每个组件都实现 Invoke/Stream/Collect/Transform 四种范式，会产生大量无意义的样板代码（比如 ChatModel 天然是"输入非流、输出可流"，让它实现 Collect 没有实际业务含义）。Eino 让组件只声明自己真正支持的范式，框架在 Compile/运行阶段按优先级（Invoke 模式下：Stream>Collect>Transform；Transform 模式下：Stream>Collect>Invoke）自动用"装箱/拼接"补全缺失的范式，组件作者的心智负担降到最低。

## 四、流式处理机制（8 问）

**Q38：Eino 流式编程的四种范式是什么，分别对应什么通信模型？**
| 范式 | 输入 | 输出 | 通信模型 | 构造方法 |
|---|---|---|---|---|
| Invoke | 非流 | 非流 | Ping-Pong | `compose.InvokableLambda` |
| Stream | 非流 | 流 | Server-Streaming | `compose.StreamableLambda` |
| Collect | 流 | 非流 | Client-Streaming | `compose.CollectableLambda` |
| Transform | 流 | 流 | Bidirectional-Streaming | `compose.TransformableLambda` |
这个划分直接映射了 gRPC 的四种调用模型，说明 Eino 把"流式"当作一等公民而非事后补丁。

**Q39：自动拼接（Concatenate）具体怎么工作？**
当上游是 `StreamReader[T]` 而下游只接受非流式 `T` 时，框架先把流中所有 chunk 取出成 `[]T`，再拼接成一个完整 `T`。内置支持的拼接类型：`*schema.Message`（`schema.ConcatMessages`）、`string`（等同 `+=`）、`[]*schema.Message`、Map（相同 key 递归合并，遇不可合并类型报错）、其他 slice（仅当只有一个非零值元素时可合并）。自定义类型可通过 `compose.RegisterStreamChunkConcatFunc()` 注册专属拼接函数，优先级高于框架默认实现，且该注册**非并发安全**，只能在初始化阶段调用。

**Q40：自动流化（Box）解决什么问题？**
当下游只接受流式输入而上游是非流式 `T` 时，框架自动把 `T` 装箱成单帧的 `StreamReader[T]`（俗称"假流"）。这保证了组件编排时"上游是否天然产出流"这件事对下游透明，但要注意"假流"并不带来首包延迟降低的实际收益，只是接口层面的统一。

**Q41：自动合并（Merge）与自动复制（Copy）分别用在什么场景？**
- **Merge（合并）**：多路上游流式输出扇入同一个下游节点时，从多个 `StreamReader` 中"公平读取"合并为一路（要求类型相同，若为 Map 则各路 key 不能重叠）；
- **Copy（复制）**：一路流需要扇出给多个下游节点，或同时要发给下游节点和多个 Callback Handler 时，框架自动把流复制成多份独立可读的 `StreamReader`。
所有编排元素（Branch、StateHandler、Callback Handler、Passthrough、Lambda）都被要求能感知和正确处理流，这是流式设计"贯穿到底"而不是"只在个别节点特殊处理"的体现。

**Q42：为什么流用完必须 Close？**
一路真实流（如 ChatModel 的输出）在被 Copy 给多个消费方（下游节点 + 若干 Callback Handler）后，只要有任何一个消费方没有 `Close()` 掉自己拿到的那份 `StreamReader`，底层原始资源（往往关联网络连接/goroutine）就可能无法释放。这是官方文档反复强调的"流务必要 Close"的根本原因，属于资源泄露类问题，而非单纯的编程规范建议。

**Q43：Graph 以 Invoke 方式整体调用时，内部节点如何运作？**
以 Invoke 调用 Graph 时，内部所有节点都以 Invoke 范式运行：若某节点只实现了 Stream/Collect/Transform，框架按 Stream>Collect>Transform 优先级自动封装补齐（本质是内部先跑该节点原生支持的范式，再做流转非流的拼接）。反过来以 Stream/Collect/Transform 调用 Graph 时，内部所有节点统一以 **Transform** 范式运行，缺失的按 Stream>Collect>Invoke 优先级补齐。这条规则保证"整图对外的调用形态"决定"内部节点的统一执行形态"，避免部分流部分非流导致的语义混乱。

**Q44：CheckPoint 场景下流式数据如何被持久化？**
流式场景保存 checkpoint 时需要先把流拼接（Concat）成完整数据才能序列化；因此依赖同一套 `RegisterStreamChunkConcatFunc` 机制。框架内置支持 `*schema.Message`、`[]*schema.Message`、`string` 的拼接，自定义类型需要用户在初始化阶段显式注册对应的拼接函数，否则遇到流式中断/恢复场景会失败。

**Q45：为什么 StreamToolCallChecker 需要自定义实现？**
不同模型的流式输出方式不同：OpenAI 类模型直接在流的开头输出 tool_call；Claude 类模型往往先输出一段文本再输出 tool_call。默认的 `StreamToolCallChecker` 假设 tool_call 消息中只包含 tool_call、没有文本前缀；面对"调用工具前有非空文本 chunk"的模型，需要自定义判断逻辑（但会牺牲一部分"读首帧即可判断"的流式优势）。工程实践上更推荐用 Prompt 约束模型（如"调用工具时不要输出额外文本"）来规避这个问题。

## 五、Callback 与 CallOption 机制（8 问）

**Q46：Callback 机制要解决的两类问题是什么？**
①**横切面功能注入**：logging、tracing、metrics 等业务无关的通用功能需要统一挂载点；②**中间状态透出**：让用户拿到组件内部执行过程中的中间信息（如具体调用的 DB Name、模型实际用的 temperature）。用户注册 Callback Handler（一组函数），Eino 在固定切点回调，两类需求用同一套机制解决，而不是分别造轮子。

**Q47：Callback 的 5 个切点是什么，判定规则是什么？**
`OnStart` / `OnEnd` / `OnError` / `OnStartWithStreamInput` / `OnEndWithStreamOutput`。判定规则：输入为流触发 `OnStartWithStreamInput`（否则 `OnStart`）；输出为流触发 `OnEndWithStreamOutput`（否则 `OnEnd`）；出错触发 `OnError`。不同 Handler 之间的**触发顺序不保证**，因此不建议依赖多个 Handler 间的执行先后关系。

**Q48：Callback 有哪三种触发实体，触发方式有何不同？**
- **Component Callback**：组件实现内部主动调用（需实现 `Checker` 接口且 `IsCallbacksEnabled()` 返回 true，向外声明"我自己已处理回调"）；
- **Node Callback**：若组件自身不主动触发，Graph 会在节点方法外自动埋点，触发 Invoke 还是 Stream 版本取决于组件支持的范式与 Graph 运行方式的匹配关系；
- **Graph Callback**：Graph 自身作为一种 Component，按其被调用的方式（Invoke/Stream 等）触发对应切点；作为子节点嵌入更大图时，复用其内部 Graph Callback。

**Q49：Callback Handler 如何注入，粒度有哪些？**
| 方式 | 范围 |
|---|---|
| `callbacks.AppendGlobalHandlers` | 全局注入，非并发安全，建议初始化时调用一次 |
| `compose.WithCallbacks(...)` | 对整个 Graph 生效 |
| `.DesignateNode(...)` | 顶层 Graph 指定节点（若为嵌套 Graph 则整体生效） |
| `.DesignateNodeWithPath(...)` | 指定嵌套子图内部具体节点 |
| `InitCallbacks(ctx, info, handlers...)` | Graph 外手动注入 |
子 Context 会继承父 Context 中已有的所有 Handler，与普通 Context Value 继承机制一致。

**Q50：HandlerHelper 和 HandlerBuilder 分别解决什么便利性问题？**
`HandlerHelper`（`utils/callbacks`）按官方组件类型（ChatModel/Tool/Retriever 等）过滤并自动把 `any` 转换为具体类型的 Input/Output，省去用户手写 `RunInfo.Component` 判断 + 类型转换的"胶水代码"；`HandlerBuilder`（`callbacks`）则允许按需只实现部分切点（比如只关心 `OnError`），不必实现完整的 5 方法 `Handler` 接口。

**Q51：CallOption 与组件 Config 的本质区别是什么？**
Config 是**实例粒度**：组件创建时确定，实例存续期间固定；CallOption 是**请求粒度**：每次调用可以不同，由 Graph 入口直接下发给特定节点/组件类型，而不是像普通数据一样从上游节点传入。典型场景：同一个 ChatModel 节点在不同请求里被临时传入不同 `Temperature`。

**Q52：组件的 CallOption 为什么要分"抽象层"和"实现层"两级？**
抽象层（如 `model.Options{Temperature, MaxTokens, TopP, Stop}`）定义所有 ChatModel 实现都可能支持的通用参数；实现层（如 Claude 专属的 `TopK`）通过 `model.WrapImplSpecificOptFn[T]` 泛型函数封装，无需修改抽象接口即可让每个实现自由扩展专属参数。组件内部通过 `GetCommonOptions`/`GetImplSpecificOptions` 两个泛型函数分别提取，实现了**类型安全**且**互不侵入**的双层扩展——抽象层不需要知道实现层字段，实现层也不破坏统一接口。

**Q53：编排层 CallOption 的四级分发粒度是什么？**
全局（`WithCallbacks(handler)`，对 Graph 所有节点生效）→ 类型级（`WithChatModelOption(...)`/`WithToolOption(...)`，对所有该类型节点生效）→ 节点级（`.DesignateNode("node_1")`，仅顶层图指定节点）→ 路径级（`.DesignateNodeWithPath(NewNodePath(...))`，嵌套子图内部具体节点）。四级递进、逐级收窄，`WithXxxOption` 系列函数是连接组件级 CallOption 与编排级 CallOption 的桥梁。

## 六、Interrupt & CheckPoint（6 问）

**Q54：Interrupt 有哪几种触发方式？**
①**静态 Interrupt**：`Compile(ctx, compose.WithInterruptBeforeNodes([...]), compose.WithInterruptAfterNodes([...]))`，在图 Compile 时声明节点前/后中断点，不支持单次请求临时改变；②**动态 Interrupt**：节点内部通过 `compose.Interrupt(ctx, info)` / `compose.StatefulInterrupt(ctx, info, state)` 主动触发，可携带用户可见信息与局部状态；③**外部主动 Interrupt**：通过 `WithGraphInterrupt(parent)` 拿到 `ctx` 和触发函数，用于服务优雅退出等场景，此时框架自动保存被中断节点的 input。

**Q55：CheckPoint 如何持久化，序列化机制是怎样的？**
用户需实现一个极简的 KV 接口 `CheckpointStore{Get(key) / Set(key, value)}`。简单类型和 eino 内置类型（`Message`、`Document`）无需额外操作；自定义 struct 需要 `schema.RegisterName[*T]("type_v1")` 注册类型名用于序列化携带类型信息，且**注册 key 一旦确定不可更改**（否则历史 checkpoint 无法恢复）；未导出字段不会被存储；若类型实现了 `json.Marshaler`/`Unmarshaler` 会优先使用；默认 JSON 序列化，可通过 `WithSerializer` 切换为 gob。

**Q56：中断后如何恢复执行，新旧版本（v0.7.0 前后）有何差异？**
v0.7.0 之前：通过 `WithStateModifier(func(ctx, path, state) error)` 修改全局 State 后**重跑整个流程**（旧输入无效）。v0.7.0 及之后：支持**精细化恢复**——`Resume(ctx, interruptIDs...)` 恢复指定中断点不带数据；`ResumeWithData(ctx, interruptID, data)` 恢复单点并带数据；`BatchResumeWithData(ctx, map)` 批量恢复多个中断点各自带数据。`interruptID` 从中断错误的 `InterruptInfo.InterruptContexts[0].ID` 提取。新版本的核心改进是支持**局部状态保存**、**内部信号透出**、**并行中断**（多个节点同时中断，可分别恢复）。

**Q57：嵌套子图中的 Interrupt & CheckPoint 如何配置？**
父图必须先配置 `WithCheckPointStore`，再通过子图节点的编译选项单独开启子图内部的中断点：`g.AddGraphNode("node1", subGraph, WithGraphCompileOptions(WithInterruptAfterNodes([...])))`。若父图未配置 CheckPointer，`Compile` 时会直接报错。子图中断后，`StateModifier` 修改的对象是**子图自己的 State**，而不是父图 State，体现了子图状态的封装性。

**Q58：Interrupt & CheckPoint 的典型适用场景是什么？**
Human-in-the-loop（如高风险工具调用前的人工审批）、长任务断点续传（大任务跑到一半服务重启，从 checkpoint 恢复而不是从头跑）、服务优雅退出时保存现场（`WithGraphInterrupt` + 超时强制中断，未完成任务在恢复时重跑）。这三类场景的共性是：执行过程可能被"非本次调用能控制的外部因素"打断，且打断后的状态必须能够被准确还原，而不是靠业务代码手写一套临时的进度记录。

**Q59：断点续传对 Graph 结构、CallOption 有什么隐含要求？**
断点续传只恢复**输入数据**和**各节点运行时数据**，前提是 **Graph 编排结构必须完全相同**（不能一边跑一边改图结构再恢复），且恢复调用时需要**重新完整传入 CallOption**（CallOption 不会被持久化，因为它代表"这次调用"的请求级参数，语义上不应该被跨越中断继承）。这个约束提醒我们：CheckPoint 保存的是"数据+进度"，不是"完整的调用上下文快照"。

## 七、ADK 与多智能体（8 问）

**Q60：ADK 的核心接口设计是什么？**
```go
type Agent interface {
    Name(ctx context.Context) string
    Description(ctx context.Context) string
    Run(ctx context.Context, input *AgentInput, options ...AgentRunOption) *AsyncIterator[*AgentEvent]
}
```
`Run` 是 **Future 模式**：启动异步任务后立即返回 `AsyncIterator`，事件持续写入其中，调用方通过迭代消费而非阻塞等待，这使得流式事件、长任务、并行多 Agent 天然可组合。

**Q61：ChatModelAgent 的公式化设计是什么？**
`ChatModelAgent = 输入构造 + ChatModel + 动态 Tools + ReAct Graph + AgentAction + Middleware`。有工具时运行 `ChatModel ⇄ ToolNode`，无工具时运行模型 Chain；模型不再发 ToolCall、ReturnDirectly、Exit、Transfer、迭代耗尽或错误/取消都会终止当前路径。Middleware 不只加日志，还能在 Agent 前动态改工具，在模型前重写消息，在调用点替换模型或包裹工具。

**Q62：Workflow Agents（Sequential/Loop/Parallel）与 AgentAsTool 的定位区别？**
Workflow Agents 的控制边由代码固定：Sequential 串行、Parallel 扇出、Loop 循环，并为 interrupt/resume 保存各自状态。Agent-as-Tool 的调用边由父模型临场选择，子 Agent 完成后结果作为 ToolResult 回父 Agent；内层的 Exit/Transfer/BreakLoop 不允许越过工具边界。前者强调确定性，后者强调委派自治，可以组合使用。

**Q63：Runner 相比直接调用 Agent.Run() 多提供了什么能力？**
`Agent.Run()` 已能产生事件；Runner 负责把 Agent 放入可转移、可恢复的 flow session 中：解释 `TransferToAgent`，统一转发 `RunPath` 事件，遇到 Interrupt 时把状态写入 `CheckPointStore`，并通过 `Resume/ResumeWithParams` 恢复目标组件。v0.8.0 不存在旧稿声称的 TurnLoop `Push/Preempt/Stop`，主动取消依赖传入 context。

**Q64：DeepAgent 与普通 ChatModelAgent 的差异体现在哪？**
DeepAgent 是 `ChatModelAgent` 的预置装配：增加 TODO/任务提示、可选 filesystem middleware、`task` Tool 和 SubAgents；每个 SubAgent 经 `NewAgentTool` 包装，未禁用时还创建一个拥有主 Agent 同类工具的 `general-purpose` 子 Agent。它没有另起一套循环，也不会自动拥有 shell/search；实际能力取决于配置的 Tools、Backend 和 Handlers。

**Q65：Supervisor 模式解决什么问题？**
Supervisor 把自由 Handoff 收敛成星型拓扑：Supervisor 可转移到专家，但每个专家都由 `AgentWithDeterministicTransferTo` 包装，完成后只能回 Supervisor，不能横向跳转；外层 container 还统一整棵调用树的 trace root。它解决路由治理和观测聚合，不等于 DeepAgent 的 Task Tool 委派。TCUM-AI 当前主链没有直接采用该 prebuilt。

**Q66：Middleware 机制与 DeepSeek Harness 的"扩展点"设计有何相似性？**
Eino ADK 的 Middleware 让能力（文件系统访问等）以"可插拔增强层"的方式接入 ChatModelAgent 的运行时，而不需要修改 ReAct 核心循环；这与 DSH"新增能力挂到已声明的扩展点（`ctx.llm`/`ctx.tools`/`agent/*` 事件），把改 loop 视为例外"的思路本质相同——都是用**显式挂载点 + 组合**取代"直接改核心循环"，这是当前主流 Agent 框架的共识设计范式，而不是某一家的独创。

**Q67：多 Agent 场景下的取消/中断如何处理？**
取消以 `context.Context` 向模型、ToolNode、子 Agent 传播；实现方仍必须确保自建 goroutine、HTTP client 和 stream reader 响应 `ctx.Done()` 并正确 Close。中断则不是取消：Agent/Workflow 把可序列化 `InterruptInfo` 和本地状态交给 Runner 保存，后续 Resume 从对应子 Agent/并行分支继续。Agent-as-Tool 默认受父工具调用生命周期约束；真正脱离父请求的后台任务需要另建持久任务系统，不能只启动孤儿 goroutine。

## 八、面试式取舍与总结（7 问）

**Q68：Eino 最大的优点是什么？**
把"组件抽象、图编排、流式处理、Callback、Agent"统一到同一套类型系统和编排语义下，在 AddEdge/Compile 阶段提前暴露大量接线错误；同时用自动拼接、装箱、合并和复制机制降低组件作者适配四种流式范式的成本。

**Q69：Eino 最大的代价是什么？**
概念面较宽：四种流式范式+自动转换规则、五种 Callback 切点+三种触发实体、两级 CallOption+四级分发粒度、Workflow 多种 FieldMapping API、Interrupt/CheckPoint 的新旧版本差异——要在这些概念之间建立准确心智模型需要一定学习成本。对"只是简单调一次模型 API"的场景，直接用 SDK 反而更快，Eino 的价值在**多组件、需长期维护、需类型安全**的场景才充分释放。

**Q70：什么场景不适合直接上手 Eino 的全套编排能力？**
一次性脚本、无需复用组合、不关心并发/流式细节的简单调用场景；或者团队 Go 经验不足、短期内难以理解泛型 + Compile 期检查带来的调试方式变化（错误更多出现在 `Compile()` 阶段而非运行时日志里）的团队。这类场景可以先只用 Component 层（直接 `model.Generate()`），编排层按需引入。

**Q71：Eino 与国内其他 Go Agent 框架/DSH（TypeScript）相比，设计取向的共性是什么？**
共性是"不把功能固化进一个私有主循环"：Eino 用组件+编排+Middleware，DSH 用插件+Cordis 能力接缝+事件流。差异在切入点：Eino 从**类型系统**切入解决"接线是否正确"，DSH 从**事件溯源**切入解决"运行过程是否可审计/可恢复"。两者可以互相印证——一个成熟的 Agent 框架，往往同时需要"编译期/类型级别的正确性保证"和"运行期/事件级别的可观测可恢复能力"，只是各家先做深了哪一半。

**Q72：如何评价 Eino 的类型检查"不完全"（interface→具体类型场景推迟到运行时）这一设计？**
这是一个务实的折中：完全依赖静态类型会拒绝掉大量合法但编译期无法证明的合理用法（插件化组件、多态 Tool 等），完全放弃静态检查则失去 Eino 的核心卖点。选择"能查就查、不能查就在运行时用类型断言查、绝不静默跳过"，本质上是把 Go 语言本身"接口 + 类型断言"的惯用法一致地延伸到了编排层，而不是发明一套全新的、更严格但也更受限的类型系统。

**Q73：如果要把 Eino 的设计思想迁移到自己的框架，优先落地哪几条？**
①组件接口**统一输入输出类型+Option 模式**，让"能否互换实现"的判断尽量前移；②流式与非流式的转换（拼接/装箱/合并/复制）做成框架自动处理的通用能力，不要求每个组件都手写四种范式；③横切面（日志/追踪/审批）统一走一套 Callback/中断机制，而不是散落在各个组件内部各自实现。不建议一开始就复制 Workflow 的字段级映射或 ADK 的全部预置 Agent 模式，先把类型系统和流式基座打稳。

**Q74：面试中如何用一句话总结 Eino？**
"Eino 的关键不在某个组件或 Agent 模式，而是用 Go 类型把『组件怎么拼』尽量前移到 AddEdge/Compile 检查，再以统一流转换、Callback、CallOption 和 Middleware 承担运行时扩展；ADK 的 ReAct 与多 Agent 都建立在这套基座上。"
